## 1. 判据与权重（先填这张）

| 判据 | 权重（1–5） | 为什么对**你的团队**重要（必须具体，不许写「很重要」） |
|------|------------|----------------------------------------------|
| 流程覆盖（specify → converge 的完整度） | | |

| 与现有工具链 / 代码托管方式的摩擦 | | |
| 学习成本（谁是第一个上手的人？） | | |
| 模型无关性 / 供应商锁定 | | |
| 许可证、数据边界与合规 | | |
| 社区活跃度与可退出性（规格能不能带走） | | |

> ⛔ 判据 ≤ 7 条。超过之后，每一行都在稀释前面几行的权重。
> ⛔ 权重必须先于对比独立确定 —— 它们来自团队现状，不来自任何一款工具的卖点。

## 3. 分场景建议（验收硬要求）

L12 的验收标准是「能给出**什么团队该选什么**的具体建议，不止罗列功能」。
至少写三种团队画像：

| 团队画像 | 建议 | 理由（指回 §1 的判据） |

| 例：跨职能团队、规格需交付给外部方 | | |

## 4. 被否决项与推翻条件

| 工具 / 方案 | 否决理由（写触发事实，不写「感觉不合适」） | 什么信号出现时重新评估 |
|------------|--------------------------------|---------------------|
| | | |

> 📌 「否决」不是永久封杀。推翻条件把否决变成「当前条件下不选」，
> 将来环境变了知道该看哪个信号 —— 与 ADR 模板的同一原则。

## 5. 明确不比的维度（反清单）

> ⛔ 至少列 2 个你**故意不打分**的维度，并写明为什么。
> 没有反清单的对比表会越比越宽，最后比的是「谁的功能列表长」。
> 示例：内置模型额度（会随定价策略每月变化，不构成选型依据）、UI 美观度。
