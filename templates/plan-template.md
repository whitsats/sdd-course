## 5. 验收标准 → 测试的映射计划

> **在写代码之前先列这张表**，它决定了你的测试策略。

| 验收标准 | 测试类型 | 测试文件 | 断言什么 |
|---------|---------|---------|---------|
| AC-1 | 契约测试 | | |
| AC-2 | 单元测试 | | |
| AC-3 | 集成测试 | | |
| AC-4 | **属性测试** | | 随机输入下不变量成立 |

**测试类型怎么选：**

| 类型 | 什么时候用 | 抓什么 |
|------|-----------|-------|
| 单元 | 纯函数、边界计算 | 逻辑错误 |
| 契约 | 跨边界（API、DB、外部服务） | 接口变化 |
| 集成 | 多组件协作 | 装配错误 |
| 属性 | 有「对任意输入都成立」的不变量 | 你想不到的输入 |
| 快照 | 输出结构稳定 | 意外改动 |

> 📌 **表格驱动优先。** 权限矩阵这类「组合」用表格驱动写 14 行比写 14 个测试函数好维护得多。
> 见 `examples/taskflow/tests/contract/auth-matrix.spec.ts`。

## 7. 三种「牙齿」

> **规格要被强制，必须有牙齿。** 逐项确认本项目有哪几种：

| 牙齿 | 本项目是否具备 | 具体是什么 |
|------|--------------|-----------|
| **类型约束** | ☐ | <例：zod schema / 类型系统> |
| **契约测试** | ☐ | <例：OpenAPI 断言 / 候选测试> |
| **CI 门禁** | ☐ | <例：覆盖率门禁 / 分层边界> |
| **生成物一致性** | ☐ | <例：spec-as-source 的 git diff 校验> |

**至少要有两种。** 只有一种时不具备强制力——见 L09。
