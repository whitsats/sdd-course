# Agent 提示词片段库

> 用途：在 SDD 各阶段对 AI agent 说话时，**可直接抄的句子**。
>
> ⛔ **本文件里的每一句都可以抄，但不能只抄一句。**
> 提示词的作用是**约束**，不是**请求**。
> 「请仔细检查」不是约束；「逐条回答：哪条标准没被任务覆盖」是约束。
>
> 📌 **判断一句提示词有没有用**：它是否让 agent 的输出**更难被敷衍**。
> 加一句「请认真」是没用的；加一句「每条必须给出文件路径与行号」是有用的。

---

## 通用规律（先读这一节）

| 无效的写法 | 有效的写法 | 差别在哪 |
|-----------|-----------|---------|
| 「请写得详细一点」 | 「每个决策后面写它服务哪条验收标准」 | 给了**判定标准** |
| 「注意边界情况」 | 「逐条回答：空输入、0、最大值、超上限时的行为分别是什么」 | 给了**清单** |
| 「不要写实现细节」 | 「规格里不得出现库名、类名、文件路径」 | 给了**可检查的禁令** |
| 「检查一下有没有问题」 | 「按五类检查，每类必须给出位置/问题/后果/建议；没有就写「无」」 | 给了**结构与「无」的出口** |
| 「尽量准确」 | 「时间一律 ISO 8601 带时区偏移」 | 给了**唯一正确答案** |
| 「保持简洁」 | 「正文不超过 800 字」 | 给了**可数的上限** |

> 📌 **最后一条「给了「无」的出口」值得单独强调。**
> 不要求 agent 可以说「无」的时候，它会在每一类里都找出点什么 ——
> 然后你会花时间排查不存在的问题，最后不再信任它。

## 阶段一 · 写规格（`/speckit-specify` 前后）

### 打开一个 feature

```
我要为 <项目> 写一个 feature 规格，主题是：<一句话描述>。

约束：
- 规格里不得出现库名、类名、文件路径 —— 那些属于 plan.md
- 每条验收标准用 EARS 句式（WHEN/IF/WHILE/WHERE … SHALL …）
- 每条标准必须能被一个确定性断言测试，不能出现「友好」「合理」「尽快」「适当」这类词
- 每写完一条，自问：这句话能不能被判定为「遵守」或「违反」？不能就重写

先不要写代码，写完规格等我确认。
```

### 补六类歧义区

```
在规格里补一节「六类歧义区」，逐条给答案：

① 边界与极值：空、0、负数、最大值、超上限
② 错误与失败：依赖失败谁看到什么、能否重试、部分成功怎么办
③ 权限与可见性：谁不能做什么、越权时返回「无权限」还是「不存在」
④ 并发与顺序：同时修改同一条数据、乱序事件、重复提交
⑤ 时间与时效：时区、跨天/跨周归属、是否依赖系统时钟
⑥ 状态转换：有哪些状态、哪些转换合法、非法转换怎么处理

每一格都必须有答案。「本期不涉及」也是有效答案。**留空不是。**
```

### 让 agent 做组合检查 ⭐

```
请做一次「标准组合检查」：
从规格里任取两条不相关的验收标准，把它们放进同一个极端场景里，
看是否出现一条标准要求 A、另一条要求 B 的情况。

对每一组组合，明确回答：出现矛盾 / 未出现矛盾。
若出现，指出是哪两条、在什么输入下、以及规格缺少哪条规则来消解它。

这个检查的目标是找出**两条标准叠加后才浮现**的缺口 ——
逐条读规格发现不了它们。
```

> 📌 **这段提示词是本仓库里验证过最有价值的一段。**
> 它挖出了 `focuslog` 里「跨天会话归属 × 周报排除活跃会话」
> 导致的「会话在周报里凭空消失」——
> 见 `examples/focuslog/notes/L06-LLM审阅记录.md`。

## 阶段二 · 技术方案（`/speckit-plan`）

```
基于 specs/<NNN>-<name>/spec.md 写技术方案。

必须包含一张「可追溯性表」，每行格式：
| # | 技术决策 | 服务的验收标准 | 判定 |

规则：
- 每条技术决策都必须指向至少一条验收标准或宪法条款
- **填不出来的行，直接标 ❌ 并说明它应该被删除还是推迟**
- 请在最后统计 ❌ 行的占比；超过 20% 说明这个方案在实现另一个需求

另外单独列一节「已经发生的范围蔓延」，
记录你考虑过但决定不做的技术方案，以及砍掉它们的理由。
```

> 📌 **「填不出来的直接标 ❌」这一句是关键。**
> 不要求它，agent 会为每个决策硬凑一条标准 ——
> 然后可追溯性表会变成一份自我确认的文档，失去检测能力。

## 阶段三 · 任务拆分（`/speckit-tasks`）

```
基于 plan.md 拆分任务。

要求：
- 按「可独立交付的批次」组织，不是按文件或按层
- 每个批次结束时系统必须可运行
- 每个任务后面写：来源（哪条验收标准）、文件、验证方式（测试名）
- 标出可并行的任务（判据：不修改同一个文件）

最后附一张**反向表**：从每条验收标准出发，列出覆盖它的任务。
**只要有验收标准对应「无」，本清单就不算完成。**
```

> 📌 **「反向表」比正向表有用得多。**
> 从任务出发看它服务什么，永远填得满；
> 从标准出发看谁覆盖它，才会暴露遗漏。

## 阶段四 · 实现（`/speckit-implement`）

```
按 tasks.md 逐批次实现。

铁律：
- 只实现当前批次的验收标准覆盖的行为。**发现规格外需求时，停下来问我，不要顺手加。**
- 先写测试再写实现。测试写完先跑一次，**它必须是红的**；
  如果直接绿了，说明它没在测这条标准，回去改。
- 每个批次结束跑一次全量测试与门禁，绿了再进下一批。

完成后报告：
1. 每批次的测试结果
2. 有没有偏离规格的地方（有就明确列出）
3. 有没有「实现了但规格没写」的行为（有就列出，我来决定补规格还是删代码）
```

> 📌 **第 3 条是防止「顺手多写」的关键。**
> agent 很容易实现一个「更完整」的版本 —— 那不是帮你的忙，那是范围蔓延。

## 阶段五 · 一致性检查（`/speckit-analyze`）

```
对 specs/<NNN>/ 做一致性检查，按四类逐条回答：

① 标准互斥：有没有两条验收标准在某种输入下要求不同行为（给出具体输入）
② 孤儿标准：有没有验收标准没有任何任务覆盖
③ 孤儿任务：有没有任务不服务任何验收标准
④ 映射缺口：有没有验收标准没有对应测试

每类都要回答。**没有发现问题就明确写「无」，不要编凑。**
输出用表格：| 类别 | 结果 | 具体位置 | 严重程度 |
```

## 阶段六 · 收敛与漂移（`/speckit-converge`）

```
对比实现与规格，找出所有偏离。

对每条偏离，给出：
| 偏离 | 规格怎么说 | 代码怎么做 | 谁对 | 处置 |

「谁对」只有三个答案：规格错 / 代码错 / 规格没写清。
- 规格错 → 走规格变更流程（先让测试变红）
- 代码错 → 修代码
- 规格没写清 → 补规格，然后回到上面两步之一

⛔ 不允许出现第四种处置：「先这样，以后再说」。
```

## 阶段七 · 让 agent 审你的规格（对抗式）

```
你是一个严格的规格审阅者。找出缺陷，不要夸它。

每条意见必须包含：位置（引用原句或指出「缺失」）、问题、后果、建议。

按五类检查，没有发现就写「无」：
① 歧义（无法判定的词、两种合理解读）
② 矛盾（某种输入下两条标准要求不同）
③ 缺口（六类歧义区留空处）
④ 不可测（写不出确定性断言）
⑤ 实现泄漏（类名、库名、文件路径）

最后按严重程度给出「最该先修的 3 条」。
```

**这一段的现成脚本**：`scripts/agnes-review.py`

```bash
export AGNES_API_KEY='sk-...'
python scripts/agnes-review.py examples/focuslog/specs/001-focuslog-mvp/spec.md
```

> ⛔ **不要把它接进 CI 当门禁。** 它是非确定性的：同一份规格两次可能给出不同意见。
> **非确定性的门禁 = 会误报的门禁 = 团队会学会无视它。**
> 它的位置是「外脑」：人读它的输出，然后决定改不改规格。

## 反模式：这些说法一定没用

| 说法 | 为什么没用 |
|------|-----------|
| 「请仔细检查」 | 没有判定标准，agent 无法知道「仔细」到什么程度 |
| 「注意边界情况」 | 没有清单，它会检查它想得到的那些，正好漏掉你担心的 |
| 「写得专业一点」 | 「专业」不可判定 |
| 「确保代码质量」 | 同上。质量是多个具体属性的集合，要逐个说 |
| 「参考一下最佳实践」 | 最佳实践因场景而异；说清你的场景与约束 |
| 「不要出错」 | 最没用的一句。出错是默认状态，约束才能改变它 |
| 「尽量完整」 | 「完整」是范围蔓延的另一种说法 |

> 📌 **共同点：它们都在表达「期望」，而不是在施加「约束」。**
> Agent 不缺期望，缺的是**判定标准** ——
> **它能知道什么时候算做完了、什么时候算做错了。**
