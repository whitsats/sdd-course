## 怎么用这份清单

1. **按批次执行，一个批次一个 commit。** 每个批次结束时，系统应当是**可运行**的。
2. **`/speckit-implement` 之前先人工重排一次。** 生成的顺序是逻辑顺序，
   但真实工作有额外约束（依赖外部团队、需要先拿到数据、技术风险要提前验证）。
   重排的对照见 `examples/focuslog/specs/001-focuslog-mvp/tasks.md`。
3. **每个任务后面带它服务的验收标准。** 没有来源的任务是范围蔓延。
4. **完成就打勾，并写下一行证据**（测试名或命令），不写「已完成」三个字。

## 本清单**不**包含的事

| 事项 | 为什么不在这里 | 该放哪里 |
|------|--------------|---------|
| 部署与运维变更 | 不属于本 feature 的代码交付 | 运维清单 |
| 数据迁移 | 独立的风险与回滚要求 | 单独一份迁移方案 |
| 性能优化 | **先让它对，再让它快** | 后续 feature |
| 重构既有代码 | 混进功能 PR 会让 review 无法聚焦 | 独立 PR |

> 📌 **最后一行是个高频错误**：功能 PR 里顺手重构，导致 reviewer 无法区分
> 「行为变化」与「结构变化」。**重构单独开 PR。**
