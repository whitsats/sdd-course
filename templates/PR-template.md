# PR 模板（SDD 版）

> **本文件是 L12 §4 的完整参考产出。**
> 复制到 `.github/pull_request_template.md` 即刻生效。
>
> **为什么要有这个文件**：靠自觉的流程会在两个月内死掉；写进 PR 模板的流程会活下来。

```markdown
## 本次变更

<!-- 一句话说明为什么做这个改动（不是做了什么） -->

## ① 是否改变了对外行为？

对外行为 = 输出格式 / 退出码语义 / 错误码 / 状态流转 / 权限判定 / 存储 schema。

- [ ] **是** → 对应 `spec.md` 的哪条验收标准？（**必填，写编号**）
      → 标准编号：
      → 若无对应标准：说明为什么不需要（见下）
- [ ] **否** → 说明为什么（例如：内部重构、只改日志措辞）

> ⚠️ 如果选「是」但找不到对应标准，**说明这次改动扩大了范围**。
> 正确做法是**先改 spec，再写代码**（L09 §5 的六步流程），而不是在这里填「无」。

## ② 自查清单

- [ ] `spec.md` 已同步更新（若 ① 选「是」）
- [ ] `docs/验收标准-测试映射.md` 已同步（新增验收标准必须加行）
- [ ] **改行为时，测试先变红过**（不是先写实现再补测试）
- [ ] 没有手工编辑生成产物（若项目使用了代码生成）
- [ ] `plan.md` 的决策表已更新（若引入了新的技术决策）
- [ ] 无新增的「指不回 spec 或宪法」的决策

## ③ CI 门禁

- [ ] Type check 通过
- [ ] 契约测试通过
- [ ] **规格覆盖率 100%**（`spec_count == mapped_count`）
- [ ] 分层边界检查通过

> 性能基准只警告不阻断，因此不在此列 —— 见 L09 §3 的门禁设计原则。

## ④ 变更类型

- [ ] feat（新功能 → 通常需要新增验收标准）
- [ ] fix（修 bug → 判断是哪一层的问题：实现 / 规格 / 任务）
- [ ] refactor（内部重构 → 通常不改 spec，但需确认无对外行为变化）
- [ ] docs / test / chore

## ⑤ 已知偏差与未决项

<!-- 
  这里必须显式列出，不能留空说「无」而不核对。
  参考 templates/acceptance-record.md 里的「未决项」小节。
-->

- 已知偏差：
- 未决项（需要他人决策的）：
```

## 使用说明

### 第 ① 节是整个模板的核心

它把「**改行为必须先改规格**」这条宪法条款，从**人的记忆**变成了**PR 上的一个必填项**。

**三种回答的处置**：

| 回答 | 含义 | 处置 |
|------|------|------|
| 有对应标准编号 | 正常流程 | 合并 |
| 「是」但无标准 | **范围蔓延** | 回去改 spec，再重新提 PR |
| 否，且理由成立 | 内部改动 | 合并 |

### 为什么第 ③ 节的性能项不列进来

因为它是**只警告不阻断**的。把它列在「门禁」里会让人误以为它必须绿——
**然后有人会因为一次 runner 抖动而关掉整个 CI。**

> 门禁的价值建立在「红灯必有意义」之上。

### 渐进上线建议

| 阶段 | 模板里先放哪几项 |
|------|----------------|
| 第一周 | 只放第 ① 节（行为变更 + 标准编号） |
| 第一个月 | 加第 ② 节自查 |
| 第三个月 | 加第 ③ 节（此时 CI 门禁已稳定） |

**不要一次全上。** 第一周就要求填满五节，团队会把它当形式，然后连第 ① 节也开始糊。
