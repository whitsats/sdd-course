# 规格台账 · <团队 / 仓库名>

> 位置：`notes/L12-规格台账.md`
>
> 用途：spec 超过三份、或跨仓库 / 跨 agent 之后，回答三个没人主动回答的问题：
> **这份规格归谁？它还活着吗？谁在消费它？**
> 配套章节：[L12 §2](../lessons/12-team-rollout.md)（规格作为交接契约）。
>
> 📌 **台账本身也是文档，也会腐化。** 它的「门禁」是复审周期：
> 过期未复审的行，状态自动视为可疑 —— 表里要有这一列，且要真的看它。
>
> 📌 什么时候**不**建台账：spec < 3 份、单仓库、单人维护。
> 这时台账是仪式，`specs/` 目录本身就是台账。

---

## 1. 台账

| 规格（feature / 仓库） | owner（人名，不是团队名） | 状态 | 消费者（谁实现 / 谁依赖） | 门禁 | 复审周期 | 废弃条件 |
|----------------------|------------------------|------|------------------------|------|---------|---------|
| 例：`001-billing-mvp` | 张三 | active | billing-app；报表服务读错误码 | 覆盖率 + 编译期校验 | 每季度 | 计费下线 |
| 例：`002-task-tags` | 李四 | draft | — | 无（未实现） | 每迭代 | 002 正式排期或放弃 |
| | | | | | | |

**状态只有四种**，流转必须走 change-request（L09）：

| 状态 | 含义 | 允许的动作 |
|------|------|-----------|
| `draft` | 还没被任何实现消费 | 随便改；改完要过 clarify |
| `active` | 有实现、有门禁、有消费者 | 只能走 change-request；改动必带波及面分析 |
| `deprecated` | 被别的规格取代或业务不再需要 | **禁止修改**；保留原文 + 指针（「被 XXX 取代」） |
| `archived` | 已归档的历史规格 | 只读；删除 = 销毁证据，不做 |

## 2. 三条硬规则

1. **owner 是人名，不是团队名。** 「平台组拥有」等于没人拥有——出问题时你要的是
   一个能叫醒的人，不是一张 org chart。
2. **deprecated 不删除。** 标状态、留指针。三个月后有人问「为什么 001 的排序规则
   和 003 不一样」，答案是台账里的一行，不是考古。
3. **没有消费者的 active 规格是嫌疑犯。** 消费者一列空着，说明要么台账没更新
   （信息腐化），要么规格真的没人用（该降级为 draft 或废弃）——两种都要处理。

## 3. 每次复审问四个问题

- [ ] 还有人按它实现吗？（消费者列是否仍然为真）
- [ ] 它的门禁还绿吗？（绿 ≠ 有效：门禁可能有盲区，见 AP-29）
- [ ] 它与别的规格冲突吗？（横向对照——agnes-review 的整体审阅适合这里）
- [ ] 它的 owner 还在这件事上吗？（owner 离开 = 立即改派，不是「先放着」）

## 4. 反清单（明确不用台账管的事）

> ⛔ 至少写两条。台账管**资产状态**，不管这些：

- **内容评审** —— 那是 clarify / checklist（L06）的事，复审不重打质量勾
- **变更历史** —— 那是 change-request 与 git log 的事，台账只放指针
- **优先级 / 排期** —— 那是项目管理的事；台账记录「是什么状态」，不决定「下一步做什么」
