# 团队落地检查清单 · <团队名>

> 位置：`notes/L12-团队流程.md`
>
> 用途：L12 的第二个交付物 —— 把「我们要用 SDD」翻译成三段**有时间盒**的验收动作。
> 配套章节：[L12 · 团队化落地与生态选型](../lessons/12-team-rollout.md)。
>
> 📌 **第一周不上 CI 门禁**（L12 验收硬要求）。先建立手感，再谈强制力 ——
> 顺序反了，团队学会的第一课是「怎么绕过门禁」。
>
> 📌 填法：每打一个勾，后面必须跟着**证据**（一个链接、一次演示、一个数字）。
> 没有证据的勾是愿望，不是状态。

---

## 0. 前置（开始之前）

- [ ] 宪法草案 ≤ 1 页，每条带「可机械检查吗」自评（L02）
- [ ] 试点 feature 已选定：**真实、不大、有明确验收标准**（不选最难的，也不选造出来的假任务）
- [ ] 试点的人选定了：先一个人主导，其他人围观 —— 不立刻全员上
- [ ] 工具选型已完成并留档（见 [`tool-selection-template.md`](tool-selection-template.md)）

## 1. 第一周 —— 手感（无门禁）

- [ ] 试点 feature 走完 `specify → plan → tasks`，**每个 plan 决策都填了可追溯性表**
- [ ] 至少 3 处「我原以为清楚、写规格时才发现不清楚」记录在案（L06）
- [ ] 围观的人看过 spec 与 plan，并**提出过至少一条异议**（没人在看，等于没围）
- [ ] 本周复盘一次：记下大家抱怨最多的那一步 —— 它就是下周要优化的对象

## 2. 第一个月 —— 规则

- [ ] 试点 feature 完成实现与逐条验收（L05 的验收纪律：跑通 ≠ 完成）
- [ ] 记录两个成本数字：**返工次数**（每 10 个任务里几个因理解错而重做）与**规格变更波及面**（改一条标准平均动几个文件）—— 方法见 L09
- [ ] 评审分工定了：谁审 spec、谁审 plan、各自看什么
- [ ] 上了**第一条**门禁：`check-spec-coverage.sh`（最不容易误报的一条，见 scripts/README 的渐进顺序）
- [ ] 观察一周误报率：**高于 5% 先修判据，不急着加下一条**

## 3. 第三个月 —— 强制力与度量

- [ ] 门禁扩展到分层边界与漂移检查（仍遵循「红灯必有意义」原则）
- [ ] 指标基线建立：漂移率 / 返工率 / 规格覆盖率（对谁可见、多久看一次）
- [ ] 明确列出 **3–4 个「不测的反指标」**（L12 验收硬要求；例：不统计 prompt 字数、不考核 spec 页数）
- [ ] 第二个 feature 由**非发起人**主导走完全流程 —— 只有第一个人会用的流程不是团队流程
- [ ] 失败模式复盘：对照 `reference/anti-patterns.md`，确认没在犯其中任何一条

## 4. 退出信号（预先写下，不是事后补）

> 📌 退出条件是**现在**写的。事后补的退出条件不叫退出条件，叫辩护词。

| 信号 | 阈值（写具体数字） | 触发后的动作 |
|------|-----------------|------------|
| 例：spec 返工率连续 N 周高于 X% | | 重新评估**范围**（哪类任务适合），不是放弃全流程 |
| 例：门禁误报率 > Y% 且修了两轮没修好 | | 收窄门禁范围至不再误报的那部分 |
| 例：团队规模 / 人员变动 | | 重走一遍 §0 前置，而不是默认沿用 |
