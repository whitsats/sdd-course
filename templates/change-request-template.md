# 规格变更申请 · <feature 名>

> 位置：`specs/<NNN>-<feature-name>/changes/CR-<NNN>-<简述>.md`
>
> 用途：**功能已经上线，现在要改它的行为。**
> 这是课程里最容易被跳过的一步 —— 写作「新功能」容易，改动「已有行为」难。
>
> 📌 **为什么需要一份独立的申请，而不是直接改 `spec.md`？**
>
> 因为直接改的话，`git diff` 只会显示「规格变了」，
> **看不出「为什么变」以及「谁受影响了」**。
> 三个月后有人问「为什么 3.5 的排序规则不一样了」，答案是「不知道」。

### 3.1 对用户的影响

| 用户类型 | 受影响吗 | 怎么受影响 | 需要通知吗 |
|---------|---------|-----------|-----------|
| | | | |

### 3.2 对**已有数据**的影响 ⭐

> **最常被漏掉的一节。**

| 问题 | 答案 |
|------|------|
| 变更前产生的数据还合法吗？ | |
| 需要数据迁移吗？ | |
| 迁移可以回滚吗？ | |
| 迁移期间的中间状态是否可服务？ | |

**例**：把标签上限从 32 放宽到 64 → **旧数据不受影响**（旧数据都 ≤ 32），
所以**不需要迁移**。但反向收紧（64 → 32）**需要**迁移：
已有的 40 字符标签怎么办？截断？拒绝？保留但标记？

### 3.3 对**契约**的影响 ⭐

| 契约 | 会被破坏吗 | 谁会受影响 |
|------|-----------|-----------|
| API 请求/响应结构 | | |
| 错误码表 | | |
| **输出格式模板**（见 focuslog 的规则二） | | |
| 数据库 schema | | |
| 命令行参数 | | |

> 📌 **「去掉一个错误码」和「新增一个错误码」的风险完全不同：**
> 前者会破坏依赖它的客户端，后者不会。
> **删除类变更一律按「破坏性」处理。**

## 4. 变更后要执行的操作（有序）

> ⛔ **顺序不能乱。** 尤其是「先让测试变红」这一步 ——
> 它不是仪式，而是**证明你的测试真的在测这条标准**。

- [ ] **① 改规格**（`spec.md`）
- [ ] **② 改映射表**（加/改对应行）
- [ ] **③ 跑覆盖率门禁** → 此时会红（标准变了，测试还没变）
      → **这个红是预期的，它证明了门禁在工作**
- [ ] **④ 改测试**（改断言以匹配新标准）
- [ ] **⑤ 跑测试** → 此时应当**红**（实现还没改）
      → **这个红更重要：它证明测试真的在检查这条标准**
      → 如果这里直接绿了，说明**你的测试没有覆盖这条标准**，回去补
- [ ] **⑥ 改实现** → 测试变绿
- [ ] **⑦ 跑全部门禁** → 全绿
- [ ] **⑧ 数据迁移**（若需要）
- [ ] **⑨ 更新文档 / 通知受影响方**

> 📌 **⑤ 是整条链路里最关键的一步。**
>
> 大多数人跳过它：改规格 → 改测试 → 改实现 → 全绿。
> 这样做的代价是**你永远不知道「④ 改的测试」是否真的在测这条标准** ——
> 它可能测的是一个巧合（比如断言了错误的字段），而实现改对了纯属顺便。
>
> **先让测试红，是唯一能证明「测试与标准绑定」的手段。**
