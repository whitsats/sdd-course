# 工具脚本：把「判据」从人脑搬进 CI

这里的 7 个脚本不是示例代码，是**能直接接进 CI 的工具**。它们存在的唯一理由是：

> **规格的约束力不来自文档写得多好，而来自偏离时会不会有人报警。**

没有脚本，SDD 就退化成「先写文档」——而文档的约束力是建议性的，会悄悄腐烂。有了脚本，`spec.md` 和代码之间那根绳子才真正绷紧。

```bash
# 一条命令验完全部（16 项）
bash scripts/run-all-gates.sh

# 只输出结论
bash scripts/run-all-gates.sh --quiet
```

| 脚本 | 它守护的东西 | 对应课程 |
|---|---|---|
| `run-all-gates.sh` | 总验收：一次跑完下面全部 | L09 / L12 |
| `check-spec-coverage.sh` | 每条验收标准都有测试对应 | L07 / L09 ★ |
| `check-layer-boundary.sh` | 宪法的架构边界不被绕过 | L02 / L07 |
| `verify-generated.sh` | 生成物未被手改、未过期、幂等 | L10 |
| `find-change-hotspots.sh` | 存量仓库先给哪块补规格 | L11 |
| `check-rendering.sh` | 折叠块内容真的被解析（构建绿但页面坏） | L12 |
| `agnes-review.py` | 规格的对抗式外部审阅 | L06 |

**这些脚本全部实测跑过**——包括**故意制造违规确认它们真的会红**。原因见下面「元验证」一节：一个不会红的门禁不是门禁，是仪式。

---

## `check-spec-coverage.sh` — spec-anchored 的标志性门禁

**它检查什么**：`spec.md` 里的验收标准条数 vs `docs/验收标准-测试映射.md` 的行数。两者不等 = 有标准没有测试在守 = 阻断合并。

```bash
bash scripts/check-spec-coverage.sh examples/taskflow          # 只查活跃 feature
bash scripts/check-spec-coverage.sh examples/taskflow --all    # 查全部 feature
```

```
── 001-taskflow-mvp ──
标准条数: 40   映射行数: 40
✅ 覆盖完整
```

这一条**就是 spec-first 与 spec-anchored 的分界线**。两个项目的规格可以写得一样漂亮，差别只在有没有人比对这两个数字。

**多 feature 的归属规则**（踩过坑才知道要写下来）：

1. 优先用 `<feature>/docs/验收标准-测试映射.md`
2. 否则用项目级 `<项目>/docs/验收标准-测试映射.md`，**但仅当该文件明确声明了对应本 feature 时**（判定方式：内容里出现该 feature 的目录名，如 `001-taskflow-mvp`）
3. 都不满足 → 报「该 feature 尚未规划」，**视为失败**

第 2 条防的是：第二个 feature 拿第一个 feature 的映射表去比对，算出一个**看起来像覆盖率不足、实际是归属错乱**的结论。

**它不检查测试文件是否存在**——只比对条数与编号。这是刻意的：编号是人的承诺，文件是否存在是另一层（由测试框架自己回答）。知道门禁的边界在哪，比相信它全能更重要。

## `check-layer-boundary.sh` — 把宪法的边界变成机械检查

```bash
bash scripts/check-layer-boundary.sh examples/taskflow ts
bash scripts/check-layer-boundary.sh examples/focuslog py
```

退出码：`0` 边界完好 · `1` 有越界 · `2` 定位不到源码目录。

⚠️ **本脚本最容易被写错的地方**：不能直接在源码里 grep 模块名。`state-machine.ts` 的注释里写着「本文件不得 import fastify」——naive 的 grep 会把这句话判成违规，于是门禁**每次都红**。

一旦门禁经常误报，团队就会把它关掉，然后连真正的违规也一起失去（这是 AP-18 的完整死法，L09 §3 有全过程）。正确做法是**先过滤出真实的 import/require 行，再在其中查模块名**。

另一个区分要记住：**修误报 ≠ 放宽门禁**。

- 修误报 = 提高判据精度（判据从「层目录在不在」改成「`src/` 在不在」，**能力不降**）
- 放宽门禁 = `|| true`，**能力归零**

两者表面上都让 CI 变绿，一个保留能力，一个放弃能力。

## `verify-generated.sh` — spec-as-source 的机械守卫

```bash
bash scripts/verify-generated.sh examples/rulesmith "node tools/generator/index.ts" src/generated
```

它抓三件事：① 有人手改了生成产物 ② 有人改了 spec 但忘了重新生成 ③ 生成不幂等。

⚠️⚠️ **顺序至关重要：必须先检测，再重新生成。**

第一版脚本是「先重新生成，再 `git diff`」——**错的**。重新生成会把手改直接覆盖掉，于是 `git diff` 变空，脚本报告「✅ 通过」。**它修好了问题却报告没事**：手改被静默吞掉，作者永远不知道发生过。

这类「看起来在工作、实际什么都没检测」的门禁，比没有门禁更危险。

## `find-change-hotspots.sh` — 存量改造的优先级

```bash
bash scripts/find-change-hotspots.sh . 6 20
```

按提交数降序列出模块，并给出建议的补规格范围（前 20%）。

核心原则：**规格的价值 ≈ 该意图被复用的次数 × 违背它的代价。** 半年不动的模块，规格优先级是 0。这是 L11 的第一步——在给存量仓库补规格之前，先决定**给哪里补**。

> 本脚本要 `git log`，所以：仓库自己还不是 git 仓库时它跑不了（本教程的 `examples/` 正是如此）。这是正常的——它是给真实存量仓库用的。

## `check-rendering.sh` — 抓「构建绿、页面坏」

```bash
bash scripts/check-rendering.sh          # 查源码（site-out/ 存在时顺带查产物）
bash scripts/check-rendering.sh --site   # 强制要求产物
```

它拦的是一个**只有人打开页面才能发现**的坑：`<details>` 折叠块的内容默认**不解析 markdown**。

| 写法 | 结果 |
|---|---|
| `<details>` | ❌ 内容原样输出，`**加粗**` 的星号直接显示在页面上 |
| `<details markdown="1">` | ✅ 正常解析 |
| `??? note "答案"`（缩进 4 空格） | ✅ 且带主题样式 |
| `???+ note "答案"` | ✅ 且默认展开 |

危险的不是这个坑，是**它的形状**：构建 ✅ 通过（`--strict` 也不吭声）→ 产物 ✅ 生成 → CI ✅ 全绿 → **页面上是一整块没格式的文本**。

这个门禁是真实事故留下的：本仓库 12 节课的自测答案折叠块当初全是第一种写法，**站点上线后**才在浏览器里发现。它检查两件事：

1. **源码**：不允许裸 `<details>`（代码围栏内的示例不算，避免误报）；开闭必须成对（只开不闭会把后面整页内容吞进折叠块）。
2. **产物**（若已构建）：每个折叠块的内容里必须出现块级标签——没有就说明 markdown 根本没被解析。

> **这个脚本自己踩了三个坑，都写在头部注释里**：状态变量跨文件泄漏（导致它跳过了全部 12 节课却报「一切正常」）、`END` 块里的 `FILENAME` 是最后一个文件而不是出错的那个、以及 **`close` 是 awk 内建函数名**（拿它当变量 → 语法错误 → 被 `2>/dev/null` 吞掉 → 那段检查**从未运行过**）。
>
> 三个都是「静默不检查」，而不是「误报」。所以本仓库每道门禁都必须通过**反向验证**——见下面「元验证」一节。

## `agnes-review.py` — 规格的对抗式审阅

`/speckit-analyze` 检查**规格内部一致性**（标准之间有没有矛盾、有没有孤儿标准）。本脚本让一个模型从**外部视角**挑刺——两者互补：

> **工具擅长确定性检查，模型擅长发现「话还没说全」的地方。**

```bash
export AGNES_API_KEY='sk-...'   # 只从环境变量读，绝不写进文件
python scripts/agnes-review.py examples/taskflow/specs/001-taskflow-mvp/spec.md --focus "并发与权限"
```

实测它挖出过一条**逐条读规格发现不了的缺口**：`US2.5`（跨天会话计入开始日）与 `US3.6`（周报排除活跃会话）各自都对，但**放进同一个场景**——周一 23:50 开始、周二 00:10 结束的会话——这 20 分钟会从用户视野里凭空消失。

模型的价值在这里：**工具只能查你说过的话是否自洽，模型能看出你漏了哪句话。**

⚠️ **两个使用心得**：

1. **模型的排序依据通常是文本严重程度，不是对用户的后果。** 它把「输出格式未定义」排在第一位（文本上最刺眼），但真正会让用户困惑的是上面那条跨周会话消失。**排序要自己重排。**
2. **审阅意见必须人来判定。** 模型会给出一条听起来很对的建议，而它对项目上下文一无所知。它是**扩音器**，不是决策者。

地址与模型名实测记录见 [Agnes API 速查](../reference/agnes-api.md)——里面有一个**值得单独读的坑**：某个域名下 `/models` 返回 200 却不校验凭证，照着它判断「地址对了、是密钥的问题」会一路错到底。

## 元验证：怎么证明门禁真的在工作

**一个不会红的门禁不是门禁，是仪式。**

所以这些脚本全部通过了**反向验证**——不是「跑一遍是绿的」，而是「故意弄坏，看它红不红」：

| 元验证 | 做法 | 预期 |
|---|---|---|
| 覆盖率门禁 | 从映射表删掉一行 | 报出**具体缺哪一条** |
| 分层门禁 | 在 domain 层写一句 `import fastify` | 报出文件:行号 |
| 生成物门禁 | 手改 `src/generated/` 里的一个值 | 报出真实 diff，而非静默覆盖 |
| 生成器引用校验 | 在 spec 里引用未定义产生式 | **构建期**报错，不是运行期 |
| 链接检查器 | 人为造一个断链 | 报出断链位置 |
| 渲染完整性 | 把折叠块改回裸 `<details>` / 改成只开不闭 | 报出**文件:行号**；围栏内的示例不误报 |

**这五项是 L09 §4「对抗演练」的现成题库**——你可以在自己的项目上照做，把红当成及格线。

## 接进自己的项目

三个脚本都有 `::error::` 前缀的 GitHub Actions 注解格式，可直接用。以 `taskflow` 为例（`examples/taskflow/.github/workflows/sdd-gate.yml`）：

```yaml
- name: 验收标准覆盖率
  run: bash scripts/check-spec-coverage.sh .
- name: 分层边界
  run: bash scripts/check-layer-boundary.sh . ts
```

⚠️ 脚本里 `cd "$(dirname "$0")/.."` 的写法意味着：**放进自己项目时要确认相对路径基准**。`run-all-gates.sh` 假定它在仓库根的 `scripts/` 下。

**别一开始就上全套。** 顺序建议（L12 的渐进落地）：

1. 只上 `check-spec-coverage.sh`（最容易见效，也最不容易误报）
2. 用一两个 feature 观察误报率——**误报率高于 5% 就先修判据，别急着加下一条**
3. 再上分层边界；生成物校验只对 spec-as-source 的项目才有意义

**门禁的价值来自「红灯必有意义」。** 一条经常误报的门禁会被关掉，然后连真话也一起失去。
