# SDD 反模式清单

按「你在哪一阶段会撞上它」排列。每条格式：**症状 → 根因 → 修法 → 出现在**。

留着这份清单，每次做完一节回来看一眼。

---

## 阶段一：地基

### AP-1 · 把 SDD 当流程宗教

- **症状**：给一个三天就扔的脚本写 200 行规格；团队把「必须写 spec」当成不可讨论的规矩，产出速度反而下降。
- **根因**：忘了规格的价值公式 —— **价值 ≈ 该意图被复用的次数 × 违背它的代价**。
- **修法**：回到 [L01 第 5 节](../lessons/01-why-sdd.md)，明确四类**不该**写规格的场景并写进团队约定。
- **出现在**：L01

### AP-2 · 宪法当口号墙

- **症状**：宪法里写「我们要写高质量、可维护、健壮的代码」。
- **根因**：把**价值观**错当成**约束**。
- **修法**：每条原则必须能构造出「违反它」的具体案例，且这个案例能作为 code review 的拒绝理由。构造不出来就删。
- **出现在**：L02

### AP-3 · 宪法写成长篇小说

- **症状**：8 页、50+ 条。跑 `/speckit-plan` 时 agent 开始忽略部分条款，产出变得泛泛而谈。
- **根因**：宪法挤占 agent 的上下文预算。超长之后它从「约束」退化成**有害噪声**——还挤掉了真正关键的信息。
- **修法**：硬性 1 页上限。超了就往 spec 或团队 wiki 移。**15 条可判定原则 ≫ 50 条正确的废话。**
- **出现在**：L02

### AP-4 · 宪法与工具默认模板冲突不管

- **症状**：agent 行为忽冷忽热，同一类问题有时按你的规矩办，有时按默认模板办。
- **根因**：存在互相矛盾的判据，agent 每次都在两者间做随机选择。
- **修法**：显式删除或改写冲突项。**留着冲突比写错更糟。**
- **出现在**：L02

## 阶段二：最短闭环

### AP-5 · spec 里出现技术栈 ⚠️ 最高频

- **症状**：`spec.md` 里写着「使用 Fastify 实现 REST 接口」「数据存 Postgres」。
- **根因**：人习惯性地边想需求边想实现。
- **修法**：搜一遍 `spec.md`，框架名/库名/数据库名/云服务名**一个都不许有**。技术决策全部推到 `/speckit-plan`。写早了会**污染 what 层的思考**——可能你真正需要的架构完全不同，但因为你已写下 Fastify，思路就不会往那边走。
- **出现在**：L03

### AP-6 · 验收标准不可验收 ⚠️ 最高频

- **症状**：「导出功能要正常工作」「用户体验良好」「性能要好」。
- **根因**：把**感想**当成了**需求**。
- **修法**：念这句话——「什么样的观察结果会证明这条要求被违背了？」说不出具体的观察结果就重写。用 [EARS 句式](./ears.md)，一定附数字或布尔判据。
- **出现在**：L03

### AP-7 · 漏掉异常分支

- **症状**：正常路径实现得很好，一上生产就在空输入、超时、并发、重复提交、权限边界上出事。
- **根因**：规格只写了 happy path。**正常路径 agent 自己就会补，异常路径只有你能给。**
- **修法**：每条需求过一遍 [EARS ⑤ 的异常清单](./ears.md)。高价值异常（并发冲突、幂等）必须写成 `IF … THEN … SHALL …`。
- **出现在**：L03

### AP-8 · 跳过 plan review 直奔 tasks

- **症状**：拿到的代码看起来很对，但架构和你想的完全不是一回事，返工代价巨大。
- **根因**：把 plan 当成自动生成的中转产物，而不是**人类纠偏点**。
- **修法**：黄金法则——**永远不要从 spec 直接跳到 code**。计划必须过目，任务必须过目，review 一次的成本远低于返工一次。
- **出现在**：L04

### AP-9 · plan 里出现 spec 没要求的东西

- **症状**：你只要导出周报，agent 顺手加了缓存层、插件系统、遥测上报、i18n。
- **根因**：这个是**范围蔓延**的典型入口，而且它在 plan 阶段看起来「很专业」，最容易被放过。
- **修法**：逐条检查 plan 中的每项技术决策，能否指回 `spec.md` 的某一条？指不回的删掉，或者显式补进 spec 并承认范围扩大了。
- **出现在**：L04

### AP-10 · 提交即完成

- **症状**：命令跑通了就宣布做完，然后逐个发现行为缺口。
- **根因**：缺少**验收纪律**——没有把每条 EARS 标准逐条对照验证。
- **修法**：建立验收记录表，每条标准对应一个具体的验证动作和结果。**不允许出现「应该没问题」。** 更不要**让 agent 自己写验收结论**。
- **出现在**：L05

### AP-11 · 默许规格外功能

- **症状**：agent 顺手实现了规格外的功能，你看了一眼觉得「也行」，留下了。
- **根因**：没意识到这是**漂移的起点**——今天默许一个，明天规格和实现就开始分叉，而没有任何机制会提醒你。
- **修法**：规格外产出，要么删，要么**显式补进 spec 并走一次规格变更**。没有第三条路。
- **出现在**：L05

## 阶段三：规格锚定

### AP-12 · 在歧义上做规划

- **症状**：跳过 clarify 直接 plan，结果整份 plan 建立在你和 agent 对某个概念的不同理解上。
- **根因**：以为「我已经说清楚了」。**澄清阶段最大的产出是「你发现了几处自己以为很清楚其实不清楚的地方」。**
- **修法**：clarify 必跑。回答 agent 的每个追问时，**不许回答「你看着办」**——那等于把歧义原封不动推进下游。
- **出现在**：L06

### AP-13 · checklist 当待办列表

- **症状**：实现完才去把 checklist 逐项打勾。
- **根因**：混淆了两种工件。自定义 checklist 是**需求质量的评审工件**（打勾 = 我认为这条要求写清楚了），**不是实现完成度**。
- **修法**：以**评审人**身份在**实现之前**打勾。**没有靠猜打勾的项。**
- **出现在**：L06

### AP-14 · 契约测试只测 happy path

- **症状**：CI 全绿，生产出事。
- **根因**：契约测试退化成了「接口不报错测试」。
- **修法**：每条验收标准至少映射一个自动化测试，**映射关系显式记录**。并且——留**至少一条故意会失败的测试**作为「测试真的能抓到偏离」的证据。状态机测试、权限矩阵测试、错误码表都要覆盖。
- **出现在**：L07

### AP-15 · analyze 报冲突却「先实现再说」

- **症状**：`/speckit-analyze` 明确指出 spec 和 plan 矛盾，你想着后面再修。
- **根因**：低估了矛盾在下游的放大效应。analyze 是**只读**的便宜检查，代价最低的修复点就在这里。
- **修法**：**在源头改，然后重跑 analyze 到 clean 为止。**（做 L08 的刻意留矛盾练习时例外——那是故意用来验证工具的。）
- **出现在**：L08

### AP-16 · 一次性 implement 全部任务

- **症状**：一口气跑完所有任务，出了问题时**无法定位是哪一层错的**——是 spec 没说清？plan 设计错？还是某个任务拆解有误？
- **根因**：放弃了人类纠偏点。一次性跑完等于**让错误在无人区累积**。
- **修法**：**分阶段实现，每个阶段停下来人工验收。** 至少有一个阶段应该因为验收而调整任务顺序或拆解方式——没发生这种情况，说明你在走过场。
- **出现在**：L08

### AP-17 · converge 报 gap 就手改绕过 ⚠️

- **症状**：converge 说有缺口，你直接改代码把它填上（或者更糟，把 spec 改成符合现状）。
- **根因**：把 converge 当成了麻烦而不是信号。
- **修法**：**往 tasks.md 回填新任务**，然后 `implement → converge` 循环到报告 Converged。这是 converge 的设计意图。
- **出现在**：L09

### AP-18 · 门禁太严，最后被团队关掉

- **症状**：每次提交都要改规格，一周后有人把 CI 检查注释掉了。
- **根因**：门禁范围没有克制。**没人会长期忍受一个总在挡路的检查。**
- **修法**：门禁只盯**对外行为**：契约测试、状态机、权限矩阵、错误码。别去管内部重构、日志措辞、变量命名。分阶段上线，先警告后阻断。
- **出现在**：L09

### AP-19 · 改行为不改规格

- **症状**：实现悄悄偏离了规格，而规格文件停留在三个月前。
- **根因**：忘了 spec-anchored 的**制度基础**——「行为变更必须先改规格」。这条应该在宪法里（L02 第 ⑦ 类）。
- **修法**：把它写进宪法 + 写进 PR 模板的检查项，靠制度而非自觉。
- **出现在**：L09

## 阶段四：进阶

### AP-20 · 把 spec-as-source 当终极目标套到处用

- **症状**：在 UI、算法调优、探索性需求上强推「人只改规格」，结果生成器比手写代码更难维护。
- **根因**：忘了 spec-as-source 只适用于**高度结构化、模式重复**的领域（DSL、协议、数据管道、报表规则）。
- **修法**：L10 的验收标准里明确要求你**说出本项目不适合规格即源的部分及原因**。这个边界感才是那节课的真正价值。
- **出现在**：L10

### AP-21 · 生成器本身没人维护

- **症状**：生成器比它生成的东西更脆。改一个模板，几十个产物全崩。
- **根因**：生成器被当成一次性工具，没有测试、没有版本管理、没有 owner。
- **修法**：生成器是**一等公民代码**——它需要自己的测试（含幂等再生测试）和负责人。
- **出现在**：L10

### AP-22 · 手改了生成产物

- **症状**：某人直接编辑了生成的文件，下次再生成时改动被覆盖。
- **根因**：缺少机械化的守卫。
- **修法**：用 CI 校验生成物的可复现性（重新生成 → diff 必须为空）。文件头加 `DO NOT EDIT` 标记。
- **出现在**：L10

### AP-23 · 逆向补规格时把 bug 固化成规范

- **症状**：从存量代码反推规格时，把现有实现的错误行为描述成了「需求」。
- **根因**：「现状」和「期望」没分开。
- **修法**：偏差清单里**每一处都要明确归类为「改代码」或「改规格」**，归类时问一句：这个行为是我们**有意设计**的吗？
- **出现在**：L11

### AP-24 · 想一次补齐所有历史代码的规格

- **症状**：三个月过去了，规格还没补完，团队已经放弃。
- **根因**：全量改造的野心。
- **修法**：**按变更热点渐进。** 只给「接下来要动的模块」补规格。存量代码如果半年不动，它的规格优先级是零。
- **出现在**：L11

### AP-25 · 没有退出策略

- **症状**：流程明显在拖累团队，但没人敢说「这个模块不该用 SDD」。
- **根因**：流程一旦建立就有了自我延续的惯性。
- **修法**：L12 要求你**预先定义「什么信号意味着该收手」**。这是成熟度的标志，不是失败。
- **出现在**：L12

## 补充（v2 审阅新增）

以下三条是审阅学习计划时补上的真实缺口——原来 25 条没覆盖到。

### AP-26 · converge 永远不收敛

- **症状**：`implement → converge` 循环了七八轮，每次 converge 都报新的 gap，永远到不了 Converged。
- **根因**：**没有判断 gap 属于哪一层**。往往是规格本身错了或不清楚，但你在反复重跑实现。
- **修法**：三层分流判断——
  | gap 的性质 | 回哪一层 |
  |-----------|---------|
  | 代码没实现规格要求的行为 | → `implement` |
  | 规格没说清 / 自相矛盾 | → `clarify` 或 `specify` |
  | 任务拆解漏了或拆错了 | → `tasks` |
  
  **判断错层级就会陷入无限循环**。反复重跑 implement 是最常见的误判。
- **出现在**：L09

### AP-27 · 「跑过一次流水线」当成掌握 SDD

- **症状**：单 feature 从零走到收敛，就觉得自己会了；一上真实项目就懵。
- **根因**：课程化场景剔除了两个真实工作里的常态——**改已有功能**和**同时维护多个 feature**。
- **修法**：L08 必须真的开第二个 feature 并演练切换上下文（靠 `.specify/feature.json`，不是 git 分支）；L09 必须真的走一遍**规格变更**（改一条已有验收标准，先让测试变红再改实现）。
- **出现在**：L08、L09

### AP-28 · 技术规模冒充教学价值（规划层的坑）

- **症状**：为了「更真实」，把案例项目设计得很大——12 个端点、3 个角色、多模块。
- **根因**：把**规模**和**严谨度**搞混了。这门课要练的是后者。
- **修法**：反复问「这个额外复杂度让**目标技能**更清楚，还是只制造了噪音？」项目 B 的目标是演示强制力，7 个端点 2 个角色就够，14 格权限矩阵已经能暴露全部问题。
- **出现在**：L07、L09（以及学习计划本身的审阅）

> 📌 这条特别值得记住：**审阅时要能抓自己的同类错误。**
> 我在 `projects/README.md` 里刚批评完「技术规模冒充教学价值」，转头就在项目 B 的原始设计里犯了同一个错。

## 一页速查：出现这些症状时，问题在哪一层？

这是排查时最有用的一张表。**先分类，再修。三类问题的修复路径完全不同。**

| 症状 | 问题层 | 该改哪里 |
|------|--------|---------|
| 实现的和我要的不是一回事 | **规格不清** | 改 `spec.md`，补 EARS 语句 |
| 规格说清楚了但架构选错了 | **规划有误** | 改 `plan.md`，或补 ADR |
| 架构是对的但代码有 bug | **实现跑偏** | 改代码 |
| agent 每次都忘记项目规矩 | **宪法问题** | 改 `constitution.md`（多数是太长了） |
| 任务做完但功能不完整 | **拆解问题** | 改 `tasks.md`，跑 `/speckit-converge` 回填 |
| 改一处坏一处 | **缺强制力** | 补契约测试 + CI 门禁（L09） |
| 团队越来越不想用 | **门禁太严或范围太广** | 收窄门禁到对外行为 |
| converge 反复报 gap | **gap 层级判错** | 先分层（实现/规格/任务），再动手（AP-26） |
| 改一个功能要动十份文档 | **规格变更流程缺失** | 建立 delta spec 流程（L09） |
| agent 开始忽略项目规矩 | **宪法太长** | 回到 AP-3 压到 1 页以内 |
