# L02 · Constitution：给项目立宪

> **时长** 90 min ｜ **前置** [L01](./01-why-sdd.md) ｜ **产出** 1 页以内的 `constitution.md` + 一份可复用模板

---

## 1. 宪法到底是什么

最容易搞错的一点：

> ❌ 宪法不是「描述我们要做什么」——那是 spec 的活。
> ✅ 宪法是**约束后续每一个决策的评判标准**。

换句话说：**spec 说的是「建什么」，宪法说的是「无论建什么，都必须遵守的规矩」。**

宪法的作用机制是这样的——之后每一次 agent 产出（spec、plan、tasks、code），都会被拿来和宪法对照。它相当于给 agent 装了一个**常驻的判据**，让它在没人盯着的时候也不至于跑偏。

### 宪法 vs spec vs plan

| | 宪法 | spec | plan |
|---|---|---|---|
| **范围** | 全项目，跨所有 feature | 单个 feature | 单个 feature |
| **回答** | 我们守什么规矩 | 是什么、为什么 | 怎么做 |
| **更新频率** | 极少（每个项目一次） | 每个 feature | 每个 feature |
| **写错的代价** | 最贵——它会污染之后所有决策 | 贵——后面全返工 | 中 |

**「写错的代价」那一行是本节最重要的信息。** 宪法在整个链条的最上游，它的每一次模糊都会被下游放大。

## 2. 宪法七类条款

一个够用的宪法，覆盖面就是下面七类。**每一类只写 1–3 条，且必须是可判定的。**

### ① 技术栈与版本

```markdown
- 运行时：Python 3.10+，不使用低于 3.10 的语法特性
- 依赖管理：uv；禁止在仓库中提交 requirements.txt
- 第三方依赖：单个 feature 新增依赖不超过 2 个，且必须在本文件登记
```

> 为什么要限制依赖数量？因为依赖是**永久成本**，而「加一个库」的决策成本极低——不加限制，agent 会一路加下去。

### ② 架构边界

```markdown
- 核心业务逻辑必须与 I/O 分离：`domain/` 不得 import 任何 IO 相关模块
- CLI / HTTP 层只能调用 `services/`，不得直接访问存储
```

### ③ 测试与质量门禁

```markdown
- 所有公开行为必须有自动化测试覆盖
- 规格中的每条验收标准必须至少映射到一个测试用例，映射关系记录在 plan.md 中
- 测试必须能在无网络环境下运行
```

### ④ 安全与隐私

```markdown
- 所有外部输入在进入领域逻辑前必须经过校验
- 日志中禁止出现用户标识符的明文
- 不得引入任何会把用户数据发往第三方端点的依赖
```

### ⑤ 性能预算

```markdown
- 任何面向用户的命令/接口，本地执行耗时 P95 < 200ms；超出必须在 README 说明
```

> 注意：**性能预算必须带数字**。「性能要好」是不可判定的，等于没写。

### ⑥ 可观测性

```markdown
- 所有错误必须携带机器可读的错误码
- 关键状态变更（创建/删除/状态流转）必须记录结构化日志
```

### ⑦ 文档与提交规范

```markdown
- 任何改变对外行为的变更，必须同步更新对应的 spec.md
- 提交信息格式：<type>: <描述>，type ∈ {feat, fix, refactor, docs, test}
```

> 第七条的第一句是**把「改行为必须先改规格」写进宪法**——这是 spec-anchored 的制度基础。

## 3. 动手：为 hello-sdd 立宪

回到 L00 建好的 `hello-sdd/` 目录，在 agent 聊天里调用：

```
/speckit-constitution hello-sdd 是一个纯本地实验项目。
不引入任何持久化存储（除家目录下的单个 JSON 文件），不依赖网络，
所有产物必须可以直接删除重建。

具体约束：
- 只使用 Python 标准库，零第三方依赖
- 业务逻辑与文件读写必须分离，文件读写集中在一个模块内
- 所有公开函数必须有 docstring 和对应的单元测试
- 时间戳统一使用 ISO 8601 格式，时区为本地时区，且必须可在测试中注入
- 任何改变输出格式的变更，必须同步更新 spec.md
```

**注意最后两条的写法。** 「时区为本地时区，且必须可在测试中注入」——这是一条**可判定的**约束：如果时间戳直接调 `datetime.now()` 而没有注入点，就违反了宪法，code review 可以据此拒绝。这就是 L01 里说的「能否被用作不给过的理由」。

### 生成后必须做的三件事

**① 逐条验伪。** 对每条原则问：*我能构造一个「违反了它」的具体例子吗？* 构造不出来，说明这条太虚。

**② 检查有无越界。** 宪法里**不该有功能需求**。看到类似「用户应能导出周报」的句子，删掉——那是 L03 spec 的内容。

**③ 检查有无和工具默认模板打架。** Spec Kit 会生成一份默认宪法模板。你的条款如果和它冲突，要么改你的，要么明确删掉冲突项——**留着冲突比写错更糟**，因为 agent 每次都要在矛盾中做选择，行为会变得不可预测。

## 4. 压力测试：故意写一版太长的宪法

这一步请真的做一遍。把宪法扩充到 8 页、50+ 条（可以让 agent 帮你「把每条展开成三小条」），然后拿一个新 feature 去跑 `/speckit-plan`，观察：

- agent 是否开始**忽略**其中某些条款？
- 它的产出是否变得更泛泛、更爱说套话？
- 你是否发现自己也懒得再读它了？

**这就是核心机制：宪法占据 agent 的上下文预算。超过一定长度，它从「约束」退化成「噪声」——而且是有害的噪声，因为它挤掉了真正重要的信息。**

然后把宪法精简回 1 页以内，重跑同一个 `/speckit-plan`，对比产出差异。

> 📌 **结论：宪法的价值不随长度增长，而是随「可判定性」增长。**
> 15 条可判定的原则 ≫ 50 条正确的废话。

### 精简的判断标准

砍掉一条之前问自己：

| 问题 | 该砍 |
|------|------|
| 这条例违反了会有任何具体后果吗？ | 没有 → 砍（如「代码应保持整洁」） |
| 这条是「价值观」还是「约束」？ | 价值观 → 砍，或改写成约束 |
| 这条是否已被某条更上游的原则覆盖？ | 是 → 砍 |
| 这条是否只对某个特定 feature 有意义？ | 是 → 移到该 feature 的 spec |

## 5. 可复用模板

把下面这段存下来，之后每个项目起手都从它改：

```markdown
# <项目名> 宪法

## 技术栈与版本
- 运行时：
- 依赖管理：
- 依赖登记规则：

## 架构边界
- <分层规则，明确哪层不得 import 哪层>

## 测试与质量门禁
- 验收标准 ↔ 测试用例的映射要求：
- 环境要求（离线可跑等）：

## 安全与隐私
- 输入校验边界：
- 日志脱敏要求：

## 性能预算
- <带数字的阈值 + 超标时的处理动作>

## 可观测性
- 错误码规范：
- 结构化日志要求：

## 文档与提交规范
- 行为变更必须同步更新 spec（spec-anchored 的制度基础）
- 提交信息格式：

## 修订
- 最后更新：<日期>
- 修订原因：<一句话>
```

**最后那个「修订」小节别省。** 宪法是活的——但它的每次变更都应该是被意识到的、有理由的。这个记录本身就在保护你不在无意中把流程放松掉。

## 6. 交付物与验收

### 交付物

1. `hello-sdd/` 中生成的宪法文件（位置以你本地为准，通常在 `memory/` 下）
2. `templates/constitution-template.md` —— 上面那套模板，你自己的版本
3. `notes/L02-宪法压力测试.md` —— 长版 vs 精简版的产出对比

### 验收清单

- [ ] 宪法**不超过 1 页**（打印出来一页装得下）
- [ ] 每一条原则都能给出**一个具体的违反案例**，并且这个案例能作为 code review 的拒绝理由
- [ ] 宪法中**没有任何功能需求**（没有「用户应能…」这类句子）
- [ ] 宪法中**没有与技术栈无关的空话**（「高质量」「整洁」「健壮」这类词为零）
- [ ] 所有性能/质量指标**都带数字或明确的布尔判据**
- [ ] 你做过长版压力测试，并能说出「太长的宪法具体是怎么坏事的」

### 自测

1. 「所有代码必须有单元测试」和「所有公开函数必须有单元测试」——哪条更好？为什么？
2. 为什么宪法要限制「单个 feature 新增依赖不超过 2 个」？这条约束真正在防什么？
3. 如果团队说「我们的宪法是：写高质量、可维护的代码」，你会怎么改写它？

<details>
<summary>答案</summary>

1. 后者。前者不可判定边界（「所有代码」包括配置文件吗？），实际执行会变成谁都不管；后者的判定是完全机械的。
2. 防的是**决策成本不对称**：加一个库的即时成本近于零，而它带来的永久维护成本由未来的团队承担。限制条数逼着人做取舍。
3. 拆成可判定的约束，例如：「新增依赖需在宪法中登记，单 feature ≤ 2 个」「所有公开 API 必须返回机器可读错误码」「合并前必须通过 contract test」。「可维护」这种词无法作为判据，改写成 2–3 条具体规则才有约束力。

</details>

## 7. 踩坑预警

| 坑 | 后果 | 解法 |
|----|------|------|
| **宪法写 8 页** | 退化成噪声，agent 开始忽略，人也懒得读 | 严格 1 页上限；超了就往 spec 移 |
| **塞进功能需求** | 与 spec 职责重叠，两边都变得不可信 | 看到「用户应能…」就删 |
| **写成价值观宣言** | 无法判定，等于没写 | 每条都要能构造违反案例 |
| **和默认模板冲突留着不管** | agent 在矛盾中做选择，行为不可预测 | 显式删除或改写冲突项 |
| **每个 feature 都改宪法** | 上游频繁变动，下游全部失效 | 宪法每个项目一次；feature 级约束放 spec |
| **忘了「行为变更必须同步更新 spec」** | 直接丢掉 spec-anchored 的制度基础，L09 会做得很痛苦 | 这条是必写项 |

## 8. 本节术语

| 术语 | 含义 |
|------|------|
| constitution | 项目级、跨 feature 的长期约束；agent 的常驻判据 |
| guardrail | 护栏——限制 agent 行为边界的约束 |
| quality gate | 进入下一阶段前必须通过的检查 |
| 可判定性 | 一条原则能否被机械地判断「违反了没有」；宪法质量的唯一标准 |
