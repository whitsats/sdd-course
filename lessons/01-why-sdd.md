# L01 · 为什么是 SDD：心智模型与成熟度模型

> **时长** 60 min ｜ **前置** [L00](./00-setup.md) ｜ **产出** 一页心智模型笔记

上一节结束时你手里有一个「有完整 spec/plan/tasks、但零代码」的项目。这节我们回答那个问题：

> **为什么不直接跟 agent 说「给我写个 hello-sdd」？**

---

## 1. 一句话定义

> **SDD 把精确、可执行的规格当作唯一真相源，把代码当作由规格生成、并被规格验证的产物。**
> 规格声明意图，代码实现意图。

注意关键词是 **可执行**。这是整门课最重要的一句话，也是 90% 的「SDD 讲解」漏掉的部分。

### 传统设计文档 vs SDD 规格

| | 传统设计文档 | SDD 规格 |
|---|---|---|
| **读者** | 人 | 人 **和 agent** |
| **约束力** | 建议性——开发者可以偏离 | **可执行**——偏离即测试失败 |
| **生命周期** | 逐渐过时，最后变成考古现场 | 活的，持续被校验 |
| **存放位置** | wiki（没人打开的地方） | **仓库 + CI/CD** |
| **失效方式** | 悄悄腐烂 | 红灯报警 |

最后一行是这个模式全部的威力所在。

> 「传统规格是给人读的；SDD 规格作为 BDD 场景、API 契约测试或模型仿真被执行。」
> —— Piskala, *Spec-Driven Development: From Code to Contract in the Age of AI Coding Assistants*, arXiv 2602.00180 (2026-01)

---

## 2. 为什么是 2026 年

SDD 的核心思想不新——契约优先、BDD、formal specification 都讲了几十年。**它现在爆发，是因为 AI 改变了成本结构。**

一句话解释：

> **AI agent 极其擅长写代码，极其不擅长猜你想要什么。**

这两件事的性质完全不同：

| | AI 的表现 | 正确的应对 |
|---|---|---|
| 写实现 | 极强，且越来越便宜 | **别自己写**，让 agent 写 |
| 猜意图 | 极差，且错误会累积 | **别让它猜**，写清楚 |

于是**人类努力的支点发生了转移**：从「敲实现」前移到「定义意图」。SDD 是对这个转移的工程化回答。

### vibe coding 的三种破产方式

vibe coding（2025 年初 Karpathy 带火的词）指松散地提示 AI、拿到什么就用什么的开发方式。它做原型很好，做要维护的东西很糟。破产方式有三种：

**① 需求漂移（drift）**
你在第 1 轮说「导出周报」。到第 5 轮，一个不相关的改动让导出开始漏掉周三的数据。**没有任何东西会告诉你这件事**——因为「导出周报要包含周一到周日全部数据」这句话，从未以任何可执行的形式存在过。它只存在于你和 agent 对话的上下文里，而那个上下文早就滚出窗口了。

**② 上下文丢失**
长对话后，agent 忘了三轮之前的约束。你重新解释一遍，它又改好了——顺带弄坏了别的地方。因为没有**持久化的意图载体**，只有会蒸发和会膨胀的对话。

**③ 无法验证「做完了」**
你说「任务看板做完了」。凭什么？「能拖动卡片」算完吗？权限呢？并发编辑呢？**没有验收标准，就没有完成这个概念**——只有一个模糊的「看起来差不多」，然后在生产环境里逐个发现缺口。

**回到 L00 的问题**：

> 那三个 Markdown 文件解决了什么？

它们把**只存在于对话里的意图**，变成了**存在于仓库里、可审阅、可追溯、可校验、不会遗忘的工件**。这就是全部答案。

**问你自己**：上面三种破产方式，你哪一次踩得最深？那次如果先写清验收标准，会在哪一步被拦住？

## 3. 成熟度模型：三级严谨度

这是学术与工业界在 2026 年收敛出的框架。**不要跳级——选你实际需要的等级。**

### Spec-First（规格优先）

```
规格为最初的生成提供种子 ──► 之后允许代码自由漂移
```

- **怎么做**：写规格 → 让它引导第一次生成 → 后面随便改
- **成本**：低，几乎没有额外开销
- **保证**：短期质量提升。**没有长期保证**
- **适合**：原型、AI 辅助做的单个功能、一次性脚本

### Spec-Anchored（规格锚定）🎯

```
规格与代码共同演化 ──► 自动化测试强制二者保持对齐
```

- **怎么做**：规格是活的；契约测试 / BDD 场景把规格变成可执行断言；CI 在漂移时失败
- **成本**：中等。规格变更需要配套改测试
- **保证**：**漂移会被发现，而不是被埋起来**
- **适合**：生产系统 —— Piskala 的论文称这是「大多数生产系统的甜点区」

**这是本课程的目标。** L09 是达标节点。

### Spec-as-Source（规格即源）

```
人只编辑规格 ──► 代码 100% 生成，永不手改
```

- **怎么做**：规格 → 生成器 → 产物。版本库里没有手写的实现
- **成本**：高。需要成熟可信的生成工具链
- **保证**：从设计上消除漂移（因为根本没有手写代码可以偏离）
- **适合**：高度结构化、模式重复的领域：DSL、协议、数据管道、报表规则引擎、脚手架
- **现状**：对大多数团队**仍然是探索区**——这是营销话术最密集、落地证据最少的一级

### 升级路径

```
Spec-First
    │  加「活的测试」+ CI 强制
    ▼
Spec-Anchored 🎯 ◄──── 本课程目标：价值在这里
    │  信任生成能力，彻底停止手改代码
    ▼
Spec-as-Source
```

**热度和价值不在同一格。** 声量最大的是 spec-as-source，真正赚钱的是 spec-anchored。

## 4. 规范工作流

所有主流工具（Spec Kit / Kiro / OpenSpec / BMAD）都实现了大致同一根流水线，区别只在命名和自动化程度。Spec Kit 当前的核心流程是：

```
Specify ──► Plan ──► Tasks ──► Implement ──► Converge
```

生产级场景走**完整路径**，中间加入三个质量门禁：

```
constitution（每个项目一次）
   ↓
specify  ──►  clarify  ──►  plan  ──►  checklist  ──►  tasks  ──►  analyze  ──►  implement  ──►  converge
   是什么        消灭歧义     怎么做      需求质量审查      拆解        一致性检查      实现           收敛验证
```

| 阶段 | 回答的问题 | 关键纪律 |
|------|-----------|---------|
| **constitution** | 项目必须遵守的规则是什么 | 每个项目一次，控制在 1 页内 |
| **specify** | **是什么、为什么** | ⛔ 禁止出现技术栈 |
| **clarify** | 哪里还没说清楚 | 自己先交出答案，不许「你看着办」 |
| **plan** | **怎么做** | 技术决策**只**允许在这里，且必须可追溯到 spec |
| **checklist** | 这些要求写好了吗 | 以**评审人**身份打勾，不是实现完成度 |
| **tasks** | 拆成哪些原子项 | 依赖排序，粒度不均等才是对的 |
| **analyze** | 三份文档自相矛盾吗 | 只读检查，发现问题回源头改 |
| **implement** | 开始写 | 读完 checklist 状态作为门禁；可分阶段 |
| **converge** | 代码和规格一致吗 | 有 gap 就往 tasks.md 回填，别手改绕过 |

> ⚠️ **黄金法则：永远不要从 spec 直接跳到 code。**
> 计划必须过目，任务必须过目。每一个阶段边界都是一次人类纠偏机会——**放弃一次，等于把纠错成本推给未来的自己。**

注意：`constitution → ... → converge` 是一条完整链路，但在 Spec Kit 里，**修复 bug 和评估想法是独立的入口，不是这条链的强制前置**。L11 会讲这两个分支。

## 5. 什么时候**不该**写规格

这段是本节对你最实用的部分。**过度规格化也是一种浪费**，而且它会让团队对整个方法论失去信心。

以下四类场景，**不要**上完整 SDD：

| 场景 | 为什么不适合 | 该怎么做 |
|------|------------|---------|
| **三天不变量、写完就扔** | 一次性脚本、临时数据清洗。规格成本 > 代码成本 | 直接写，或者直接让 agent 写 |
| **探索性需求** | 你自己都不知道要什么，写出来的规格是假精确——它会把错误固化 | 先做 spike 探清边界，再写规格 |
| **高频变更的 UI 细节** | 间距、动效、交互手感。写进规格的维护成本远超收益 | 保持在设计稿 / 组件库 / 视觉回归测试里 |
| **算法调优与性能攻坚** | 目标是一个数字（更快），路径要靠实验找 | 用 benchmark 当「规格」，用实验逼近 |

**判断准则**（记住这一句就够）：

> **规格的价值 ≈ 该意图被复用的次数 × 违背它的代价。**

- 会被反复引用（测试、新人、三个月后的你） → 值得写；
- 违背了后果严重（资金、安全、合规、数据） → 必须写；
- 两者都不满足 → 别写。

## 6. 动手：写你的心智模型笔记

建一个 `notes/` 目录，写 `L01-心智模型.md`，回答下面四个问题。**每个问题都要落到具体项目名，不要写抽象感想。**

```markdown
# 我的 SDD 心智模型

## 1. 我踩过最深的坑
哪个项目、什么现象、属于「需求漂移 / 上下文丢失 / 无法验证完成」中的哪一种？
如果当时写清了验收标准，会在哪一步被拦住？

## 2. 我的三级分类
列出我手上 3 个真实项目，给每个定级（spec-first / spec-anchored / spec-as-source），
并写一句理由：
- 项目名 —— 级别 —— 理由

## 3. 不值得写规格的
我手头哪个需求属于第 5 节的四类场景之一？为什么？

## 4. 我的第一优先级
如果只能给一个项目补规格，选哪个？它的第一条验收标准会是什么？
```

### 验收标准

- [ ] 三个问题都落到了**具体项目名**，没有抽象空话
- [ ] 第 2 题的定级里，**至少有一个项目你选择了 spec-first 而不是更高级别**（如果三个都选了 spec-as-source，说明你还没理解成本）
- [ ] 第 4 题的那条验收标准，你能说出「什么样的观察结果会让它失败」

最后一条是第 3 节的精髓：**不可验收的要求等于没写。**

## 7. 自测题

不看上文回答：

1. 传统设计文档和 SDD 规格，哪一个差别是**最本质**的？（提示：不是「给谁看」）
2. 为什么 spec-anchored 比 spec-as-source 更值得作为目标？
3. 「我们要求代码高质量、注释完整」——这句话放进宪法算合格吗？为什么？
4. 你的规格里写了「用 Fastify 实现接口」。这句话应该在哪个阶段出现？写错阶段会造成什么后果？

<details markdown="1">
<summary>答案</summary>

1. **约束力**：SDD 规格是可执行的——偏离会让测试失败。这一点决定了它不会腐烂。
2. 因为 spec-as-source 需要成熟可信的生成工具链，且只适用于高度结构化领域；spec-anchored 用「测试强制对齐」就拿到了绝大部分收益，适用范围广得多。
3. 不合格。无法被用作「不给过」的判据。合格版本如：「所有公开 API 必须有 schema 校验，非法输入返回 400 与机器可读的错误码。」
4. 应该在 **plan** 阶段。写进 spec 会让「是什么/为什么」的讨论被技术约束污染——可能你真正需要的是完全不同的架构，但因为你已经写下了 Fastify，思路就不会往那边走了。

</details>

## 8. 本节术语

| 术语 | 含义 |
|------|------|
| vibe coding | 松散提示 AI、拿到什么用什么的心态；原型可用，维护灾难 |
| drift（漂移） | 实现与规格/意图逐渐背离，且无人察觉 |
| spec-first | 规格只做初始种子，之后允许漂移 |
| spec-anchored | 规格与代码共同演化，测试强制对齐（**生产甜点区**） |
| spec-as-source | 人只改规格，代码全生成，永不手改 |
| EARS | 需求句式语法，把自然语言需求变成可验收语句（见 [reference/ears.md](../reference/ears.md)） |
| quality gate | 进入下一阶段前必须通过的检查点 |
