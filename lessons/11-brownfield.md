# L11 · 存量改造：给已存在的仓库补规格

> **时长** 120 min（实操通常 3–4 h）｜ **前置** [L10](./10-spec-as-source.md) ｜ **产出** 偏差清单（每处已归类）+ 一页适配性判定

前面十个案例都是 **greenfield**（从零开始）。但你不会天天做新项目——**你会天天碰存量代码。**

这一节是全课程最接近你真实工作的一节，因为它解决的是一个残酷的现实：

> **你手上已经有一堆代码了。它们的规格在哪里？没有。**

> 📁 **本节的配套脚本**：`scripts/find-change-hotspots.sh` —— 见 §5 的实际输出。

---

## 0. 本节的特殊规则

⛔ **不要用课程的那三个项目。** 挑一个**你自己手头真实的**存量小仓库。

理由：greenfield 项目的代码是「规格的产物」，逆推回去很容易——**那是个假练习**。真实存量代码里充满了历史决策、废弃路径、复制粘贴的重复，以及没人记得为什么那么写的地方。

**只有真实仓库才能让你体会这节的难度。**

---

## 1. 为什么存量改造比新项目难

| 维度 | Greenfield | Brownfield |
|------|-----------|-----------|
| 规格来源 | 你脑子里 | **代码里（且可能是错的）** |
| 判定标准 | 规格 vs 意图 | 规格 vs 代码 vs 意图，**三者都可能各不相同** |
| 主要风险 | 规格写得不清楚 | **把 bug 固化成规范** |
| 完成信号 | converge 报告 clean | 没有干净的完成信号 |

**最后一行是关键。** 存量改造没有「Converged」这种明确的终点——你只能逐步逼近。

所以本节的目标不是「补完所有规格」，而是**建立一套判定方法**。

---

## 2. 接入：按存量项目路径走

```
specify --help
```

找到存量项目相关的入口/指引（Spec Kit 对已有代码库有专门的 adopting 路径，具体命令以你本地输出为准）。

**关键差别**：新项目是先有 `.specify/` 再有代码；存量项目是**反过来的**——代码存在，你要在上面补流程状态和约束。

### 先做宪法，这次要「从代码里读出来」

```
/speckit-constitution [你的项目名] 是一个已有的 [类型] 项目。

请先分析现有代码，提炼出**事实上的**约束，再让我确认：

- 实际使用的语言与版本、依赖管理方式
- 实际的架构分层（如果存在）与它的边界是否被严格遵守
- 实际的测试覆盖情况与测试类型
- 实际存在的（或缺失的）错误处理与日志规范
- 代码中已经存在但从未记录过的约定
```

**注意最后一条：** 「代码中已经存在但从未记录过的约定」——存量仓库里到处都是这种东西（某个目录只能被某层 import、某个字段必须加密、某个 API 调用必须重试）。**它们只存在于老员工的记忆里。**

把它显式化，本身就是巨大的价值。

### ⚠️ 宪法这一步最容易犯的错

**不要把现状当成规范。** 如果代码里 `domain/` 层直接访问了数据库（违反了分层），你有两个选择：

- 写成「不许跨层访问」→ 承认现状是**技术债**，需要修
- 写成「允许 domain 访问数据库」→ **把错误固化成规范**

**选第一个。** 宪法的职责是定义「应该怎样」，不是「现在怎样」。**这条原则在本节后面还有更重要的应用。**

## 3. 逆向规格化：从代码提炼 spec

**不要试图一次覆盖全部。** 选一个模块开始——选**你接下来几周会改的那个**（理由见第 5 节）。

### 做法

```
/speckit-specify 请阅读 `src/<选定模块>/` 下的实现，反推出该模块的 feature 规格。

要求：
- 用 EARS 句式写验收标准
- 每一条验收标准都必须标注它的**依据**：
  - [code] 从实现中直接观察到的行为（附文件与行号）
  - [test] 现有测试覆盖的行为（附测试名）
  - [assumption] 你的推断，无直接依据
- **不要**假设现有实现是正确的。遇到看起来可疑的行为，标注 [suspicious] 而不是当成需求
- 显式列出你**无法确定**意图的部分
```

**三个标注类型是本节的精髓：**

| 标注 | 含义 | 后续处置 |
|------|------|---------|
| `[code]` | 代码里明确观察到的行为 | 判定「有意设计？」 |
| `[test]` | 有测试保护的既有行为 | 通常可信度最高 |
| `[assumption]` | agent 的推断 | **必须人来确认**，不可直接采信 |
| `[suspicious]` | 看着可疑的行为 | 进偏差清单，**绝不能直接写进规范** |

> 📌 **`[assumption]` 和 `[suspicious]` 的存在，是逆向规格化与其他 SDD 阶段最大的区别。** 在 greenfield 里，spec 是你的意图；在这里，spec 是**你对代码意图的猜测**。必须把猜测标记出来。

## 4. 两类偏差 + 归类 ⭐ 本节核心产物

逆向规格化会产生两类偏差。**每一处都必须被归类，不许留「待定」。**

### 类型 A：实现里有、规格没写

| 处置选项 | 什么情况下选它 |
|---------|--------------|
| **补进 spec** | 这个行为是**有意设计的**，且我们要保留它 |
| **删掉代码** | 这是遗留代码、废弃路径、或者 bug |
| **标记为技术债** | 行为是正确的，但实现方式不对（如跨层访问） |

**判定问句：这个行为是我们有意设计的吗？**

- 找得到设计依据（ADR、issue、commit message、老同事记忆）→ 补进 spec
- 找不到，但行为合理且有人依赖 → 补进 spec，**并标注「历史行为，来源不明」**
- 找不到，且行为可疑 → **这是 bug**，删掉或修掉

### 类型 B：规格写了、实现没有

| 处置选项 | 什么情况下选它 |
|---------|--------------|
| **补实现** | 规格是对的，代码没做完（最常见的「未完成的 feature」） |
| **删规格** | 这个需求已经过期/被放弃了 |

**判定问句：这个需求现在还成立吗？**

### 偏差清单模板

```markdown
# 偏差清单

## A 类：实现里有、规格没写

| # | 行为 | 位置 | 判定 | 处置 | 依据 |
|---|------|------|------|------|------|
| A1 | 金额字段超过 10000 时自动跳过某些记录 | `report.py:88` | **有意设计** | 补进 spec | 找到 2024-03 的 issue #412 |
| A2 | 空标签时用 "untagged" 填充 | `domain/tag.py:31` | **过期的 legacy** | 删代码 | 无任何依据，且新代码里已有正确路径 |
| A3 | 导出接口支持 `format=xml` | `export.py:120` | **有人依赖** | 补进 spec + 标注来源不明 | 有 2 个客户在用，但找不到设计文档 |
| A4 | domain 层直接读了数据库 | `domain/user.py:15` | **技术债** | 标记技术债，不改行为 | 违反宪法分层，但改动风险大 |

## B 类：规格写了、实现没有

| # | 规格条目 | 状态 | 处置 |
|---|---------|------|------|
| B1 | 应支持按项目过滤 | 未实现 | 补实现（需求仍成立） |
| B2 | 应发送邮件通知 | 已废弃 | 删规格（改用 webhook，忘记更新文档） |

## 无法判定的部分（必须显式列出）
- `billing/` 模块的舍入规则：代码用 `round()`（银行家舍入），
  但业务上是否要求四舍五入无法确认。**需要找业务方确认，暂不写进 spec。**
```

**最后那个「无法判定的部分」小节千万别省。** 存量改造里最危险的不是判错，而是**假装判定了**。把不确定的东西显式挂起来，比给它一个假答案安全得多。

## 5. 按变更热点渐进，不要全量 ⭐

**这是本节最重要的策略判断。**

### 反例：全量改造

```
目标：给整个仓库的 80 个模块补规格
进度：3 个月后完成 12 个
结果：团队放弃
```

这是 [AP-24](../reference/anti-patterns.md) 的标准剧本。

### 正确做法

**只给「接下来要动的模块」补规格。**

```markdown
# 变更热点排序

| 模块 | 近 6 个月提交数 | 本次是否补规格 |
|------|--------------|--------------|
| `report/` | 47 | ✅ 立即补 |
| `api/handlers/` | 31 | ✅ 立即补 |
| `billing/` | 12 | ⏳ 下次要改它时再补 |
| `legacy/import/` | 1 | ❌ **永不为它补规格** |
| `auth/` | 0（稳定 2 年） | ❌ 不为它补规格 |
```

**`legacy/import/` 和 `auth/` 这两行才是这段的重点。**

> **存量代码如果半年不动，它的规格优先级是零。**

为它花时间写规格，收益是零（因为没人依赖它的规格做决策），成本是真实的。**这不叫严谨，这叫浪费。**

### 判断顺序（已写成可直接运行的脚本）

`scripts/find-change-hotspots.sh` 把上面四步全做了。**在任意 git 仓库里跑一下就知道该给哪些模块补规格：**

```bash
$ bash scripts/find-change-hotspots.sh . 6 20
统计窗口：2026-03-22 起（6 个月）

=== Top 20 变更热点模块 ===
模块                                          提交数   占比
api/handlers/                                    31   18.6%
report/                                          27   16.2%
billing/                                         12    7.2%
legacy/import/                                    1    0.6%
...

=== 建议补规格范围（前 20%，共 6 个模块）===
  ✅ api/handlers/  (31 次提交)
  ✅ report/        (27 次提交)
  ...

=== 明确不补规格（长尾）===
  ❌ legacy/import/  (1 次提交) —— 优先级 0，等要改它时再补
```

**最后那一行就是本节的全部要点。** 脚本直接把它打印出来，避免你凭感觉决定给谁补规格。

## 6. 「写不出干净的规格」本身是个信号

验收标准里有一条：

> 如果你发现**没法给这个仓库写出干净的规格**，记录下原因。

**这往往才是真问题所在。**

常见原因和它们指向的真问题：

| 写不出规格的原因 | 真问题 |
|----------------|-------|
| 同一个函数在不同调用点行为不同 | **职责不清** —— 它其实该拆成两个函数 |
| 说不清这个模块的边界在哪 | **架构缺失** —— 没有分层，或者分层被打破了 |
| 每个字段都有一堆例外规则 | **领域模型错误** —— 你在用错误的抽象描述业务 |
| 「取决于配置」到处都是 | **配置爆炸** —— 应该拆成不同的组件，而不是加开关 |
| 问了三个人得到三个答案 | **知识孤岛** —— 关键决策只活在个人记忆里 |

**发现这些比写出一份「勉强能看」的规格有价值得多。** 因为一份勉强能看的规格会把问题掩盖起来，而你刚发现的这些问题才是真正该修的。

## 7. 交付物与验收

### 交付物

1. 存量仓库接入了 `.specify/`（含从代码里提炼的宪法）
2. `specs/` 下至少一个模块的逆向规格（含 `[code]` / `[test]` / `[assumption]` / `[suspicious]` 标注）
3. **偏差清单**（A 类 + B 类 + 无法判定部分）
4. `notes/L11-变更热点.md` —— 排序 + 补规格范围决策（含明确不补的模块）
5. `notes/L11-适配性判定.md` —— 这个仓库适不适合 SDD，理由

### 验收清单

**逆向规格化**

- [ ] 每条验收标准都有**依据标注**（`[code]` / `[test]` / `[assumption]` / `[suspicious]`）
- [ ] `[assumption]` 项**全部经你人工确认**过，没有直接采信
- [ ] `[suspicious]` 项**没有一条**被直接写进规范

**偏差清单 ⭐**

- [ ] A 类每一处都判定了「有意设计 / 过期遗留 / 技术债」
- [ ] B 类每一处都判定了「补实现 / 删规格」
- [ ] **没有任何一处停留在「待定」**（这是硬性要求）
- [ ] 有「无法判定」小节，且列出了原因和待确认对象

**策略**

- [ ] 做了变更热点排序，明确了**哪些模块这次不补规格**（必须有明确排除的）
- [ ] 能说出「半年不动的模块为什么优先级是零」

**判断力（最重要）**

- [ ] 你**没有把 bug 固化成规范**——偏差清单里能找出至少一处被你判为「这是 bug」的
- [ ] 你能说出接入过程中**最难写规格的是哪个模块**，以及它暴露了什么真问题
- [ ] 给出了「这个仓库适不适合 SDD」的明确判定与理由

### 自测题

1. 为什么存量仓库的宪法要「从代码里读出来」，而不是直接写「应该怎样」？
2. `[suspicious]` 标注为什么绝不能直接写进 spec？
3. 一个模块两年没动过，要不要给它补规格？为什么？

<details>
<summary>答案</summary>

1. 两个原因：① 你需要知道**现状**才能定义**迁移路径**——如果我写的宪法是「domain 层不许访问数据库」，而现状是到处都在访问，那我需要知道这个差距有多大；② 存量仓库里存在大量**只活在代码里、从未被记录的约定**，这些是真正的资产，读出来本身就是价值。**但读出≠采信**：现状要被记录，规范要按「应该怎样」写，两者必须分开。
2. 因为 `[suspicious]` 的定义就是「agent 看着可疑」——它**可能**是 bug，也可能是有意为之的边界处理（历史兼容、特定客户需求）。直接写进 spec 就等于把一个**未经验证的怀疑**变成了**必须遵守的规范**，从此再也改不掉。**这是 [AP-23](../reference/anti-patterns.md) 的标准剧本。**
3. **不要。优先级是零。** 规格的价值 ≈ 该意图被复用的次数 × 违背它的代价。一个没人改的模块，它的规格不会被任何决策依赖（复用次数≈0）。为它花 2 小时写规格，收益接近零而成本是真实的。**正确做法是：要改它的那一刻再补。** 把时间花在变更热点上——那里每一小时投入都能立刻兑现。

</details>

## 8. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **把 bug 固化成规范** | 现有实现的错误行为被写进了 spec | 判定问句：这是**有意设计**的吗？找不到依据就进偏差清单（[AP-23](../reference/anti-patterns.md)） |
| **想一次补齐全部** | 三个月还没补完，团队放弃 | **按变更热点渐进**，只补接下来要动的（[AP-24](../reference/anti-patterns.md)） |
| **给从不改动的模块补规格** | 花时间写了没人看的文档 | 半年不动的模块优先级是零 |
| **采信 `[assumption]`** | agent 的推断被当成需求 | 所有假设必须人工确认 |
| **偏向清单留「待定」** | 不确定的东西挂着不管 | 显式列出「无法判定」+ 原因 + 待确认对象。**假装判定比判错更危险** |
| **把「写不出干净规格」当失败** | 硬凑一份勉强能看的规格 | 它是个**信号**：指向职责不清、架构缺失、领域模型错误 |
| **宪法只写现状** | 宪法里全是「现在是怎么做的」 | 现状要被**记录**，规范按**应该怎样**写，两者分开 |
| **给一个自己都不敢改的模块补规格** | 补完也没法验证 | 换一个你了解且有权限动的模块 |

## 9. 本节术语

| 术语 | 含义 |
|------|------|
| brownfield | 存量项目：已有代码，需要在其上补规格 |
| 逆向规格化 | 从现有代码反推 feature 规格 |
| reverse specification | 同上 |
| 偏差清单 | 「代码有规格没写」与「规格有代码没做」的对照表 |
| 变更热点 | 被频繁修改的模块；**存量改造只补这里** |
| 依据标注 | `[code]` / `[test]` / `[assumption]` / `[suspicious]` |
| 技术债标记 | 行为正确但实现方式不符合规范的条目 |
| 无法判定项 | 显式挂着的不确定条目；比假答案安全 |
