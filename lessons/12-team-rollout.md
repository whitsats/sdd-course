## 1. 工具横评：Spec Kit 之外还有什么

你整门课都用 Spec Kit，因为它是**事实上的参考实现**。但选型要基于团队现实。

| 工具 | 强项 | 最适合 | 主要代价 |
|------|------|-------|---------|
| **GitHub Spec Kit** | 开源、模型无关、38 种 agent 集成、可完全替换流程本身 | **不想被厂商锁定**；团队已经在用混合 agent | 需要自己搭 CI 门禁；扩展生态质量参差 |
| **AWS Kiro** | Agentic IDE，自带 hooks 自动守则，AWS/Serverless 深度集成 | AWS 原生团队；想要开箱即用的护栏 | 与 AWS 生态耦合；IDE 绑定 |
| **Claude Code (`cc-sdd`)** | 终端优先，`/sdd:*` 命令族 | 独立开发者、CLI 工作流 | 终端体验对团队新人门槛略高 |
| **Cursor Plan Mode** | IDE 优先，内联 diff 审阅，MCP 接 Spec Kit | **把审阅体验放在第一位**的团队 | 依赖 Cursor 本身 |
| **OpenSpec** | 极轻，Markdown + YAML，框架无关 | 独立开发者、极简主义 | 缺强制力机制，容易停在 spec-first |
| **BMAD-METHOD** | 社区方法论，多角色扮演，宪法驱动 | 想要灵活框架、愿意自建流程 | 自建成本高；一致性依赖团队自律 |
| **Tessl** | 合规导向，审计轨迹，受监管行业模板 | 金融、医疗等**需要留痕合规**的场景 | 偏重流程，轻迭代速度 |
| **Google Antigravity** | Agent 自主性 + 规格约束的探索 | 愿意试前沿的团队 | 生态仍在早期 |

### 选型判断的三条要点

**① 关键分水岭是「你要不要自己搭强制力」。**

Kiro 和 Cursor 把一些护栏做进产品里；Spec Kit 给你模板和流程，**CI 门禁要你自己写**（就是 L09 那几十行 YAML）。

- 团队工程能力强、想要自由 → Spec Kit
- 团队想少写基础设施、接受一定绑定 → Kiro / Cursor Plan Mode

**② 别在同一团队里混用多种 SDD 工具。**

它们对「spec 长什么样」「阶段怎么命名」的假设不同。混用会导致交接时的语义错位——**规格作为交接契约的前提是格式统一**。

**③ 工具是最后一步，不是第一步。**

⚠️ **如果你还没走通 L09（spec-anchored 闭环），换任何工具都不会让你成功。** 工具解决的是便利性，不是纪律。**先把方法跑通，再优化工具。**

## 2. 多 agent 协作：规格作为交接契约

### 核心原则

> **交接时不要口头同步。交接工件。**

「我昨天改了权限那块，你注意一下」——这句话承载的信息量，**等于零**。而一份更新过的 `spec.md` + `plan.md` + 映射表，承载的是全部约束。

### 一个必须知道的技术事实 ⚠️

`.specify/feature.json` 记录的是**单个** feature 目录。这意味着：

> **一个 feature 只能有一个活跃上下文。**

所以多 agent 并行时：

| 做法 | 可行性 |
|------|-------|
| 按 **feature** 粒度切分（agent A 做 001，agent B 做 002） | ✅ 可行——各自有独立的 spec/plan/tasks |
| 按 **任务** 粒度切分（两个 agent 同做 001 的不同任务） | ⚠️ **危险**——共享同一份 spec/plan/tasks，会互相覆写 |
| 串行交接（A 完成后 B 接手同一 feature） | ✅ 可行——靠 `tasks.md` 的勾选状态交接 |

**按任务粒度并行是新人最容易踩的坑。** 两个人同时跑 `/speckit-implement` 在同一个 feature 上，`tasks.md` 会被覆盖——而且**没有任何警告**。

### 交接清单

跨 agent（或跨人）交接一个 feature 时，交付这四样：

```markdown
- [ ] spec.md 是最新的（对照代码再确认一次）
- [ ] tasks.md 的勾选状态反映了真实进度，且没有「未完成但已勾」的项
- [ ] 当前活跃的是正确的 feature（`.specify/feature.json` 已确认）
- [ ] 已知的偏差与未决项（「无法判定」的东西）显式列出，不是口头说
```

### 宪法也要定期对账

多个 agent 长期并行后，宪法可能出现「每个 agent 都以为别人知道」的空洞。**每个迭代做一次宪法 review**——任何一条已经不再被遵守的，要么恢复执行，要么正式删掉。

**留着一条名存实亡的宪法条款，比没有这条更糟**——它会让 agent 在矛盾中随机选择（[AP-4](../reference/anti-patterns.md)）。

## 3. 定制你自己的流程

Spec Kit 把流程本身做成了可修改的工件——这是它与其他工具最大的结构性差异。

| 概念 | 用途 | 你什么时候需要它 |
|------|------|---------------|
| **presets** | 调整核心流程的配置 | 团队有固定偏好（比如统一用 pnpm + vitest） |
| **extensions** | 给流程增加能力 | 需要 CI Guard、Architecture Guard 这类治理扩展 |
| **workflows** | 编排多个步骤 | 一次跑完「specify → clarify → plan」而不是逐步确认 |
| **bundles** | 打包整套配置分享 | 多个项目/多个团队复用同一套流程 |

### 建议的定制顺序

```
1. 先什么都不定制，跑通 3 个真实 feature   ← 最重要
2. 只加最痛的那一个扩展（通常是 CI 门禁相关）
3. 把一个反复手打的步骤做成 workflow
4. 团队稳定后再打包成 bundle 给新项目用
```

⛔ **不要一开始就定制。** 你还不理解流程的哪些部分是必需的、哪些是可抛弃的，此时的定制就是凭想象删掉护栏。

> 顺带说一句：Spec Kit 的流程**可以被完全替换**（社区里有 AIDE、Canon、Product Forge 等完全不同的流程，甚至有用来写小说的）。这说明它不只是「SDD 工具」，而是一个**流程载体**。理解这一点，你以后就不会被任何一个具体工具绑住。

## 4. 评审流程：谁在什么时候看什么

SDD 的评审不是「多看几份文档」，而是**在三个时机看三样不同的东西**。

| 检查点 | 谁审 | 看什么 | 不通过就怎样 |
|--------|------|-------|------------|
| **spec 之后** | 产品 / 需求方 | ① what 和 why 对吗 ② 每条验收标准可验收吗 ③ 非目标写清了吗 | 回 clarify，**不要进 plan** |
| **plan 之后** | 技术负责人 | ① 每项决策能指回 spec 吗 ② 有范围蔓延吗 ③ 代价清楚吗 | 回 plan 改，**不要进 tasks** |
| **tasks 之后** | 执行者本人 | ① 粒度合理吗 ② 依赖顺序对吗 ③ 测试和实现同级吗 | 手工重排 |
| **PR** | 评审人 + CI | ① CI 绿吗 ② 改行为时 spec 同步改了吗 | 拒 |

### 三个「不要」

- ⛔ **不要在 spec 阶段讨论技术方案。** 那会锁死思路（[AP-5](../reference/anti-patterns.md)）
- ⛔ **不要在 plan 阶段讨论需求是否合理。** 那应该回 spec
- ⛔ **不要跳过任何一个检查点。** 每一个阶段边界都是一次纠偏机会，放弃一次就是让未来的自己承担成本

### PR 模板（直接抄）

```markdown
## 本次变更
- [ ] 是否改变了对外行为？
  - 是 → 对应 spec.md 的哪条验收标准？（必填）
  - 否 → 说明为什么不需要改 spec

## 自查
- [ ] 映射表已同步（新验收标准都有对应测试）
- [ ] 改行为时测试先变红过
- [ ] 没有手工编辑生成产物（如涉及）
```

**第二段的三行是这套流程能不能活下去的关键。** 靠自觉的流程会在两个月内死掉；写进 PR 模板的流程会活下来。

## 5. 度量：测什么，以及千万不要测什么

### 该测的四个指标

| 指标 | 定义 | 为什么测它 |
|------|------|-----------|
| **规格覆盖率** | 映射表行数 ÷ 验收标准条数 | 唯一能机械测的、直接反映「规格是否可执行」的指标。目标 100% |
| **漂移率** | CI 红灯中「契约测试失败」的占比 | 反映了**未察觉的偏离**有多少。持续为 0 反而可疑——说明门禁可能失效了 |
| **返工率** | 每 10 个任务中因「理解错了」而重做的数量 | 直接反映 clarify/checklist 的质量 |
| **规格变更周期** | 改一条验收标准 → 合入的时间 | 反映流程的**摩擦系数**。太长说明门禁过度或映射表维护成本太高 |

### ⛔ 千万不要测的指标

| 反指标 | 为什么有害 |
|-------|-----------|
| **规格字数 / 文档页数** | 会激励写废话。宪法 1 页上限就是因为这个（[AP-3](../reference/anti-patterns.md)） |
| **spec 文件数量** | 会激励为不值得写规格的东西写规格（[AP-1](../reference/anti-patterns.md)） |
| **人均 SDD 步骤完成数** | 纯流程形式主义。走的步数多不代表产出好 |
| **AI 代码占比** | 与质量无关。100% 生成也可能是垃圾 |

> **判断一个指标好不好，问一句：为了让它变好看，最省事的作弊方式是什么？**
> 如果答案是「多写文档」「多走流程」，这个指标就不要用。

### 第一个月看什么

**只看两个：规格覆盖率和返工率。**

- 覆盖率揭示「映射表有没有跟上」
- 返工率揭示「clarify 有没有真的消灭歧义」

漂移率和变更周期在第二个月再看——第一个月数据太少，噪声大于信号。

## 6. 团队落地检查清单

### 第一周

```markdown
- [ ] 选一个**真实但不大**的 feature 试跑（不要选最难的，也不要选造出来的假任务）
- [ ] 只一个人主导，其他人围观 —— 先建立手感，不要立刻全员上
- [ ] 跑通最短路径：constitution → specify → plan → tasks → implement
- [ ] 结束时做一次复盘：哪一步最别扭？为什么？
```

**⛔ 第一周不要上 CI 门禁。** 先把流程跑通，否则你会把「流程不熟」和「门禁太严」两个问题混在一起，最后怪到方法论头上。

### 第一个月

```markdown
- [ ] 第二、三个 feature 用完整路径（含 clarify / checklist / analyze）
- [ ] 补上 CI 门禁：先只上「契约测试」，再上「映射表覆盖率」
- [ ] 建立 PR 模板里的 spec 同步检查项
- [ ] 每两周做一次宪法对账
- [ ] 看两个指标：规格覆盖率、返工率
```

### 第三个月

```markdown
- [ ] 上漂移率与规格变更周期两个指标
- [ ] 做一次**红蓝对抗**（让一个人刻意制造漂移，验证门禁抓得住）
- [ ] 选一个存量模块做 brownfield 试点（L11 的方法）
- [ ] 定制流程：只加最痛的那一个扩展
- [ ] 复盘：这套流程在当前团队规模下，成本收益是正的吗？
```

### 常见信号与诊断

| 信号 | 可能的原因 | 先检查什么 |
|------|-----------|-----------|
| 大家觉得「流程太重」 | 门禁范围太广 | 是否在管内部重构、日志措辞 |
| spec 更新总是滞后 | 缺制度约束 | 宪法里有没有「行为变更必须同步 spec」；PR 模板有没有检查项 |
| 门禁红灯被无脑忽略 | 有随机红灯 | 把概率性失败改成只警告（[AP-18](../reference/anti-patterns.md)） |
| agent 开始不守规矩 | 宪法太长 | 是否超过 1 页（[AP-3](../reference/anti-patterns.md)） |
| 新人上手慢 | 缺交接清单 | 有没有把「已知偏差与未决项」写下来 |
| 澄清会开成了辩论会 | 决策权不清 | 明确谁对哪类决策拍板 |

## 7. 退出策略 ⭐ 大多数人不会主动想的事

**这是本节最重要的一节。**

任何流程一旦建立，就有了自我延续的惯性。**没人敢说「这个模块不该用 SDD」**——那听起来像是能力不足或者态度问题。

**这是错的。** 预设退出条件是成熟度的标志，不是失败。

### 该收手的五个信号

| 信号 | 具体表现 | 该怎么做 |
|------|---------|---------|
| **变更频率超出规格维护能力** | 同一个模块每周都要改行为，spec 永远滞后 | 该模块降级为 spec-first，或直接不上规格 |
| **探索性工作占比高** | 还在找方向，需求每周推翻 | spike 阶段不上规格。**探索用探索的方式** |
| **红灯被无脑忽略** | 大家开始「反正跑一下就好，不行就重试」 | 门禁已经失效——**立刻收窄范围，恢复红灯的可信度** |
| **「事后补 spec」成了常态** | 先改代码，spec 有空再补（然后永远没补） | 形式化已经发生。要么严格执行，要么承认不再做 spec-anchored |
| **成本账连续两个季度为负** | 额外投入 > 返工节省 + 变更可预测性 | 缩小适用范围，别扩大 |

### 关键认知：退出是**分模块**的，不是全有全无

```
报告模块        → spec-anchored ⭐（高频变更、有合规要求）
API 层          → spec-anchored ⭐（对外契约，必须稳定）
工具脚本        → 不上规格（一次性）
算法调优        → 不上规格（用 benchmark 当规格）
遗留导入模块    → 不上规格（半死不活，优先级零）
探索中的新功能  → 先 spike，方向定了再写规格
```

**这张图才是成熟团队的真实状态。** 「全公司上 SDD」这种说法，通常意味着没人认真想过边界。

### 预先把退出条件写下来

在你**还没投入**的时候写下这些条件，因为那时候你最客观：

```markdown
# 本项目的 SDD 退出条件

我们承诺在这个项目上使用 spec-anchored，直到：
1. 单月返工率连续两月高于 30%（说明规格质量没跟上）
2. 规格变更周期中位数超过 3 天（说明流程摩擦过大）
3. 核心模块月均行为变更超过 20 次（说明变化速度超出规格维护能力）

触发任一条时，我们**重新评估**范围，而不是默默忍受或直接放弃全流程。
```

> 📌 **「触发时重新评估范围，而不是放弃全流程」——这句是关键。**
> 大多数团队的 SDD 失败，不是因为它没用，而是因为一次挫败就全盘推翻。

## 8. 课程全景：你走过的路

```
阶段一 · 认知与地基
  L00 环境与空跑      → 建立「斜杠命令 = 流程步骤」的手感
  L01 心智模型        → 三级严谨度、vibe coding 的三种破产
  L02 宪法            → 1 页以内的可判定约束

阶段二 · 最短闭环（项目 A · focuslog · Python）
  L03 Specify         → EARS 句式，把意图写成可验收的语句
  L04 Plan & Tasks    → 可追溯性检查，抓范围蔓延，人工重排任务
  L05 Implement       → 验收纪律；亲手证明「规格无强制力」

阶段三 · 规格锚定 ⭐（项目 B · taskflow · TypeScript）
  L06 Clarify         → 六类歧义区，不许说「你看着办」
  L07 契约规格        → 三种牙齿 + 验收标准↔测试映射表
  L08 Analyze         → 故意留矛盾验证工具；多 feature 工作流
  L09 Converge ⭐     → CI 门禁、红蓝对抗、规格变更、成本账

阶段四 · 进阶与自主化
  L10 Spec-as-Source  → 生成器、幂等再生、**边界感**
  L11 存量改造        → 逆向规格化、偏差归类、按变更热点渐进
  L12 团队化          → 选型、评审、度量、**退出策略**
```

### 如果只记三件事

1. **分界线是强制力，不是文档详细度。**
   spec-first 和 spec-anchored 的区别只有一条：有没有机器检查。**L09 那几十行 YAML 就是分界线。**

2. **规格的价值 ≈ 该意图被复用的次数 × 违背它的代价。**
   所以「不值得写规格」是常态。能主动判断什么时候不写，比会写规格更重要。

3. **审阅要能抓自己的同类错误。**
   这门课的学习计划本身就被审阅并修掉了四个结构性缺陷——其中一个是我刚批评完「技术规模冒充教学价值」，转头就自己犯了。**规划也要被审阅，不能只审代码。**

### 诚实的话

SDD **不会**让 AI 自动写完你的后端。它做的是：

> **把工程判断从「写代码」前移到「定意图」。**

如果你的需求本身是模糊的、矛盾的、或者你根本不知道要什么——**SDD 不会救你，它只会更早、更便宜地暴露这件事。**

而这恰恰是它的价值。

## 9. 交付物与验收

### 交付物

1. `notes/L12-工具选型.md` —— 对比表 + 针对你团队的选型建议与理由
2. `notes/L12-团队流程.md` —— 你的定制流程（含 PR 模板）
3. `notes/L12-度量方案.md` —— 选哪几个指标、为什么、**以及明确不测哪些**
4. **`notes/L12-退出条件.md`** —— 预先写下的退出条件
5. 团队落地检查清单（已按你团队规模调整）

### 验收清单

- [ ] 选型表能给出「**什么团队该选什么**」的具体建议，不止罗列功能
- [ ] 你能说出「工具是最后一步」的理由
- [ ] 度量方案里**明确列出了三到四个「不测的反指标」**
- [ ] 落地检查清单分了**第一周 / 第一个月 / 第三个月**三段
- [ ] 第一周**没有**上 CI 门禁
- [ ] **退出条件已经写好**，且明确「触发时重新评估范围，而不是放弃全流程」
- [ ] 能说出**至少两个**「在我们团队，这个模块不该用 SDD」的具体模块

### 最后一次自测

1. 为什么工具选型应该放在最后，而不是第一步？
2. 一个团队说「我们全公司都上了 SDD」。这句话的问题在哪？
3. 为什么「漂移率持续为 0」反而可疑？

<details markdown="1">
<summary>答案</summary>

1. 因为工具解决的是**便利性**，纪律解决的是**有效性**。如果你还没走通 spec-anchored 闭环（L09），换工具只会让你更快地、更舒适地失败。**先把方法跑通，再优化工具**——而且此时你才知道自己真正需要什么。
2. 因为 SDD 的适用性**是分模块的**。变更频率、合规要求、变更模式各不相同，用一个统一的严谨度覆盖全部模块，必然在某些模块上过度投入（工具脚本写 200 行规格）、在另一些模块上投入不足（高频变更的核心模块规格滞后）。**「全都上了」通常意味着没人认真想过边界。**
3. 因为漂移是**必然发生**的——需求会变、人会疏忽，总有某次改动让契约测试失败。持续为 0 更可能意味着：**门禁根本没在跑**、**被设成了只警告**、或者**契约测试不覆盖真正会变的路径**。它不是好消息，而是「你的检测机制可能失效了」的信号。

</details>

## 10. 课程术语总表

| 术语 | 含义 |
|------|------|
| 规格覆盖率 | 映射表行数 ÷ 验收标准条数；目标 100% |
| 漂移率 | CI 红灯中契约测试失败的占比 |
| 返工率 | 每 10 个任务中因理解错误而重做的数量 |
| 规格变更周期 | 改一条验收标准到合入的时间；反映流程摩擦 |
| 反指标 | 会激励形式主义、不该测的指标 |
| 交接契约 | 用工件（spec/plan/tasks/映射表）而非口头同步来交接 |
| 退出条件 | 预先写下的、触发即重新评估适用范围的条件 |
| 范围重新评估 | 触发退出条件时的正确动作；区别于「全盘推翻」 |
