# L03 · Specify：把意图写成规格

> **时长** 120 min ｜ **前置** [L02](./02-constitution.md) ｜ **产出** `focuslog` 的 `spec.md`

阶段二开始。前两节你都在看别人生成的产物，这节开始**你亲手写**。

这是整门课**最重要的单项技能**。原因很简单：如果 spec 阶段写歪了，后面 plan、tasks、code 再漂亮，也只是把一个误解实现了三遍。

## 0. 本节的目标产物

```

├── .specify/            流程状态

└── specs/001-focuslog-mvp/
    └── spec.md          ← 本节的唯一交付物
```

**只交付 `spec.md`。** 这节不碰 plan、不碰代码。

## 1. 项目初始化 + 宪法专业化

```bash
cd projects
specify init focuslog --integration <你的 agent> --script ps
cd focuslog
```

### 先做宪法

用 L02 的模板，针对 focuslog 专业化。**关键：把「时区可注入」这类约束提前定下来**，否则等到 L05 实现时你会为了测试去改一堆代码。

在 agent 聊天里调用：

```
/speckit-constitution focuslog 是一个本地优先的开发者专注日志 CLI。

约束：
- 运行时 Python 3.10+，依赖管理用 uv
- 第三方依赖仅允许 Typer；其余用标准库
- 业务逻辑（domain/）不得直接读写文件；文件读写集中在单一 storage 模块
- 存储格式：用户家目录下的一个 JSON 文件，人类可读可手改
- 当前时间必须可通过参数或依赖注入提供，禁止在业务逻辑中直接调用系统时间
  （保证所有涉及时间的测试无需 mock 系统时钟）
- 所有公开命令必须返回明确的退出码：0 成功，1 参数错误，2 运行期错误
- 所有错误必须输出机器可读的错误码
- 任何改变输出格式或退出码语义的变更，必须同步更新 spec.md

非目标：
- 不做多用户、不做云同步、不做 GUI
```

注意最后那个 **`非目标`** 小节。宪法里写清「我们不做什么」，是在给下游所有阶段的**范围蔓延**设一道墙（对照 [AP-9](../reference/anti-patterns.md)）。

另外注意 `- 当前时间必须可通过参数或依赖注入提供` 这条——这是**可判定**的：只要有人在 domain 里写了 `datetime.now()`，code review 就能据此拒绝。

## 2. `/speckit-specify`：怎么写输入

### Bad 版（你可能会这么写）

```
/speckit-specify 用 Python 和 Typer 写一个专注计时 CLI，数据存 JSON 文件，
支持 start/stop/report/stats 四个子命令。
```

**问题在哪？**

1. 技术栈污染——`Python`、`Typer`、`JSON` 出现在 spec 生成输入里，它们会渗进 `spec.md`（[AP-5](../reference/anti-patterns.md)）
2. 只有命令名，没有**用户价值**——「report 命令」是形态，不是需求
3. 零个验收维度——它完全没说「什么样算做对了」

### Good 版

```
/speckit-specify 为需要提升专注力的开发者做一个本地专注日志工具。

用户价值：
我经常一天下来感觉自己很忙，但说不清时间花在哪了。我需要一种几乎无摩擦的方式
记录「我刚刚专注做了一件事」，并在一周结束时看到时间去向的分布——
按标签（如 reading / coding / writing）聚合。

核心场景：
1. 准备开始一段专注时，我用一行命令标记它开始，并打上一个标签
2. 结束时用一行命令收尾，工具告诉我这段持续了多久
3. 一周结束时，我能拿到一份 Markdown 周报，看到每天的时长和一些标签分布
4. 我想看看长期各标签的累计时长，判断自己的时间结构是否合理

约束与非目标：
- 完全本地，不联网、不要账号
- 单用户（只有我自己）
- 不做番茄钟式的强制提醒，不打断我
- 不做 GUI，只在终端里用
```

**对比一下什么变了：**

| | Bad 版 | Good 版 |
|---|---|---|
| 技术栈 | 有 | **无** |
| 用户价值 | 无 | 有（「说不清时间花在哪」） |
| 场景 | 命令名 | 4 个可演示的场景 |
| 非目标 | 无 | 显式 4 条 |
| 技术决策空间 | 已被锁死 | 留给 plan 阶段 |

最后一行才是关键：**Good 版没有锁死任何技术决策**，所以 plan 阶段才真正有得选。

## 3. 审阅生成的 `spec.md`

拿到 `spec.md` 后，**逐项过这张表**。这是本节的第一个硬技能。

### 三层检查

**第一层：污染检查（机械可做）**

```bash
# 在 spec.md 里搜技术词，命中即扣分
grep -inE "python|typer|json|sqlite|fastapi|node|react|docker|postgres" \
  specs/*/spec.md
```

命中数应该是 **0**。命中任何一条，就把它移到 plan 里去（现在 plan 还没生成，先记在笔记里）。

> ⚠️ 注意：`JSON` 这种情况要判断——如果它出现在「存储格式」这种语境，它其实是技术决策；如果出现在「用户可读可手改的文件」这种语境，那是需求。**判断标准是：它是不是在回答「怎么做」。**

**第二层：结构检查**

- [ ] 有 **3–5 个用户故事**？少于 3 个说明需求没展开，多于 5 个说明一个 story 里塞了太多
- [ ] 每个故事都是「**作为某角色，我想要某能力，以便某价值**」的完整形式？
- [ ] 有 **out of scope / 非目标**小节？
- [ ] 每个故事**能独立演示**？

**第三层：验收标准检查（最核心）**

对每条验收标准，念这句话：

> **「什么样的观察结果会证明这条要求被违背了？」**

说不出具体观察结果 → 重写。第 4 节专门干这件事。

## 4. 用 EARS 重写全部验收标准 ⭐

这是本节的核心产出。详细句式见 **[EARS 句式速查](../reference/ears.md)**，这里直接做 focuslog 的实例。

### 改写前（agent 典型产出）

```markdown
### 验收标准
- 用户可以开始一个新的专注会话
- 用户可以结束会话并看到时长
- 周报能正确导出
- 统计功能要准确
- 程序要能处理错误情况
```

**五条全废。** 「可以开始」——什么算可以？「正确导出」——正确的定义是什么？「要准确」——不可判定。「处理错误情况」——哪些错误？怎么处理？这是 [AP-6](../reference/anti-patterns.md) 的教科书案例。

### 改写后

```markdown
### 用户故事 1：开始一段专注

AS A 开发者 WHO 准备专注做一件事
I WANT TO 用一行命令标记开始并打上标签
SO THAT 我不用离开终端、不用打断思路就能留下记录

#### 验收标准

- WHEN 用户执行 `start --tag reading`
  WHILE 当前没有活跃会话
  THE system SHALL 创建一个新会话，记录开始时间与标签 `reading`，
  并以退出码 0 输出确认信息（含开始时间）。

- WHEN 用户执行 `start --tag reading`
  WHILE 已存在一个活跃会话
  THEN THE system SHALL 拒绝该命令，退出码为 2，
  输出错误码 `SESSION_ALREADY_ACTIVE`，且不修改任何已有数据。

- IF 用户执行 `start` 时未提供 `--tag`
  THEN THE system SHALL 拒绝该命令，退出码为 1，
  输出错误码 `TAG_REQUIRED`。

- IF 用户提供的标签包含空白字符或长度超过 32
  THEN THE system SHALL 拒绝该命令，退出码为 1，
  输出错误码 `TAG_INVALID`。

- WHERE 用户重复执行同一 `start --tag reading`（已有活跃会话）
  THE system SHALL 每次都以 `SESSION_ALREADY_ACTIVE` 拒绝，
  且会话开始时间保持不变（幂等）。
```

### 一次改写里发生了什么

看这份对照，你能总结出 EARS 改写的全部套路：

| 原来 | 改后 | 用了什么 |
|------|------|---------|
| 「可以开始会话」 | 拆成 1 条正常 + 4 条异常 | **拆解**：一条模糊需求里其实藏着 5 条 |
| 「用户可以结束会话」 | `WHEN 用户执行 stop` | **事件驱动**：找到明确的触发点 |
| —— | `WHILE 当前没有活跃会话` | **补状态前提**：原需求没说这个场景只在无活跃会话时成立 |
| 「处理错误情况」 | 4 条 `IF … THEN …`，每条带退出码和错误码 | **异常穷举**：参见 [EARS ⑤ 的清单](../reference/ears.md) |
| —— | 「重复执行…开始时间保持不变（幂等）」 | **补幂等性**：这是最常被漏掉、上线后最痛的一类 |
| 「时长要准确」 | 见下面用户故事 2 | **给判据**：把形容词换成可计算的规则 |

**最重要的一行是那条幂等性要求。** 它不在原始需求里，是你**问出来的**——问「如果用户手抖按了两次会怎样？」。整个 L03 想让你形成的能力就是这个：**主动追问那些没人会主动说出口的边界**。

### 用户故事 2：结束一段专注

```markdown
#### 验收标准

- WHEN 用户执行 `stop`
  WHILE 存在活跃会话
  THE system SHALL 记录结束时间，并输出该会话时长（以分钟为单位，
  向下取整），退出码 0。

- WHEN 用户执行 `stop`
  WHILE 不存在活跃会话
  THEN THE system SHALL 拒绝该命令，退出码 2，
  输出错误码 `NO_ACTIVE_SESSION`。

- WHEN 用户执行 `stop` 两次
  THE system SHALL 第一次成功并结束会话，第二次以 `NO_ACTIVE_SESSION` 拒绝，
  且第一次的结束时间不被第二次操作修改。

- IF 一个会话的时长计算结果小于 1 分钟
  THEN THE system SHALL 将其记为 1 分钟，并输出提示说明已取整。

- IF 一个会话的开始时间与结束时间位于不同的本地日期
  THEN THE system SHALL 将整个会话时长计入**开始时间所在的日期**，
  并在输出中提示该会话跨越了日期边界。
```

注意最后一条——**这是「跨天怎么算」这个歧义被显式固化的地方。** 你可以选择别的规则（比如按比例拆分），但**必须选一个并写下来**。留着「以后再想」就是在给未来的自己埋雷。

### 用户故事 3：周报

```markdown
#### 验收标准

- WHEN 用户执行 `report --week`
  THE system SHALL 输出 Markdown 周报，覆盖**当前 ISO 周的周一至周日**
  （ISO 8601 定义，周一为一周第一天）。

- THE system SHALL 在周报中包含：每天的会话总时长、每天的会话条数、
  按标签聚合的时长分布。

- IF 当前 ISO 周内没有任何会话
  THEN THE system SHALL 输出"本周没有记录"，退出码 0（**不是错误**）。

- WHEN 用户执行 `report --week --json`
  THE system SHALL 输出机器可读格式，字段名与上文所列内容一一对应。
```

「本周没有记录」用退出码 0 而不是错误码——**这个选择必须被写下。** 否则实现者很可能让它报错，而你在脚本里 `focuslog report --week` 就会意外失败。

### 用户故事 4：累计统计

```markdown
#### 验收标准

- WHEN 用户执行 `stats`
  THE system SHALL 按标签输出累计时长，按时长从多到少排序。

- IF 存在时长相同的标签
  THEN THE system SHALL 按标签名字典序升序排列（保证输出稳定可测）。

- IF 系统中不存在任何会话
  THEN THE system SHALL 输出"暂无记录"，退出码 0。
```

「时长相同时按字典序」——**排序稳定性是测试能不能写的前提**。没有这条，你的测试会随机失败，然后你会开始怀疑测试框架。

## 5. 用 agent 反向审查你的规格

写完之后，**让 agent 来挑你的毛病**：

```
读 specs/001-focuslog-mvp/spec.md，逐条检查验收标准。
对每一条回答：能否写出一个一定会失败的测试？
把所有"无法被测试"或"存在多种合理解释"的条目列出来，不要修改文件，只报告。
```

这是整门课会反复用的技巧：**用同一个工具反向验证自己输入的质量**。

它会挑出来的东西，往往是你自己看不见的模糊处。把它挑出来的每一条都改掉——**这就是你的 `spec.md` 从「能读」变成「能被实现」的过程。**

## 6. 交付物与验收

### 交付物

1. `projects/focuslog/specs/001-*/spec.md`
2. `notes/L03-spec审阅记录.md` —— 记录你做了哪些修改、为什么

### 验收清单

**结构**

- [ ] 4 个用户故事，每个都是完整的「作为/我想要/以便」形式
- [ ] 每个故事都能**独立演示**
- [ ] 有明确的非目标（out of scope）小节

**污染**

- [ ] spec.md 中搜不到任何技术栈词汇（框架、库、数据库、云服务）
- [ ] 所有被你删掉的技术内容都记在了笔记里，等着放进 plan

**验收标准质量**

- [ ] 每条验收标准读一遍「什么样的观察结果会证明它被违背了」，都能立刻答出来
- [ ] 六个 EARS 句式里，**至少用到四种**
- [ ] `WHEN`（事件）和 `WHILE`（状态）**没有混用**
- [ ] 每条异常路径都带**退出码 + 错误码**
- [ ] 存在至少一条**幂等性**要求
- [ ] 存在至少一条**跨边界**规则（跨天/跨周/跨月）
- [ ] 存在至少一条**排序/输出稳定性**要求
- [ ] 所有「准确」「正常」「良好」这类形容词**数量为零**

**反向验证**

- [ ] 跑过 agent 的反向审查，它挑出的问题**全部处理完毕**

### 自测题

1. 为什么 `IF 当前 ISO 周内没有任何会话 THEN … 退出码 0` 要用 0 而不是错误码？
2. 「用户执行 `stop` 两次」这条，如果规格里不写，实现会怎么处理？后果是什么？
3. 你的 spec 里有没有一条要求，是 agent 生成的版本里没有、你主动加上去的？它是问什么问题问出来的？

<details>
<summary>答案提示</summary>

1. 因为「本周没有记录」是**合法的业务结果**，不是错误。如果返回非零退出码，用户在 shell 脚本里写 `focuslog report --week` 就会意外中断。**退出码语义是规格的一部分，必须显式定义。**
2. 大概率会静默成功并覆盖结束时间，或者抛异常。后果是：用户的时长数据被无声损坏，且没有任何迹象。这类问题上线后才被发现，且很难复现。
3. 这题没有标准答案——**关键是你要能说出这个「追问」是什么**。如果一条都答不出来，说明你还不习惯主动穷举边界；回去对照 [EARS ⑤ 的异常清单](../reference/ears.md) 再过一遍。

</details>

## 7. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **spec 里写技术栈** | spec.md 出现框架名/库名 | 全搜一遍，命中就移到 plan（[AP-5](../reference/anti-patterns.md)） |
| **形容词残留** | 「准确」「正常」「友好」「高效」 | 换成数字或布尔判据；换成不掉的删掉 |
| **只写 happy path** | 全篇都是 `WHEN … SHALL …` | 对照 [EARS ⑤ 清单](../reference/ears.md) 补 `IF … THEN …` |
| **`WHEN`/`WHILE` 混用** | 「当会话进行中…」写成 `WHEN` | 持续条件一律 `WHILE`；这会直接改变测试写法 |
| **一条里塞两个 SHALL** | 「记录时长并输出提示并更新统计」 | 拆成独立条目，否则测试无法精确定位失败点 |
| **留着「以后再想」** | 某些边界条件没写规则 | **必须选一个并写下来。** 未定义的边界 = 未定义的实现 |
| **自己改完就交差** | 没跑反向审查 | 用第 5 节的方法让 agent 挑毛病，它看得见你看不见的 |
| **把 spec 当一次性文档** | 写完再也不看 | spec 是活的（L09 会强制这件事）；现在就该习惯 |

## 8. 本节术语

| 术语 | 含义 |
|------|------|
| user story | 用户故事：作为/我想要/以便三件套 |
| acceptance criteria | 验收标准：判定需求是否满足的判据 |
| EARS | 需求句式语法，见 [速查手册](../reference/ears.md) |
| out of scope | 非目标：显式声明不做什么，防范围蔓延 |
| 反向规格审查 | 让 agent 审你的规格，找出「无法被测试」的条目 |
| 幂等性 | 同一操作重复执行，结果与执行一次相同 |

## 9. 下一节预告

你现在有一份**每条都能被测试**的规格。下一步是把它变成技术方案：

`/speckit-plan` 会把你在笔记里攒下的那些技术决策（Python / Typer / JSON 存储 / 时区注入）收进来，生成架构与数据模型；`/speckit-tasks` 再把它拆成有依赖顺序的原子任务。

**L04 的重点不是学会打这两个命令**，而是学会在 plan review 时做一件事：**逐条追问「这个决策服务哪条验收标准？」** 追不上的，就是范围蔓延（[AP-9](../reference/anti-patterns.md)）。
