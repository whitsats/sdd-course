# L10 · Spec-as-Source：当人只改规格

> **时长** 120 min（实操通常 5 h）｜ **前置** [L09](./09-converge-drift.md) ｜ **产出** `rulesmith` 生成器 + 一次「只改 spec」的完整变更

前三个阶段都在回答一个问题：**怎么让规格驱动代码？**

这一节问一个更激进的：

> **能不能让人完全不写代码？只改规格，代码全量再生？**

听起来是终极形态。但本节真正的考核目标不是「你成功用了它」，而是：

> **你有了边界感。**

> 📁 **本节的完整参考产出**（全部可运行、已实测）：

## 1. 重申：三级严谨度

| 等级 | 人改什么 | 代码状态 |
|------|---------|---------|
| Spec-First | 规格 → 生成种子 → 然后随便改 | 允许漂移 |
| Spec-Anchored | 规格 + 代码一起改 | 测试强制对齐 |
| **Spec-as-Source** | **只改规格** | **100% 生成，永不手改** |

spec-as-source **从设计上消除漂移**——因为根本没有手写代码可以偏离。

**代价是：你需要一套成熟可信的生成工具链。** 而这套工具链本身要有人维护、要测试、要有 owner。

---

## 2. 先确认适用条件：为什么选报表规则 DSL

spec-as-source **只适用于高度结构化、模式重复的领域**。我们选报表规则引擎，正是因为它满足全部四个条件：

| 条件 | rulesmith 的满足情况 |
|------|-------------------|
| 语法是有限的 | 规则 DSL 的语法可以写成 EBNF，几十条产生式封顶 |
| 错误情形可以穷举 | 未知字段、类型不匹配、循环引用、优先级冲突 |
| 产物形态固定 | 解析器 + 校验器 + 文档，三件套永不变 |
| 变更模式重复 | 「加一个字段」「加一个运算符」都是同类改动 |

**反过来说，下面这些领域不适合**（记住，这是本节的考点）：

- **UI 与视觉细节** —— 「看起来对不对」无法形式化
- **算法调优** —— 目标是性能数字，路径靠实验找
- **探索性需求** —— 你自己都不知道要什么，写出来的规格是假精确
- **业务规则极度易变且无序** —— 生成器跟不上变化速度，维护成本反而更高

## 3. 写 DSL 的规格

新建项目：

```bash
cd projects
specify init rulesmith --integration <你的 agent> --script ps
cd rulesmith
```

规格要写四件事：**语法、语义、错误情形、产物定义**。

### ① 语法（用 EBNF，这是唯一能精确表达语法的形式）

```ebnf
(* ── 语法层：全小写名字 → 进语法分析器的产生式表 ── *)
program       = { rule } ;
rule          = "rule" IDENT "{" "when" condition "then" action "}" ;
condition     = or_expr ;
or_expr       = and_expr { "or" and_expr } ;
and_expr      = comparison { "and" comparison } ;
comparison    = field operator value | "(" or_expr ")" ;
field         = IDENT { "." IDENT } ;
operator      = ">" | ">=" | "<" | "<=" | "=" | "!=" | "in" | "notin" ;
value         = NUMBER | STRING | list ;
list          = "[" [ value { "," value } ] "]" ;
action        = "flag" STRING [ "escalate" "to" STRING ] ;

(* ── 词法层：全大写名字 → 扫描器的 token 类型，**不进**产生式表 ── *)
(*    语法里引用 IDENT = 此处放一枚 kind 为 "ident" 的 token *)
IDENT         = letter { letter | digit | "_" } ;
NUMBER        = digit { digit } [ "." digit { digit } ] ;
STRING        = '"' { any_char } '"' ;
```

### ⚠️ 上面这段里的「分层」，是拿一个真实 bug 换来的

`IDENT` / `NUMBER` / `STRING` 描述的是**扫描器怎么切出一个 token**，不是语法规则。
如果生成器把 `IDENT` 也当成语法产生式发射，它会引用字符类 `letter` —— 而 `letter` 不是产生式。

**后果是：生成器成功退出、产物看起来正常、CI 全绿，而生成的 parser 在运行期抛
`未定义的产生式: letter`。**（完整故事见 §6.5 故障 ①）

所以本项目在规格里把三件事**显式写下来**：

| 约定 | 内容 | 为什么必须写 |
|------|------|------------|
| ① | 全大写名字的产生式属于词法层，不进语法产生式表 | 不写，生成器无从知道分层；`letter` 这种引用会被当成语法错误或静默炸 |
| ② | 预定义字符类清单：`letter` `digit` `any_char` `ws` | 不写，`letter` 就是凭空的魔法名字 |
| ③ | token 类型的名字必须能被扫描器实现（名字小写即种类） | 不写，spec 可以要求一个扫描器没实现的种类，然后产物在运行期炸 |

> 📌 **这三条约定本身就是「规格必须完整」的体现。**
>
> 第一版规格里没写它们 —— 不是因为不重要，而是因为**我自己心里知道**。
> 而 spec-as-source 的规格是给**机器**读的：**你心里知道的东西，生成器不知道。**
>
> **判据：凡是「我默认如此」的东西，要么写进规格，要么送进生成器的默认值 ——
> 不能留在心里。**

### ② 语义（EARS 在这里同样适用）

```markdown
## 语义

- THE system SHALL 将 `field` 解析为输入记录的字段路径，`a.b` 表示嵌套访问。
- WHEN `field` 引用的路径不存在于输入 schema 中
  THE system SHALL 在校验期（而非运行期）报告 `UNKNOWN_FIELD` 错误。
- IF `operator` 为 `in` 而其右值是标量（非数组）
  THEN THE system SHALL 报告 `TYPE_MISMATCH`。
- IF 规则存在优先级冲突（两条 `escalate` 目标不同且条件可能同时成立）
  THEN THE system SHALL 报告 `PRIORITY_CONFLICT` 并指出冲突的两条规则。
- THE system SHALL 保证校验器不产生假阴性：**任何校验通过的规则，
  在运行期都不会因语法或类型原因出错。**
```

**最后那条不变量是本项目的核心规格。** 它把「校验器要可靠」这个模糊要求变成了一个可测试的强命题。

### ③ 错误情形（穷举，这是生成的校验器的输入）

```markdown
| 错误码 | 触发条件 | 报告位置 |
|--------|---------|---------|
| `PARSE_ERROR` | 不符合语法 | 行号 + 列号 |
| `UNKNOWN_FIELD` | 字段路径不在输入 schema | 规则名 + 字段路径 |
| `TYPE_MISMATCH` | 运算符与值类型不匹配 | 规则名 + 运算符 |
| `PRIORITY_CONFLICT` | 两条 escalate 规则可能同时命中 | 两个规则名 |
| `UNKNOWN_OPERATOR` | 运算符不在允许集合内 | 行号 |
```

**注意错误码表用的是表格，不是列表。** 这不是审美问题：

> 生成器要读它。**表格有列名，列名是契约；措辞不是。**
>
> 所以可以随意改「不符合语法」为「不符合 §2 定义的语法」（生成器不受影响），
> 但把列名 `触发条件` 改成 `条件` 就会**构建期报错**。
> 这条边界被一条测试固定住了：`generator.spec.ts::spec 读取器`。

### ④ 产物定义

```markdown
## 生成产物（⛔ 禁止手改）

| 产物 | 内容 |
|------|------|
| `src/generated/lexer.ts`      | 词法分析器：关键字表 + 符号表 + TOKEN_KINDS + 扫描器 |
| `src/generated/parser.ts`     | 语法分析器：产生式表 + 表驱动回溯 |
| `src/generated/validator.ts`  | 语义校验器：上表全部错误码 + 运算符分类 |
| `docs/rules-dsl.md`           | 面向业务方的 DSL 文档（含从 §2 注入的示例） |
```

**以下四条是硬约束（缺一条，整个模式就失效）：**

1. 以上四个文件由 `pnpm generate` 产出，**任何人不得手工编辑**
2. 每个产物头部带 `DO NOT EDIT` 标记，并注明应改 `spec.md` 后重新生成
3. CI 重新生成并校验 `git diff` 为空；非空即失败
4. 生成器必须**幂等**：同一份 spec 连续生成两次，输出**字节级相同**

> 📌 **第 4 条看起来像「代码质量要求」，实际不是 —— 它是本模式的生存条件。**
>
> 没有幂等性，CI 的 `git diff` 校验会**随机**变红。
> 而随机的红灯会让团队学会无视红灯（见 `reference/anti-patterns.md` AP-18），
> 最后把它注释掉 —— **然后手工编辑产物就开始悄悄积累，而没有人会知道。**
>
> 在别的模式里，一个偶尔输出顺序不同的生成器只是不够优雅；
> **在这里，它会让整个强制层失效。**

## 4. 关键：让 agent 写**生成器**，不是成品

这是本节最容易做错的地方。

```
/speckit-plan 实现方式：

本项目采用规格即源。我们**不**直接编写 lexer/parser/validator 的成品代码，
而是在 `tools/generator/` 下编写一个生成器，由它读取 spec.md 中的语法
（EBNF 部分）与错误码表，产出 `src/generated/` 下的四个文件。

生成器本身是手写代码，需要：
- 自己的单元测试（含幂等性测试：连续运行两次，输出字节一致）
- 自己的 owner（本项目就是你）
- 在 CI 中被调用以校验生成物可复现
```

### ⛔ 如果你直接让 agent 写 parser

它会给你一个**完美的、手写的 parser**——然后 spec-as-source 就名存实亡了。因为你下次改语法时，还是得手改那个 parser。

**你必须反复确认它写的是生成器。** 判断方法很简单：

> **改一处 spec，重新生成，产物变了吗？**

- 变了 → 你得到的是生成器 ✅
- 没变 → 你得到了一个手写产物 ❌

## 5. 幂等再生：spec-as-source 的生命线

```yaml
# .github/workflows/sdd-gate.yml
- name: Regenerate and verify reproducibility
  run: |
    pnpm generate
    if ! git diff --quiet; then
      echo "::error::生成物与 spec 不一致，或有人手改了生成产物"
      git diff --stat
      exit 1
    fi
```

**这个检查做三件事：**

1. 阻止手改生成产物（改了就会被覆盖，且 diff 非空 → 红）
2. 保证生成是**幂等**的（同样输入 → 同样输出；否则随机 diff）
3. 阻止「改了 spec 但忘了重新生成」

### 文件头加警告标记

生成器产出的每个文件开头都要有：

```typescript
// ⚠️ 此文件由 tools/generator 生成，请勿手动编辑。
// 修改行为请改 specs/001-rulesmith-dsl/spec.md，然后运行 pnpm generate。
```

**别省这两行。** 它会在某人打开文件准备手改时拦住他——这比 CI 报错友好得多（CI 报错时他已经改完了）。

## 6. 完整的「只改 spec」演示 ⭐ 本节核心交付物

**这是你要录下来的东西。** 全程不许碰 `src/generated/` 下的任何文件。

> 📁 **真实运行记录（含完整终端输出与逐文件 diff 行数）**：
> `examples/rulesmith/notes/L10-只改spec演示.md`
>
> **下面是它的实测摘要，数字都是真的跑出来的，不是示意。**

### 变更内容：给 `operator` 产生式加一个 `matches`

改动**只有一行**：

```diff
- operator = ">" | ">=" | "<" | "<=" | "=" | "!=" | "in" | "notin" ;
+ operator = ">" | ">=" | "<" | "<=" | "=" | "!=" | "in" | "notin" | "matches" ;
```

### 实测输出

```bash
$ node tools/generator/index.ts
规格: specs/001-rulesmith-dsl/spec.md
产生式: 11   词法 token 类型: 3   关键字: 11   符号: 14   错误码: 8
起始产生式: program

  ✎ 已更新  src/generated/lexer.ts  (145 行)
  ✎ 已更新  src/generated/parser.ts  (416 行)
  · 未变  src/generated/validator.ts  (74 行)
  ✎ 已更新  docs/rules-dsl.md  (99 行)
```

### 逐文件的实际差异

| 产物 | 变化 | 差异行数 |
|------|------|---------|
| `lexer.ts` | ✎ 已更新 | **1**（关键字表多一项） |
| `parser.ts` | ✎ 已更新 | **4**（`PRODUCTIONS.operator` 多一个分支） |
| `validator.ts` | **· 未变** | **0** |
| `docs/rules-dsl.md` | ✎ 已更新 | **6** |

lexer 的真实 diff：

```diff
   "in",
+  "matches",
   "notin",
```

### ⭐ 为什么 `validator.ts` **正确地没有变**

它里面有两张从 `operator` 推导出来的表：

```ts
export const NUMERIC_OPERATORS = ["<", "<=", ">", ">="] as const;
export const LIST_OPERATORS    = ["in", "notin"] as const;
```

`matches` 既不是数值运算符（不匹配 `/^[<>]=?$/`），也不是列表运算符 —— 所以它**同时落在两张表之外**。

**如果生成器是「机械地把新运算符塞进每一张表」，这里就会出错**：
`matches` 会被误当作数值运算符，然后校验器会对 `field matches "regex"` 报出
错误的 `TYPE_MISMATCH`（说右侧必须是数字）。

> 📌 **这一条比「产物跟着变了」更重要。**
>
> 好生成器的判据**不是「凡输入变则输出全变」**，而是
> **「只改真正受影响的部分，并且不改不该改的部分」**。
>
> 前者容易（无条件重算一遍就行），后者需要**把推导关系写清楚**：
> 「哪些产生式决定哪些表」必须在生成器里显式表达，而不是靠遍历。

### 反向验证：A→B→A 必须字节级还原

```bash
# 把 spec 改回去，重新生成，再与演示前的快照逐字节对比
diff -q /tmp/rs_before/lexer.ts     src/generated/lexer.ts      # ✓ 一致
diff -q /tmp/rs_before/parser.ts    src/generated/parser.ts     # ✓ 一致
diff -q /tmp/rs_before/validator.ts src/generated/validator.ts  # ✓ 一致
diff -q /tmp/rs_before/rules-dsl.md docs/rules-dsl.md           # ✓ 一致
```

**四个文件全部字节级还原 —— 这叫双向幂等，它比单向幂等强得多。**

| 性质 | 只测「跑两次相同」 | 测「A→B→A 回到 A」 |
|------|------------------|-------------------|
| 能证明什么 | 可能只是缓存或偶然 | 证明生成是**纯函数**，无隐藏状态 |

**为什么它重要**：不满足双向幂等时，**回滚一次规格变更会留下一堆「看起来无关」的差异**。
团队会以为是上次改动的残留，于是不敢回滚 —— **规格就不敢改了**。
而规格一旦不敢改，spec-as-source 的前提（规格是活的）就没了。

### 耗时对照

| 步骤 | 生成路线 | 手写路线 |
|------|---------|---------|
| 改 spec | 20 秒 | 1 分钟 |
| 改产物 | `pnpm generate`（< 1 秒） | 改 4 个文件，约 7 分钟 |
| **判断哪些产物要改** | **不需要（自动）** | **5 分钟，而且最容易漏** |
| 检查 diff | 1 分钟 | 2 分钟 |
| **合计** | **约 2 分钟** | **约 15 分钟** |

> 📌 **注意最贵的一项是「判断哪些产物要改」。** 它贵在**它是判断，不是操作** —— 而判断会出错。
> 生成器把这一步从「每次都要重新判断」变成了「一次性判断，之后自动」。
> **这才是生成器真正省掉的东西：不是打字时间，是重复判断。**

## 6.5 四个真实故障 ⭐ 这一节比演示本身更值钱

> **下面四个都是实现本项目时真实发生的，不是举例。**
> 它们的共同点是：**都只有在真的「改一笔、跑一遍」时才会暴露。**
> 光读代码、光读规格，一个都发现不了。

### 故障 ①：生成器成功退出，但产物在**运行期**炸

**故障现象**

```
Error: 未定义的产生式: letter
    at match (parser.ts:415:23)
    at parse  (parser.ts:468:13)
```

**根因**：EBNF 里混了**两个层级** ——
`IDENT` 是**词法层**（描述扫描器怎么切 token），它的右部引用了字符类 `letter`。
但 `letter` 不是产生式。生成器把 `IDENT` 也当语法产生式发射了。

**危险的形状（重点看这个，不是看修法）**

| 环节 | 当时的实际表现 |
|------|--------------|
| 生成器运行 | ✅ **成功退出** |
| 生成的产物文件 | ✅ **看起来完全正常** |
| 在 CI 里的表现 | ✅ **全绿**（只要没人调 `parse()`） |
| 第一次真实调用 | 💥 **炸** |

> 📌 **这才是 spec-as-source 最危险的失效模式：
> 生成器不报错，但产出会在运行期炸。**
>
> 它比「生成器报错」危险得多 —— 后者当场就发现了。
> 而一份「看起来正常」的产物可能过了 code review、过了 CI、部署到生产，
> 直到某个代码路径第一次被走到。

**修法：把引用校验加进生成器，让它变成构建期错误**

```typescript
// 现在这么写会构建期报错，而不是发射一份运行期才炸的代码
for (const p of parserProductions) {
  for (const r of refsOf(p.rhs)) {
    if (parserNames.has(r) || tokenNames.has(r)) continue;
    if (charClasses.has(r)) {
      throw new Error(
        `语法层产生式 \`${p.name}\` 引用了字符类 \`${r}\`。\n` +
        `  字符类只能出现在词法层（全大写）产生式里。`,
      );
    }
    throw new Error(`未定义的终结符：${r}\n  已定义：${[...parserNames].join(', ')}`);
  }
}
```

**这个修法的可迁移之处**：不是在生成器里「小心一点」，而是**把校验变成生成器的一部分**。
生成器的职责不只是发射，还包括**验证自己的输入**。

**完整记录**：`examples/rulesmith/notes/L10-只改spec演示.md` 末尾。

### 故障 ②：使用文档教了一个语法不接受的写法

**故障现象**

生成的 `docs/rules-dsl.md` 里给的示例是：

```
rule high_value {
  when amount > 10000 and ...
}
```

**而当时 `rule` 产生式里根本没有 `when`。**

**为什么会这样**：示例是在发射器里**硬编码**的字符串 ——
它和 EBNF 是两份互不相干的东西，于是可以静默脱节。

**修法（两层，缺一层都不行）**

| 层 | 做法 |
|----|------|
| **消除脱节的可能** | 示例从 spec 的 ```rulesmith 块**注入**，不再硬编码 |
| **抓住已经发生的脱节** | 加测试：**规格自带的例子必须能跑通自己生成的解析器** |

**元验证（反向证明门禁真的会红）**：把 `"when"` 从 EBNF 里删掉 → **11 个测试失败**。

> 📌 **注意：生成器本身抓不住这个错**（它只保证语法自洽），抓住它的是**测试**。
>
> 「把示例当契约来测」这个动作，是**人生出来的**，不是工具生出来的。
> 工具的职责边界：**生成器保证「产物由规格而来」，测试保证「规格里的示例确实过得了」。**
> 两者谁都不覆盖对方。

---

### 故障 ③：规格写成 checkbox，门禁**看不见**它

**故障现象**

rulesmith 的规格里，验收标准是这么写的：

```markdown
- [ ] 连续两次生成，输出字节级相同
- [ ] 校验器「无假阴性」不变量有属性测试覆盖
```

覆盖率门禁跑出来的结果是：

```
::error::001-rulesmith-dsl 尚未规划：找不到对应它的验收标准-测试映射.md
```

**根因**：门禁的计数逻辑只认 `| 编号 |` 形式的表行。
**它不知道 checkbox 也是验收标准。**

**修法：改规格，不改门禁。**

```markdown
| # | 成功标准 | 验证方式 |
|---|---------|---------|
| 9.3 | 同一份 spec 连续生成两次，输出字节级相同（幂等） | `tests/generator.spec.ts::幂等性与确定性` |
| 9.10 | 校验器「无假阴性」不变量有属性测试覆盖 | `tests/validator.spec.ts::核心不变量` |
```

> 📌 **为什么必须改规格而不是放宽门禁：**
>
> 门禁的判定规则（「可被计数的标准」）是**跨项目一致**的；
> checkbox 只是个别的书写习惯。
> 为了让门禁变绿而放宽门禁，等于**把三级成熟度往回退** —— 见 `reference/anti-patterns.md` AP-18。
>
> **这件事揭示了 spec-as-source 的一个隐含要求：
> 规格的结构（而不只是内容）必须足够规整，门禁才能拿它做判断。
> 规格是要被机器读的 —— 它得先能被机器读到，才能被机器强制。**

---

### 故障 ④：门禁在「没有代码的项目」上误报

**故障现象**

```
::error::找不到 examples/focuslog/src/focuslog/domain
```

分层边界检查在 focuslog 上失败了 —— 但 focuslog 是**项目 A 的规格示例，本来就没有实现代码**。

**根因**：脚本把两种情况当成了同一种：

| 情况 | 应该怎么做 |
|------|-----------|
| ① 项目**还没有代码**（只有 spec，spec-first 阶段的正常状态） | **跳过**，不是失败 |
| ② 项目**有 src，但层目录没按约定命名** | **真错误，必须报** |

**修法的关键在判据**：判据必须是「`$ROOT/src` 是否存在」，
而不是「层目录是否存在」—— 后者会把情况 ① 误判为情况 ②。

```bash
require_layers() {
  local domain="$1"
  if [ ! -d "$ROOT/src" ]; then
    echo "· 跳过：$ROOT 下没有 src/ 目录（该项目目前只有规格，尚未实现）"
    echo "  分层边界检查的对象是实现，不是规格 —— 实现出现后本检查自动生效。"
    exit 0
  fi
  if [ ! -d "$domain" ]; then
    echo "::error::找不到 $domain（但 $ROOT/src 存在 → 目录结构不符合约定的分层）"
    exit 2
  fi
}
```

> 📌 **修误报与「放宽门禁」的区别，就在这一节里。**
>
> - **修误报**：改的是**判据的精度**（从「层目录在不在」改成「src 在不在」），
>   检查的能力**没有下降** —— 情况 ② 照样会被抓住。
> - **放宽门禁**：如把失败改成 `|| true`、加 `continue-on-error`，
>   检查的能力**直接归零**。
>
> 两者表面上都是「让 CI 变绿」，但一个保留了能力，一个放弃了能力。
> **每次处理红灯时，先问自己：我在提高判据的精度，还是在降低检查的能力？**

---

### 这一节的结论：这些东西**只有跑起来才能发现**

| 故障 | 读代码能发现吗 | 读规格能发现吗 | 跑一遍能发现吗 |
|------|--------------|--------------|--------------|
| ① 运行期才炸 | ❌ 产物看起来正常 | ❌ 规格自洽 | ✅ 一跑就现形 |
| ② 文档教错语法 | ❌ | ⚠️ 对照着读能发现，但要非常仔细 | ✅ 测试立刻红 |
| ③ checkbox 不被计数 | ❌ | ⚠️ 要理解门禁的计数规则 | ✅ 门禁直接报错 |
| ④ 无代码项目误报 | ❌ | ❌ | ✅ 一跑就报 |

**四个里有三个，答案都是「只有跑起来才知道」。**

> **这正是本课程反复强调实证的原因：规格和代码都是「静态的文本」，
> 而 bug 住在「它们一起跑起来的时候」。**

## 7. 边界感 ⭐ 这才是本节的真正考点

做完演示，回答下面三个问题，写进 `notes/L10-边界感.md`：

### ① 本项目哪些部分**不适合**规格即源？

诚实回答。参考方向：

- **生成器本身**（`tools/generator/`）—— 它是手写的，且永远不会由规格生成。**这是规格即源的递归边界：总得有一层是人写的。**
- **运行期引擎**（把 AST 应用到一个具体记录上）—— 「怎么执行一个条件」是通用逻辑，与语法无关，不必生成
- **测试** —— 测试需要人的判断（该测什么、断言什么），不该由规格机械生成
- **错误消息的措辞** —— 「字段 `user.age` 不存在」vs「未知字段：user.age」，这是产品决策，不是规格能穷举的

### ② 什么时候该**放弃**规格即源？

- 变更频率超过生成器的维护能力时
- 需要人做审美/产品判断的部分变多时
- 产物形态开始分化（不再固定是三件套）时

### ③ 一个诚实的问题

> **本项目里，生成器和手写产物，哪个维护成本更高？**

如果你写生成器花了 4 小时，而手写四个产物只需要 2 小时——**那这次的投入是不划算的**。

**这不代表你做错了。** 它代表你理解了一件重要的事：

> **规格即源的本质是「用一次性的生成器，换长期的变更成本」。**
> 只有当**变更次数足够多**时，这笔投资才回本。

**记录下你的盈亏平衡点估算**：这个生成器要支撑多少次语法变更才回本？

2. `tools/generator/`（含自身单元测试 + 幂等性测试）
3. `src/generated/` 四个产物
4. CI 可复现性检查生效

6. **`notes/L10-边界感.md`** —— 第 7 节三个问题的回答

### 验收清单

**核心 ⭐**

- [ ] 仓库里**没有任何手工编辑的生成产物**（CI 校验 `git diff` 为空）
- [ ] 完成一次「只改 spec、全量再生、行为生效」的完整演示
- [ ] **你能说出本项目不适合规格即源的部分，以及原因**（没做这条等于本节没上）
- [ ] 你**确认了 agent 写的是生成器而非成品**（用「改 spec 看产物变不变」验证过）

**工程**

- [ ] 生成器有自己的单元测试
- [ ] 生成器有幂等性测试（连续两次生成，输出字节一致）
- [ ] 生成物文件头有 `DO NOT EDIT` 标记
- [ ] 校验器的「无假阴性」不变量有测试覆盖

**判断力**

- [ ] 估算了生成器的盈亏平衡点（要支撑多少次变更才回本）
- [ ] 能说出「规格即源的递归边界」是什么（总有一层是人写的）

### 自测题

1. 为什么「生成器本身」不能被规格生成？这说明规格即源的什么性质？
2. 如果幂等性检查缺失，会发生什么？
3. 你写生成器花了 4 小时、手写产物只要 2 小时。这次投入是错的吗？

<details>
<summary>答案</summary>

1. 因为它会导致**无限递归**——生成器的生成器又需要生成器。所以任何规格即源系统都存在一个**人写的基底**。这说明：**规格即源不是「消灭手写代码」，而是「把人的手写工作集中推到极少数、且变更频率最低的那一层」。** 这个认知是关键——它告诉你该在哪里投入人的精力。
2. **生成产物会变得不可复现。** 同样的 spec 在不同时间生成出不同的文件（比如生成器遍历 Map 的顺序不稳定、或嵌入了时间戳），于是 CI 的 `git diff` 检查永远非空，门禁随机变红。然后团队就会把它关掉——**这正是门禁失效最典型的死法**。
3. **不算错，但必须知道它什么时候回本。** 规格即源换的是**长期变更成本**，不是单次成本。如果这个 DSL 之后要变 10 次语法，生成器就是巨大收益；如果只有这一次，那手写更划算。**判断标准不是「这次花了多少」，而是「后续会变多少次」。** 这也是为什么探索性、一次性需求不该上规格即源。

</details>

## 9. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **让 agent 写成品而非生成器** | 得到一个漂亮的手写 parser，改 spec 时产物不变 | 用「改 spec 看产物变不变」验证（[AP-20](../reference/anti-patterns.md)） |
| **生成器没人维护** | 改一个模板，几十个产物全崩 | 生成器是**一等公民代码**：要有测试、owner、CI（[AP-21](../reference/anti-patterns.md)） |
| **手改了生成产物** | 下次生成时改动被覆盖 | CI 校验 `git diff` 为空 + 文件头 `DO NOT EDIT`（[AP-22](../reference/anti-patterns.md)） |
| **缺少幂等性测试** | 生成物不稳定，门禁随机红 | 加「连续两次生成字节一致」的测试 |
| **把 spec-as-source 当终极目标** | 套到 UI、算法调优、探索性需求上 | 回到第 2 节的四个适用条件（[AP-20](../reference/anti-patterns.md)） |
| **不做边界感分析** | 觉得「一切都能生成」 | 第 7 节三问是本节考点。说不出边界的，就是没理解 |
| **不算回本点** | 在只变一次的项目上投入生成器 | 判断标准是「后续会变多少次」，不是「这次花多少」 |

## 10. 本节术语

| 术语 | 含义 |
|------|------|
| spec-as-source | 人只改规格，代码全量生成、永不手改 |
| 生成器 | 读规格产出代码的程序；**它本身是手写的** |
| 幂等再生 | 同规格重复生成得到字节级相同的产物 |
| 生成产物 | 由生成器产出、禁止手改的文件 |
| 递归边界 | 规格即源系统中始终存在的人写基底 |
| 盈亏平衡点 | 生成器需要支撑多少次变更才回本 |
| EBNF | 扩展巴科斯范式；精确表达语法的唯一实用形式 |
| 无假阴性不变量 | 「校验通过的规则运行期必不出错」这类强命题 |
