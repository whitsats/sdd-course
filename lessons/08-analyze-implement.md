# L08 · Analyze 与分批实现

> **时长** 120 min ｜ **前置** [L07](./07-architecture-contracts.md) ｜ **产出** analyze 零冲突报告 + 分阶段 PR + 两个 feature 的上下文切换

> 📁 **本节的完整参考产出**：
> - `examples/taskflow/notes/L08-feature切换.md` —— 多 feature 切换的**真实操作记录**，含验证步骤、状态文件内容、以及一个防坑 shell 函数
> - `examples/taskflow/specs/002-task-tags/` —— 第二个 feature（在 L06 里被列为非目标的「标签」）
>
> 切换那篇里有一节值得先看：**「最容易出事的环节」** —— 它描述了一个不会报错、但会让你白做一整天的问题，
> 以及一个防它的 shell 函数。

你有三份文档和一堆测试骨架了。现在的风险是：**它们之间自相矛盾。**

而且按经验，**三者不一致是常态，不是例外**——spec 里写的状态集合、plan 里画的状态机、tasks 里拆的任务，很可能来自三次不同的生成，互相没对过账。

---

## 1. `/speckit-analyze`：只读的便宜检查

```
/speckit-analyze
```

它检查 `spec.md` ↔ `plan.md` ↔ `tasks.md`，报告**冲突、缺口、歧义**。

**关键性质：它是只读的。** 它不会替你改任何东西——发现问题的**修复动作必须回到源头**。

这一点很重要，因为最常见的错误处理方式是「在 analyze 报告上打补丁」（比如为了让 analyze 闭嘴而手改 tasks），那就失去了检查的意义。

---

## 2. 故意留一处矛盾 ⭐ 先验证工具

**规则：任何检测机制，必须先被证明能检测到东西。** 这是 L07 元验证测试的习惯，现在放大到流程层面。

### 步骤

**① 制造矛盾。** 编辑 `plan.md`，在数据模型里**悄悄**加上一个 spec 里不存在的状态：

```markdown
## 任务状态机

todo → doing → in_review → done
                  ↑         |
                  └─────────┘  (驳回)

新增：archived 状态 —— done 的任务 30 天后自动归档
```

**注意这个矛盾设计得很真实**：
- 它「很合理」（归档是常见需求）
- 它**只出现在 plan 里**，spec 里完全没有
- 它会连带影响 tasks（谁负责自动归档？定时任务？）和代码（状态枚举多一个值）

**② 跑 `/speckit-analyze`。**

**③ 看它能不能抓出来。**

**④ 记录下来。** 三种可能的结果，每种都有不同的处置：

| 结果 | 说明 | 你该做什么 |
|------|------|-----------|
| ✅ 准确指出 spec 与 plan 的状态集合不一致 | 工具有效 | 继续 |
| ⚠️ 抓到了，但描述含糊（「可能存在不一致」） | 工具有效但提示不够精确 | 说明你的 spec 里的状态集合表达得不够显式。回去把状态列成一个明确的枚举清单 |
| ❌ 完全没抓到 | **工具的检查维度不覆盖这个** | 这是重要发现：说明你不能只依赖 analyze。记录下来，这就是为什么还需要 L09 的 CI 门禁 |

**三种结果都有价值。** 第三种尤其重要——**知道工具的盲区在哪，比相信它全能更重要。**

### ⑤ 修复，并重跑

**在源头修**：删掉 plan 里的 `archived`，**或者**显式把它补进 `spec.md` 并承认范围扩大了。

然后**重跑 analyze 到 clean**。不是「大概没问题了」，是报告里确实没有冲突项。

## 3. 分批实现：人类检查点是唯一有效的纠偏点

```
/speckit-implement
```

**分三个批次，每批停下来人工验收：**

| 批次 | 内容 | 停下来验什么 |
|------|------|------------|
| **批 1** | 迁移 + repository + domain 纯规则 | 状态机单测通过？权限判定纯函数可测？ |
| **批 2** | routes + services（含 zod 校验、错误码） | 契约测试的权限矩阵 14 格全过？ |
| **批 3** | 并发控制 + cursor 分页 + 审计日志 | 并发测试通过？分页边界（size=1000）正确？ |

### 为什么必须分批

> **一次性跑完 = 错误在无人区累积。阶段边界是人类唯一有效的纠偏点。**

出了问题时，分批让你能定位**是哪一层错了**：

- 批 1 就有问题 → 领域规则理解错了，回去改 spec
- 批 1 好、批 2 出问题 → plan 的分层设计有问题
- 批 1、2 好、批 3 出问题 → 任务拆解漏了并发/分页的依赖

**一次性跑完，这三种情况会长得一模一样：一堆红测试。**

### 验收标准里有一条：至少一个阶段因人工验收而**调整了任务顺序或拆解方式**

这一条是防你走过场的。**真实情况一定会有调整**——比如你可能发现「审计日志」不该在批 3，因为批 1 的 repository 层就需要它来记录写入结果，晚做要回头改。

**如果你三个批次全部按原计划顺顺当当跑完、什么都没调，那说明你在照抄。**

## 4. 多 feature 工作流 ⭐ 本课程此前一直缺的一课

### 为什么现在讲

前面 8 节课，你一直在做**单个 feature** 从零走到收敛。这不是真实工作。

真实工作是：**功能上线两周后要加东西，而第一个 feature 的规格还躺在那儿。**

### 先理解机制

Spec Kit 靠 **`.specify/feature.json`** 记录「当前活跃的是哪个 feature」。所有命令都从这个状态文件解析上下文，**不依赖 git 分支**。

你可以在 L00 读过这个文件，但它一直没影响过你——因为有且只有一个 feature。

现在演练它。

### 练习：给 taskflow 开第二个 feature

任务是**「任务标签」**：给任务打标签，按标签过滤列表。

**① 开新 feature**

先看清当前状态：

```bash
cat .specify/feature.json
```

然后启动第二个 feature 的规格（具体调用形式以你本地 `--help` 为准；Spec Kit 会创建新的编号目录，例如 `002-task-tags`）：

```
/speckit-specify 给任务增加标签能力：一个任务可以有多个标签（最多 5 个），
标签名长度 1–32，同一项目内标签名唯一。列表接口支持按标签过滤，
支持多标签「与」语义。
```

**② 检查：新 feature 的 spec 是不是干净的**

```bash
ls specs/
# 001-taskflow-mvp/    002-task-tags/
```

**③ 关键环节：切换上下文**

现在你的 `.specify/feature.json` 指向 `002-task-tags`。请验证两件事：

```bash
# 切回第一个 feature，跑一次 analyze
# 更新 .specify/feature.json 指向 001-taskflow-mvp（或设 SPECIFY_FEATURE_DIRECTORY）
# 再跑 /speckit-analyze
```

- [ ] 切回去后，analyze 检查的是 **001 的** spec/plan/tasks
- [ ] 001 的文档**没有被 002 的操作污染**

### 三条纪律

| 纪律 | 说明 |
|------|------|
| **宪法可复用，规格不可** | 两个 feature 共用一份 `constitution.md`（它是跨 feature 的）；但 spec/plan/tasks 绝不共用 |
| **不要手动改 `feature.json` 之后就忘了** | 这是最常见的混淆来源：你以为在看 A，其实命令在处理 B |
| **不要靠 `git checkout` 切换 feature** | git 分支只是组织形式（可选扩展），**活跃 feature 由状态文件决定** |

> 📌 **第二条值得强调**：以后遇到「命令行为很怪」「产出对不上」的情况，**第一反应就是查 `.specify/feature.json`**。这跟你以后遇到诡异的包问题先查 `node_modules` 是同一个反射。

## 5. 交付物与验收

### 交付物

1. analyze 零冲突报告（贴进 `notes/L08-analyze.md`）
2. 矛盾演练记录：analyze 抓到了没有、精度如何
3. 分阶段实现的 PR（3 个批次）+ 每批的验收记录
4. `specs/002-task-tags/` 的 spec
5. `notes/L08-feature切换.md` 记录切换验证过程

### 验收清单

**analyze**

- [ ] 故意制造的矛盾**有明确的检测结论**（抓到 / 精度不足 / 没抓到，三种都算完成）
- [ ] 修复发生在**源头**（spec 或 plan），不是打补丁
- [ ] 重跑后报告 clean

**分批实现**

- [ ] 实现了**三个批次**，每批次后有独立验收记录
- [ ] **至少一个批次因验收而调整了任务顺序或拆解方式**（没发生就是走过场）
- [ ] 权限矩阵 14 格全过
- [ ] 并发冲突测试通过（先到者胜 + 返回当前状态）
- [ ] `size=1000` 被截断为 100 且返回 `next_cursor`

**多 feature**

- [ ] `specs/` 下有两个 feature 目录
- [ ] 能演示在两个 feature 间切换，且 analyze 检查的是正确的那一个
- [ ] 001 的文档没有被 002 污染
- [ ] 你知道「命令产出对不上」时第一件事该查什么

### 自测题

1. 为什么 `/speckit-analyze` 是只读的？如果它能自动修改，会有什么问题？
2. 如果 analyze 对「plan 里多了一个状态」完全没抓到，你该怎么调整自己的流程？
3. 为什么宪法可以跨 feature 复用，而 spec 不行？

<details markdown="1">
<summary>答案</summary>

1. 因为它**没有权限判断该改哪一层**。「plan 里多个状态」这个矛盾，可能是 plan 错了（删掉），也可能是 spec 漏了（补上并扩大范围）。这是**业务决策**，只能由人做。自动修改会让它随机选一个方向，而你会失去发现「自己需求漏了」的机会。**只读是它的设计前提，不是功能缺失。**
2. 说明**不能只依赖 analyze**。你要补上第二道检测：把 spec 里的状态集合写成显式的枚举清单（让不一致变得机械可比），并在 L09 的 CI 门禁里加一条 schema 与 spec 的一致性检查。**知道工具盲区在哪，比相信它全能更重要。**
3. 因为宪法说的是「无论建什么都必须遵守的规矩」（跨 feature 的长期约束），而 spec 说的是「这个 feature 是什么」（只在它自己的范围内成立）。复用 spec 会导致第二个 feature 的验收标准里混进第一个的行为——**而且是静默的**，你只会在实现时发现任务对不上。

</details>

## 6. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **analyze 报冲突却「先实现再说」** | 想着后面再修 | 在源头改，重跑至 clean（[AP-15](../reference/anti-patterns.md)） |
| **在 analyze 报告上打补丁** | 手改 tasks 让报告闭嘴 | 修复必须回到 spec/plan 源头 |
| **跳过矛盾演练** | 觉得「没必要验证工具」 | 你会在真实矛盾出现时才第一次检验它——那时代价最高 |
| **一次性 implement 全部** | 出问题时无法定位层级 | 分三批，每批验收（[AP-16](../reference/anti-patterns.md)） |
| **批次全按原计划跑完** | 没有任何调整 | 走过场了。真实实现一定会发现拆解需要调整 |
| **复用第一个 feature 的 spec** | 第二个 feature 的验收标准混进旧行为 | 宪法可复用，**spec 不可** |
| **靠 git 分支切 feature** | `git checkout` 后命令行为没变 | 活跃 feature 由 `.specify/feature.json` 决定 |
| **改了 feature.json 忘了** | 以为在处理 A，其实在改 B | 行为异常时第一件事查这个文件 |

## 7. 本节术语

| 术语 | 含义 |
|------|------|
| cross-artifact analysis | 跨文档一致性检查（spec ↔ plan ↔ tasks） |
| 只读检查 | 只报告不修改；修复必须回到源头 |
| human checkpoint | 人类强制验收的节点；分批实现的批次边界 |
| 增量实现 | 分批推进，每批独立验收，不一次性跑完 |
| 多 feature 上下文 | 靠 `.specify/feature.json` 或 `SPECIFY_FEATURE_DIRECTORY` 切换 |
| 工具盲区 | 检测机制覆盖不到的地方；必须知道它存在 |
| 污染 | 第二个 feature 的产出意外混入第一个的文档 |

## 8. 下一节预告 ⭐

**L09 是整门课的价值拐点。**

到这里你拥有的一切——规格、映射表、契约测试、分批实现——都还是**靠你主动执行**的。而 L05 的漂移演练已经证明：**没人会天天主动对照。**

L09 要做的，是让那件「靠自觉」的事变成「**靠机器**」：

1. 用 `/speckit-converge` 循环到收敛——**以及判断不收敛时该回哪一层**
2. 上 CI 门禁——**让漂移变红灯，而不是事后发现**
3. 红蓝对抗——用 L05 那份漂移记录，验证门禁真的抓得住
4. **规格变更流程**——真实工作里最高频的场景：改一个已有功能
5. 算一笔成本账

走完 L09，你会拿到这门课真正的目标：**spec-anchored 闭环。**
