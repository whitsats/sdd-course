## 1. 这一节在整门课里的位置：第四根轴

到这里，约束光谱已经有四段：

```
编译期(L13) → 测试期(L07) → 合并前(L09) → 数据层(L14) → ？？？
```

前四段管的全是「**写出来之前**」：代码还没上线，就有东西拦它。
但生产系统里规格照样失效——而且失效方式更隐蔽，因为**没有红灯了**：
没有 CI 在跑，没有构建在断，只有用户在默默承受一个「跑得好好的但不对」的系统。

本节补上最后一段：**运行期**。前三根轴问「多早 / 多晚 / 考卷给谁」，
这节问：**上线三个月后，谁还在替规格站岗？**

> 一句话：前面所有课保证「交付的瞬间是对的」；本节回答「交付之后它还是对的吗，
> 以及**谁先知道它不对了**」。

---

## 2. 生产里规格失效的三种方式

**① 行为静默偏离 —— 没有报错，只是不对。**
5xx 会触发告警，400 会被日志记下；但「跨天会话在周报里凭空消失」这类 bug
（L06 挖出的真缺口）**不产生任何错误信号**——系统认为一切正常。
谁先发现？用户。这失败了两次：体验坏了，而且是用户替你做的回归测试。

**② 多份真相源分叉 —— 各自都对，合起来不对。**
订单服务用 Python 实现「预占超时 30 分钟」，库存服务用 Go 实现同一句话。
各自的单测全绿、各自的 CI 全绿——但一个按接收时间算，一个按支付时间算。
规格只写了一份，实现有两份，**没有人对比过它们对同一句话的理解**。

**③ 「没做」被悄悄做了 —— 非目标长出了实现。**
spec 白纸黑字写着「标签功能是非目标（见 002）」。半年后代码里已经有了
标签查询接口——没人改规格，也没人记得是谁加的。**规格约束的是要做的；
没约束的，默认靠什么拦？** 之前几节课没有答案。

三种失效对应三个工具：**生产探针**、**契约交叉验证**、**flag 对账**。

---

## 3. 工具一：生产探针（把验收标准翻译成遥测查询）

[`patrol.sql`](../examples/stockflow/README.md) 的约定是本节的种子：
**每条查询都必须返回 0 行**——任何一行输出都意味着「有人在约束之外写了数据」。
它跑在数据库里；把同一个思路搬到生产遥测上（日志、指标、错误码率），
就是生产探针：

> **探针 = 一条对着生产遥测的查询 + 一条规格编号。查询非空 = 这条标准此刻不成立。**

数据源不用手抄——`check-error-codes.py --json` 的机器可读投影
（`code → 标准编号`）就是现成的桥梁：每个错误码天生连着它的标准。

### 哪些标准值得上探针（本节的真价值）

**不是每条标准都该上告警。** 告警噪声会杀死 on-call 的信任，比没有探针更糟
（和 AP-18 同构：红灯失去意义，绿灯也跟着失去意义）。三条判据，全部满足才上：

1. **违反后静默**——不产生 4xx/5xx、不抛异常、用户可感。错误码类标准不用探针：
   它们已有日志与现成告警，再架一层是重复。
2. **高频路径**——低频路径出问题，人工验收与工单追得上；高频路径的静默偏离
   才是「没人发现」的重灾区。
3. **能用现有遥测表达**——如果为了一条探针要先造一套新埋点，你是在**为检查
   改变系统**。先问遥测里有没有，没有就记进 backlog，不要顺手加。

**每条探针还必须回答：半夜响了谁起床、起床去干什么。** 答不出来，
它就不是探针，是许愿——和 L09 的「红灯必有意义」同一原则，生产版叫
「**呼叫必有意义**」。

---

## 4. 工具二：契约交叉验证（多份实现，一份规格）

「各自测各自的」拦不住 ② 号失效：两个实现的测试**都对**，
因为它们测的都是**自己对自己实现的理解**。缺的是第三样东西——
**同一个提问，分别打两份实现**。这就是消费方驱动契约（consumer-driven contract）
的内核：不是实现方自证「我符合规格」，而是**消费方出题**：「我要的是这个」。

不用上 Pact 这类框架也能先做纸面版，三步：

1. 找出同一份规格的**第二个消费方**（真实或假想：给 taskflow 的状态机
   加一个「周报服务」，它只关心「什么状态算已完结」）；
2. 让消费方写下它的**最小断言集**——不是整个 spec，只是它依赖的子集；
3. 把两份消费方的断言集放在一起：**交集 = 真正的公共契约**，
   它必须能逐条指回 spec 的标准编号（机器可读投影在这里再次派上用场）。

交集之外的部分最值得看：**只有一个消费方要、但两条实现都提供了的行为**，
是隐性耦合的温床——要么升格进 spec（走 change-request），要么明确标记为
实现细节、不许消费方依赖。

---

## 5. 工具三：flag 对账（让「没做」可见）

特性开关（feature flag）是规格的运行期开关：`pricing_v2_enabled = false`
的意思应该是「`00X-pricing-v2` 尚未启用」，而不是「这坨代码没人管」。
对账只做一件事：

> **把项目里所有「默认关」的行为列出来，每一个指回 spec 的一条标准或一行非目标。**
> 指不回来的 = 没有规格的行为 = 漂移已经发生，只是发生在暗处。

对账的副产品常常是删除：flag 关了半年、规格标了 draft 没人认领——
删掉它，规格标 deprecated。**「暂时不做」的正确归宿是非目标清单，
不是永远关着的 if。**

---

## 6. 动手（三步，全程可纸面）

1. **探针筛选**：从 focuslog 的 23 条标准里按 §3 判据筛出候选（实测你会发现
   大部分被筛掉——错误码类有日志、低频类不值得、纯 UI 输出遥测里没有），
   给留下的 2–3 条写出「查询 + 标准编号 + 呼叫应答」三件套。
2. **交叉验证**：给 taskflow 状态机做一次两消费方纸面推演，写出交集清单，
   每行标上它指回的标准编号；指不回的行标「实现细节」或走 change-request。
3. **flag 对账**：对自己手头任意一个真实项目做一次——这是本节唯一
   直接作用于你日常工作的练习，也是最容易被「我项目里没几个 flag」低估的
   一个（对账对象包括所有「默认关的 if」，不只是 flag 系统）。

---

## 7. 边界：什么时候整个本节都不用做

- **没有生产系统**（学习项目、一次性脚本）：探针无处安放，纸面推演的判据
   可以读一读，交付物不必强求。
- **单一实现、无第二消费方可言**：契约交叉验证退化成普通的契约测试（L07 已覆盖）。
- **团队没有 on-call**：「呼叫必有意义」没有对象，探针清单降级为周报巡检
   （stockflow 的 patrol 模式——定时跑，人看结果，不叫人）。

诚实地说：这是全课程**离「今天就能跑」最远、离「下个季度会不会后悔」最近**的一节。
它的产出是判据和清单，不是基础设施——基础设施等你真有生产系统再建，判据现在就该有。

| 问的问题 | 约束放多**早** | 约束放多**晚** | 考卷给**谁** | 上线后**谁站岗** |

## 交付物与验收

**交付物**：

- `notes/L16-探针清单.md` —— 筛选理由 + 三件套（查询 / 标准编号 / 呼叫应答）
- `notes/L16-交叉验证.md` —— 两消费方断言集 + 交集 + 逐行归属
- `notes/L16-flag对账.md` —— 每个默认关行为的标准指针（或删除记录）

**验收标准**：

- [ ] 每条探针都能指回 spec 编号，且通过了三条判据（写明每条的筛选理由）
- [ ] 每条探针回答了「半夜响了谁起床」——答不出的已降级为定时巡检
- [ ] 交集清单里没有「指不回标准、又标注为公共契约」的行
- [ ] flag 对账没有一行停留在「回头再看」（L11 的老规矩：不留在待定）
- [ ] 你能说出本节为什么没有可运行的新门禁（两个理由：方差与告警噪声）

## 踩坑预警

1. **探针绑实现细节**。「日志里出现『预占失败』就告警」——文案一改探针就哑。
   绑机器可读的东西：错误码（投影给好了）、指标名、状态分布。
2. **把探针当门禁**。探针红了不改 spec 也不修系统，只是「又响了」——
   三次之后它就被静音了。探针的出口必须接回 L09 的变更流程。
3. **flag 永不归档**。开关是「暂时的」，债务是永久的——对账日期写进台账的
   复审周期里（L12 的治理模板正好放得下这一列）。
4. **消费方契约写成对方的义务**。消费方断言的是「我要什么」，
   不是「你必须怎么实现」——越界的那部分写进 change-request 去，别塞进契约。
5. **只有一份消费方就宣称交叉验证**。一份断言集没有交集可言；
   做不出第二个消费方时，诚实的结论是「这一层暂时用不上」，而不是硬编一个。
