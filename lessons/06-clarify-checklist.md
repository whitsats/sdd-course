# L06 · Clarify & Checklist：把歧义清零

> **时长** 120 min ｜ **前置** [L05](./05-implement.md) ｜ **产出** 澄清后的 `spec.md` + 已评审的 checklist

阶段三开始。项目 A 让你走通了最短路径，但你也看到了它的天花板：**规格没有强制力**。

项目 B `taskflow` 的目标是把严谨度推到 spec-anchored。而在上任何强制手段之前，有一件更基础的事必须先做——**把歧义清零**。

因为：**在歧义上做规划，等于把钱花在错的图纸上。**

> 📁 **本节的完整参考产出**：`examples/taskflow/specs/001-taskflow-mvp/spec.md`
> 那是 clarify 之后的成品 —— **40 条验收标准**（不是 31，我手数错过一次，被覆盖率脚本抓了出来），六类歧义区全部有显式定义，每条 `IF … THEN …` 都对应一次追问。
> 对照它看你自己的产出，重点看两处：① 状态机是不是穷举的 ② 并发冲突那条写了几句话。

## 0. 为什么 clarify 是 SDD 最直接的收益来源

回想项目 A 里那条「跨天会话归属开始日」。如果你当时没写下来，实现会随手选一个（很可能选「算到结束日」），然后你要么接受一个错误行为，要么返工。

**这就是 clarify 要防的东西：不是你不会写规格，而是你不知道自己没说清楚。**

`/speckit-clarify` 的价值不在它生成的答案，而在**它问出了什么问题**。那些问题就是你的盲区地图。

### 先立宪（这次和项目 A 不同）

```
/speckit-constitution taskflow 是一个团队任务协作 API。

语言与运行时：
- TypeScript（strict 模式，禁止 any）、Node 20+、pnpm 管理依赖
- HTTP 框架 Fastify，输入校验用 zod，测试用 vitest，存储用 Postgres

架构边界：
- 路由层只做「解析请求 → 调 service → 序列化响应」，禁止直接访问数据库
- 所有领域规则（状态机、权限判定）集中在 domain 层，必须纯函数、可独立测试
- 数据库访问集中在 repository 层；domain 不得 import 任何 IO

测试与质量门禁（本项目的重点）：
- spec.md 中的每一条验收标准必须映射到至少一个自动化测试用例，
  映射关系记录在 plan.md 的「验收标准 ↔ 测试」表中
- 契约测试必须覆盖：合法流转、非法流转、权限拒绝、并发冲突、分页边界
- 测试必须能在无网络环境下运行

安全与隐私：
- 所有外部输入在进入领域逻辑前必须经过 zod 校验
- 日志中禁止出现用户标识符明文与完整 token

性能预算：
- 列表接口 P95 < 200ms（本地 Postgres，1000 条任务量级），单页返回 ≤ 100 条

可观测性：
- 每个响应错误必须携带机器可读错误码
- 审计日志字段固定为：actor / action / target / result / timestamp

文档与提交（spec-anchored 的制度基础）：
- 任何改变对外行为的变更（含错误码、状态流转、权限），
  必须同步更新 spec.md 中对应的验收标准
- 提交信息格式：<type>: <描述>
```

**对比一下项目 A 的宪法**：技术栈不同，但结构完全一样；差异在「测试与质量门禁」这一节——这里多了**映射表**和**契约测试覆盖面**的要求。

**这不是巧合，这是本阶段的全部内容。** 宪法的措辞直接决定了后面能不能落地强制力。

## 3. `/speckit-clarify`：六个必炸的歧义区

```
/speckit-clarify 聚焦以下区域：状态流转规则、评论权限、并发冲突、
鉴权边界、分页语义、审计日志字段。
```

### ① 状态流转规则

含糊版：「任务能在看板列之间移动」

必须澄清的：

- 有哪几列？`todo / doing / in_review / done` 四列吗？
- **哪些转移是合法的？** `todo → done` 允许吗（跳过中间步骤）？
- `done` 是终态吗？能重新打开吗？
- 谁能改状态？普通成员能直接标 done 吗？
- 状态变更要不要留痕？

**为什么致命**：`done` 是否终态，决定了你要不要写「重开」逻辑、审计日志要不要记两次、统计口径怎么算。**含糊一句，实现里差一百行。**

### ② 评论权限

含糊版：「任务下面能评论」+「要有权限控制」

必须澄清的：

- 成员能删**自己的**评论吗？
- 负责人能删**别人的**评论吗？能改吗？
- 被移出项目的成员，他之前的评论怎么办？保留？匿名为「已退出的成员」？
- 已删除任务下的评论，还能通过 API 访问吗？

### ③ 并发冲突 ⚠️ 最容易翻车

含糊版：什么都没有。**需求里完全没提**——这本身就是最大的歧义。

必须澄清的：

- 两个成员同时把同一任务移到不同的列，谁赢？**先到者胜还是后到者胜？**
- 输的那方收到什么？`409`？错误码叫什么？
- 响应里要不要带上服务端的当前状态？（**强烈建议要**——否则客户端无法自行恢复）
- 「同时」的判定窗口是多少？

**为什么致命**：这是 [AP-7](../reference/anti-patterns.md) 的典型场景。需求里一个字都没提，实现里必然会出 bug，而且是最难复现的那种。

### ④ 鉴权边界

含糊版：「要有权限控制」

必须澄清的：

- 成员能看**其他项目**的数据吗？（哪怕知道 ID）
- 负责人能被移除吗？**最后一个负责人呢？**（这是经典的「把自己锁在门外」问题）
- 未认证请求返回 `401` 还是 `404`？（信息泄露考量：`404` 不暴露资源存在性）
- 无权访问现有资源返回 `403` 还是 `404`？

### ⑤ 分页语义

含糊版：「要能分页」

必须澄清的：

- `offset` 还是 `cursor`？**（任务会被并发创建，offset 分页会漏数据/重复！）**
- 默认页大小？上限？
- 请求 `size=1000` 时是拒绝、还是截断到上限？（**必须选一个**）
- 排序字段？排序稳定性怎么保证？

### ⑥ 审计日志字段

含糊版：「要留痕」

必须澄清的：

- 记哪些动作？只有状态变更，还是包含评论、成员变更？
- 字段固定为哪几个？
- 失败的操作要不要记？（**要。否则无法排查越权尝试**）

### ⑦ clarify 实际问出来的问题（原文）

上面六类不是我自己想的——**是 `/speckit-clarify` 一条条问出来的**。这里给出真实的问答记录，包括我第一遍答错的地方。

**Q1（状态流转）**
> “任务能在看板列之间移动” —— 请确认：
> 1. 有哪几列？
> 2. `todo` 能否直接到 `done`？
> 3. `done` 之后能否重新打开？

**我的回答**：四列 `todo/doing/in_review/done`；不能跳；**能重新打开**。

**⚠️ 追问（这一条价值最高）**：
> 若能重新打开，请确认：审计日志记一次还是两次？统计口径中该任务算完成还是未完成？`done` 的时间戳是否保留？

**我改口了**：改成「**`done` 是终态，不可重新打开**」。

> 📌 **看这里发生了什么。** 我原来的答案（「能重新打开」）听起来更灵活、更友好。
> 但追问把「代价」摊开了：**灵活性带来三处未定义行为**。
> **默认选项往往不是最优选项，只是你没想过的选项。**

**Q2（并发冲突）** —— 需求里一个字都没提
> 需求未提及并发修改。请确认：两个成员同时把同一任务改为不同状态时，谁胜出？输的一方收到什么？响应里是否包含服务端当前状态？

**我的回答**：先到者胜；后者返回 `409 CONFLICT`；**响应含 `current` 对象**。

**⚠️ 追问**：
> `current` 字段是必须的吗？客户端可以自己去重新拉取。

**我的回答（这一条我想清楚了）**：必须。没有它，客户端收到 409 后不知道服务端当前状态，只能额外拉一次；且在弱网下可能拿到更新的版本，陷入无意义的冲突循环。

> 📌 **注意：这是我自己选的选择，并说清了理由。** 如果当时回答「你看着办」，agent 可能会省掉 `current`——**而你不会察觉，因为它看起来更精简。**

**Q3（分页）**
> “要能分页” —— 请确认：offset 还是 cursor？默认页大小？上限？请求 `size=1000` 时是报错还是截断？排序规则？

**我的回答**：cursor；默认 20；上限 100；**截断（不报错）**，并以 `effective_size` 明示；排序按 `created_at DESC, id DESC`。

**⚠️ 这里的第三个追问是我没想到的**：
> 为什么用 cursor 而不用 offset？

**我花了两分钟才答上来**：因为任务列表是**高频写入**的场景。
> offset 分页在数据插入/删除时会导致**漏数据或重复**——例如翻到第 2 页时有人新建了一个任务，第 2 页的第 1 条就会后移到第 1 页的末尾，客户端拿不到了。
>
> 📌 **技术选型看似属于 plan，但它其实由需求的写入特征决定。** 这是 clarify 阶段就该想清楚的事。

**Q4（鉴权边界）**
> “要有权限控制” —— 请确认：成员能看其他项目（哪怕知道 ID）吗？最后一个负责人能被移除吗？未认证返回 401 还是 404？无权访问现有资源返回 403 还是 404？

**我的回答**：不能；**不能（`422 LAST_OWNER`）**；401；**404（不暴露资源存在性）**。

**⚠️ 第四个追问**：
> 确定用 404 而不是 403？代价是前端无法区分「不存在」和「无权限」，调试体验会变差。

**我的回答**：确定。因为 403 会泄露「该 ID 存在」，可被用于枚举。**代价我接受，并写进了 spec 的说明里。**

**Q5（审计字段）**
> “要留痕” —— 记哪些动作？字段固定为哪几个？**失败的操作要不要记？**

**我第一遍漏了第三个**，直接答了前两个。追问才让我意识到：**如果只记成功操作，就无法发现「有人在反复尝试越权」——而那恰恰是审计最有价值的场景。** → 于是有了标准 5.3 与 5.4。

## 4. 回答追问：不许说「你看着办」

`/speckit-clarify` 会逐个问你。**这是本节的关键纪律。**

> ⛔ **不许回答「你看着办」或「你决定就好」。**

原因很直接：**「你看着办」等于把歧义原封不动推进下游。** agent 会选一个看起来合理的答案，而你不会有任何感觉——直到 L08 实现出来才发现不是你要的。

### 参考答案（供你对照，但请先自己答）

这里给几个典型决策，**注意每个决策都附了「代价」**：

| 问题 | 决策 | 代价 |
|------|------|------|
| 合法流转 | 只允许 `todo→doing→in_review→done`，以及 `in_review→doing`（驳回） | 用户不能一键标完成，必须有流转体验 |
| `done` 是终态吗 | **是**。要重开必须新建任务 | 「误标完成」无法回退，用户会抱怨 |
| 并发冲突 | **先到者胜**，后者 `409 CONFLICT` + 返回服务端当前状态 | 客户端要处理冲突并重新渲染 |
| 分页 | **cursor 分页**，默认 20，上限 100，超限**截断**并返回 `next_cursor` | cursor 实现比 offset 复杂，且无法跳页 |
| 最后一个负责人 | **不可移除**，返回 `422 LAST_OWNER` | 用户需要先指定新负责人 |
| 无权访问 | 返回 `404`（不暴露资源存在性） | 前端难区分「不存在」和「无权限」，调试体验略差 |

**每一个「代价」都在告诉你：这个决策不是免费的。** 而 clarify 的价值就是逼你在**成本最低的时刻**付这个成本——现在。

## 5. `/speckit-checklist`：以评审人身份打勾

```
/speckit-checklist
```

### 关键区分（这里最容易搞错）

| | 是什么 | 打勾意味着 |
|---|-------|-----------|
| **自定义 checklist** | **需求质量的评审工件** | 「我认为这条要求写清楚了、可验收」 |
| 实现完成度 | 另一回事 | 「这段代码写完了」 |
| `checklists/requirements.md` | 由 `/speckit-specify` 和 `/speckit-clarify` 维护的内置清单 | 与上两者都不同 |

**自定义 checklist 打勾 ≠ 实现完成。** 它是「**需求的单元测试**」——你在检查**要求本身的质量**，而不是功能是否做出来了。

### 打勾的纪律

- ✅ 现在打（**在 plan 和 implement 之前**）
- ✅ 只有当你**确信这条要求可被测试**时才打勾
- ⛔ 不许「靠猜」打勾
- ⛔ 不许实现完再回头打勾（那就变成待办列表了，见 [AP-13](../reference/anti-patterns.md)）

**打勾时机错了，这个工件就废了。** 因为它的作用是在投入实现工作量**之前**拦住问题。

## 6. 记录「我原本以为清楚」的地方 ⭐

这是本节的验收硬指标：**至少 3 处**。

建 `notes/L06-澄清收获.md`：

```markdown
# 澄清收获

## 我原本以为很清楚、其实不清楚的地方

### 1. 并发冲突
我以为「两个人都改状态」是边缘情况，不值得写进需求。
澄清时才发现：需求里完全没提这件事，而它是必然会发生的。
→ 教训：需求里的**空白**比需求里的**含糊**更危险，因为你根本不会去看它。

### 2. 分页方式
我以为「分页」就是 offset + limit。
澄清时被问到「任务会被并发创建，offset 分页会怎样」才意识到：
offset 分页在数据插入/删除时会漏数据或重复——而任务列表正是高频写入的场景。
→ 教训：技术选型看似属于 plan，但它其实由**需求的写入特征**决定。

### 3. done 是不是终态
我默认「done 可以改回 doing」，因为这样更灵活。
澄清时被问「那审计日志记几次？统计口径怎么算？」才发现
「灵活」的代价是引入了一堆规则。最终选了「终态」。
→ 教训：**默认选项往往不是最优选项，只是你没想过的选项。**

## 对照：我的预判清单漏了什么
（贴出第 2 节你自己写的找茬清单，对照上面六条，看你漏了哪几个）
```

**最后那个「对照」小节最重要。** 你的预判清单漏掉的每一条，都是你的盲区——而这正是下一步要针对性训练的地方。

<details markdown="1">
<summary>答案</summary>

1. agent 会选一个**看起来合理**的答案，而你不会察觉——因为它看起来确实合理。这个选择会一路传到实现。**你只在最后验收时才会发现，而那时返工成本最高。** 歧义不会消失，它只会转移到成本最高的地方爆发。
2. 因为「先到者胜还是后到者胜」是**业务规则**，不是技术选择。技术选择是「用什么实现乐观锁」（plan 的事），业务规则是「输了的人该看到什么」（spec 的事）。把业务规则推到 plan，等于让技术方案决定业务行为。
3. 因为它的作用是**在投入实现成本之前拦住问题**。plan 之后、implement 之后，你已经花了成本；此时打勾只能确认「我知道有问题」，无法阻止成本发生。**评审工件的价值取决于它的时机。**

</details>

## 8. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **跳过 clarify 直接 plan** | 整份 plan 建立在双方对某个概念的不同理解上 | clarify 必跑（[AP-12](../reference/anti-patterns.md)） |
| **回答「你看着办」** | agent 替你做了业务决策 | 不许。歧义不会消失，只会转移 |
| **只澄清「发生了什么」，不管「发生时谁赢」** | 并发、超限、越权场景没定义 | 对每个区问：**冲突时谁赢？输的一方看到什么？** |
| **checklist 实现后才打勾** | 变成待办列表 | 必须在 plan 之前（[AP-13](../reference/anti-patterns.md)） |
| **checklist 靠猜打勾** | 为了让流程往前走而勾 | 你的 checklist 从此失去价值。宁可留着不打勾并注明原因 |
| **澄清只走流程不看输出** | 提问回答了，但没回写到 spec | 检查 spec 里六类区域是否都有对应条目 |
| **不记「我漏了什么」** | 下次还漏同类问题 | 第 6 节的预判对照是本节真正的学习点 |

---

## 9. 本节术语

| 术语 | 含义 |
|------|------|
| clarify | 流程化消灭歧义：agent 追问 → 你回答 → 回写 spec |
| 歧义区 | 需求中天然含糊的高危区域（并发、权限、边界、终态） |
| requirements quality | 需求质量：要求本身写得够不够好 |
| reviewer-owned artifact | 评审人所有的工件；自定义 checklist 属于此类 |
| cursor 分页 | 基于游标的分页；在并发写入场景下比 offset 分页正确 |
| 代价意识 | 每个决策都附上代价；没有免费的设计选择 |

## 10. 下一节预告

你现在有一份歧义清零、质量评审过的规格。下一步是**给它装上牙齿**。

L07 要解决一个核心问题：

> **怎么把「验收标准」这种给人读的句子，变成会导致 CI 失败的可执行断言？**

三种武器：类型约束（zod schema）、契约测试（vitest 用例）、CI 门禁。其中最关键的产物是一张 **「验收标准 ↔ 测试用例」映射表**——它是 spec-anchored 能够成立的技术基础。
