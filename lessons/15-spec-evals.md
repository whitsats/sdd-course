# L15 · 把验收标准变成评测集 ⭐

| 项 | 内容 |
|----|------|
| **时长** | 90 min（实操通常 2 h） |
| **前置** | L07（验收标准 ↔ 测试映射表）与 L09（验收纪律）。**不依赖 L13 / L14** |
| **案例** | 复用项目 A `focuslog` 的 23 条标准 —— 本节**不新建项目** |
| **产出** | 一份评测集（JSONL）+ 一轮判定记录 + 每处翻转的归类 |
| **验收** | ① 23 张评测卡全部生成 ② 至少 3 张卡经过真实判定并留证 ③ 每处 FAIL 或「无法判定」都归了类：改 spec 还是改 code ④ 你能说出评测**为什么不能进 CI 当门禁** |

> 📁 **本节的配套工具**：[`scripts/generate-evals.py`](../scripts/README.md) ——
> 纯标准库、零依赖，把 spec 的验收标准与映射表拼成评测卡（JSONL）。
> 本节所有脚本输出都是实测；**判定结果**由你自己的运行产生，本节不代替你跑。

---

## 1. 这一节在整门课里的位置

L13 和 L14 换了两根轴：**约束该放在多早**（编译期）、**多晚**（数据层）。
本节换第三根：**约束作用在谁身上**。

前三阶段所有的强制力都指向「代码」—— 测试拦代码，CI 拦合并。
但当写代码的是 agent 时，还有两个对象从来没被约束过：

- **规格本身**：一条写得含糊的验收标准，测试和 agent 都会「各自理解」，
  而且都自信满满；
- **执行规格的模型**：同一个 spec 喂两次，产出可能不同。你不量化它，
  就永远只在「感觉这次不太行」的层面抱怨。

> **一句话**：L13 问约束放多早，L14 问放多晚，L15 问——**考卷出给谁**。
> 规格写完不只是给人看、给测试断言用的，它还是 agent 的考卷。

本节刻意标为可选。它不引入新的门禁（恰恰相反，§6 会论证评测**不能**当门禁），
它补的是一门课容易漏掉的最后一块：**验收纪律的可重放性**。

---

## 2. 测试回答不了的两个问题

L07 的映射表保证了「每条标准有测试守」。但有两个问题，测试在结构上答不了：

**① 这条标准本身可执行吗？**
「用户体验良好」写不成断言，但更隐蔽的是那些**看起来能写、跑起来才知道不行**的标准：
两个触发条件打架、退出码写了但输出格式没写、引用了别的章节的格式却没说冲突时听谁的。
测试只会红给你看，不会告诉你「红的原因是标准自己说不清」。

**② 换一个执行者，规格还成立吗？**
契约测试是**你**写的断言，绑定**这一个**实现。换一个 agent 重新实现，
断言不一定还适用；而验收标准是独立于实现的行为描述——**它应该对任何实现都判定得出来**。
判定得不出来，就是标准的问题，不是实现的问题。

这两问的答案都不在代码里，在**标准原文 vs 实际行为**的逐条对照里。
这就是评测（evaluation）：把每条标准变成一张**判定卡**，喂上真实行为，逐条给结论。

| | 契约测试（L07） | 评测（本节） |
|---|---|---|
| 判定依据 | 断言（人写的代码） | 标准原文（自然语言） |
| 判定者 | 测试框架，**确定性** | 模型或人，**有方差** |
| 对象 | 这一个实现 | 任何实现的行为 |
| 挂了说明 | 代码偏离规格 | 代码偏离规格，**或规格自己说不清** |
| 能进 CI 吗 | ✅ 门禁 | ⛔ 不能（§6） |

## 3. 评测卡长什么样

`generate-evals.py` 为每条标准生成一行 JSON，核心是 `card` 字段——
一张可以直接粘给评审模型（或人）的判定卡。骨架如下（focuslog 3.1，真实生成，仅「待判定行为」留空）：

```text
【判定卡 · 验收标准 3.1】
WHEN 用户执行 `focuslog start --tag reading` WHILE 当前不存在活跃会话
THE system SHALL 创建一个新会话，记录开始时间与标签 `reading`，
以退出码 0 结束，并输出确认信息（含标签与开始时间）。……

【待判定行为】
<在此粘贴：命令与实际输出 / agent 产出 / 截图转写。留空 = 无法判定。>

【判定要求】
1. 只依据上面的标准原文判定，不引入标准之外的假设。
2. 结论三选一：PASS / FAIL / 无法判定。
3. FAIL 或无法判定时，引用标准原文中缺失或矛盾的部分作为证据；禁止编造行为细节。
4. 若这条标准本身不可验收，输出「无法判定」，并把它改写成可验收的标准。
```

四条判定要求，每条都不是装饰：

- **「不引入标准之外的假设」**——模型最大的失效模式是拿常识补规格的洞。
  它一补，评测就变成了「模型觉得好不好」，而不是「标准怎么说」。
- **「三选一，含无法判定」**——没有这个出口，模型会硬编一个结论。
  「无法判定」是**有价值的结果**：它标记的是标准的信息缺口。
- **「引用原文作证据」**——让判定可复核。没有证据的 FAIL 和抱怨没有区别。
- **第 4 条是回馈入口**——评测发现「判不了」的标准，改写建议直接产生
  下一次 spec 迭代的输入。这是评测和 agnes-review 最大的分工差异（§7）。

## 4. 动手（五步）

### ① 生成评测集

```bash
# 在仓库根目录。用 python / py，别用 python3（Windows 存根坑，见 L00）
python scripts/generate-evals.py examples/focuslog --out notes/L15-evals.jsonl
# ✅ 23 张评测卡 → notes/L15-evals.jsonl（来源：examples\focuslog\specs\.../spec.md）
```

五个案例项目的实测解析数（与覆盖率门禁同源，行语法一致）：

| 项目 | focuslog | taskflow | rulesmith | billflow | stockflow |
|------|----------|----------|-----------|----------|-----------|
| 评测卡 | 23 | 40 | 10 | 21 | 26 |

**数字对不上覆盖率门禁的实测值 = spec 或映射表行格式有问题**，先修格式再继续。
（脚本与 `check-spec-coverage.sh` 用同一套行判据，这是刻意的：两个工具不该对
「什么是一条标准」有两种理解。）

### ② 挑卡，不是全做

23 张全判定一遍是体力活，第一轮只挑 **3–5 张**。挑法有讲究：

- **边界类优先**。focuslog 的边界标准占 48%（11/23）——它们最容易出现
  「标准说不清 → 模型各自理解」的分歧，正是评测的价值区。
- **跨标准组合一张**。L06 的教训（AC 3.7 的由来）是：两条各自正确的标准，
  叠加后出现凭空消失的会话。把两条放进**同一张卡**的场景里判一次。
- **跳过纯主路径**。`start` 成功创建会话这种卡，判定结果和测试结果几乎必然一致，
  第一轮不值得花在上面。

### ③ 逐条判定

每张卡填上真实行为（跑一遍命令，粘贴输出），交给判定者：

- **有人工就人工判**。判定卡本身就是验收记录的骨架——L05 的验收纪律
  从「逐条看过」升级成「逐条可重放」：换个人拿着同一张卡，应该得出同一结论。
- **用模型判时**，卡片原样粘给任何对话模型即可（不必是特定 API；
  `agnes-review.py` 的使用环境可直接复用）。**同一张卡至少跑两次**：
  两次结论不一致，本身就是发现 —— 要么标准说不清（回 ④），
  要么你的判定要求写得不够死。

### ④ 记录翻转

把判定结果记成一张表，只关心**非 PASS** 的行：

| 标准 | 结论 | 证据（引用原文） | 归类：改 spec 还是改 code |
|------|------|----------------|------------------------|
| 1.4 | 无法判定 ×2（两次结论不一致） | 「超过 32 个字符」——超长时**输出什么**没写 | 改 spec：补输出要求 |
| … | | | |

分类纪律与 L05 完全相同：**规格不清 → 改 spec；实现跑偏 → 改 code**。
唯一新增的一类是「标准不可验收」——它表面上是改 spec，
根因常常是当初写标准时没人试着**执行**过这条判定。

### ⑤ 回馈

- 改 spec 的部分走标准流程：`change-request-template.md`（改的是**已有**标准的行为），
  改完重跑覆盖率门禁与映射表同步。
- 改 code 的部分回 tasks 补任务，不要手痒直接修 —— 这是 L09 的老纪律，评测不豁免它。

## 5. 评测不是门禁（本节最重要的一段）

课程反复讲「门禁最危险的失效是沉默」，也讲过「随机红灯的必然结局是团队关掉门禁」。
评测两个都占：

- **判定有方差**。同一张卡，两次运行结论可能不同——不是模型坏了，
  是自然语言判定天然带噪声。红灯随机出现的门禁会被关掉，然后连真正的违规
  一起失去（AP-18 的完整死法）。
- **判定者与被判定者共用同一个理解盲区**。评审模型对标准原文的误读，
  可能恰好和实现 agent 的误读是同一种。两个错误互相印证，比一个错误更难发现。

所以：**评测进报告，不进 CI**。确定性的检查（覆盖率、分层、生成物可复现）
继续当门禁；评测是**验收与规格质量的人工增强层**，它的产出（归类与改写建议）
通过正常的 spec 变更流程落回仓库 —— 落回之后的部分，才有资格被门禁守着。

---

## 6. 什么时候不值得做

诚实记录边界，和 L13 / L14 同一格式：

- **行为可以全靠断言覆盖**：纯函数、输入输出都有机器判据的库——契约测试就是
  100% 可重放的评测，再出判定卡是重复劳动。
- **规格少而稳定**：一次性脚本、三五条标准、写完三个月不动——
  直接 L05 手工验收就够了，评测集的维护成本收不回来。
- **没有 agent 参与的既有团队流程**：本节的主要增量是「执行者换了」，
  团队如果人写代码 + 评审纪律健全，它的边际价值最小。

它最值得用的场景恰好是本课程的主场景：**规格交给模型执行，行为由人来验收**。

## 7. 与 agnes-review.py 的分工

两个工具都让模型审规格，方向相反：

| | `agnes-review.py`（L06） | 评测集（本节） |
|---|---|---|
| 方向 | **横向**：读完整个 spec 找矛盾、缺口 | **纵向**：逐条标准对照行为判定 |
| 输入 | spec 全文 | 一张卡 = 一条标准 + 一段真实行为 |
| 提问 | 「这份规格哪里没说全？」 | 「这个行为符合这条标准吗？」 |
| 时机 | specify 之后、plan 之前 | 实现验收时、以及每次 spec 变更后 |
| 产出 | 缺口清单 → 回 specify | 判定 + 归类 → 回 spec 或回 code |

先横向再纵向：L06 挖缺口，L15 验可执行性。顺序反了，
会拿一堆「判不了」的卡去喂一个本来就有洞的规格。

## 交付物与验收

**交付物**：

- `notes/L15-evals.jsonl` —— 生成的评测集（23 张卡）
- `notes/L15-评测记录.md` —— 挑卡理由 + 判定表 + 每处非 PASS 的归类
- 每处「改 spec」的回馈：一条真实的 change request 或 spec diff

**验收标准**：

- [ ] 评测卡数量与覆盖率门禁实测值一致（23 = 23）
- [ ] 至少 3 张卡完成真实判定，**每张留有可复现的行为证据**（命令 + 输出）
- [ ] 同一张卡至少判过两次，或明确说明为何一次足够
- [ ] 每处 FAIL / 无法判定都归了类，没有一条停留在「待定」（L11 的老规矩）
- [ ] 你能不看讲义说出：评测为什么不能进 CI 当门禁（两个理由）

## 踩坑预警

1. **把评测结果当测试结果**。PASS ≠ 测试绿：一个是有方差的判定，一个是确定性断言。
   两者冲突时，先怀疑判定卡的证据是不是复现充分，再怀疑标准。
2. **判定卡里塞上下文**。把整份 spec 粘进卡里稀释了判定焦点——模型开始
   「整份读下来感觉符合」。一张卡只允许引用标准原文 + 一段行为。
3. **忘记「无法判定」也是结果**。强行 PASS/FAIL 的评测集会把信息缺口
   永久埋掉——那一行记录的改写建议，是整个流程里最值钱的产物。
4. **用评测替代验收记录**。判定卡是骨架，行为证据必须真实粘贴；
   「模型说 PASS」不是证据，是意见。
5. **评测集腐化**。spec 改了评测集没重新生成，卡里还是旧标准——
   和映射表脱节是同一种病。重跑脚本是廉价的，把它加进规格变更清单的末行。

## 术语

evaluation（评测）、eval set（评测集）、judge（评审模型 / 判定者）、
verifier card（判定卡）、flip（翻转：两次判定或两轮版本间结论改变）、
non-deterministic check（非确定性检查 —— 永远不该当门禁的东西）
