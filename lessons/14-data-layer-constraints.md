## 1. 这一节在整门课里的位置

L13 把约束往前推：推到编译期，让写错的人**拿不到可运行的产物**。那一节的方向感很强 —— 「越早越好」。

本节往**反方向**走，而且要先说清一件事：

> **「越早越好」有一个前提 —— 违背约束的那次写入，会经过你放约束的那段代码。**

前四个案例（A 测试 → B CI 合同 → C 生成器 → D 编译期）**全都默认这个前提成立**。
一旦它不成立，那些约束一起失效，而且是**静默**失效：测试是绿的，CI 是绿的，
只是有一条数据被别人从侧门放进去了。

库存系统里，侧门很多：

```
                      ┌──────────────────────────┐
   HTTP 请求 ─────────▶│                          │
   定时任务 ──────────▶│   你的应用代码            │
                       │   （测试/CI/编译期约束    │
                       │     全都挂在这里）        │
                       └────────────┬─────────────┘
                                    │
  运维手工补数据 ──────────────────▶│
  数据迁移脚本 ────────────────────▶│
  监控系统改状态 ──────────────────▶│   ┌──────────────────┐
  另一个服务的直连 ────────────────▶└──▶│   数据库          │
  DBA 的一条 UPDATE ──────────────────▶│  ← 约束该住在这里 │
                                        └──────────────────┘
```

于是本节要回答的问题只有一句：

> **一条规格，如果要拦住「不经过你的代码的写入」，它必须住在哪里？**

答案是**数据层** —— 不是因为它更高级，而是因为在那些路径上，
**它是唯一还在场的位置**。

### 「更晚」不等于「更弱」

这是本节的第一个反直觉点：

| | L13（更早） | L14（更晚） |
|---|---|---|
| 约束住在 | 编译器 / 字节码 | schema |
| 拦住谁 | 写错代码的人 | **任何**写入者 |
| 失效形态 | 构建绿、校验零执行 | 测试绿、幽灵行入库 |
| 前提 | 编译配置（`proc:none` 会让它消失） | **连接前提**（见 §7） |

注意最后一行：**两端都引入了一个「前提」**。L13 的前提是构建配置，L14 的前提是连接参数。
两者的失效形态完全一样 —— **一切正常，只是什么都没发生。**

> 这不是巧合，也不是本课程在凑主题。**约束离「被检查的对象」越远，
> 就越需要一次「兑现动作」把静态的文字变成运行期的行为** ——
> 对编译器是「加载处理器」，对数据库是「启用外键」。兑现动作不会自己发生，
> 而它没发生的时候，**没有任何一处会报警**。

## 2. 判据：一条规格该住在哪一级

搬进数据层不是越彻底越好。`plan.md` 里用的判据只有一条，先记住它，后面的所有取舍都由它推导：

> **这条标准要拦住的写入，会经过我这段代码吗？**
> 不会 → 它**必须**住在数据层。
> 会 → 它可以住在任何一级，那就**优先用低的一级**。

### 约束阶梯

按「数据层能表达多复杂的条件」从小到大排开，**优先用低的一级**：

| 级 | 载体 | 能表达 | 失败信息的定位精度 |
|---|---|---|---|
| ① | 列类型 + `NOT NULL` + `STRICT` | 「这一列必须是整数」 | 列 |
| ② | `CHECK` | **单行内**的取值 | 列 |
| ③ | `UNIQUE` / `PRIMARY KEY` | 跨行**唯一性** | 列 |
| ④ | `FOREIGN KEY` | 跨表**存在性** | 表 |
| ⑤ | `TRIGGER` | 跨行**聚合与派生** | 触发器名（需要再翻译一次） |
| ⑥ | 事务（调用方） | 多个动作**同生共死** | 应用 |

本案例里这六级都用上了（26 条标准的「保证者」分布见映射表）：

```
① STRICT    2 条      ④ FK        1 条（⚠ 依赖连接前提）
② CHECK     8 处      ⑤ TRIGGER   8 个
③ UNIQUE    1 条      ⑥ 事务      3 条只能靠它
```

### 为什么「优先用低的」是有理由的，不是风格偏好

看两条报错：

```
CHECK constraint failed: qty > 0          ← ② CHECK：能直接对应到规格编号 1.5
INSUFFICIENT_STOCK                        ← ⑤ TRIGGER：我们自己起的名字，要多一次翻译
```

**可定位性是有成本的。** 触发器报错只给你一个名字，而这个名字是**你起给规则的**，
不是引擎给的。所以判据是：

> **能用 `CHECK` 表达的，绝不用触发器。** 触发器存在的唯一理由是
> **条件里含聚合** —— 而 `CHECK` 禁止子查询。

`migrations/001_init.sql` 里 8 个触发器全部满足这个理由，没有一个是「顺手写成触发器」的。

### ③ 不能换成「先 SELECT 再 INSERT」

这是本节唯一一处**不是「更清晰」而是「根本做不到」**的选择。幂等（AC 1.4）的载体必须是 `UNIQUE`：

```sql
-- 反例：两个并发请求可以同时通过 SELECT 检查，然后都 INSERT
SELECT /* 有没有同 request_id 的记录？ */;
INSERT ...;

-- 正解：唯一约束由引擎原子保证，没有这个窗口
UNIQUE (request_id)
```

并发正确性不能靠「检查得够仔细」，只能靠**引擎在同一个动作里完成检查与写入**。
这一条在 L08（并发冲突策略）已经出现过一次，这里它是**同一个教训的另一种形态**。

### ① 与 ② 的区别最容易被忽略，代价最大

SQLite 默认是**动态类型**：一个声明为 `INTEGER` 的列会欣然接受 `'abc'`。
实测（AC 5.1）：

```
⑦ INSERT INTO reservation ... qty = 'abc' ...
   → rejected: cannot store TEXT value in INTEGER column reservation.qty
```

**这一行之所以能拒绝它，是因为表建成了 `STRICT`。** 没有 `STRICT` 时，

> 「数量必须是整数」这条标准，其实**没有被任何东西保证**。

—— 声明类型在老 SQLite 里只是**给优化器的建议**，不是约束。
一个从 MySQL / PostgreSQL 过来的人在这里会翻车，因为那些库的声明类型就是约束。

## 3. 机制：把验收标准直接写进 schema

`001_init.sql` 的写法只有一个特点：**每个约束后面都挂着一个规格编号**。

```sql
CREATE TABLE reservation (
  res_id      TEXT    PRIMARY KEY,
  request_id  TEXT    NOT NULL,
  sku_id      TEXT    NOT NULL REFERENCES sku(sku_id),        -- AC 1.6
  qty         INTEGER NOT NULL CHECK (qty > 0),               -- AC 1.5
  state       TEXT    NOT NULL CHECK (state IN ('held','committed','released')),
  created_at  INTEGER NOT NULL,
  expires_at  INTEGER NOT NULL CHECK (expires_at > created_at), -- AC 3.1
  settled_at  INTEGER,

  -- AC 2.2 / 5.1：held 必须没有终结时刻；终结态必须有。
  CHECK ((state = 'held') = (settled_at IS NULL)),

  -- AC 1.4 幂等的**载体**（见上节：不能换成「先 SELECT 再判断」）
  UNIQUE (request_id)
) STRICT;
```

三个值得逐条记住的点：

**① 表级 `CHECK` 表达的是「两列之间的关系」。**
`(state = 'held') = (settled_at IS NULL)` 这一行把两列**绑成一致的一对**。
两条列级 `CHECK` 做不到这件事 —— 因为它们各自只能看见自己那一列。
「状态与终结时刻必须同时出现」是一条**关系**，不是两个**取值**。

**② 规格编号写在 SQL 注释里，而注释会被 `check-spec-coverage.sh` 之外的机制验证。**
`TRIGGER` 的名字无法自证它对应哪条标准，所以映射表要有一列 **保证者**：

| 编号 | 规格摘要 | 测试 | 保证者 |
|---|---|---|---|
| 1.2 | 预占后可用量不得小于 0 | `behavior.spec.mjs`、`schema.spec.mjs`、`check-sql-enforcement.sh` | `TRIGGER` |
| 1.6 | 目标 SKU 不存在时拒绝 | 同上 | `FK` ⚠ **依赖连接前提** |
| 4.1 | 库存守恒 | `invariant.spec.mjs` | **巡检**（schema 强制不了） |

**这一列是本案例对 `check-spec-coverage.sh` 的一次诚实补充。**
覆盖率脚本只会数「每条标准有没有测试」，它**无法区分**「被强制了」与「只是被测试了」。
补一列不是解决方案，只是一个**局部**答案 —— 我在 ADR-004 结尾把它标成了「还没有答案的连带问题」。

**③ 把等式做成视图，让不变量变成可查询的事实。**

```sql
-- AC 4.1：库存守恒。这一行必须恒等于 0，对任意操作序列成立。
CREATE VIEW v_conservation AS
SELECT s.sku_id,
       s.on_hand
       + COALESCE((SELECT SUM(r.qty) FROM reservation r
                    WHERE r.sku_id = s.sku_id AND r.state = 'committed'), 0)
       - COALESCE((SELECT SUM(c.qty) FROM receipt c WHERE c.sku_id = s.sku_id), 0)
         AS delta
FROM sku s;
```

「相信代码是对的」被换成了一条**可以直接 SELECT 的等式**。测试可以断言它，
巡检可以查询它，出故障时你可以直接把它贴进工单。

## 4. 招牌演示：完全不加载一行 JavaScript

这是本节最值得亲手跑一遍的演示。**整个过程中没有任何应用代码参与**，连 import 都没有：

```bash
cd examples/stockflow
cp var/stockflow.db /tmp/bypass.db
sqlite3 /tmp/bypass.db "PRAGMA foreign_keys;"      # → 0
```

八条直写，**全部由引擎判定**：

```
①  UPDATE sku SET on_hand = -1;                                → rejected  CHECK constraint failed: on_hand >= 0
②  INSERT INTO reservation ... qty = 0 ...                     → rejected  CHECK constraint failed: qty > 0
③  INSERT INTO reservation ... sku_id = 'GHOST' ...            → ACCEPTED  ← 唯一漏掉的一条
④  INSERT INTO reservation ... qty = 999 ...                   → rejected  INSUFFICIENT_STOCK
⑤  UPDATE reservation SET state='held' WHERE res_id='R-DEMO';  → rejected  INVALID_STATE
⑥  UPDATE reservation SET qty=0 WHERE res_id='R-DEMO';         → rejected  IMMUTABLE_FIELD
⑦  INSERT INTO reservation ... qty = 'abc' ...                 → rejected  cannot store TEXT value in INTEGER column
⑧  INSERT INTO reservation ... expires_at < created_at ...     → rejected  CHECK constraint failed: expires_at > created_at

SELECT count(*) FROM reservation WHERE sku_id='GHOST';         → 1
```

**7 拦 1 漏。而漏掉的那一条，恰好是强制力挂在 `PRAGMA foreign_keys` 上的那一条。**

这不是运气不好，这是一个**结构性的结论**，也是本节要你带走的最重要的东西：

| | 随什么走 | 需要兑现吗 |
|---|---|---|
| `STRICT` / `CHECK` / `UNIQUE` / `TRIGGER` | **schema 的一部分，随库走** | 不需要 |
| `REFERENCES`（外键） | 写在 schema 里 | **需要每一次连接兑现前提** |

> 写在 schema 里 ≠ 一定会执行。
> **只有一部分约束是「结构」，另一部分是「协议」** —— 而协议需要每一方自己遵守。

## 5. 为什么单看「AC 4.3 有 6 个子项」是不够的

规格 4.3 写的是「绕过应用程序的写入必须被拒绝」，下面挂了 6 个子项：

```
① 负的在手量          ② 非正数量的预占        ③ 引用不存在的 SKU
④ 计次超量的预占      ⑤ 从终结态出发的流转    ⑥ 生效中预占量 > 在手量
```

在规格里这 6 条**长得一样**（都是「非法写入必须被拒绝」），而且它们**都对应测试**。
但在实现里它们分成两类：

| 子项 | 强制机制 | 需要前提吗 |
|---|---|---|
| ①②④⑤⑥ | `CHECK` / `TRIGGER` | 不需要 —— 随库走 |
| ③ | `FOREIGN KEY` | **需要** —— 取决于谁来连接 |

> **规格不该谈机制，所以规格没有区分它们；而实现必须知道这个区别。**
> 不知道这个区别的人，会写出一个「测试全绿、线上放行」的系统 ——
> 因为他的测试用的是**开启了外键的客户端**（Node 驱动默认开），
> 而他线上那条路径未必是。

这也是本节给你的第一个可迁移动作：

> **把你的每条「必须被拒绝」的标准，标上它的强制机制。**
> 标不出机制的那些，就是你现在**只靠信念**在保护的部分。

## 6. 同一个库、同一条语句、三个客户端

```
INSERT INTO reservation (res_id, request_id, sku_id, qty, ...) VALUES ('r1','q1','GHOST',1,...);
```

实测结果（`notes/L14` §4 有原始输出）：

| 客户端 | SQLite 版本 | `PRAGMA foreign_keys` | 结果 |
|---|---|---|---|
| Node `node:sqlite` | 3.50.4 | **1** | ✅ `FOREIGN KEY constraint failed` |
| Python `sqlite3` | 3.37.2 | **0** | ❌ **写入成功** |
| `sqlite3` 命令行 | 3.44.4 | **0** | ❌ **写入成功** |

**没有哪个默认值是 bug。** 这个 PRAGMA 默认关闭来自 SQLite 的早期历史：
加这个特性时已有大量依赖「可以插幽灵行」的存量应用，为了向后兼容才默认关闭。
Python 与命令行客户端保留了那个默认值，Node 选了相反的一侧。

> 这张表值得你停下来看十秒。**同一个数据库文件、同一条 SQL、三种结果。**
> 你对「外键会拦住幽灵行」的全部信心，取决于一件**不在 schema 里的事**。

### 更糟的是：那一行 PRAGMA 自己也可能「写了但没生效」

实测（同一段代码，只改一件事 —— 有没有把设置包在事务里）：

```
① 默认值                    = 1
② 显式关闭后                = 0
db.exec('BEGIN');
db.exec('PRAGMA foreign_keys = ON');     ← 不抛错
③ 事务内设 ON（读回）       = 0           ← 但没生效
COMMIT;
④ 提交后（读回）            = 0           ← 也没有「延迟生效」
db.exec('PRAGMA foreign_keys = ON');     ← 事务外设置
⑤ 非事务内设 ON（读回）     = 1           ← 这才生效
   → 幽灵行被拒绝：FOREIGN KEY constraint failed
```

**「写了 PRAGMA 但没生效」与「schema 里写了 REFERENCES 但没生效」是同一个形态** ——
都不报错，都静默。所以 `src/db.mjs` 的做法是：

```js
db.exec('PRAGMA foreign_keys = ON');
assertForeignKeys(db);      // ← 读回来断言，不是「设置完就相信」
```

和 L13 里 `check-java-build.sh` 断言「注解处理器真的跑过」是**同一个动作**：
把「我配置过了」升级成「我验证过它生效了」。

> 💡 **一个建设性的副作用发现**：`journal_mode = WAL` 与 `foreign_keys` 都是 `PRAGMA`，
> 但**前者随库文件持久化，后者随连接生灭**。
> 怎么知道？只能查文档或实测一次 —— 我在这里猜错了（我以为两个都随库）。
> **同类东西表面的相似性，是排查时最贵的陷阱。**

## 7. 测试写法的一次反转：故意不 import 应用代码

本案例 44 个测试里，有 **16 个**（`tests/schema.spec.mjs` 的全部）
**不碰应用的连接逻辑与业务代码**，直接用裸连接打库：

```js
const db = rawConnect(t.path);  // 注意：外键**未启用** —— 与多数客户端一致
```

在普通项目里，这会被当成坏味道：**测试绕过了被测试的东西**。
这里反过来 —— 因为规格 4.3 要拦住的**正是**「不经过应用」的写入：

> 在存在绕过路径的前提下，一组只走应用层的测试，
> 提供的信心是**假的** —— 它证明了「我们的代码很小心」，
> 而不是「绕过它也拦得住」。

这组测试产出的最诚实的一条断言，是一条**记录缺陷的测试**：

```
✔ 外键**在未启用时**拦不住幽灵 SKU —— 这不是期望行为，是被记录的代价（AC 4.3③）
✔ 同一个库、同一条语句：启用外键的连接会拒绝它（AC 1.6 / 4.3③）
```

**第二条**才是本案例的核心：它把「承诺」变成「条件成立时的事实」，
并用测试名把**条件**写了出来。

## 8. 元验证 A–E（含两次「元验证本身出错」）

老规矩：**一个不会红的门禁不是门禁，是仪式。** 五条全部实测，原始输出在 `notes/L14`：

```
元 A  删掉 trg_reservation_no_oversell
      ✖ 超卖（AC 1.2） 期望 INSUFFICIENT_STOCK，实际：已预占 {...qty:7}
      ✖ ③ 直写**成功**了：超量预占（AC 4.3⑥）
      ✖ 巡检发现违规行：│ 0 │ 'OVERSELL' │ 'SKU-1' │ 10 │ 0 │
      失败：4 项（通过 16 项）

元 B  删掉 sku 的 CHECK (on_hand >= 0)
      ✖ ① 直写**成功**了：在手量改负（AC 4.3①）
      ✖ 库存守恒被破坏
      失败：3 项（通过 17 项）

元 C1 驱动层关外键 + 删掉显式 PRAGMA，但**保留**断言
      ✖ 建 SKU 失败
      ✖ 超卖（AC 1.2）→ file:///…/src/db.mjs:40      ← 连接那一刻就炸，大声失败
      失败：19 项

元 C2 在 C1 基础上**再把断言也删掉**
      ✖ SKU 不存在（AC 1.6） 期望 UNKNOWN_SKU，实际：已预占 {...}
      ✖ ⑧-b 同一写入经由应用**没有**被拒绝
      失败：2 项                                        ← 静默降级

元 D  只删掉 db.exec('PRAGMA foreign_keys = ON')，保留断言，不碰驱动默认值
      通过：20 项检查                                    ← 门禁全绿

元 E  从映射表删掉一行
      标准条数: 26   映射行数: 25
      ::error::覆盖率不完整：spec 有 26 条标准，映射表有 25 行。
      缺少测试映射的标准编号：1.3
```

### C1 / C2 是本案例最有价值的一对

同一个缺陷（外键没生效），**有没有那条断言**决定了它的形态：

| | 有断言（C1） | 没断言（C2） |
|---|---|---|
| 表现 | 连接时抛错，19 项失败 | 安静地放行脏数据，只有 2 项失败 |
| 什么时候发现 | 立刻 | 不知道什么时候 |
| 成本 | 一行代码 | —— |
| **失败的数量** | **多** | **少** |

> **「失败得更少」不等于「更健康」。** C2 只失败 2 项，看起来比 C1 好得多 ——
> 但那 19 项是在**大声报告前提没兑现**，而那 2 项背后是一个**已经写进去的幽灵行**。
> **门禁的失败数量不是健康指标。**

### 元 D 是一个诚实但尴尬的发现

`db.exec('PRAGMA foreign_keys = ON')` 那一行在当前 Node 驱动上是**冗余的** ——
驱动默认已开，所以删掉它**门禁不会红**。

它的价值在于**未来的默认值变化**（或换驱动、换运行环境），
而**门禁只能验证现在，无法验证一个尚未发生的未来**。

> 所以：**不要把「门禁没红」当成「这段代码没用」的证据。**
> 判据是「删掉它之后，什么情况下会出事」，而不是「删掉它之后 CI 什么颜色」。
> —— 这条判据同样适用于 L13 里那类「现在看不出差别」的防线。

### 元验证自己出错的两次（比上面五条更值得记）

**第一次：我把「关掉外键」实现成「删掉那行 PRAGMA」，结果门禁全绿。**
真相是 Node 驱动默认就开着，我的注入**什么都没关掉**。
于是我以为「元验证失效了」，差点据此放宽门禁。

> **一次错误的元验证会让人误信门禁无效 —— 这比不做元验证更危险。**

**第二次：C1 里我以为自己做的是「关掉外键」，其实驱动层设置没生效，
真正起作用的是我顺手留下的那条断言。** 修好注入方式之后才拿到上表里 C1/C2 的真对照。

两次都是同一个错：**注入的东西和我以为注入的东西不是同一个**。
所以元验证的正确姿势是**先确认注入生效**（读回状态），再去看门禁红不红 ——
这和 §6 里 `assertForeignKeys()` 是同一个动作。

## 9. 门禁自己踩的四个坑 ⭐

这一段比 §8 更有用。写 `check-sql-enforcement.sh` 的过程中，这个门禁自己出了 **4 个问题**，
而且**全部是「静默不检查 / 报错报在错的地方」，没有一个误报**。
它们与它要防的东西是**同一个形态**，所以逐条记下来：

### ① 错误码检查读到空字符串

`run_cli` 里有 `2>/dev/null`，而 CLI 的稳定错误码（AC 5.3）是打到 **stderr** 的：

```
✖ 超卖（AC 1.2） 期望 INSUFFICIENT_STOCK，实际：        ← 后面是空的
```

修法：拆成两个包装器 —— 取数值的丢 stderr，**查错误的连 stderr 一起取**。

### ② `$RID` 是空串 → 「什么都没发生」被当成了「写入成功」

```sql
UPDATE reservation SET state='held' WHERE res_id='';    -- 匹配 0 行
```

不报错。而判断是「没有输出 = 写入成功」，于是**假绿**：

```
✖ ④ 直写**成功**了：从终结态复活（AC 4.3⑤） —— 这条约束没有生效
```

真相是那条约束好好地在那儿，只是**没有任何行被碰过**。
**一个空变量让门禁从「检查约束」变成了「检查一次空气」。**
修法有两处：用 `--res=` 固定标识（不让随机 id 造成歧义），
**并且**在直写之前先断言目标行存在且状态正确。

### ③ `set -o pipefail` 让「断言它失败」的检查永远失败

```bash
# 错的写法
if cli reserve GHOST 1 | grep -q UNKNOWN_SKU; then ... fi
```

被检查的命令以 1 退出 → `pipefail` 让**整条管道**返回 1 → grep 找到了匹配也白搭 → `if` 永远走 else：

```
✖ ⑧-b 同一写入经由应用**没有**被拒绝 —— 外键在我们的连接上也没生效
```

真相是它**被正确拒绝了**。这是本仓库里唯一一个**假红灯**，
而它比假绿灯更容易被忽略 —— 人会去改**代码**，而不是去看**门禁**。

修法：凡是「断言某命令失败」的地方，**先落变量再匹配**。

### ④ 元 C 第一次注错了（见 §8）

### 三个坑的共同点

```
① 取错了流            → 读到空 → 判据恒假/恒真
② 变量为空            → 匹配 0 行 → 「没发生」读成「成功」
③ 退出码来源搞错      → 断言恒假 → 永远报红
④ 注入错了            → 结论无效
```

**四个都不是语法错误，四个都不会让脚本崩。** 它们的共同形态是
**「脚本在运行、结论是错的、看起来一切正常」** —— 和它要防的「幽灵行」一模一样。

> 这就是为什么本仓库每道门禁都必须通过**反向验证**：
> 不是「跑通了」，而是「**我确认过它会红**」。

## 10. 数据层做不到的事

ADR-001 的结论很容易被读成「那就把一切都搬进 schema」。
**`ADR-004` 记录的是搬不过去的那部分** —— 而它的重要性不低于 ADR-001：

> 一份只知道「该搬什么」而不知道「什么搬不了」的方案，
> 在遇到第一条例外时就会变成一份被违反的方案 ——
> 而**被违反的方案比没有方案更糟**，因为它让所有人以为有保护。

四类搬不过去的东西：

| 类别 | 例子 | 为什么 |
|---|---|---|
| **需要解释的错误** | 想要 `INVALID_QTY`，只能拿到 `CHECK constraint failed: qty > 0` | 引擎的报错文本里**没有**足够信息。这是精度上限，不是「再努力一点」能解决的 |
| **跨表语义** | 「预占的 SKU 必须属于同一租户」（要读三张表） | 触发器**可以**写，但会变成一段自己不受约束保护的 SQL |
| **与业务流程绑定的策略** | 「VIP 可透支 5%」「促销期间允许透支」 | 规则**随时间变化且有例外** —— 那是策略，不是结构。搬进去 = 每次调整一次迁移，而迁移可能**重建表** |
| **需要人类判断** | 「这条看起来像测试数据，应该拒绝」 | 无法表达，也不该表达 |

### 被接受的替代方案：把「不可强制」降级为「可观测」

对搬不过去的那部分，**不假装它被强制了**，而是把它变成一条必须返回 0 行的查询：

```sql
-- queries/patrol.sql（① 库存守恒的巡检版本，AC 4.1）
SELECT 'CONSERVATION' AS rule, sku_id, on_hand,
       on_hand + COALESCE((SELECT SUM(qty) FROM reservation
                            WHERE sku_id = sku.sku_id AND state = 'committed'), 0)
               - COALESCE((SELECT SUM(qty) FROM receipt WHERE sku_id = sku.sku_id), 0) AS delta
FROM sku
WHERE on_hand + COALESCE(...) - COALESCE(...) <> 0;   -- 任何一行都是违规
```

规则文件顶部写着两条约定，值得抄进你自己的仓库：

```
① 每一条查询都必须返回 0 行。
② 任何一行输出都表示「有人在约束之外写了数据」——
   这时不要去责怪写入方，先问「为什么这条规则没能变成约束」。
```

以及一句必须写在报告里的区分：

> **触发器让违规「不可能发生」；巡检让违规「可见」。
> 两者都需要，但不是同一种东西 —— 不要在报告里把它们混成「都做了检查」。**

> **把「无法强制的规则」明确降级为「可观测的规则」，
> 比把它伪装成强制的规则要诚实。**

本案例在 5.4 上正是这个态度：它没有说「在手量一定正确」，
它说的是「**在手量必须可被推导出来**」—— 后半句是可机械验证的。

### 顺带一个必须量化的代价

SQLite 的 `ALTER TABLE` 只支持很有限的操作（加列 / 改名 / 删列，3.35+）。
**修改一条 `CHECK`、给触发器换条件、改列类型 —— 一律要「建新表 → 搬数据 → 换名」。**

| 规格改动 | 住在应用层 | 住在数据层 |
|---|---|---|
| 改一句判断 | 改一行代码，跑测试 | **一次迁移**：建新表 + 搬数据 + 换名 + 处理存量违规数据 |
| 加一条新约束 | 加一个 `if` | 一次迁移，且要回答「存量数据违反新约束怎么办」 |
| 删除一条约束 | 删一个 `if` | 一次迁移（且要**重新声明一遍整个表**） |

所以判据是**加权的**，不是无条件的：

> **约束住在数据层，当且仅当「它要拦住的写入可能不经过应用」且「它本身足够稳定」。**
> **两个条件缺一不可。**

「库存不能为负」两个都满足（几十年的供应链系统都同意这一条）。
「VIP 可透支 5%」不满足第二个 —— 它应该住在策略层。

## 11. 另一个机制：把「现在几点」做成一张表

AC 3.5 要求「一切与时间有关的行为都从调用方提供的时刻推导，不得读系统时钟，
以保证同一组输入在任何时刻重放都得到相同结果」。做法是一张单行表：

```sql
CREATE TABLE clock (
  id   INTEGER PRIMARY KEY CHECK (id = 1),   -- 只允许一行
  now  INTEGER NOT NULL
) STRICT;
INSERT INTO clock (id, now) VALUES (1, 0);
```

**为什么这比「注入一个 `now()` 函数」更强：**

| | 注入时钟（应用层） | 时钟表（数据层） |
|---|---|---|
| 谁受约束 | 调用我们 API 的代码 | **SQL 语句本身**，包括命令行里的直写 |
| 触发器的过期判定 | 无法统一 —— 触发器读什么时刻？ | 与视图读**同一行**，口径不可能不一致 |
| 重放 | 要重建整个对象图 | 一条 `UPDATE clock SET now = ?` |

本案例把这一条当作**可复现性的地基**：因为时刻可控，
「过期」与「收割」在演示里是**可复现的实验**，不是需要等待的现象。

```bash
node src/cli.mjs reserve SKU-1 4 --at=1000 --ttl=200 --req=REQ-A --res=R1
node src/cli.mjs show   --at=1000    # 可用量 6
node src/cli.mjs show   --at=1300    # REQ-A 已过期 → 可用量回到 10（AC 3.2）
node src/cli.mjs commit R1 --at=1300 # EXPIRED（AC 2.6）
node src/cli.mjs reap   --at=1300    # 收割 1 条
```

> **可测试性是设计出来的，不是补出来的。**「读系统时钟」这个看似无害的便利，
> 是绝大多数「偶发失败」的源头 —— 而把它变成一张表只要五行 SQL。

## 12. 踩坑预警（全部真实撞到）

### ① 不要按分号切分 SQL 文件

```js
// 会碎在 CREATE TRIGGER ... BEGIN ... END; 上 —— 触发器体里本来就有分号
sql.split(';').forEach(s => db.exec(s));

// 正解
db.exec(wholeFileContent);
```

### ② 每个 `store` 函数自带事务 → 组合调用时会炸

`store` 的每个公开函数都自带事务（这样单独调用它就满足 AC 4.4），
但一个真实业务动作往往要组合几个函数。第一版直接报：

```
cannot start a transaction within a transaction
```

修法是**用 SAVEPOINT 做可重入事务**（`src/db.mjs` 的 `tx()`）：
内层失败只回退到自己的保存点，内层被接住时**外层可以继续**，外层失败则整体回滚。

> 注意当时的诱惑：在 store 里加「我现在是不是已经在事务里了」的判断。
> 那种判断会很快长成一张谁也不敢改的网。**用引擎的机制（SAVEPOINT），别用状态判断。**

顺带一个实测收益：`BEGIN IMMEDIATE`（开事务时立刻取写锁，而不是等第一次写入）
在多写入者竞争下把锁冲突提前，于是 `busy_timeout` 从那一刻开始计时。
40 路并发争抢 10 件库存的测试：**恰好 10 个成功，零超卖，无 `SQLITE_BUSY`。**

### ③ `node:sqlite` 返回的行对象**原型是 `null`**

`assert.deepStrictEqual` 会比较原型 —— 于是两个字段完全相同的对象报
「deepStrictEqual 失败」，而打印出来的 actual 与 expected **一模一样**。
看到这种报错先想原型。

### ④ 用一个「没有真正违反约束」的用例去测约束

```js
// 旧值就是 'SKU-1'，于是 NEW <> OLD 为假，触发器**正确地**没有触发
for (const set of ['qty = 0', "sku_id = 'SKU-1'", ...]) { ... }
```

失败的是**测试**，不是代码。这类假失败会浪费一轮排查 ——
而它和 §9 里的门禁坑是同一类：**检查本身的正确性也是一个需要验证的对象。**

### ⑤ `node:sqlite` 需要 Node ≥ 22.5

版本不够时「跑不了」与「跑了没问题」在报告里差别巨大。
`run-all-gates.sh` 用 `gate_soft` 只在**缺 node** 时跳过；
**版本不够时脚本以退出码 2 结束并说明原因**，而不是计入「通过」。
（跳过项从来不计入通过 —— 这条规则在 L09 就立下了。）

## 13. 这套约束**不该**用在什么场合

| 信号 | 说明 |
|---|---|
| **团队里没人能读 SQL** | schema 会成为只有一个人敢改的文件。先解决这个，再谈下沉 |
| **规则本身在剧烈变化** | 策略类规则（促销、额度、等级）搬进去 = 每次调整一次可能重建表的迁移 |
| **主要写入路径旁没有绕过路径** | 判据的第一条不满足时，搬进去只换来更差的错误信息和更高的演化成本 —— **收益为零，成本为正** |
| **还在探索期的原型** | 结构与策略的边界还没稳定，此时固化进 schema 会锁死错误的决定 |
| **需要跨行、跨表、跨服务的复杂语义** | 写出来的触发器自己不受约束保护。**退到「应用层检查 + 一条巡检查询」** |

还有一条最根本的：

> **数据层的约束，代价付在「演化」上，收益来自「绕过」。**
> **如果你的系统根本没有绕过路径，这套东西对你就是纯负债。**

## 14. 自测（先自己想，再展开）

**第 1 题**：为什么「超卖」这条标准**必须**住进数据层，
而「VIP 可以透支 5%」**不该**住进去？请用判据里的两个条件回答。

<details markdown="1">
<summary>答案</summary>

判据是两个条件**缺一不可**：「要拦住的写入可能不经过应用」且「它本身足够稳定」。

- **超卖**：两个条件都满足。库存可能被迁移脚本、另一个服务、DBA 的手工 `UPDATE` 改到 ——
  这些写入不经过应用；且「库存不能为负」是几十年的领域共识，不会下个月改。
  → 必须下沉。
- **VIP 可透支 5%**：满足第一个条件（同样可能被绕过），但**不满足第二个**。
  它是策略，会变、有例外（大客户、促销期）。搬进去之后每次调整都要一次迁移，
  而 SQLite 改 `CHECK` 要重建表。
  → 留在策略层，用巡检查询让违规**可见**。

**关键不是「哪个更好」，而是这类规则一旦混在一起，你会得出「全都搬进去」或「都不搬」的结论** ——
两个结论都错。
</details>

**第 2 题**：你的门禁报告「20 项检查全部通过」。它还可能是空的吗？给出两种可能。

<details markdown="1">
<summary>答案</summary>

可能，而且本节的 `check-sql-enforcement.sh` 两种都踩过：

1. **检查读到的输入是空的** —— 错误码在 stderr 上，而包装器丢了 stderr，
   于是「期望 `INSUFFICIENT_STOCK`」读到的实际值是**空字符串**。判据恒假/恒真。
2. **被检查的动作什么都没发生** —— `UPDATE ... WHERE res_id=''` 匹配 0 行、不报错，
   而判据是「没有输出 = 写入成功」。**一个空变量让门禁从「检查约束」变成「检查一次空气」。**

防御方式有三层：
① 三条**反假绿**设计 —— **合法的写入必须成功**（否则只读库也能全绿）、
**先断言目标行存在**（否则「没发生」被读成「成功」）、
按实测的 PRAGMA 决定预期（否则在别的客户端上给出**假红灯**）。
② **元验证**：删掉/关掉被保护的东西，确认门禁真的会红。
③ **先确认注入生效**（读回状态），再看门禁红不红 —— 否则失败的元验证会误导你放宽门禁。
</details>

**第 3 题**：同一个库、同一条 `INSERT`，Node 拒绝、Python 放行。
这是 SQLite 的 bug 吗？如果是你的项目，你会怎么处理这个差异？

<details markdown="1">
<summary>答案</summary>

**不是 bug。** `PRAGMA foreign_keys` 默认关闭是 SQLite 为向后兼容做的历史决定
（加这个特性时已有大量应用依赖「可以插幽灵行」）。
Python 与命令行客户端保留了那个默认值，Node 驱动选择了相反的一侧。

处理方式不是去改客户端默认值（你改不了别人的连接），而是**承认强制力取决于连接**，
把它变成一件**会被检查的事**：

1. **应用自己的连接**：设置 + **读回断言**（`assertForeignKeys()`），
   启用不了就**立刻失败**，而不是静默降级（AC 4.5）。
2. **对不可控的连接**：写进文档与 ADR，并给这条标准打上「依赖连接前提」的标记
   （映射表的保证者一列）。
3. **对重要的写入路径**：在数据层再放一道**不依赖前提**的检查 ——
   例如用一个 `BEFORE INSERT` 触发器去查 SKU 是否存在（它不依赖 PRAGMA）。
   代价是触发器的报错只指向触发器名，比 `FOREIGN KEY constraint failed` 更难定位。
4. **端到端验证**：一条**直写**测试 + 一条**记录该差异本身**的测试（本案例两条都有）。
</details>

## 15. 术语

| 术语 | 含义 |
|------|------|
| **约束下沉（constraint pushdown）** | 把规格约束从应用层搬到数据层执行，使其对不经过应用的写入同样生效 |
| **强制力的前提（precondition of enforcement）** | 让约束从「写在 schema 里」变成「本次连接会执行」的那次兑现动作（如 `PRAGMA foreign_keys`） |
| **结构 vs 协议** | 随库走的约束（`CHECK`/`STRICT`/`TRIGGER`）与需要每一方遵守的约束（`FOREIGN KEY` 的连接前提） |
| **巡检（patrol）** | 对无法强制的规则的定期查询；**让违规可见**，而非不可能 |
| **保证者（guarantor）** | 映射表里标明「这条标准由谁保证」的一列：`CHECK` / `TRIGGER` / 事务 / 巡检 |
| **可重入事务** | 用 `SAVEPOINT` 实现、可嵌套的事务包装；避免在业务代码里判断「是否已在事务中」 |
| **反假绿（anti-false-green）** | 让「什么都没发生」不可能被读成「检查通过」的设计：先断言前置条件成立 |

## 16. 交付物与验收

**交付物**：

- 一份**自己承担强制力**的 schema（`migrations/*.sql`），每条约束挂着规格编号
- 一份**保证者**映射表（26 行，机械校验条数）
- 一份「搬不过去的东西」的清单（对应 ADR-004）与对应的巡检查询
- 五条元验证的真实现象记录

**验收标准**：

- [ ] `bash scripts/check-sql-enforcement.sh` 通过（**含「合法写入必须成功」的反假绿检查**）
- [ ] `node --test tests/*.spec.mjs` 全过，且其中**至少一组不 import 应用代码**
- [ ] 用 `sqlite3` 命令行直写脏数据 → **被引擎拒绝**，且你能说出**哪一条漏了、为什么**（本节答案是外键）
- [ ] `bash scripts/check-spec-coverage.sh examples/stockflow` 报「26/26 覆盖完整」
- [ ] 找出你项目里**一条**「在应用层检查得过早」的规则并搬进数据层 ← **动手的一条**
- [ ] 说出一条**不该**搬进数据层的规格，并给出两个条件的判断 ← **最重要的一条**

> ⚠️ 最后两条是刻意的，而且方向相反。
> 只做到第一条的人，下一步一定会把不该搬的东西也搬进去 ——
> 然后在下一次需求变更时付出一次重建表的代价，并从此开始怀疑整套方法。

## 17. 到这里，强制力光谱走完了

```
强制力光谱（越往右，违背代价暴露得越早；但「谁被拦」的覆盖面不同）

  无强制力        测试红灯        CI 红灯        编译失败       无法构造        数据层
  ────────────────────────────────────────────────────────────────────────────────►
  spec-first     spec-anchored           构建期强化（L13）          结构强化（L14）
  项目 A         项目 B                  项目 D                    项目 E

  拦住写代码的人 ─────────────────────────────────────▶   拦住**任何**写入者
```

两端各有一次「兑现动作」，而**两次兑现都不会自己发生**：

| | L13（构建期） | L14（数据层） |
|---|---|---|
| 兑现动作 | 注解处理器被加载 | `PRAGMA foreign_keys` 被启用 |
| 谁负责 | 构建配置 | 每一个连接 |
| 没兑现时 | 构建绿、规格校验为零 | 测试绿、幽灵行入库 |
| 检查它是否兑现 | `check-java-build.sh` 断言标记行 | `assertForeignKeys()` 读回断言 |

**这门课反复出现的那条线，在最后一节再写一次：**

> **门禁最危险的失效不是报错，是沉默。**
> 所以每一道门禁都必须通过**反向验证** ——
> 不是「跑通了」，而是「**我确认过它会红**」。
