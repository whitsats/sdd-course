# L05 · Implement 与手工验收

> **时长** 120 min（实操通常 4–6 h）｜ **前置** [L04](./04-plan-tasks.md) ｜ **产出** 可运行的 `focuslog` + 验收记录

阶段二的最后一节。要拿到的不只是一个能跑的 CLI，而是**验收纪律**——以及一次刻意的自我拆穿。

本节最重要的产出其实不是代码，而是这句纪律：

> **跑通 ≠ 完成。让 agent 写验收结论 = 没有验收。**

## 1. `/speckit-implement` 会做什么

```
/speckit-implement
```

它会按 `tasks.md` 的依赖顺序执行任务。有两件事你要知道：

**① 它会读 checklist 的门禁状态。** 如果存在未打勾的 checklist 项，它会**先问你**要不要继续。注意：它**不会**替你改 checklist 文件或勾选标记——自定义 checklist 始终是**评审人所有**的工件（L06 会展开这个区别）。

**② 它可以分阶段跑。** 大 feature 可以一次只跑一个阶段。focuslog 不大，但请**至少分两批**：

```
批次 1：T001–T003（存储 + domain）
→ 停下来，人工验收 domain 层
批次 2：T004–T009（services + cli）
→ 停下来，端到端验收
```

**为什么必须分批**：一次性跑完，出错时你无法定位是哪一层错了。分批则把「存储层对不对」「领域规则对不对」变成两个互不干扰的问题。

## 2. 验收纪律 ⭐ 本节核心

建 `notes/L05-验收记录.md`，用这张表。**每一条 EARS 标准都要有一行。**

```markdown
# focuslog 验收记录

| 验收标准（简写） | 验证动作 | 实际结果 | 结论 |
|----------------|---------|---------|------|
| start 无活跃会话时成功 | `focuslog start --tag reading` | 输出确认信息，退出码 0 | ✅ |
| start 有活跃会话时拒绝 | 先 start 再 start | 输出 SESSION_ALREADY_ACTIVE，退码 2 | ✅ |
| stop 两次幂等 | start → stop → stop | 第二次 NO_ACTIVE_SESSION，首次时长未变 | ✅ |
| 周报无记录时退码 0 | 清空数据后 `report --week` | 打印"本周没有记录"，退码 0 | ✅ |
| stats 排序稳定 | 造两个时长相同的标签 | 按字典序输出 | ❌ 反了，见下 |
| 跨天会话归属开始日 | 手工改 JSON 造跨天数据 | 归属正确，有跨天提示 | ✅ |
| 标签含空格被拒 | `start --tag "a b"` | TAG_INVALID，退码 1 | ✅ |
```

### 三条铁律

1. **「验证动作」必须是可复制的命令或步骤**，不是「试了一下」。
2. **「实际结果」写你看到的**（输出文本、退出码），不是「正常」。
3. ⛔ **不允许出现「应该没问题」。** 写了就等于没验证。

### 第三条铁律最重要

「应该没问题」是 vibe coding 留在你身上的最后一块化石。它意味着你把**验证责任**外包给了一个不存在的保证。

### ⛔ 绝不要让 agent 自己写验收结论

哪怕它说「已验证全部通过」。这是自己给自己判卷——它验证的是**它自己的理解**，而 L01 就讲过，它最不擅长的就是猜你想要什么。

**验收必须由你，对着 spec.md，逐条人工做。**

## 3. 端到端演示每个用户故事

验收记录表是逐条查，这一步是**整体演示**。对 L03 的 4 个用户故事，各录一段完整的终端会话：

```bash
# US1 开始一段专注
$ focuslog start --tag reading
✔ 已开始专注 [reading] 09:15

# US2 结束一段专注
$ focuslog stop
✔ 本次专注 50 分钟 [reading]

# US3 周报
$ focuslog report --week
# 2026 第 39 周（09-21 ~ 09-27）

| 日期 | 时长 | 条数 |
|------|------|------|
| 09-22 | 50 min | 1 |

## 标签分布
- reading: 50 min

# US4 累计统计
$ focuslog stats
reading     50 min
```

**每个故事都要能独立演示。** 如果演示 US3 必须先做 US1，那不算「独立」——说明你的用户故事划分有问题，回 L03 修。

## 4. 刻意制造漂移演练 ⭐ 有自虐但极有价值

这是本节的核心练习。**现在请你主动破坏自己的项目。**

### 步骤

**① 制造漂移。** 挑一条验收标准，在**不修改 spec.md** 的前提下改代码，让它偏离。建议选这个：

> spec: 「stats 在时长相同时按标签名字典序升序」

把代码改成按时长倒序、时长相同则按插入顺序（改成这个反而更「自然」）：

```python
# 故意去掉稳定排序
return sorted(totals.items(), key=lambda x: -x[1])
```

**② 不要立刻去看代码。** 假装你是三个月后接手的人。

**③ 用三种方式分别尝试发现它：**

| 途径 | 怎么做 | 能发现吗？ |
|------|-------|-----------|
| **跑测试** | `pytest` | ？ |
| **看代码** | 打开 `services/stats.py` | ？ |
| **对着 spec 验收** | 打开 `spec.md` 逐条对照 | ？ |

**④ 记录结果。** 九成人的结果是：

- 跑测试 → **发现不了**（因为你大概没为这条写测试，或者写了但断言不严谨）
- 看代码 → **发现不了**（倒序看起来完全合理）
- 对着 spec 验收 → **能发现**（因为 spec 白纸黑字写了「字典序升序」）

### 这个演练说明了什么

**规格本身是有效的——问题在于没有强制力。**

你唯一能发现漂移的方式，是**主动去对照规格**。而现实中没人会天天主动对照。所以：

> **规格的价值，取决于它被自动对照的频率。**

这就是 L09 要解决的事。你刚刚亲手证明了为什么需要 CI 门禁——**这比任何说理都有说服力。**

**把这次演练的记录存下来**，L09 会用同一份记录做对比。

## 5. 发现漂移后的分类 ⭐

演练中你发现了漂移。现在做分类——**三类问题的修复路径完全不同**：

| 现象 | 问题层 | 修哪里 |
|------|-------|-------|
| 实现和 spec 不一致 | **实现跑偏** | 改代码 |
| spec 说不清「字典序升序」是什么意思（按 Unicode 码点？忽略大小写？） | **规格不清** | 改 spec |
| spec 说清楚了，但 plan 没定排序实现方式，任务也没包含它 | **规划/拆解有误** | 改 plan 或 tasks |

**本次演练的正确答案是第一类**（实现跑偏），因为 spec 写得够清楚。但请**故意再问一遍自己**：「按字典序升序」对 `reading` 和 `Reading` 谁在前？——如果 spec 没回答这个，那它就同时属于**第二类**，你要回去补一句话。

> 📌 这个「再问一遍」的习惯，是区分「会做 SDD」和「在走 SDD 形式」的分水岭。

## 6. 阶段二收尾：spec-first 的局限

你现在有了一个可运行、验收过的 `focuslog`。停一下，看清楚你**实际拿到了什么、没拿到什么**。

### 拿到了

- ✅ 规格与实现一致（**在你验收的那一刻**）
- ✅ 每条行为都有来源（可追溯到 spec 的某条 EARS 语句）
- ✅ 有一个可追溯的完整链路：EARS 标准 → spec → plan 决策 → task → 代码

### 没拿到

- ❌ **规格没有强制力**。第 4 节的演练已经证明了：改了代码，没有任何东西会报警
- ❌ **规格会腐烂**。三个月后再改代码，没人会去更新 spec
- ❌ **一致性靠人肉维持**。而第 4 节证明了人肉不可靠

**这就是 spec-first 的天花板。** 它是正确的起点，但停在这是不够的——因为你拥有的是一份「当下正确、然后开始缓慢腐烂」的规格。

要突破这个天花板，只差一件事：**让规格可执行**。

## 7. 交付物与验收

### 交付物

1. 可运行的 `focuslog`（4 个子命令全部可用）
2. `tests/` 下的 pytest 测试
3. `notes/L05-验收记录.md` —— 逐条验收表
4. `notes/L05-漂移演练.md` —— 第 4 节的三种发现途径结果
5. 漂移演练的代码改动（**提交或 stash 起来，L09 要用**）

### 验收清单

**功能**

- [ ] `start` / `stop` / `report --week` / `stats` 全部可运行
- [ ] 4 个用户故事**各自独立演示**通过
- [ ] 退出码语义符合 spec：0 / 1 / 2 各至少验证一次
- [ ] 跨天会话的归属规则验证过（手工构造数据）
- [ ] 无记录时 `report --week` 退出码为 **0**，不是错误码

**纪律**

- [ ] 验收记录表**每一条** EARS 标准都有一行
- [ ] 没有任何一行写着「应该没问题」
- [ ] 「实际结果」列写的是具体输出与退出码，不是「正常」
- [ ] **没有让 agent 写验收结论**
- [ ] 实现**分成了至少两个批次**，且每批后都有验收

**漂移演练**

- [ ] 制造了漂移，且**没有修改 spec.md**
- [ ] 三种发现途径的尝试结果都记下来了
- [ ] 你能说出：为什么「看代码」和「跑测试」发现不了，而「对照 spec」能发现
- [ ] 对发现的漂移做了层级分类，并说明了属于哪一类

### 自测题

1. 为什么「应该没问题」这四个字等同于没做验收？
2. 演练中「跑测试」为什么没发现漂移？这是测试写得不好，还是别的原因？
3. 如果 spec 没写清「字典序」的大小写规则，这个漂移算实现错还是规格错？

<details markdown="1">
<summary>答案</summary>

1. 因为它记录的不是**观察结果**，而是**你的预期**。验收的全部价值在于用真实输出对照规格，而不是用记忆确认印象。「应该」二字暴露了你根本没跑。
2. **都不是。** 因为这条验收标准**没有对应的测试**——而这不是疏忽，而是结构性问题：在 spec-first 模式下，验收标准是**人读的文档**，不是**可执行的断言**。没有任何机制强制每条标准都有测试。这正是 L09 要修的。
3. **规格错**（或者说规格不完整）。「字典序」在英文/中文/数字混排、大小写混合时都有多种合理实现。规则不清 → 实现多样性 → 漂移。**判断口诀：如果两个不同的实现都能被认为是「符合 spec」，那就是 spec 的问题。**

</details>

## 8. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **提交即完成** | 命令跑通就宣布做完 | 跑验收记录表，逐条对照（[AP-10](../reference/anti-patterns.md)） |
| **「应该没问题」** | 验收记录里出现这四个字 | 等于没验证。重做 |
| **让 agent 写验收结论** | 「agent 说全部通过了」 | 它验的是它自己的理解。你必须人工验 |
| **默许规格外功能** | agent 顺手实现了 spec 没有的能力，你留下了 | 要么删，要么**显式补进 spec 并走规格变更**（[AP-11](../reference/anti-patterns.md)） |
| **一次性 implement 全部** | 一次跑完 T001–T009 | 分批。否则出错时无法定位层级 |
| **跳过漂移演练** | 觉得「太麻烦、反正我知道会怎样」 | **你恰恰不知道。** 九成人跑完才发现自己唯一有效的检测手段是对照 spec |
| **验收记录写「正常」** | 结果列全是「正常」 | 写具体输出和退出码。「正常」是印象，不是证据 |

## 9. 本节术语

| 术语 | 含义 |
|------|------|
| 验收 | 用真实输出对照规格，而不是确认印象 |
| 验收纪律 | 「跑通 ≠ 完成」「不让 agent 自己判卷」 |
| 漂移检测途径 | 跑测试 / 看代码 / 对照 spec。**只有第三条在无强制力时可靠** |
| 端到端演示 | 每个用户故事独立跑一遍完整流程 |
| spec-first 天花板 | 规格当下正确，但无强制力、会腐烂、靠人肉维持一致性 |

### 进入阶段三前，记住这个落差

阶段三的案例是 **项目 B `taskflow`**，目标是把严谨度提升到 **spec-anchored**。它会引入 4 件事：

1. **clarify** —— 在规划前消灭歧义（L06）
2. **checklist** —— 把需求当代码来审查（L06）
3. **契约测试** —— 让规格变成可执行断言（L07）
4. **CI 门禁** —— 让漂移变红灯（L09）

**这 4 件事的共同目标只有一个**：把阶段二里「靠你主动对照」的那件事，变成「系统自动对照」。

那时你回头看第 4 节的漂移演练，会有完全不同的感受——因为你精心制造的漂移，**一提交就让 CI 红了。**
