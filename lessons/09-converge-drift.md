## 1. `/speckit-converge`：检查代码与文档的一致性

```
/speckit-converge
```

它比对**代码库**与 `spec.md` / `plan.md` / `tasks.md`。如果发现缺口，**它会把新任务追加到 `tasks.md`**。

**这是它的设计意图，也是它最重要的行为：缺口以「新任务」的形式落回 tasks，而不是靠你手改代码悄悄填上。**

```
/converge  →  发现 3 个 gap  →  追加 3 个任务到 tasks.md
   ↑                                      │
   └──────  /implement  ←─────────────────┘
```

循环直到它报告 **Converged**。

## 2. converge 不收敛怎么办 ⭐ 三层分流判断

**循环报 gap 是常态，不是异常。** 有些人卡在这里：反复重跑 implement，gap 越来越多，最后放弃。

原因是**判断错了 gap 属于哪一层**。

### 三层分流表

| gap 的性质 | 回哪一层 | 怎么识别 |
|-----------|---------|---------|
| 代码没实现规格要求的行为 | `implement` | spec 里白纸黑字有这条，代码就是没有 |
| **规格没说清 / 自相矛盾** | `clarify` 或 `specify` | 你看着 gap 心里想「嗯……这确实没定义过」 |
| 任务拆解漏了或拆错了 | `tasks` | spec、plan 都对，但 tasks 里没有对应的步骤 |

### 为什么判错层级会无限循环

假设真实情况是「**规格没说清**」（第二层），但你判成了「代码没实现」（第一层）：

1. 重跑 implement → agent 按它自己的理解实现了一个版本
2. converge → **又报 gap**，因为规格里的定义仍然模糊，无法判定
3. 再重跑 implement → agent 换了个理解，实现了另一个版本
4. converge → **报了新的 gap**

**你会永远在这个循环里，因为没有一层是稳定的。**

### 本节硬性要求

> **至少遇到一次不收敛，并正确判定它属于哪一层。**

记录在 `notes/L09-不收敛分流.md`：

```markdown
# 不收敛案例

## 现象
第 3 轮 converge 仍报 gap，内容是「任务排序规则未定义」。

## 我的误判
前两轮我都判定为「实现没做」，重跑了 implement。agent 第一次按 created_at 排序，
第二次改成了 updated_at——每次都"实现了"，但 converge 每次都报。

## 正确判定
**第二层：规格没说清。** spec 只写了「列表接口支持分页」，
从没定义默认排序字段。

## 修复
回 spec 补一条 EARS：
- WHEN 列表接口被调用而未指定排序
  THE system SHALL 按 created_at 降序返回（新建的在前），
  并以 id 降序作为次级排序键保证稳定性。

然后重跑 converge → clean。

## 教训
「看起来能实现」不等于「规格说清了」。
agent 每次都能给你一个实现，正是问题所在——因为它在替你补规格。
```

**最后那句教训是本节最重要的一句话**：agent 总能补上你没写的东西，**而这恰恰掩盖了规格的缺口**。

## 3. CI 门禁设计：只盯对外行为

这是 spec-anchored 从「流程」变成「制度」的一步。

### 配置 GitHub Actions

```yaml
name: sdd-gate

on: [pull_request]

jobs:
  contract:
    runs-on: ubuntu-latest
    services:
      postgres: { image: postgres:16, env: { POSTGRES_PASSWORD: test }, ports: ['5432:5432'] }
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile

      # ① 类型约束层
      - name: Type check
        run: pnpm tsc --noEmit

      # ② 契约测试层（阻断）
      - name: Contract tests
        run: pnpm vitest run --project contract

      # ③ 映射表覆盖率（阻断）★
      - name: Spec coverage
        run: |
          SPEC=$(grep -cE '^- (WHEN|WHILE|WHERE|IF|THE)' specs/*/spec.md)
          MAP=$(grep -c '^| [0-9]' docs/验收标准-测试映射.md)
          echo "spec: $SPEC  mapped: $MAP"
          [ "$SPEC" -eq "$MAP" ] || { echo "::error::有验收标准没有对应测试"; exit 1; }

      # ④ 性能基准（只警告）★
      - name: Perf baseline
        run: pnpm vitest run --project perf || echo "::warning::性能基准超标（不阻断）"
```

### 两个刻意的设计 ⭐

**① 第 ③ 步是整门课最值钱的十几行代码。**

它把「每条验收标准都要有测试」从**人的自觉**变成了**CI 的强制**。任何新增验收标准而不加测试的 PR，会直接红掉。

**它当场抓出了我的一个错误。** 我在写 `examples/taskflow` 的映射表时，把标准条数手写成了 **31**——
实际是 **40**。我是跑脚本时看到的：

```bash
$ bash scripts/check-spec-coverage.sh examples/taskflow
spec 标准条数: 40
映射表行数:    40
✅ 覆盖完整
```

**人手的数会错，脚本不会。** 这就是这十几行的价值——它不只防实现偏离，还防**文档写错**。
（顺带：`examples/focuslog` 的映射表我同样写错过一次，21 vs 实际 22。）

**这就是 spec-anchored 和 spec-first 的分界线。** 不是文档更详细了，是**多了一道机器检查**。

**② 第 ④ 步只警告不阻断。**

因为共享 runner 的性能抖动会导致随机红灯，而**随机红灯的必然结局是团队把门禁关掉**（[AP-18](../reference/anti-patterns.md)）。

> **原则：只把「确定性失败」设成阻断门禁。**
> 门禁的价值建立在「红灯必有意义」之上，破坏这个前提比少一道门禁更糟。

### 门禁范围纪律

| 该阻断 | 不该阻断 |
|-------|---------|
| 契约测试（对外行为） | 内部重构 |
| 类型检查 | 日志措辞 |
| 映射表覆盖率 | 变量命名 / lint 风格 |
| 状态机、权限矩阵、错误码 | 注释覆盖率 |

**判断依据：这个失败会不会让「实现对不上规格」？** 会，才阻断。

---

### ⚠️ 一个真实教训：门禁的第一版有误报

写 `scripts/check-layer-boundary.sh`（把宪法的分层约束变成 CI 检查）时，
**第一版一跑就误报了**：

```bash
$ bash scripts/check-layer-boundary.sh examples/taskflow ts
::error file=.../state-machine.ts::domain 层出现越界 import，匹配 /fastify/
❌ 分层边界被破坏
```

**然而 `state-machine.ts` 根本没有 import 任何东西。** 真相是它**注释里写了「本文件不得 import fastify」这句话**，
而我在直接 grep 模块名。

#### 为什么这个 bug 值得单独讲

因为它**正好是 §3 那个原则的反面教材**：

> 门禁的价值建立在「红灯必有意义」之上。

一个会误报的门禁，每次提交都报错 → 大家开始无视它 → **有人干脆把它注释掉** →
连真正的违规也一起失去。**这就是 [AP-18](../reference/anti-patterns.md) 的完整死法。**

#### 修法（两轮才修对）

| 轮次 | 改动 | 结果 |
|------|------|------|
| 1 | 只匹配真实 import 行（先过滤 `^\s*(import|export)`，再查模块名） | 规则 1 修好了 |
| 2 | 过滤注释行 —— 且**必须考虑 `grep -rn` 的 `path:行号:` 前缀** | 规则 2 修好了 |

第二轮那个细节值得一提：我写的过滤器是 `grep -vE '^[[:space:]]*//'`，
但 `grep -rn` 的输出前缀是 `路径:行号:内容`，所以 `^[[:space:]]*//` **永远匹配不到**——
注释行根本没被过滤掉。正确写法要先把前缀让过去：

```bash
strip_comments() {
  grep -vE '^[^:]*(:[0-9]+)?:[[:space:]]*([*#]|//|/\*)'
}
```

#### 元验证（必须做）

修完之后，**造一个真实违规**确认它还能抓到：

```bash
# 写入一个同时含「注释提及」和「真实违规」的文件
$ bash scripts/check-layer-boundary.sh examples/taskflow ts
::error file=.../__violation.ts::domain 层越界 import：import { pool } from '../repositories/task.repo';
::error file=.../__violation.ts::domain 层出现 IO 或副作用：export const bad = () => process.env.DATABASE_URL;
❌ 分层边界被破坏
```

**恰好 2 条报错，恰好对应两行真实违规。注释那行没被误报。**

> 📌 **注意这个顺序：先修误报，再做元验证。**
> 如果跳过修误报直接上 CI，你会得到一个人人忽视的门禁；
> 如果跳过元验证，你会得到一个看似干净、但已经抓不到任何东西的门禁。
> **两者都是失败的。**

## 4. 红蓝对抗 ⭐ 让门禁接受检验

**规则同前：任何检测机制，必须先被证明能检测到东西。**

这次不是写一条假测试，是**用 L05 那份真实的漂移**。

### 步骤

**① 找出 L05 的漂移改动**（你当时 stash 或提交了）：

```typescript
// 当时在 focuslog 里做的：去掉稳定排序
// 现在在 taskflow 里做同等的事 —— 违反一条已有的验收标准
```

对应 taskflow 的版本：spec 要求列表「以 id 降序作为次级排序键保证稳定」，你把它删掉。

**② 提交一个 PR。**

**③ 观察 CI。**

| 结果 | 判定 |
|------|------|
| ✅ CI 变红，且**指出的正是排序稳定性那条** | **本节通过** |
| ⚠️ CI 变红，但指出的用例不对 | 映射表或断言需要修正 |
| ❌ **CI 全绿** | **本节没及格。** 说明门禁有洞，回去补 |

**没变红就是本节没及格。** 这一条在验收标准里是硬性的——因为如果你精心制造的漂移都能溜过去，那真实的漂移更不用想。

### 加深一层（可选但推荐）

让人（或另一个 agent）在**不告诉你改了哪里**的前提下制造漂移。你只能靠 CI 定位。这是最接近真实 code review 的演练。

## 5. 规格变更流程 ⭐ 真实工作里最高频的场景

前面所有课都是「从零走到收敛」。但**你未来 80% 的时间会花在这件事上**：

> **功能上线两周后，要改它的行为。**

### 反例（大多数人会这么做）

```
改代码 → 手动测一下 → 提交 → 想起来 spec 已经过期了 → 有空再更新 → 永远没更新
```

**这就是退回了 vibe coding。** 你的 spec 会在三个月内变成考古现场。

### 正确流程（六步）

以「任务状态增加 `archived`」为例（对，就是 L08 你故意删掉的那个——**现在它有了正当流程**）。

**① 先改 spec**

```markdown
# specs/001-taskflow-mvp/spec.md

- WHEN 任务被移动到 done 且距完成超过 30 天
  THE system SHALL 将其状态变为 archived。

- IF 任务状态为 archived 且用户尝试修改状态
  THEN THE system SHALL 返回 422 TERMINAL_STATUS。
```

**② 重跑 analyze —— 看下游被破坏了什么**

```
/speckit-analyze
```

它会告诉你：plan 的状态机只有 4 个状态、tasks 里没有归档任务、映射表里没有对应行。

**这就是「先改规格」的全部价值：它把影响面在动手前一次性暴露出来。**

**③ 更新 plan 与 tasks**

- plan：状态机加 `archived`，写明「归档是定时任务触发，不是用户操作」
- plan：数据模型确认 `status` 枚举扩展
- tasks：新增「定时归档任务」「archived 状态的终端性测试」

**④ 让测试先变红**

这是**关键的一步**，也是区分「真做」和「走过场」的地方：

```typescript
it('done 超过 30 天的任务应归档', async () => {
  const task = await finishTask(await createTask(), { doneDaysAgo: 31 });
  await runArchiveJob();
  expect((await getTask(task.id)).status).toBe('archived');  // ← 现在必然失败
});
```

跑一次，**确认它红**。这就是你在 L07 学到的元验证习惯在流程层面的应用。

**⑤ 改实现到测试变绿**

**⑥ converge 到 clean，合并**

### 为什么必须先让测试变红

因为它证明了**这个测试确实在检查你要改的行为**。

如果你先写实现、再补测试，测试可能因为各种原因「恰好」通过（写错了断言、测了别的路径、被 mock 掉了），而你永远不会知道它其实没在检查任何东西。

### 顺带：这个流程暴露你的成本

第 ② 步会告诉你：**改一条验收标准，要动几个文件。**

在你当前的 taskflow 里大概是：`spec.md` + `plan.md`（状态机 + 数据模型）+ `tasks.md` + 映射表 + 迁移文件 + 2-3 个测试文件 ≈ **7-8 处**。

**记下这个数字。** 它是第 6 节成本账的核心输入。

## 6. 成本量化方法 ⭐ 验收要求你算账，所以得给方法

验收标准里有一条：「你能量化说明 spec-anchored 相比项目 A 多花了多少成本、多拿回了什么。」

**这里给你两个可操作的指标。**

### 指标 1：返工次数

> **每 10 个任务里有几个，是因为「理解错了」而重做的？**

怎么算：回顾 L08 的三个批次，数出哪些任务被返工过，以及返工原因：

```markdown
| 任务 | 是否返工 | 原因 |
|------|---------|------|
| T-存储层 | 否 | |
| T-状态机 | 是 | 我漏写了「驳回」流转，实现后才发现 |
| T-权限矩阵 | 否 | 14 格在 L06 就定清了 |
| T-并发控制 | 否 | ADR-002 把策略定死了 |
| T-分页 | 是 | cursor 编码格式没定，改了一版 |
```

**项目 A 的对照值**：凭记忆估。你在 focuslog 上返工了几次？（大概率是「大部分任务都返工过至少一次」，因为验收标准是边写边发现的。）

**关键对比不是你返工了几次，而是「返工原因的类型」：**

| 返工原因 | spec-first（项目 A） | spec-anchored（项目 B） |
|---------|-------------------|----------------------|
| **「理解错了」**（规格问题） | 高 | **应该显著下降**（因为 clarify 提前解决了） |
| **「实现有 bug」**（实现问题） | 中 | 中（这本来就该由测试覆盖） |
| **「规格变了」**（范围问题） | 低 | 低 |

**如果「理解错了」这一项没下降，说明你的 clarify 或 checklist 没做到位**——不是 SDD 没用，是那一步没执行。

### 指标 2：规格变更波及面

> **改一条已有验收标准，平均要动几个文件？**

从第 5 节算出来（当前约 7-8 处）。

**这个数字本身不是问题，它的意义在于：**

- 它是**可预测的**。你在动手前就知道要动 7-8 处（因为第 ② 步的 analyze 告诉你了）
- 对比 vibe coding：改一条行为，你要动几处？**你不知道**——因为你不知道哪里依赖了旧行为。你会改到 CI 红为止，然后发现改过头了。

> **所以成本账不是「SDD 更贵」，而是「SDD 把不确定性换成了可预测的工作量」。**

### 成本账模板

```markdown
# spec-anchored 成本账

## 投入
- L06 clarify + checklist：约 2h（项目 A 无此步骤）
- L07 契约测试 + 映射表：约 3h（项目 A 的测试约 1h）
- L09 CI 门禁：约 1h（项目 A 无）
- 合计额外投入：约 6h

## 产出
- 「理解错了」类返工：项目 A 约 6 次 → 项目 B 2 次
- 每次此类返工的平均代价：约 40min（含重新验收）
- 直接省下：4 次 × 40min ≈ 2.7h
- **漂移检测能力**：从「靠人主动对照」→「CI 自动报警」  ← 这项无法用小时计价
- 规格变更可预测性：动手前知道要动 7-8 处，而不是改到 CI 红为止

## 结论（必须回答）
这 6h 换回了什么？如果要在你手上的真实项目里推广，你会怎么选？
```

**最后那行是本节的真正考点。** 验收标准里说「如果你说不清多花的成本换回了什么，说明你只是照着流程走了形式」——就是它。

**converge**

- [ ] 循环到报告 **Converged**

- [ ] 遇到**至少一次不收敛**，并正确判定了层级（[AP-26](../reference/anti-patterns.md)）

- [ ] 契约测试 + 类型检查 + **映射表覆盖率**三层都在 CI 里

- [ ] 性能基准是**只警告**的
- [ ] 门禁范围只覆盖对外行为，不管内部重构

**红蓝对抗 ⭐**

- [ ] 制造了漂移并提交 PR
- [ ] **CI 确实变红，且指出的正是那条被违反的验收标准**
- [ ] **没变红就是本节没及格**——回去补门禁，不要跳过

**规格变更流程**

- [ ] 走完六步，且**测试先变红过**
- [ ] 第 ② 步 analyze 暴露的下游影响被记录了
- [ ] 记录了「改一条验收标准要动几处文件」

**成本账**

- [ ] 有返工次数对比，且**按返工原因分类**
- [ ] 有规格变更波及面数字
- [ ] **回答了「这 6 小时换回了什么」**——说不清就是走了形式

### 自测题

1. 为什么 converge 的缺口要以「追加任务」的形式处理，而不是直接改代码？
2. 映射表覆盖率检查为什么能成为 spec-anchored 的标志性门禁？
3. 规格变更流程里，为什么必须让测试先变红？
4. 如果「理解错了」类返工没有下降，问题出在哪？

<details>
<summary>答案</summary>

1. 因为**缺口可能是规格的问题，不只是代码的问题**。追加任务会强迫你再看一遍规格：这条要求真的对吗？说得够清楚吗？而直接改代码会把「规格可能错了」这个信号彻底抹掉。**tasks.md 是缺口的记账本，绕过它等于烧掉账本。**
2. 因为它**机械地、无歧义地**检查了「规格与实现的对应关系」。契约测试只保证「测的行为是对的」，但无法保证「规格里的每条要求都被测了」。覆盖率检查把后一半补上了——**任何新增验收标准而不加测试的 PR 会直接红掉**。这一小段 shell 就是 spec-first 与 spec-anchored 的分界线。
3. 因为**它证明了这个测试确实在检查你要改的行为**。如果先写实现再补测试，测试可能因为写错断言、测错路径、被 mock 掉而「恰好」通过——你永远不知道它其实什么都没检查。**先红后绿是测试有效性的唯一证据。**
4. 出在 **clarify 或 checklist 没做到位**，不是 SDD 方法论的问题。「理解错了」的根因是歧义没被消灭；而 clarify 正是干这个的。回去检查：L06 里六类歧义区是否真的全部处理完了？checklist 是不是有靠猜打勾的项？**如果这两步走了形式，那 cost 花掉了、收益没拿到，这是最差的组合。**

</details>

## 8. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **converge 报 gap 就手改绕过** | 直接改代码填上，或把 spec 改成符合现状 | **回填 tasks.md**，再 implement（[AP-17](../reference/anti-patterns.md)） |
| **不收敛时反复重跑 implement** | gap 越跑越多 | 三层分流：先判断是规格问题还是实现问题（[AP-26](../reference/anti-patterns.md)） |
| **门禁太严被团队关掉** | 每次提交都要改规格 | 只阻断对外行为；性能类设成警告（[AP-18](../reference/anti-patterns.md)） |
| **映射表覆盖率没进门禁** | 覆盖率靠自觉维持 | 这是 spec-anchored 的**标志性门禁**，必须上 |
| **跳过红蓝对抗** | 假设门禁有效 | **没变红就是没及格。** 这是本节不可跳过的验收项 |
| **改行为直接改代码** | 事后再补 spec（然后永远不补） | 先改 spec 再改代码，走六步（[AP-19](../reference/anti-patterns.md)） |
| **测试后写** | 实现完再补测试，全绿通过 | 先让测试红，再改实现 |
| **成本账只算投入不算产出** | 结论是「SDD 更贵」 | 产出里要有「漂移检测能力」和「变更可预测性」——这两项无法用小时计价 |
| **把门禁当终点** | 上了 CI 就以为完成了 | 门禁只管**代码是否偏离规格**，管不了**规格本身对不对**。那仍然需要人的判断 |

## 9. 本节术语

| 术语 | 含义 |
|------|------|
| converge | 比对代码与三份文档；缺口以新任务形式回填 |
| 三层分流 | gap 属于实现层 / 规格层 / 任务层的判定 |
| CI 门禁 | 自动化阻断检查；只对确定性失败设阻断 |
| 红蓝对抗 | 主动制造漂移，验证门禁能抓住 |
| 规格变更 / delta spec | 改已有行为的完整流程：先改规格 → 让测试红 → 改实现 |
| 先红后绿 | 测试有效性的唯一证据 |
| 覆盖率检查 | 验收标准条数与映射表行数必须相等 |
| 成本账 | 投入（额外工时）vs 产出（返工下降 + 可预测性） |

### 回头看 L05

L05 里你制造漂移，发现只有主动对照 spec 才能发现它。**现在同样一件事，一提交 CI 就红了。**

这个差别就是这门课的核心，也是 SDD 真正的价值所在。**不是文档更详细了，是多了一道机器检查。**

### 你现在该有的判断力

- ✅ 知道 spec-first 和 spec-anchored 的区别不是「写得多细」，而是**有没有强制力**
- ✅ 知道门禁要克制，因为「红灯必有意义」是它存在的前提
- ✅ 知道 converge 不收敛时该判层级，而不是反复重跑
- ✅ 知道改行为必须先改规格，且**测试要先红**
- ✅ 能算出一笔成本账，说出「这 6 小时换回了什么」

**这五条，就是「会做 SDD」和「在走 SDD 形式」的分水岭。**
