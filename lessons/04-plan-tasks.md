# L04 · Plan & Tasks：技术方案与原子拆解

> **时长** 120 min ｜ **前置** [L03](./03-specify.md) ｜ **产出** `plan.md` + `tasks.md`

L03 里你被反复要求「不许写技术栈」。那些被你攒在笔记里的技术决策，现在**终于有地方放了**。

本节的核心技能不是学会打两个命令，而是学会在 plan review 时做一件事：

> **逐条追问「这个决策服务哪条验收标准？」追不上的，就是范围蔓延。**

## 1. `/speckit-plan`：把决策收进来

在 agent 聊天里调用，传入你在 L03 笔记里攒下的技术决策：

```
/speckit-plan 技术栈与架构：

- 运行时 Python 3.10+，依赖管理 uv，第三方依赖仅 Typer
- 单入口 CLI，子命令用 Typer 实现
- 分层：`cli/`（参数解析与输出）→ `services/`（业务编排）→ `domain/`（纯逻辑）
  → `storage/`（唯一允许读写文件的地方）
- 存储：用户家目录下单个 JSON 文件，人类可读可手改
- 时间来源必须可注入（不直接调用系统时钟），保证测试无需 mock 系统时钟
- 退出码语义：0 成功 / 1 参数错误 / 2 运行期错误
- 测试用 pytest，覆盖 domain 与 services；storage 用临时目录
```

**注意这里的写法**：每一条都是**技术决策**，不是需求复述。「存储」那一行是决策；「周报覆盖 ISO 周」那个规则**不在 plan 里**——它在 spec 里，plan 不该重复。

## 2. `plan.md` 的解剖

合格的 `plan.md` 有四块，缺一块就有问题：

| 块 | 内容 | 缺了会怎样 |
|----|------|-----------|
| **架构分层与边界** | 每层的职责、禁止的依赖方向 | 实现时分层形同虚设，`domain/` 里会冒出 `open()` |
| **技术决策** | 选了什么、为什么、代价是什么 | 三个月后没人知道为什么这么选 |
| **数据模型** | 存储 schema、字段、不变量 | 存储格式随手长，事后迁移地狱 |
| **依赖与版本** | 精确到版本，含为什么允许它进来 | agent 一路加库 |

### 重点看「数据模型」这一块

focuslog 的存储 schema 应该长这样：

```json
{
  "version": 1,
  "sessions": [
    {
      "id": "01J...",
      "tag": "reading",
      "started_at": "2026-09-22T09:15:00+08:00",
      "ended_at": "2026-09-22T10:05:00+08:00",
      "duration_minutes": 50
    }
  ],
  "active_session": null
}
```

**这里有三个容易被漏掉、但必须写进 plan 的东西：**

1. **`version` 字段** —— 存储格式的版本。第一版就加，成本是零；等要迁移时再加，成本是数据迁移脚本。
2. **`active_session` 是独立的顶层字段，不在 `sessions` 数组里** —— 因为它有「同时至多一个」这个**不变量**。塞进数组里，这个不变量就没法用结构表达，只能靠代码约定。
3. **`duration_minutes` 是存下来的，不是算出来的** —— 这是有意的决策：跨天会话的归属规则（你在 L03 定的：整个时长计入开始日期）如果每次动态计算，改规则会让**历史数据全部变样**。存下来则历史不变。

> 📌 **这三条是 plan 阶段真正的价值**：它们在 spec 里都不存在（spec 说的是行为），但如果不在这里定下来，实现时就会随手选一个，然后你会在半年后为此加班。

## 3. 可追溯性检查 ⭐ 本节核心

拿到 `plan.md` 后，**逐条过这张表**。这是 plan review 的实质。

### 做法

把 plan 里的每一项技术决策抄成一列，然后对每一项问：**「它服务 spec 里的哪一条？」**

| plan 中的决策 | 服务的 spec 条目 | 判定 |
|--------------|----------------|------|
| `started_at` 用 ISO 8601 带偏移量 | US1: 记录开始时间 | ✅ |
| 时间来源可注入 | 宪法：测试不许 mock 系统时钟 | ✅ |
| `active_session` 顶层字段 | US1: `SESSION_ALREADY_ACTIVE` | ✅ |
| 退出码 0/1/2 语义 | US1: `TAG_REQUIRED` 退码 1 | ✅ |
| **本地缓存层 + TTL 5 分钟** | **❌ 找不到** | 🚨 范围蔓延 |

最后一行就是你要抓的东西。它在 plan 里看起来非常专业——「本地缓存提升性能」——但：

1. spec 里**没有**任何性能要求（focuslog 是本地 CLI，读一个 JSON 文件）；
2. 它引入了**缓存失效**这个全新的复杂度；
3. 它的存在会让 `stop` 之后 `stats` 可能读到旧数据——**直接违背 spec 的验收标准**。

**这就是范围蔓延的典型入口：它披着「专业」的外衣，而且在 plan 阶段最容易被放过。**

处理方式只有两种，没有第三种：

- **删掉**（推荐）
- 或者显式补进 `spec.md`，**承认范围扩大了**

## 4. 顺手写一份 ADR（极简版）

plan 里的决策一旦写下，就不会再有人问「为什么」。给**最贵的那一个决策**写份记录——focuslog 里就是「存储用单个 JSON 文件」。

```markdown
# ADR-001 · 存储用单个 JSON 文件

## 状态
已采纳（2026-09-22）

## 背景
focuslog 需要持久化会话记录。spec 要求：完全本地、单用户、无账号、无网络。

## 决策
用用户家目录下的单个 JSON 文件，人类可读、可手改。

## 代价（必须写）
- 数据量增长后全量读写，O(n)；预计 1 万条会话后开始有感
- 无并发保护：两个进程同时写会丢数据
- 无查询能力：统计靠内存聚合

## 被否决的选项
- **SQLite**：查询与并发都更好，但代价是「记录不再是人类可读可手改的」——
  这与 spec 的「本地优先、可手改」精神冲突，且引入 sqlite3 之外的迁移复杂度
- **CSV**：无法表达嵌套结构（会话 + 活跃会话状态）

## 什么时候该推翻这个决策
- 单文件超过 5 MB
- 出现多进程写入需求（例如编辑器插件）
```

**「代价」和「什么时候该推翻」这两节是 ADR 的灵魂。** 不写代价的 ADR 是宣传材料，不是决策记录。

> L07 会用同样格式写一份更关键的 ADR（并发冲突策略）。现在先熟悉格式。

## 5. `/speckit-tasks`：拆解

```
/speckit-tasks
```

生成 `tasks.md` 后，**先别急着实现**，做两件事。

### ① 好任务的四个标准

| 标准 | 反例 |
|------|------|
| **可独立验证** | ❌「实现统计功能」——怎么算验完？ |
| **依赖明确** | ❌ 任务里没写它依赖存储 schema |
| **改动范围可控** | ❌「实现所有 CLI 命令」 |
| **完成后能立刻跑一次验收** | ❌「重构代码结构」（无验收动作） |

### ② 粒度不均等才是对的

如果你看到所有任务大小都差不多，**说明没真正拆**。真实的任务分布应该长这样：

```markdown
- [ ] T001 定义存储 schema 与读写模块（含 version 字段）        ← 中等
- [ ] T002 domain: 会话时长计算（含跨天归属规则）              ← 小
- [ ] T003 domain: 标签校验（空白字符、长度上限）              ← 很小
- [ ] T004 services: start 编排（含 SESSION_ALREADY_ACTIVE）    ← 小
- [ ] T005 services: stop 编排（含幂等、跨天提示）             ← 中等
- [ ] T006 services: ISO 周边界计算（周一为首日）              ← ⚠️ 大，要拆
- [ ] T007 services: 标签聚合统计 + 稳定排序                    ← 中等
- [ ] T008 cli: Typer 命令与退出码映射                          ← 中等
- [ ] T009 cli: report 的 Markdown 渲染器                       ← 中等
```

**T006 是刻意标出来的**：ISO 周计算有大量边界（年末跨周、闰年、时区），它比其他任务重得多。**一个诚实拆解出来的任务列表，粒度本来就不均匀。**

## 6. 人工重排依赖顺序 ⭐

**这一步不要交给 agent。** 这是`tasks.md` review 的实质内容。

把 agent 给的顺序和你重排后的顺序对比一下。典型差异：

| agent 给的顺序 | 重排后 | 为什么改 |
|--------------|-------|---------|
| T008 CLI → T001 存储 | T001 存储先 | CLI 的退出码映射依赖 services 的异常类型，services 依赖存储 |
| 所有测试放最后 | 测试跟任务同级 | 测试放最后 = 验收标准放最后 = 无法尽早发现偏差 |
| T005 stop 在 T004 start 之前 | start 先 | stop 的幂等测试需要先能创建会话 |
| T006 ISO 周在 T007 统计后 | ISO 周先 | 统计依赖周的归属规则 |

**验收标准**里有一条是「至少一个任务被你有理由地拆得更细」——**T006 就是那个**。把它拆成：

```markdown
- [ ] T006a ISO 周边界：当前日期 → 本周一/周日（含年末跨周）
- [ ] T006b 会话 → 归属日期映射（含跨天规则）
- [ ] T006c 周报数据聚合（按天、按标签）
```

**没发生这件事，说明你在照抄 agent 的输出，而不是在做工程判断。**

## 7. 交付物与验收

### 交付物

1. `plan.md`
2. `tasks.md`（**已被你人工重排过**）
3. `docs/adr/ADR-001-存储选型.md`
4. `notes/L04-可追溯性检查.md` —— 那张「决策 → spec 条目」的表

### 验收清单

**plan**

- [ ] 四项俱全：架构分层、技术决策、数据模型、依赖版本
- [ ] 数据模型里有 `version` 字段
- [ ] 存储 schema 用结构表达了「至多一个活跃会话」这个不变量
- [ ] 每项技术决策都能指回 spec 的某条**或**宪法的某条
- [ ] **至少抓到并处理掉一条范围蔓延**（记在笔记里）
- [ ] ADR 里「代价」和「什么时候该推翻」两节都写了

**tasks**

- [ ] 每个任务都能映射回一条验收标准
- [ ] 任务粒度**明显不均等**（如果都一样大，回去重拆）
- [ ] 顺序被你人工重排过，**至少一个依赖关系与 agent 的原始输出不同**
- [ ] 至少一个任务被你拆成了子任务
- [ ] 测试任务与实际实现**同级**，不是全部堆在最后

### 自测题

1. 为什么 `active_session` 要做顶层字段，而不是放进 `sessions` 数组里标个 `active: true`？
2. 「本地缓存层」在 plan 里看起来很好，为什么在本项目里是错的？判断依据是什么？
3. ADR 里「被否决的选项」这一节，不写会有什么实际损失？

<details>
<summary>答案</summary>

1. 因为「**同时至多一个活跃会话**」是一条不变量。顶层单值字段用**结构**表达了它，写不出两个活跃会话；数组 + 标记则只能靠代码约定去维护，某个分支忘了检查就崩了。**能用数据结构表达的不变量，不要用代码约定表达。**
2. 因为 spec 里没有任何性能要求，而这个决策引入了缓存失效这个新复杂度，并且会让 `stats` 可能读到旧数据——**违背已有的验收标准**。判断依据不是「它好不好」，而是「**它服务哪条要求**」。
3. 三个月后你会重新考虑一遍同样的选项，然后可能做出相反的决定。更糟的是，如果当初否决的理由仍然成立（比如「SQLite 让记录不再可手改」），你会白白浪费一轮调研。**ADR 的价值在于固化「为什么没选」，因为「选了什么」看代码就知道。**

</details>

## 8. 踩坑预警

| 坑 | 症状 | 解法 |
|----|------|------|
| **跳过 plan review** | 代码看起来很对，架构却完全不是你想的 | 黄金法则：**永远不要从 spec 直接跳到 code** |
| **不查可追溯性** | plan 里混入 spec 没要求的东西 | 逐条建「决策 → spec 条目」的表（[AP-9](../reference/anti-patterns.md)） |
| **plan 里重复 spec** | 同一句验收标准在 plan 里又写一遍 | plan 只说「怎么做」；重复会导致两处不一致 |
| **照抄 tasks 顺序** | 没有人工重排 | 重排是必需步骤，不是可选优化 |
| **任务粒度均匀** | 每个任务看起来一样大 | 说明没真拆。找那个「其实很大」的任务再拆 |
| **测试全堆在最后** | 最后一个任务是「补测试」 | 测试与实现同级。否则验收标准放最后 = 偏差留到最后才知道 |
| **不写数据模型版本** | 存储里没有 `version` | 第一版就加，成本为零；事后加要写迁移脚本 |
| **ADR 不写代价** | 只写「我们选了 X，因为 X 好」 | ADR 不是宣传材料。**不写代价的 ADR 不是决策记录** |

## 9. 本节术语

| 术语 | 含义 |
|------|------|
| plan | 技术方案：架构、模型、决策。技术决策的**唯一合法位置** |
| 可追溯性 | 每项技术决策都能回溯到某条规格要求 |
| 范围蔓延 | plan 或实现里出现了 spec 没要求的东西 |
| ADR | 架构决策记录：选了什么、为什么、**代价是什么**、何时该推翻 |
| 任务拆解 | 把 plan 切成可独立验证的原子项 |
| 不变量 | 系统必须始终成立的条件；优先用数据结构表达 |
| 粒度不均等 | 诚实的任务列表特征；均匀的粒度说明没真拆 |

## 10. 下一节预告

你现在有：一份完整的规格、一份可追溯的方案、一份重排过的任务表。

**L05 就一件事：把它实现出来，然后诚实地验收。**

这个练习会直接为 L09 铺路。因为如果连你自己制造的漂移都发现不了，那 CI 门禁就不是可选项，而是必需品。
