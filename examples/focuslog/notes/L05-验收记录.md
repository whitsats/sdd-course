## 3. 漂移演练 ⭐

### 制造的漂移

在**不修改 `spec.md`** 的前提下，改 `src/focuslog/domain/sorting.py`：

```diff
 def duration_sort_key(item) -> tuple[int, str]:
-    return (-item.duration_minutes, item.tag)
+    return (-item.duration_minutes, item.tag.lower())   # 改成忽略大小写
```

**这是一个真实的漂移**：违反了标准 3.5c（`Reading` 应排在 `reading` 前，因为按 Unicode 码点比较）。改动看起来很合理——「忽略大小写排序更符合直觉」——**这正是它危险的原因**。

### 三种途径的真实结果

| 途径 | 做了什么 | 发现了吗 | 原因 |
|------|---------|---------|------|
| **① 跑测试** | `uv run pytest -q` | ⚠️ **部分发现** | `test_sorting.py::test_tie_break_by_tag` 通过了！因为它用的两个标签是 `reading` 与 `coding`，小写比较后顺序不变。**只有 3.5c 那个 `Reading`/`reading` 的用例才会红——而它当时还没写** |
| **② 看代码** | 打开 `sorting.py` 读了 10 行 | ❌ **没发现** | `.lower()` 看起来完全合理。如果没先读过 spec 的 3.5c，这一段读起来毫无问题 |
| **③ 对照 spec 逐条验收** | 打开 `spec.md`，读到 3.5c「按 Unicode 码点」 | ✅ **发现** | spec 白纸黑字写了码点，而代码在做 `lower()`，直接冲突 |

### 结论（写下来）

> **只有「主动对照 spec」能可靠发现它。**
>
> 途径 ① 表面上「部分发现」，但它依赖「恰好写了那条边界测试」——
> 而当时没写，正说明**没有机制保证每条标准都有测试**。
>
> 途径 ② 的失败最有教育意义：代码在孤立看时是自洽的。
> **漂移不是「代码看起来错了」，而是「代码看起来对，但和规格不一致」。**
> 这就是为什么 read code review 抓不住漂移。

**这次演练直接证明了 L09 的必要性**：规格有效，但没有强制力。必须让「对照 spec」这件事自动化。

## 4. 漂移的层级分类

按 L05 第 5 节的三类分流，本次漂移属于：

| 候选层级 | 判断 | 结论 |
|---------|------|------|
| 实现跑偏 | spec 3.5c 明确写了「按 Unicode 码点」，代码在做 `lower()` | ✅ **属于这一类** |
| 规格不清 | 「字典序」在 spec 中已精确定义为「Unicode 码点」 | ❌ 不成立 |
| 规划/拆解有误 | plan D11 已定为 `(-duration, tag)`，tasks T006 也已列明 3.5c 的验收项 | ❌ 不成立 |

**修复**：恢复 `sorting.py`，并**补上缺失的测试**：

```python
def test_tie_break_by_tag_code_point():
    """标准 3.5c：按 Unicode 码点比较，不忽略大小写。"""
    items = [Item("Reading", 60), Item("reading", 60)]
    assert sorted(items, key=duration_sort_key)[0].tag == "Reading"
```

> 📌 注意修复动作有两步：改回实现 + **补测试**。
> 只改回实现是不够的——否则下次同样的漂移仍然抓不住。
> 「补测试」这一步正是把 spec-first 往 spec-anchored 推的动作。
