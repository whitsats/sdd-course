## 1. 概述

为需要提升专注力的开发者提供一个**本地优先**的专注日志工具。

**要解决的核心问题**：一天下来感觉很忙，但说不清时间花在哪了。需要一个几乎无摩擦的方式记录「刚刚专注做了一件事」，并能在一周结束时看到时间去向的分布。

**不解决**：时间管理方法、任务清单、番茄钟式强制提醒、团队可见性。

---

## 2. 用户故事与验收标准

验收标准使用 EARS 句式。关键词保留英文以保持强制性明确（`SHALL` 表示强制，不是建议）。

### US1 · 开始一段专注

**作为**一个准备专注做一件事的开发者
**我想要**用一行命令标记开始并打上标签
**以便**我不用离开终端、不用打断思路就能留下记录

**为什么是这个优先级**：这是全部功能的入口。如果开始一段记录需要超过 5 秒，这个工具就不会被用。

**独立演示**：仅执行 US1 即可看到「新建一条活跃记录」这一完整价值。

#### 验收标准

| # | 标准 |
|---|------|
| 1.1 | WHEN 用户执行 `focuslog start --tag reading` WHILE 当前不存在活跃会话 THE system SHALL 创建一个新会话，记录开始时间与标签 `reading`，以退出码 0 结束，并输出确认信息（含标签与开始时间）。**输出格式见 §2 末的「输出格式规范」，不是「随便」即可。** |
| 1.2 | WHEN 用户执行 `focuslog start --tag reading` WHILE 已存在一个活跃会话 THEN THE system SHALL 拒绝该命令，退出码为 2，输出错误码 `SESSION_ALREADY_ACTIVE`，且**不修改任何已有数据**。 |
| 1.3 | IF 用户执行 `start` 而未提供 `--tag` THEN THE system SHALL 拒绝该命令，退出码为 1，输出错误码 `TAG_REQUIRED`。 |
| 1.4 | IF `--tag` 的值为空字符串、只含空白字符、或长度超过 32 个字符 THEN THE system SHALL 拒绝该命令，退出码为 1，输出错误码 `TAG_INVALID`。 |
| 1.5 | IF `--tag` 的值含除字母、数字、`-`、`_`、`/` 之外的字符 THEN THE system SHALL 拒绝该命令，退出码为 1，输出错误码 `TAG_INVALID`。 |
| 1.6 | WHERE 用户重复执行同一 `start --tag reading`（此时已存在活跃会话）THE system SHALL 每次都以上述 1.2 的规则拒绝，且**原会话的开始时间保持不变**（幂等）。 |

**为什么 1.5 要限制字符集**：标签会被用在周报的分组键与排序键上。允许任意字符会让分组与排序在不同终端/locale 下行为不一致，无法写出稳定测试。

**1.3 与 1.4 为什么不合并**（这条是被审阅追问后补上的）：

实现者很容易把两者合并成一个「参数不对」错误，那**违反本规格**。理由是两者的**修复动作不同**：

| 错误码 | 用户看到的 | 用户该做什么 |
|--------|-----------|------------|
| `TAG_REQUIRED` | 忘了带 `--tag` | 补上 `--tag <名字>` |
| `TAG_INVALID` | 带了但名字不合法 | **改名字**（或删掉多余字符） |

合并成一个码，用户在第二种情况下会得到「缺少 --tag」这种**误导性的提示**，然后反复检查一个并不存在的问题。
**歧义不在于「能不能合并」，而在于规格之前没说清合并是否允许 —— 现在说清了：不允许。**

### US2 · 结束一段专注

**作为**一个刚完成专注的开发者
**我想要**用一行命令收尾并看到这段的时长
**以便**我得到即时反馈、确认记录没丢

**独立演示**：先手工在存储中放入一条活跃会话（或执行一次 start），执行 `stop` 即可看到完整价值。

#### 验收标准

| # | 标准 |
|---|------|
| 2.1 | WHEN 用户执行 `focuslog stop` WHILE 存在活跃会话 THE system SHALL 记录结束时间，输出该会话时长（分钟，向下取整），退出码 0，并将该会话从活跃状态转为已完成。 |
| 2.2 | WHEN 用户执行 `focuslog stop` WHILE 不存在活跃会话 THEN THE system SHALL 拒绝该命令，退出码为 2，输出错误码 `NO_ACTIVE_SESSION`。 |
| 2.3 | WHEN 用户连续执行 `stop` 两次 THE system SHALL 第一次成功结束会话，第二次以 `NO_ACTIVE_SESSION` 拒绝，且**第一次写入的结束时间不被第二次操作修改**。 |
| 2.4 | IF 计算出的会话时长小于 1 分钟 THEN THE system SHALL 将其记为 1 分钟，并在输出中提示发生了取整。 |
| 2.5 | IF 会话的开始时间与结束时间落在**不同的本地日期** THEN THE system SHALL 将该会话的**全部时长**计入**开始时间所在的日期**，并在输出中提示该会话跨越了日期边界。 |

**2.5 的取舍说明**：另一种合理规则是按时间比例拆分到两天。我们选择「全部计入开始日」，理由：规则简单、可预测、且符合「我什么时候开始做这件事」的直觉。**代价是连续跨天工作的时长统计会偏向开始日。**

**2.5 与 3.7 的组合效应（跨周边界）**：

2.5 的规则会产生一个不明显但真实的后果：**一条会话可能归属于上一条 ISO 周，于是在本周周报里「凭空消失」。**

> 场景：周一 23:50 开始，周二 00:10 结束。
> 按 2.5，这 20 分钟全部计入**周一**。
> 那么用户周二执行 `report --week` 时，**不会**看到这 20 分钟（周一属于上一周）。
>
> 如果不处理，用户会认为「记录丢了」，而实际上一切正常。

**处理方式见 3.7**：周报不显示它（保持 2.5 规则的纯粹），但**必须显式提示**存在归属到相邻周的会话。
**「按开始日归属」这个规则的代价必须被输出出来，而不能让用户自己猜。**

### US3 · 查看本周报告

**作为**一个想了解自己一周时间去向的开发者
**我想要**得到一份可读的周报
**以便**调整下一周的时间结构

**独立演示**：清空存储后执行 `focuslog report --week`，应看到空周报而非错误。

#### 验收标准

| # | 标准 |
|---|------|
| 3.1 | WHEN 用户执行 `focuslog report --week` THE system SHALL 输出覆盖**当前 ISO 8601 周**（周一为第一天，周日为最后一天）的 Markdown 报告。 |
| 3.2 | THE system SHALL 在周报中包含：每周的起止日期、每天的会话总时长、每天的会话条数、按标签聚合的时长分布。 |
| 3.3 | IF 当前 ISO 周内不存在任何已完成的会话 THEN THE system SHALL 输出"本周没有记录"，退出码为 **0**（不是错误）。 |
| 3.4 | WHEN 用户执行 `focuslog report --week --json` THE system SHALL 输出机器可读格式，其字段与 3.2 所列内容一一对应，且退出码语义与文本模式相同。 |
| 3.5 | THE system SHALL 在标签分布中按**时长降序**排列；WHEN 两个标签时长相同时 THE system SHALL 按**标签名的字典序升序**（区分大小写，按 Unicode 码点）作为次级排序键。 |
| 3.6 | WHEN 用户执行 `focuslog report --week` WHILE 存在活跃会话 THE system SHALL 正常输出周报，且**不包含该活跃会话**（未结束的会话不计入统计），并在输出末尾提示存在一个进行中的会话。 |
| 3.7 | WHEN 周报范围内存在任何已完成会话，但其归属日期（按 2.5 的规则）落在**相邻 ISO 周** THEN THE system SHALL 在本周报告末尾输出一行提示：`（另有 N 条会话归属到相邻周，未计入本报告）`，其中 N 为条数；WHEN N = 0 THEN THE system SHALL 不输出该行。 |

**3.5 为什么要规定到「Unicode 码点」**：如果只写「字典序」，`reading` 与 `Reading` 的先后在不同实现下会不一致，测试会随机失败。**排序规则不清 = 无法写测试。**

**3.6 为什么要排除活跃会话**：活跃会话的时长在持续增长。如果计入，同一命令在一分钟内执行两次会得到不同结果，无法验收。

**3.7 是怎么来的**：这条不是一开始就有的。它来自一轮外部审阅（见 `notes/L06-LLM审阅记录.md`）——
审阅者在 2.5 与 3.6 之间找到了一个交叉场景，指出规格**没有定义**它。

**这类缺口的特征：它不违反任何一条已有标准，而是两条标准叠加后才浮现的。**
逐条读规格发现不了它，必须「把两条标准放进同一个场景里跑一遍」。

**3.7 的措辞刻意规定了确切文本**（`（另有 N 条会话归属到相邻周，未计入本报告）`）：
不规定文本，测试就只能断言「输出非空」，等于没测。

### US4 · 查看累计统计

**作为**一个想判断自己时间结构是否合理的开发者
**我想要**看到各标签的长期累计时长
**以便**发现「某类事情占用了过多时间」

**独立演示**：仅执行 `focuslog stats` 即可看到完整价值。

#### 验收标准

| # | 标准 |
|---|------|
| 4.1 | WHEN 用户执行 `focuslog stats` THE system SHALL 按标签输出累计时长（仅统计已完成的会话），按时长降序排列。 |
| 4.2 | IF 存在时长相同的标签 THEN THE system SHALL 按标签名的字典序升序作为次级排序键（规则同 3.5）。 |
| 4.3 | IF 系统中不存在任何已完成的会话 THEN THE system SHALL 输出"暂无记录"，退出码为 0。 |
| 4.4 | THE system SHALL 在统计中包含标签的会话条数，格式为「标签名 · 时长 · 条数」。 |
| 4.5 | WHEN 用户执行 `focuslog stats --json` THE system SHALL 输出机器可读格式，字段与 4.4 一致。 |

---

### 输出格式规范（US1–US4 共用）

> **本节是审阅追问后补上的。** 原文只有「输出确认信息（含标签与开始时间）」这种写法 ——
> 它看起来像标准，实际不是：**不同的实现者会写出完全不同的文案，测试无法断言。**
>
> 后果不是「不够好看」，而是：CI 测试只能断言「输出非空」，
> 等于**这些标准实际上没有被测**。

#### 规则一：机器可读的部分有固定格式

凡是被**测试断言**的字段，SHALL 使用下列确切格式，不得增删空格：

| 字段 | 格式 | 例 |
|------|------|-----|
| 时间戳 | ISO 8601 带本地时区偏移，秒级 | `2026-09-22T10:00:00+08:00` |
| 时长 | 整数分钟 + 单位，中间一个空格 | `45 min` |
| 标签 | 单引号包裹 | `'reading'` |
| 错误码 | 方括号包裹，全大写 | `[TAG_REQUIRED]` |

#### 规则二：每个命令的确认信息模板

| 命令 | 模板（`<>` 为占位） | 对应标准 |
|------|-------------------|---------|
| `start` | `[OK] started <tag> at <time>` | 1.1 |
| `stop` | `[OK] stopped <tag>, duration <duration>` | 2.1 |
| 跨天提示（附加行） | `[NOTE] session crossed date boundary; all <duration> counted to <date>` | 2.5 |
| 活跃会话提示（附加行） | `[NOTE] session in progress: <tag>` | 3.6 |
| 跨周归属提示（附加行） | `（另有 N 条会话归属到相邻周，未计入本报告）` | 3.7 |
| 错误 | `[<ERROR_CODE>] <human message>` | 1.3 / 1.4 / 1.5 / 1.2 / 2.2 |

#### 规则三：附加行不影响退出码

所有 `[NOTE]` 附加行 SHALL 输出到 **stdout**（而非 stderr），且 SHALL **不改变退出码**。

#### 规则四：`--json` 模式下不输出任何人类可读文本

WHEN 使用 `--json` THEN THE system SHALL 只输出一个 JSON 对象到 stdout，
**不包含** `[OK]` / `[NOTE]` 等前缀，也 SHALL 不包含附加行。

> 📌 **规则四容易漏**：很自然的实现是把提示打在 JSON 前面，
> 然后任何 `focuslog report --week --json | jq` 都会解析失败。
> **同一个命令的两种输出模式不能用同样的「顺便打印一句」逻辑。**

#### 为什么规定到「确切文本」不是过度约束

因为这四个模板是**用户接口**，不是内部实现。
改动它们会破坏两类东西：① 用户的脚本 ② 我们的契约测试。
**所以它们该被冻结在规格里，改的时候要走规格变更流程（见 L09）。**

## 3. 非目标（Out of Scope）

以下**明确不在本次范围内**。任何实现中出现这些能力都属于范围蔓延：

- 多用户 / 账号 / 登录 / 云同步
- GUI 或 TUI（仅命令行输出）
- 番茄钟式强制提醒或终端通知
- 编辑或删除已完成的历史会话
- 按自定义日期区间查询报告（仅 `--week`）
- 导出为除 Markdown 与 JSON 之外的格式
- 跨设备统计合并
- 标签的层级结构（`a/b` 只是一个普通字符串，不是层级）

## 4. 边界条件汇总

以下是全部边界条件的集中清单，供实现与验收时逐项对照：

| 场景 | 期望行为 | 对应标准 |
|------|---------|---------|
| `start` 时已有活跃会话 | 拒绝，退码 2，`SESSION_ALREADY_ACTIVE` | 1.2 |
| `start` 无 `--tag` | 拒绝，退码 1，`TAG_REQUIRED` | 1.3 |
| `start` 标签非法 | 拒绝，退码 1，`TAG_INVALID` | 1.4 / 1.5 |
| 重复 `start` | 幂等拒绝，开始时间不变 | 1.6 |
| `stop` 时无活跃会话 | 拒绝，退码 2，`NO_ACTIVE_SESSION` | 2.2 |
| 重复 `stop` | 第二次拒绝，首次结束时间不变 | 2.3 |
| 时长不足 1 分钟 | 记为 1 分钟，输出提示 | 2.4 |
| 会话跨天 | 全部计入开始日，输出提示 | 2.5 |
| 周报区间内无记录 | 输出提示，退码 **0** | 3.3 |
| 标签时长相同 | 按名称 Unicode 码点升序 | 3.5 / 4.2 |
| 周报时有活跃会话 | 排除该会话，末尾提示 | 3.6 |
| 无任何已完成会话 | 输出"暂无记录"，退码 0 | 4.3 |

## 5. 术语

| 术语 | 定义 |
|------|------|
| 会话（session） | 一次有开始时间、结束时间、标签的专注记录 |
| 活跃会话（active session） | 已记录开始时间但尚未记录结束时间的会话。**同一时刻至多一个**。 |
| ISO 周 | ISO 8601 定义的周，周一为第一天。第 1 周是包含当年第一个周四的那一周。 |
| 标签（tag） | 用户为会话打的一类标记，如 `reading`。非层级结构。 |

## 6. 成功标准（可验证）

- [ ] 从「想起来要记录」到「完成开始记录」的操作步骤 ≤ 1 条命令
- [ ] 全部 4 个用户故事可以**各自独立**演示，无需先执行其他故事
- [ ] 上述「边界条件汇总」表中**每一行**都有对应的验证记录
- [ ] 所有错误输出都包含机器可读的错误码
