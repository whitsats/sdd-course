# focuslog —— 项目 A · spec-first

> **一个记录专注会话的命令行工具。** `start` / `stop` / `report` / `stats` 四个命令，
> 本地 JSON 存储，无网络、无数据库、无并发。
>
> 它存在的唯一目的是**让因果链最短**：从规格里的一句话，到测试里的一个断言，
> 到代码里的一行，中间不隔任何框架和抽象。**你不是来学写 CLI 的，是来学「一句话
> 怎样变成一行代码」的。**

## 这个项目演示什么

**spec-first** —— 三级成熟度里的第一级（见 [L01](../../lessons/01-why-sdd.md)）：

> 规格写全了、可测、有映射表，**但没有强制门禁**。
> 代码偏离规格时，**没人报警**。发现它的唯一方式是有人去比对。

这不是「做得不够好」，而是**刻意的起点**。你要先亲手体验「没有强制力会怎样」，
才理解 L07/L09 为什么值得花那么多力气。L05 让你亲手制造一次漂移，然后证明
**跑测试发现不了、看代码发现不了、只有逐条对照规格才能发现**。

## 为什么用 Python

不是因为 Python 适合做 CLI（虽然是的），而是因为：

| 理由 | 说明 |
|------|------|
| **因果链最短** | 一条 `US1.2` → 一个 `pytest` 断言 → 一个 `raise`。没有类型体操、没有依赖注入容器 |
| **测试即文档** | `test_cli_start.py::test_start_rejected_when_active` 这个名字本身就是验收标准 |
| **错误可枚举** | 错误码与退出码是一等公民（`errors.py`），正好对应规格里的错误码表 |
| **分层边界可机械检查** | `domain/` 不许 import IO —— 于是 `scripts/check-layer-boundary.sh` 有了真实对象 |

## 三个值得单独看的地方

**① 第 23 条标准是外部审阅挖出来的。**
前 22 条都是人写的。第 23 条（`AC 3.7`）来自一次模型对抗式审阅，它发现：`US2.5` 规定
跨天会话计入**开始日**，`US3.6` 规定周报**排除**活跃会话 —— 两条单独看都对，
叠加后出现了「周一 23:50 开始、周二 00:10 结束的会话，在周二看周报时凭空消失」。
**逐条读规格发现不了，`/speckit-analyze` 也发现不了**，必须把两条放进同一个场景跑一遍。

**② 边界类标准占了 48%（11/23）。**
如果只看主路径，这 11 条一条都不会存在 —— 而它们恰好是上线后最常出事的地方。
这是 clarify 阶段主动穷举异常分支的直接结果。

**③ 映射表里的数字是脚本实测的，不是手写的。**
我最初在正文里手数成 21，被 `check-spec-coverage.sh` 抓了出来。
**人的手数会错，脚本不会** —— 这就是把检查机械化的全部理由。

## 怎么验证

```bash
# 覆盖率：spec 的条数 vs 映射表的行数，必须相等
bash scripts/check-spec-coverage.sh examples/focuslog

# 分层边界：本项目尚未实现，脚本会明确跳过而不是假装通过
bash scripts/check-layer-boundary.sh examples/focuslog py
```

第二条的输出值得注意：

```
· 跳过：examples/focuslog 下没有 src/ 目录（该项目目前只有规格，尚未实现）
  分层边界检查的对象是实现，不是规格 —— 实现出现后本检查自动生效。
```

**「跳过」和「通过」是两件事。** 把两者混为一谈的门禁会在你没有实现时就给你绿灯 ——
而一个没有对象的绿灯，是这个仓库里最讨厌的东西。
