# ADR-001 · 存储使用单个 JSON 文件

> **本文件是 L04 的完整参考产出。** 对照重点：**「代价」与「什么时候该推翻」两节是 ADR 的灵魂。**

---

## 背景

spec 明确要求存储**人类可读、可手改**（术语表与成功标准均提及），且约束「完全本地、单用户、无账号、无网络」。

规模预期：个人使用，每天 3–8 条会话，一年约 2000 条，单条约 200 字节。

宪法规定生产依赖仅允许 Typer，且存储单文件超过 5 MB 时需重新评估。

---

## 决策

使用**用户数据目录下的单个 JSON 文件** `sessions.json`：

- Windows：`%LOCALAPPDATA%\focuslog\sessions.json`
- 其他：`$XDG_DATA_HOME/focuslog/sessions.json`（回退 `~/.local/share/focuslog/sessions.json`）

写入采用**原子替换**（写临时文件后 `os.replace`），避免崩溃时留下半截文件。

---

## 代价

这一节必须诚实。以下每一项都是真实成本：

1. **全量读写，复杂度 O(n)。** 每次 `start`/`stop` 都要读整个文件再写回。2000 条时约 400 KB，可接受；**10000 条后开始有感**（宪法已设 5 MB 触发线）。

2. **无并发保护。** 两个进程同时写会丢数据（后写者覆盖先写者）。`os.replace` 只保证不出现半截文件，**不保证合并写入**。这是一个**已知且被接受的**缺陷。

3. **无常规查询能力。** 按标签统计、按周过滤全部在内存里做。数据量增长后统计会变慢。

4. **依赖 JSON 解析的健壮性。** 用户手改导致格式错误时，整个工具不可用（我们选择报错而不是重建，见宪法第 4 条）。

5. **`os.replace` 在 Windows 上的行为限制。** 替换目标文件被其他进程打开时可能失败。目前通过「写入重试 3 次、间隔 50ms」缓解，非彻底解决。

---

## 被否决的选项

### SQLite

**支持理由**：查询能力、并发安全（WAL 模式）、事务、无需全量读写。技术上明显更优。

**否决理由**：
- **直接违背 spec 的核心要求。** spec 明确要求存储「人类可读、可手改」。SQLite 文件是二进制格式，用户**无法用编辑器查看或修正**数据。
- 与「本地优先、无依赖」的定位冲突：虽然 `sqlite3` 在标准库中，但引入 schema 迁移、连接管理、事务边界会显著增加实现复杂度——而当前规模（2000 条）完全不需要。
- **文档里必须记下这一点**：如果将来有人提议迁到 SQLite，要让他知道**这不是被忽略的选项，而是被有意识地否决的**，否决理由与「用户可手改」这条产品定位绑定。

### CSV

**否决理由**：无法表达嵌套结构。数据模型含 `sessions` 数组与独立的 `active_session` 对象，CSV 需要两张表加关联，反而比 JSON 复杂，且失去「单文件可整体复制/备份」的优势。

### 无存储（仅内存 / 环境变量）

**否决理由**：`report --week` 与 `stats` 本质是跨会话的历史统计，无持久化则核心价值不存在。

### 每会话一个文件（`sessions/2026-09-22-001.json`）

**否决理由**：可读性更好且避免全量读写，但目录会膨胀到几千个文件，`stats` 要遍历全部文件，反而更慢；且「单文件可备份」的优势丢失。

---

## 什么时候该推翻这个决策

以下是**具体、可观测的触发条件**，不是「必要时重构」：

| 触发条件 | 触发后该做什么 |
|---------|--------------|
| 存储单文件超过 **5 MB**（宪法已设线） | 重新评估，考虑按年分片为多个 JSON 文件（保留可读性） |
| 出现**多进程写入**需求（如编辑器插件、系统托盘程序） | 必须上锁或换 SQLite；当前方案会丢数据 |
| `stats` 命令 P95 超过 **500ms** | 引入索引文件或换存储；此时数据量已不在设计范围内 |
| 出现跨设备同步需求 | 存储层需重构，但那已是新产品范畴（当前非目标） |
