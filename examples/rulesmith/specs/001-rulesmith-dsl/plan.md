# 技术方案 · rulesmith 生成器

> **本文件是 L10 的关键对照产出。** 它回答一个具体问题：
>
> **「让 agent 写生成器，而不是写成品」到底长什么样？**
>
> 如果你的 `plan.md` 里出现的是「实现 lexer / parser / validator」，
> 那你已经掉进 L10 §4 的坑了——见下面 §1。

**对应规格**：`specs/001-rulesmith-dsl/spec.md`
**最后更新**：2026-09-23

---

## 1. ⛔ 最重要的一节：本方案的实现对象是什么

**本方案不实现 DSL 本身。本方案实现「从 spec.md 生成 DSL 实现」的程序。**

| | ❌ 错误方案 | ✅ 正确方案 |
|---|---|---|
| 交付物 | `src/lexer.ts`、`src/parser.ts`、`src/validator.ts`（手写） | `tools/generator/`（手写）+ `src/generated/*`（产出） |
| 改语法要做什么 | 找到对应代码，手改三处 | 改 `spec.md` 的 ```ebnf``` 块，跑 `pnpm generate` |
| 语法定义在哪 | 分散在三个手写文件里 | **只有一处**：`spec.md` |
| 漂移可能 | 四处（spec / lexer / parser / validator） | 零处（产物由 produce 而来，CI 校验 diff） |

### 一眼验证的方法

> **改 `spec.md` 的 EBNF 一个词 → 跑 `pnpm generate` → 产物变了吗？**
>
> - 变了 → 你拿到的是生成器 ✅
> - 没变 → 你拿到的是手写成品（或者生成器没读 spec）❌

**这个验证必须做，而且必须用真改真跑。** 光看代码判断不出来——
一个写得漂亮的 `parser.ts` 看起来可能是生成的，也可能是手写的。

## 2. 目录结构

```
rulesmith/
├── specs/001-rulesmith-dsl/spec.md      ← 唯一的真相源
├── tools/generator/                     ← 手写：生成器（spec-as-source 的递归边界）
│   ├── index.ts         CLI 入口：读 spec → 发射 → 写盘 / --check
│   ├── ebnf.ts          EBNF 词法与语法解析 → 产生式 AST
│   ├── spec-reader.ts   从 spec.md 提取 EBNF 块 / 错误码表 / 产物表
│   └── emit.ts          四类产物的发射器
├── src/generated/                       ← 产出：⛔ 禁止手改
│   ├── lexer.ts
│   ├── parser.ts
│   └── validator.ts
├── docs/rules-dsl.md                    ← 产出：面向业务方的文档
├── tests/generator.spec.ts              ← 手写：生成器自己的测试
└── schema.json                          ← 手写：输入数据的 shape（不属于 DSL 语法）
```

### 为什么 `tools/generator/` 在 `tools/` 而不在 `src/`

因为它是**开发工具**，不是产品代码：它不进产物的依赖图，不参与运行时，只在构建期跑。
放在 `src/` 会被误认为产品的一部分。

## 3. 数据流

```
             specs/001-rulesmith-dsl/spec.md
                          │
        ┌─────────────────┼──────────────────┐
        ▼                 ▼                  ▼
   ```ebnf``` 块      错误码表           产物表
        │                 │                  │
        ▼                 │                  │
   ebnf.ts                │                  │
  （解析产生式、          │                  │
    分类终结符）          │                  │
        │                 │                  │
        └────────┬────────┴──────────────────┘
                 ▼
              emit.ts
     ┌───────────┼───────────┬────────────┐
     ▼           ▼           ▼            ▼
 lexer.ts    parser.ts   validator.ts  docs/rules-dsl.md
（关键字表  （产生式表   （错误码表     （语法速查
  + 扫描器）  + 通用回溯    + 语义检查     + 错误码表
             解析器）      骨架）         + 写法对照）
```

**注意 `emit.ts` 的四个发射器中有三个的输出是「表 + 固定的运行时」**：
- `lexer.ts` = 关键字/符号表 + 一个固定的扫描器
- `parser.ts` = `PRODUCTIONS` 表 + 一个**表驱动回溯解析器**
- `validator.ts` = 错误码/运算符分类表 + 语义检查骨架
- `docs/rules-dsl.md` = 纯文本

**为什么不直接发射「每个产生式一个函数」的递归下降代码？**

那是更「教科书」的做法，但对本项目的代价：

| 方案 | 生成器复杂度 | 产物可读性 | 改 EBNF 的表现 |
|------|------------|-----------|---------------|
| 发射独立函数 | 高（要处理左递归消解、前视、优先级） | 高 | 函数增删，diff 清晰 |
| **发射数据表 + 通用解析器** | **低** | **低（产物是数据）** | **表变化，diff 小** |

我们选了后者：**生成器简单 400 行 vs 复杂上千行**，而产物可读性对「禁止手改」的文件不重要。

**代价（必须记录）**：通用回溯解析器**只覆盖语法，不覆盖语义**。
字段路径解析、类型检查、冲突检测仍需针对本语法的访问器 —— 见 `validator.ts` 里的 TODO。
这是 spec §7「被否决的设计 ③」的延伸：**当语义检查变复杂时，就该考虑换成真正的 parser generator。**

## 4. 技术决策与可追溯性

| # | 决策 | 服务的 spec / 宪法条目 | 判定 |
|---|------|---------------------|------|
| D1 | 用 Node 原生 TS 运行（无需构建步骤） | 宪法「零构建依赖」；Node 24 支持类型擦除 | ✅ |
| D2 | 零第三方依赖 | 宪法「依赖最小化」 | ✅ |
| D3 | 生成器读取 **spec.md 本身**（不另建语法文件） | spec §2「生成器直接读取本块」 | ✅ |
| D4 | 用「数据表 + 通用解析器」而非发射函数 | 生成器复杂度可控（§3） | ✅ |
| D5 | 产物中**不含时间戳** | spec §6 第 4 条（幂等性） | ✅ |
| D6 | JSON 序列化按键排序 | 同上（确定性） | ✅ |
| D7 | 统一 LF 换行 | 同上（Windows 下 CRLF 会造成假差异） | ✅ |
| D8 | 内容未变则不写盘（保留 mtime） | 减少无意义 diff | ✅ |
| D9 | `--check` 模式（只校验不写盘） | CI 需要；也是「先检测再生成」的前提 | ✅ |
| D10 | 终结符分类用启发式而非 spec 标注 | 不给规格增加负担（见下） | ⚠️ 有代价 |

### D10 是唯一一条「有代价」的决策 —— 诚实标注

EBNF 里的终结符混了**两个层级**：

- **词法层**（token 级）：`"rule"` `"then"` `">="` —— 需要进关键字/符号表
- **字符层**（char 级）：`"_"` `'"'` `letter` `digit` —— 它们是扫描器的输入字符，不是 token

我们**不要求 spec 标注层级**（那会增加写规格的负担），而用三条启发式：

| 规则 | 内容 |
|------|------|
| A | 只有**以字母开头**的终结符才算关键字 → 修掉 `"_"` 被误判为关键字的 bug |
| B | 等于 `"` / `'` 的是字符串定界符，不进符号表 |
| C | **单字符且全为标识符字符**的终结符是字符级终结符，两个表都不进 |

**这个 bug 是真发生过的**：第一版 `"_"` 出现在 `KEYWORDS` 里（因为 `_` 匹配了标识符字符类）。
是**跑生成器看输出**时发现的，不是看代码发现的。

**代价**：如果将来 EBNF 里出现一个「单字符但确实是 token」的终结符（比如把 `;` 当语句结束符——
`;` 是单字符但不在标识符字符类里，所以规则 C 不会误伤它），启发式会出错。
**触发条件**：出现单字符的字母数字类 token。届时改为在 spec 里加一个 `lexer: token|char` 标注列。

## 5. 生成器的测试

`tools/generator/` 是手写代码，**所以它需要自己的测试**。见 `tests/generator.spec.ts`：

| 测试 | 类型 | 为什么必须有 |
|------|------|------------|
| 幂等性：连续两次生成，输出字节相同 | **关键** | 不幂等 → CI 随机红灯 → 门禁被关掉 |
| 确定性：相同输入产出相同 `PRODUCTIONS` 表 | 关键 | 依赖 `Object.keys` 顺序会随机化输出 |
| 无时间戳：产物中不含当前年份/日期 | 关键 | 最容易被忽略的幂等性破坏源 |
| EBNF 解析：给定 EBNF → 预期产生式数量与终结符集合 | 单元 | 解析器自身的正确性 |
| 终结符分类：`"_"` 不在关键字表、`"` 不在符号表 | **回归** | 固定上面那个真实 bug |
| 错误码表解析：改列名应报错，改措辞不应报错 | 契约 | 保护「列名是契约，措辞不是」的设计 |

**「回归」那一行值得注意**：它不是「测试一个功能」，而是**把一次真实 bug 固化下来**。
这类测试最便宜，也最常被跳过。

## 6. CI 门禁

```yaml
# .github/workflows/sdd-gate.yml 摘要
- name: 生成物可复现性   # 阻断：先检测手改，再重新生成，再校验 git 一致
  run: bash scripts/verify-generated.sh . "pnpm generate" src/generated

- name: 生成物一致性（快速路径）  # 阻断：不需要 git 的比较
  run: node tools/generator/index.ts --check

- name: 生成器自身测试    # 阻断
  run: pnpm vitest run tests/generator.spec.ts

- name: 校验器无假阴性（属性测试）  # 阻断
  run: pnpm vitest run tests/validator.spec.ts
```

> ⚠️ **第一条与第二条的关系**：`--check` 是快路径（只比较，不写盘），
> `verify-generated.sh` 是慢路径（含 git 校验与「生成结果是否已提交」）。
> **两条都要保留** —— `--check` 抓不到「改了 spec 但没提交产物」，因为它不走 git。

完整文件见 `examples/rulesmith/.github/workflows/sdd-gate.yml`。

## 7. 本方案**未包含**（与 spec 非目标对齐）

- 可视化规则编辑器（spec 非目标）
- 规则的运行时热更新（spec 非目标）
- 用 ANTLR / 现成 parser generator（spec §7 被否决的设计 ③；当前语法严格 LL(1)，自研够用）
- 完整的语义检查实现 —— **这是已知的未完成部分**，见 §3 末尾与 `validator.ts` 的 TODO
- `schema.json` 的自动生成（它描述数据 shape，不属于 DSL 语法，由人手写）
