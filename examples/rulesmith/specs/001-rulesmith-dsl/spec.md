# feature 规格 · rulesmith 报表规则 DSL

> **本文件是 L10 的核心参考产出，也是本项目唯一的真相源。**
>
> ⚠️ **注意本文件与前面两个项目的根本差别**：
> `examples/focuslog` 和 `examples/taskflow` 的 spec 是**给人读的规格，驱动人写代码**；
> 本文件的 spec **本身是生成器的输入** —— `tools/generator` 会读取下面的 ```ebnf``` 代码块与错误码表，
> 产出 `src/generated/` 下的四个文件。**人改的只有本文件。**
>
> 这就是 spec-as-source：**规格不是"描述代码"，规格就是代码的来源。**

**Feature 分支**：`001-rulesmith-dsl`
**状态**：已确认
**生成命令**：`pnpm generate`

---

## 1. 概述

报表系统需要一套规则 DSL，让业务方能声明「什么条件下给一条记录打什么标记 / 升级给谁处理」，
但**不需要接触代码**。

**要解决的核心问题**：报表规则每周都在变，每次改动都要开发介入、走发布流程。
DSL + 生成器把「加一个字段」变成**改一行规格**。

**不解决**：可视化规则编辑器、规则的运行时热更新、规则的版本对比与回滚。

## 2. 语法（EBNF）⭐ 生成器直接读取本块

**以下代码块是生成器的输入。** 改动它 → `pnpm generate` → 词法/语法/校验/文档四件套自动更新。

```ebnf
(* ─────────────────────────────────────────────────────────────
   语法层：产生式 → 语法分析器
   全小写名字的产生式都进 PRODUCTIONS 表。
   ───────────────────────────────────────────────────────────── *)
program       = { rule } ;
rule          = "rule" IDENT "{" "when" condition "then" action "}" ;
condition     = or_expr ;
or_expr       = and_expr { "or" and_expr } ;
and_expr      = comparison { "and" comparison } ;
comparison    = field operator value
              | "(" or_expr ")" ;
field         = IDENT { "." IDENT } ;
operator      = ">" | ">=" | "<" | "<=" | "=" | "!=" | "in" | "notin" ;
value         = NUMBER | STRING | list ;
list          = "[" [ value { "," value } ] "]" ;
action        = "flag" STRING [ "escalate" "to" STRING ] ;

(* ─────────────────────────────────────────────────────────────
   词法层：全大写名字 → 扫描器 token 类型，**不进** PRODUCTIONS
   语法里引用它们 = 「这里放一枚该类型的 token」
   ───────────────────────────────────────────────────────────── *)
IDENT         = letter { letter | digit | "_" } ;
NUMBER        = digit { digit } [ "." digit { digit } ] ;
STRING        = '"' { any_char } '"' ;
```

### EBNF 方言的三条约定

**约定 ①：全大写名字的产生式属于词法层。**

`IDENT` / `NUMBER` / `STRING` 描述的是**扫描器怎么切出一个 token**，不是语法规则。
它们**不进**语法分析器的产生式表；语法里引用它们的意思是「此处放一枚该类型的 token」。

> ⚠️ **这条约定是拿真实 bug 换来的，值得单独记住：**
>
> 第一版生成器把 `IDENT` 也当成语法产生式发射了。于是 `PRODUCTIONS["IDENT"]` 指向一个
> 引用了 `letter` 的产生式 —— 而 `letter` 并不存在（它是字符类，不是产生式）。
> 结果是**生成器成功退出、产物看起来正常、但生成的 parser 在运行期抛
> `未定义的产生式: letter`**。
>
> 这个 bug 的性质正是 L10 想让你体会的：**生成器的失效模式不是「输出错了」，
> 而是「输出了一份运行期才炸的东西」**。因此现在生成器会在**构建期**就拒绍这种输入。

**约定 ②：预定义字符类是 EBNF 方言的固定部分。**

| 字符类 | 含义 |
|--------|------|
| `letter` | ASCII 字母 `A-Za-z` |
| `digit` | ASCII 数字 `0-9` |
| `any_char` | 除换行外的任意字符 |
| `ws` | 空白（空格 / 制表 / 换行） |

字符类**只能出现在词法层产生式里**，出现在语法层会在构建期报错。

**约定 ③：token 类型的名字必须能被扫描器实现。**

`IDENT` → `ident`、`NUMBER` → `number`、`STRING` → `string`（名字小写即扫描器种类）。
扫描器只支持这三种；若 spec 声明了别的（如 `BOOL`），生成器在**构建期**报错，
而不是发射一份运行期才炸的代码。

### 一段合法输入

**本块也被注入到 `docs/rules-dsl.md`** —— 使用文档里的示例与语法来自同一处，永不脱节。
同时 `tests/validator.spec.ts` 会逐字拿本块去跑生成的解析器：
**规格自带的例子过不了自己的语法，构建就失败。**

```rulesmith
rule high_value {
  when amount > 10000 and region in ["APAC", "EMEA"]
  then flag "high_value" escalate to "finance-review"
}
```

### 生成器从本块推导出什么

| EBNF 中的元素 | 生成器推导出的东西 |
|--------------|-----------|
| 引号内的终结符（`"rule"` / `"then"` / `"or"` / `"notin"` …） | 词法分析器的关键字与符号表 |
| 大写产生式（`IDENT` / `NUMBER` / `STRING`） | 词法分析器的 token 类型 |
| 每个产生式一条规则 | `PRODUCTIONS` 里的一条表项 |
| `{ }` 重复 / `[ ]` 可选 / `\|` 选择 / `( )` 分组 | 表项内部的操作符节点（repeat / optional / alt / seq） |

> ⚠️ **本表只规定「推导关系」，不规定「产物的代码形态」。**
> 生成器选择把产生式发射为**数据表 + 通用的表驱动回溯解析器**，而不是「每个产生式一个函数」。
> 这个取舍的理由与代价记录在 `plan.md` §3 与决策 D4。
>
> 📌 **这处措辞是被修正过的**：本表最初写的是「生成一个递归下降函数」——
> 那是**规定了实现策略**，而 §2 的其余部分只描述语法。
> 生成器按「表驱动」实现后，规格与实现之间就出现了**真实的漂移**：
> 规格说递归下降，产物里没有递归下降函数。
> 修正的方式是**让规格只描述不可变的推导关系**（哪些输入决定哪些产物），
> 把可变的实现策略留给 `plan.md` —— 因为策略会变，而「EBNF 决定词法表」不会变。
>
> **这个案例值得记住：规格里混进实现策略，是漂移最常见的源头之一。**

> 📌 **注意 `notin` 的写法：是一个词，不是 `not in` 两个词。**
> 这是刻意的——它让词法分析器只需一个关键字表，不必处理「两个 token 组成一个运算符」的
> 前视逻辑。**代价是 DSL 的可读性略差**（业务方会想写 `not in`）。
> 这个取舍见 §7 的「被否决的设计」。

## 3. 语义

- THE system SHALL 将 `field` 解析为输入记录的字段路径，`a.b` 表示嵌套访问。
- WHEN `field` 引用的路径不存在于输入 schema 中 THE system SHALL 在**校验期**（而非运行期）报告 `UNKNOWN_FIELD`。
- IF `operator` 为 `in` 或 `notin` 而其右值不是列表 THEN THE system SHALL 报告 `TYPE_MISMATCH`。
- IF `operator` 为 `>` `>=` `<` `<=` 而其右值不是数字 THEN THE system SHALL 报告 `TYPE_MISMATCH`。
- IF `operator` 为 `=` 或 `!=` 而其右值与左值类型不同 THEN THE system SHALL 报告 `TYPE_MISMATCH`。
- IF 两条规则的 `escalate to` 目标不同，且其 `condition` 可能同时成立 THEN THE system SHALL 报告 `PRIORITY_CONFLICT`，并指出冲突的两个规则名。
- IF 两个规则使用了相同的 `IDENT`（规则名） THEN THE system SHALL 报告 `DUPLICATE_RULE`。
- **THE system SHALL 保证校验器不产生假阴性**：任何通过校验的规则集，在运行期都不会因语法或类型原因出错。

**最后那条是项目的核心不变量。** 它把「校验器要可靠」这个模糊要求变成了可测试的强命题——
见 `tests/validator.spec.ts` 的属性测试（随机生成规则集 → 若校验通过 → 运行期必不抛语法/类型错误）。

## 4. 错误码（生成器直接读取本表）

**表格的列名固定为 `错误码 | 触发条件 | 报告位置`**，生成器据此产出校验器的错误类型与消息模板。

| 错误码 | 触发条件 | 报告位置 |
|--------|---------|---------|
| `PARSE_ERROR` | 不符合 §2 的语法 | 行号 + 列号 |
| `UNEXPECTED_EOF` | 输入在规则中途结束 | 行号 |
| `UNKNOWN_FIELD` | 字段路径不在输入 schema 中 | 规则名 + 字段路径 |
| `TYPE_MISMATCH` | 运算符与值类型不匹配 | 规则名 + 运算符 + 实际类型 |
| `PRIORITY_CONFLICT` | 两条 escalate 目标不同的规则可能同时命中 | 两个规则名 |
| `DUPLICATE_RULE` | 两个规则用了相同名称 | 规则名 + 两处行号 |
| `UNKNOWN_OPERATOR` | 运算符不在 §2 定义的集合内 | 行号 |
| `UNDEFINED_RULE_REF` | 保留：`action` 引用了不存在的规则 | 规则名 |

## 5. 输入 schema

规则校验需要知道「有哪些字段」。输入 schema 以独立文件提供（**不属于本 DSL 的语法**，
因为它是数据 shape 而不是规则语言的一部分）：

```json
// schema.json
{
  "amount":   "number",
  "region":   "string",
  "user": {
    "tier":   "string",
    "age":    "number"
  },
  "tags":     "string[]"
}
```

- WHEN 校验器收到规则集与 schema THE system SHALL 对照 schema 检查全部 `field` 引用。
- IF `field` 的**中间路径**不是对象（例如 `amount.x`，而 `amount` 是 number）
  THEN THE system SHALL 报告 `UNKNOWN_FIELD`，并指出类型冲突的那一段。

## 6. 生成产物 ⛔ 禁止手改

| 产物 | 内容 |
|------|------|
| `src/generated/lexer.ts` | 词法分析器：关键字表 + token 扫描 |
| `src/generated/parser.ts` | 语法分析器：产生式表 + 表驱动回溯，语法全部来自 §2 |
| `src/generated/validator.ts` | 语义校验器：§3 全部规则 + §4 全部错误码 |
| `docs/rules-dsl.md` | 面向业务方的 DSL 使用文档（含从 §2 自动生成的语法速查） |

**以下四条是硬约束：**

1. 以上四个文件由 `pnpm generate` 产出，**任何人不得手工编辑**。
2. 每个生成文件的头部 SHALL 包含 `DO NOT EDIT` 标记，并注明应修改 `spec.md` 后重新生成。
3. CI SHALL 重新生成并校验 `git diff` 为空；非空即失败。
4. 生成器 SHALL 是**幂等**的：同一份 spec 连续生成两次，输出**字节级相同**。

### 生成器自身的约束（它是手写代码）

- `tools/generator/` 是**手写**的，需要自己的单元测试
- 生成器 SHALL 有 owner（本项目为项目作者）
- 生成器 SHALL 有幂等性测试（见 `tests/generator.spec.ts`）

> 📌 **第 4 条与「生成器自身约束」这两块，是 spec-as-source 的递归边界。**
> 总有一层是人写的——本项目里就是 `tools/generator/`。
> **关键不是消除手写，而是把人的手写工作推到变更频率最低的那一层。**

## 7. 被否决的设计（记录理由，避免被重复提议）

### ① `not in` 两个词 → 改为 `notin` 一个词

**否决理由**：需要前视两个 token 才能判定运算符。递归下降手写还好，但**生成器要多产出一层前视逻辑**，
而这个逻辑无法从 EBNF 直接推导——它属于「实现技巧」，不属于语法。

**代价**：DSL 可读性下降。业务方会想写 `not in`。

**什么时候该推翻**：如果业务方反馈 `notin` 难以记忆，可以加一个**词法层的别名映射**
（把 `not` + `in` 在词法阶段合并），而不改语法——**注意这仍然是改 `spec.md`，不是改生成产物。**

### ② 规则支持 `priority` 数字显式指定顺序 → 改为靠 `PRIORITY_CONFLICT` 静态检查

**否决理由**：显式 priority 让冲突变成「可被数字掩盖的问题」——两条规则冲突时，用户加个 `priority: 5`
就看起来解决了，但**没人知道为什么是 5**。静态冲突检查强迫用户**消除冲突本身**。

**代价**：无法表达「这两条规则确实会同时命中，我就是想要 A 优先」的合法场景。

**什么时候该推翻**：出现第一个「合理的、有意为之的重叠规则」需求时。

### ③ 用 ANTLR / 现成 parser 生成器 → 自研生成器

**否决理由**：引入 ANTLR 意味着生成物是 **ANTLR 的产物**，我们要改语法就得学 ANTLR 的语法与工具链；
且生成物包含运行时依赖，体积大。自研生成器约 400 行，**改语法只改 `spec.md` 的 EBNF 块**。

**代价**：自研生成器有 bug 风险，且不支持复杂的前视/优先级声明。

**什么时候该推翻**：DSL 语法复杂度超过 LL(1)（比如需要 `x = a | b` 这样的歧义消解）时。
**当前语法是严格 LL(1) 的，自研够用。**

## 8. 非目标（Out of Scope）

- 可视化规则编辑器
- 规则的运行时热更新（规则集在启动时载入）
- 规则的版本对比、回滚、审批流
- 规则之间的相互引用（`UNDEFINED_RULE_REF` 是保留错误码）
- 自定义函数 / 内置函数（`lower(x)`、`len(x)` 等）
- 规则执行的结果持久化

## 9. 成功标准（可验证）

> ⚠️ **本表曾用 checkbox 列表（`- [ ] …`）书写，结果被覆盖率门禁完全看不见。**
> 门禁只认「`| 编号 |` 形式的表行」—— 它不知道 checkbox 也是验收标准。
> 于是 `check-spec-coverage.sh` 对 rulesmith 报出「尚未规划」。
>
> **修法是把标准写成可被机器计数的形式，而不是去改门禁的判定规则。**
> 规格是要被机器读的 —— **它得先能被机器读到，才能被机器强制。**
>
> 📌 这件事本身就是 spec-as-source 的一个隐含要求：
> **规格的结构（而不只是内容）必须足够规整，门禁才能拿它做判断。**

| # | 成功标准 | 验证方式 |
|---|---------|---------|
| 9.1 | 改一处 `spec.md` 的 EBNF → `pnpm generate` → 受影响的产物相应更新 | `notes/L10-只改spec演示.md` 的真实运行记录 |

### 本表与「映射表」的关系

这十条只存在于本文一处。它们的可执行形式（测试名 / 命令 / 门禁）记录在
`docs/验收标准-测试映射.md`，且**两份文件的条数必须相等**——
由 `scripts/check-spec-coverage.sh` 机械校验。

> 📌 **spec-as-source 项目里，「测试」不只有单元测试。**
> 10 条中真正跑测试的只有 4 条（9.3 / 9.6 / 9.7 / 9.10）；
> 其余六条靠**命令的退出码**或**人工的一次真实验证**来判定。
>
> 这打破了「验收标准必须有自动化测试」的直觉。**它成立的前提是：**
> 那些「非测试」的判定方式必须是**确定性且可复现**的（退出码、字节比较）。
> 若某条标准既不能自动验证，也不能确定性复现，**它就不是一条可验收的标准。**
