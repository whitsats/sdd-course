# 验收标准 ↔ 验证方式映射 · rulesmith

> **本文件是 spec-as-source 项目里「映射」的另一种形态。**
>
> `examples/taskflow` 的映射表指向的是**契约测试**；
> 这里指向的是**命令退出码、字节比较、人工实证**。
> 原因很简单：当规格就是产物来源时，「实现了规格」可以用**字节级相等**判定，
> 比断言代码行为强得多 —— **不需要人来写断言，也就不需要人来写错断言。**

**对应规格**：`specs/001-rulesmith-dsl/spec.md` §9
**标准总条数**：10（脚本实测值）

---

| # | 验收标准（简写） | 验证方式 :: 具体位置 | 类型 |
|---|----------------|-------------------|------|
| 9.1 | 改 spec 一处 → 受影响产物更新 | 人工执行 :: `notes/L10-只改spec演示.md`（含真实 diff 行数） | 实证 |
| 9.2 | 重新生成后 `git diff` 为空 | 脚本 :: `scripts/verify-generated.sh examples/rulesmith …` | 门禁 |
| 9.3 | 连续两次生成字节级相同 | 测试 :: `generator.spec.ts::幂等性与确定性` | 幂等 |

| 9.6 | 文档语法速查与 EBNF 自动一致 | 测试 :: `generator.spec.ts::产物与规格一致（禁止手改）` | 契约 |

## 覆盖率自检（自动化）

```bash
$ bash scripts/check-spec-coverage.sh examples/rulesmith
── 001-rulesmith-dsl ──
标准条数: 10   映射行数: 10
✅ 覆盖完整
```

**两个数字必须相等。** 脚本见 `scripts/check-spec-coverage.sh`。

> 📌 **第一次跑时这里不是绿的**：规格里写的是 `- [ ] …` checkbox，
> 门禁的计数逻辑只认 `| 编号 |` 表行，于是它看不见任何标准。
>
> **修的是规格，不是门禁。** 因为门禁的判定规则（「可被计数的标准」）
> 是跨项目一致的，而 checkbox 是个别写法。
> **如果为了让门禁变绿而放宽门禁，就等于把三级成熟度往回退。**
> 见 `reference/anti-patterns.md` AP-18。

## 按类型分布

| 类型 | 条数 | 说明 |
|------|------|------|
| 幂等 | 2 | 9.3 / 9.4 —— spec-as-source 的**生存前提**，缺它 CI 会随机红 |
| 门禁 | 2 | 9.2 / 9.5 —— 靠退出码判定，不需要人写断言 |
| 契约 | 2 | 9.6 / 9.9 —— 「文档与规格一致」「示例与语法一致」 |
| 构建期 | 2 | 9.7 / 9.8 —— **把运行期才炸的东西拦在构建期** |
| 属性 | 1 | 9.10 —— 全称命题，单元测试覆盖不了 |
| 实证 | 1 | 9.1 —— 人做一次真改真跑，记录真实输出 |
| **合计** | **10** | |

**注意「幂等」占了 2 条，并列最多。** 这不是巧合：
在 spec-as-source 里，**没有幂等性，其他一切都会失效** ——
CI 的 `git diff` 校验会随机变红，团队学会无视红灯，门禁被关掉，
然后手工编辑产物就开始悄悄积累。

> 📌 **幂等性不是「代码质量属性」，它是这个模式的生存条件。**
> 在别的模式里，一个偶尔输出顺序不同的生成器只是不够优雅；
> 在这里，它会让整个强制层失效。

## 元验证（证明这些判定真的会红）

> **「全部通过」可能意味着系统正确，也可能意味着检查根本没在工作。**
> 两者在输出上完全一样 —— 所以必须故意制造违规，确认它真的被发现。

| # | 破坏动作 | 期望 | 实测结果 |
|---|---------|------|---------|
| 元-1 | 从 EBNF 删掉 `"when"` | 示例测试失败 | ✅ **11 个测试失败**（含 9.9 那条） |
| 元-2 | 加一个 `BOOL = letter { letter } ;` | 构建期报错 | ✅ `token 类型 BOOL 需要扫描器种类 "bool"` |
| 元-3 | 语法层写 `field = letter { "." IDENT }` | 构建期报错 | ✅ `语法层产生式 field 引用了字符类 letter` |
| 元-4 | 往 `lexer.ts` 追加一行注释 | `--check` 退出码非 0 | ✅ 报「需重新生成」并列出文件 |
| 元-5 | 删除一条映射行（本表删 9.10） | 覆盖率门禁红 | ✅ `标准条数: 10   映射行数: 9` → 失败，**并点名缺的是 9.10** |

**元-1 的补充说明（值得单独记住）**：

删除 `"when"` 后，**生成器仍然成功退出了** —— 它只保证语法自洽，
管不了「示例是否还合法」。抓住它的是**测试**。

> **工具的职责边界必须清楚：生成器保证「产物由规格而来」，
> 测试保证「规格里的示例确实过得了」。两者谁都不覆盖对方。**
>
> 如果误以为「生成器成功 = 一切正常」，元-1 这类错误会一路进到用户的终端里。

## 本表**不**映射的东西

| 项 | 为什么不映射 |
|----|------------|
| `tools/generator/` 的内部实现质量 | 它是**手写层**，验收对象是它的**行为**（9.3、9.7、9.8），不是它的代码 |
| `src/generated/validator.ts` 的语义检查 | **尚未实现**（见 spec §7 被否决的设计 ③）。它不是「没测」，是「没写」——两者必须分清 |
| 业务方是否觉得 DSL 好用 | 不可判定，**不是验收标准** |

> 📌 **最后一行值得单独说：** 一个不可判定的东西写进验收标准，
> 会把整张表的水分拉高，然后其他条目也会被草率对待。
> **判定不了的，就别放进表里；想追踪它，就放进「风险」或「待观察」清单。**
