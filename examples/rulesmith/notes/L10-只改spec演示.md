# 演示记录 · 只改 spec 一个词

> **这是 L10 的核心演示，也是全课程里唯一一次「改一行规格 → 产物自己长出来」的现场。**
>
> 全部输出都是**真实终端输出**，不是示意。你可以照着重跑。

---

## 演示内容

给 `operator` 产生式加一个新运算符 `matches`（用于未来支持正则匹配）。

### 改动：一个词

```diff
- operator      = ">" | ">=" | "<" | "<=" | "=" | "!=" | "in" | "notin" ;
+ operator      = ">" | ">=" | "<" | "<=" | "=" | "!=" | "in" | "notin" | "matches" ;
```

**除这一行外，没有再改任何东西。** 没有改 lexer、没有改 parser、没有改文档。

### 命令

```bash
pnpm generate        # 等价于 node tools/generator/index.ts
```

### 真实输出

```
规格: specs/001-rulesmith-dsl/spec.md
产生式: 11   词法 token 类型: 3   关键字: 11   符号: 14   错误码: 8
起始产生式: program

  ✎ 已更新  src/generated/lexer.ts  (145 行)
  ✎ 已更新  src/generated/parser.ts  (416 行)
  · 未变  src/generated/validator.ts  (74 行)
  ✎ 已更新  docs/rules-dsl.md  (99 行)
```

### 逐文件的实际差异

| 产物 | 变化 | 差异行数 | 变了什么 |
|------|------|---------|---------|
| `src/generated/lexer.ts` | ✎ 已更新 | **1** | 关键字表多一项 |

| `src/generated/validator.ts` | **· 未变** | **0** | 见下文 —— 这是本次演示最值钱的地方 |

lexer 的实际差异只有一行：

```diff

+  "matches",
   "notin",
```

## 关键观察：为什么 `validator.ts` **正确地没有变**

`validator.ts` 里有两张由 `operator` 产生式推导出来的表：

```ts
export const NUMERIC_OPERATORS = ["<", "<=", ">", ">="] as const;   // 数值比较
export const LIST_OPERATORS    = ["in", "notin"] as const;          // 集合运算
```

`matches` 既不是数值运算符（不匹配 `/^[<>]=?$/`），也不是列表运算符（不是 `in`/`notin`），
所以它**同时落在两张表之外** —— 校验器不需要改。

**如果生成器是「机械地把新运算符塞进每一张表」，这里就会出错**：
`matches` 会被误当作数值运算符，然后校验器会对 `field matches "regex"` 报出
错误的 `TYPE_MISMATCH`（说右侧必须是数字）。

> 📌 **这一条比「产物跟着变了」更重要。**
>
> 好生成器的判据**不是「凡输入变则输出全变」**，而是
> **「只改真正受影响的部分，并且不改不该改的部分」**。
>
> 前者容易（无条件重算一遍就行），后者需要**把推导关系写清楚**：
> 「哪些产生式决定哪些表」这件事必须在生成器里显式表达，而不是靠遍历。

## 反向验证：回滚是否也能字节级还原

```bash
# 把 spec 改回去，重新生成
pnpm generate

# 与演示前的快照逐字节对比
diff -q /tmp/rs_before/lexer.ts     src/generated/lexer.ts     # ✓ 一致
diff -q /tmp/rs_before/parser.ts    src/generated/parser.ts    # ✓ 一致
diff -q /tmp/rs_before/validator.ts src/generated/validator.ts # ✓ 一致
diff -q /tmp/rs_before/rules-dsl.md docs/rules-dsl.md          # ✓ 一致
```

**四个文件全部字节级还原。** 这个性质叫**双向幂等**，它比单向幂等强：

- 只测「跑两次相同」→ 可能是缓存或偶然
- 测「A→B→A 回到 A」→ 说明生成是**纯函数**，没有隐藏状态

### 为什么双向幂等很重要

如果生成不满足它，那么**回滚一次规格变更，会留下一堆「看起来无关」的差异**。
团队会以为是上一次改动的残留，于是不敢回滚 —— **规格就不敢改了**。
一旦规格不敢改，spec-as-source 的前提（规格是活的）就没了。

## 耗时

| 步骤 | 耗时 |
|------|------|
| 改 spec 一行 | 20 秒 |
| `pnpm generate` | < 1 秒 |
| 检查 `git diff` | 1 分钟 |
| **合计** | **约 2 分钟** |

对照：如果四个产物是手写的，同样一次改动要：

| 步骤 | 耗时 |
|------|------|
| 改 spec | 1 分钟 |
| 改 lexer 关键字表 | 1 分钟 |
| 改 parser 的产生式 | 3 分钟 |
| 判断 validator 要不要改（**最容易漏的一步**） | 5 分钟 |
| 改业务方文档 | 2 分钟 |
| **合计** | **约 12 分钟** |

**一次改动省 10 分钟。** 而 `L10-边界感.md` 里算出的盈亏平衡点是 **0.4 次** ——
本次演示就是那第一次。

> ⚠️ **注意最贵的一项是「判断 validator 要不要改」（5 分钟）。**
> 它贵在**它是判断，不是操作** —— 而判断会出错。
> 生成器把这一步从「每次都要重新判断」变成了「一次性判断，之后自动」。
> **这才是生成器真正省掉的东西：不是打字时间，是重复判断。**

## 顺手抓到的两个真实问题

本节演示在实现过程中暴露了两个 bug，都值得记住：

### ① 生成的 parser 在运行期抛异常（最严重）

```
Error: 未定义的产生式: letter
```

根因：EBNF 里混了两个层级 —— `IDENT` 是**词法层**（描述怎么切 token），
但它引用了字符类 `letter`（不是产生式）。生成器把 `IDENT` 也当语法产生式发射了。

**危险之处在于生成器当时是「成功退出」的。** 产物看起来完全正常，
直到有人调 `parse()` 才炸。

修法不是「小心一点」，而是**把引用校验加进生成器**（`ebnf.ts` 的引用校验段）：
现在 `letter` 出现在语法层会产生式里，会在**构建期**报错并给出修复建议。

> 📌 **spec-as-source 的危险不是「生成器报错」，而是「生成器不报错、产出运行期才炸」。**

### ② 使用文档教了一个语法不接受的写法

生成的 `docs/rules-dsl.md` 里，示例写的是：

```
rule high_value {
  when amount > 10000 and ...
}
```

**而当时 `rule` 产生式里根本没有 `when`。** 文档与语法互相矛盾，双方都「看起来正常」。

修法分两层：

1. 示例从 spec 的 ```rulesmith 块**注入**，不再硬编码 → 文档与语法同源
2. 加测试：**规格自带的例子必须能跑通自己生成的解析器**
   （`tests/validator.spec.ts` 的「规格自带的示例必须通过自己的语法」）

**元验证（反向证明门禁真的会红）**：把 `"when"` 从 EBNF 里删掉 → **11 个测试失败**。

> 📌 注意：**生成器本身抓不住这个错**（它只保证语法自洽），抓住它的是**测试**。
> 「把示例当契约来测」这个动作，是人生出来的，不是工具生出来的。

## 这一节的方法论

```
改 spec
   ↓
pnpm generate          ← 机器做：一切可从规格推导的东西
   ↓
看 git diff            ← 人做：这次变化是否符合我的意图？
   ↓
跑测试 + 门禁          ← 机器做：产物是否与规格一致、示例是否仍有效
   ↓
提交 spec + 产物
```

**人只出现在中间两步：表达意图、审查结果。** 这两步也正是人**不可被替代**的部分。
