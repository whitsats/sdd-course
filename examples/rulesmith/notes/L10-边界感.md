# 边界感分析 · rulesmith

> **本文件是 L10 的真正考核产出。** 验收标准里写着：
>
> > **「你能说出本项目不适合规格即源的部分，以及原因」——没做这条等于本节没上。**
>
> L10 的考核重点**不是「你成功用了 spec-as-source」**，而是**你有了边界感**。
> 下面三个问题是硬性要求，逐条回答。

---

## 问题 ① 本项目哪些部分**不适合**规格即源？

### 1. 生成器本身（`tools/generator/`）—— 递归边界 ⭐

**这是最重要的一条。**

| 问题 | 答案 |
|------|------|
| 生成器能被规格生成吗？ | **不能。** |
| 为什么？ | **会导致无限递归**：生成器的生成器又需要生成器。 |
| 所以？ | 任何 spec-as-source 系统都存在一个**人写的基底**。 |

**这个认知改变了什么：**

> spec-as-source **不是「消灭手写代码」**，而是**「把人的手写工作集中推到极少数、
> 且变更频率最低的那一层」**。

本项目里：
- 变更频率**最高**的：DSL 语法（每月数次）→ **完全生成** ✅
- 变更频率**最低**的：生成器逻辑（本项目至今 0 次语义变更）→ **手写** ✅

**这个分工才是 spec-as-source 的实质。** 如果你把人的精力花在「变更频率高的那一层」，
那你就白折腾了。

### 2. 运行期引擎（把 AST 应用到一个具体记录上）

「怎么执行一个条件」（`amount > 10000` 怎么求值）是**通用逻辑，与语法无关**：
- 加一个运算符 `matches` → **语法变了**，需要重新生成 ✅
- 改数字比较的精度规则 → **求值逻辑变了**，与语法无关 → 手写 ✅

**所以运行期引擎是手写的**，它不进生成产物表。

### 3. 测试

测试**不该由规格机械生成**。理由：

- 测试的价值在于**断言选择**（该测什么、在哪里设边界）——那是判断，不是推导
- 从规格机械生成的测试会**与生成代码同源**，于是「代码错了测试也错」，检测能力趋近于零

> 📌 **这是一个容易忽略的陷阱**：spec-as-source 很容易滑向「测试也一起生成」，
> 然后你会拥有一个 100% 通过、但检测不到任何问题的测试套件。

本项目的测试是手写的，且包含**属性测试**（随机规则集 → 校验通过 → 运行期必不出错）——
那种断言没法从规格推导出来。

### 4. 错误消息的措辞

| 层 | 例子 | 谁来定 |
|----|------|-------|
| **错误码** | `UNKNOWN_FIELD` | 规格（错误码表）→ 生成 ✅ |
| **错误消息文案** | 「字段 `user.age` 不存在，可用字段：user.tier, user.name」 | **人**（产品决策） |

规格能穷举错误**情形**，但穷举不了**文案**——「提示要不要列出可用字段」是产品判断。

**所以生成产物里错误码是生成的，消息模板留了人工填写的位置。**

### 边界小结

| 部分 | 谁写 | 变更频率 |
|------|------|---------|
| DSL 词法/语法/校验器/文档 | **生成** | 高（每月数次） |
| 生成器 | 手写 | 极低 |
| 运行期求值引擎 | 手写 | 低 |
| 测试（含属性测试） | 手写 | 中 |
| 错误消息文案 | 手写 | 低 |
| `schema.json` | 手写 | 中（数据 shape 变化） |

## 问题 ② 什么时候该**放弃**规格即源？

按「先出现即触发」排序：

| 触发条件 | 具体表现 | 该改用什么 |
|---------|---------|-----------|
| **变更频率超过生成器维护能力** | 每周都要改语法，而生成器每次都要跟着修 | 退回 spec-anchored（规格+代码一起改，测试强制对齐） |
| **产物形态开始分化** | 不再固定是「四件套」，开始出现「某些 DSL 要额外生成 A，某些要 B」 | 生成器会退化成模板引擎 + 大量特例。改用模板 + 手写 |
| **语法复杂度超过 LL(1)** | 需要前视、优先级消解、歧义回溯 | 换 ANTLR 类工具（此时「自研生成器」的收益消失） |
| **语义检查需要引用外部信息** | 校验规则依赖运行时状态（当前用户、当前时间） | 部分退回手写；生成只覆盖语法层 |
| **需要人做审美/产品判断的部分变多** | 生成物要「好看」「符合品牌」 | 改用手写 + 代码审查 |

### 本项目当前的位置

**大部分条件都不满足，所以 spec-as-source 是划算的。** 但注意第 3 条已经**部分显现**：

> `validator.ts` 的语义检查是 **TODO 状态**，因为通用的表驱动回溯解析器只覆盖语法。
> 这已经踩到了「语义检查需要针对本语法的访问器」这个边界。

**这是一个真实的、正在发生的边界**，写在这里而不是藏在代码注释里。

## 问题 ③ 一个诚实的问题：生成器 vs 手写产物，哪个维护成本更高？

### 实际投入

| 项 | 工时 |
|---|---|
| 写生成器（`ebnf.ts` + `spec-reader.ts` + `emit.ts` + `index.ts`） | **约 5 小时** |
| 修两个 bug（终结符分类、`--check` 顺序） | 约 1 小时 |
| 写生成器的测试 | 约 1.5 小时 |
| **合计** | **约 7.5 小时** |

### 如果手写四个产物

| 项 | 工时 |
|---|---|
| 手写 lexer（扫描器 + 关键字） | 1.5 小时 |
| 手写 parser（递归下降） | 3 小时 |
| 手写 validator | 1.5 小时 |
| 手写业务方文档 | 1 小时 |
| **合计** | **约 7 小时** |

### 所以这次是**亏的** —— 亏了 0.5 小时

**但这不代表做错了。** 它说明了一件重要的事：

> **spec-as-source 的本质是「用一次性的生成器，换长期的变更成本」。**
>
> 只有当**变更次数足够多**时，这笔投资才回本。

### 盈亏平衡点估算

```
初始投入差额    ΔC = 7.5 - 7.0 = 0.5 小时（生成器更贵）

每次语法变更的代价：
  手写路线：改 spec + 改 lexer + 改 parser + 改 validator + 改文档 ≈ 1.5 小时
  生成路线：改 spec + 跑 generate + 检查产物 + 提交 ≈            0.25 小时

单次节省        s = 1.5 - 0.25 = 1.25 小时/次

盈亏平衡点      n = ΔC / s = 0.5 / 1.25 = 0.4 次
```

**也就是说：只要这个 DSL 未来会变更 1 次以上，生成器路线就回本。**

> 本项目的实测验证：本次演示中「加一个 `matches` 运算符」——手写路线要改 4 个文件，
> **生成路线只改了 spec 里 1 个词 + 跑一次 generate**，实测约 4 分钟。

### 但这里有个陷阱

**盈亏平衡点算出来是 0.4 次，看起来很划算——但这个数字依赖一个假设：生成器不需要维护。**

如果生成器本身每变更 3 次语法就要修 1 次，那么：

```
实际单次节省  s' = 1.25 - (0.5 / 3) ≈ 1.08 小时/次
实际盈亏平衡  n' = 0.5 / 1.08 ≈ 0.5 次
```

**影响不大。** 但如果生成器**每变更 1 次就要修 1 次**（即生成器和语法同样易变）：

```
s'' = 1.25 - 0.5 = 0.75 小时/次
n'' = 0.5 / 0.75 ≈ 0.7 次
```

**还是划算的**——因为生成器的修改成本仍然是「改一处逻辑」，而不是「改四个产物」。

### 什么时候会真的不划算

> **当生成器的修改频率 × 单次修改成本 ≥ 手写四个产物的成本时。**

本项目里唯一接近这个条件的是 §问题②第 3 条提到的：**语义检查需要访问器**。
如果语义检查的复杂度持续上升，某天你会发现「每次加一个校验规则都要改生成器」——
**那一天就该退回 spec-anchored，或者上真正的 parser generator。**

**把这个触发条件写在这里，是为了在那一天到来时不必重新论证。**

## 总结：这一节到底学到了什么

| 学到的东西 | 具体是什么 |
|-----------|-----------|
| **它有效** | 改 spec 一个词 → 3 个产物自动更新，另一个正确地没变 |
| **它的实质不是消灭手写** | 而是把人的手写推到变更频率最低的那一层（生成器） |
| **它的边界是语义** | 通用解析器覆盖语法，语义检查必然需要针对本语法的代码 |
| **它需要幂等** | 没有幂等性，CI 的 `git diff` 校验就会随机失败，然后门禁被关掉 |
| **它要算账** | 盈亏平衡点 = 一次性投入差额 ÷ 单次节省。本项目 0.4 次 |
| **最危险的不是不用它** | 而是**不假思索地用在不适合的领域**（UI、算法调优、探索性需求） |

> 📌 **这一节最该记住的一句话**：
> **spec-as-source 是「把变更成本搬到最不常变的那一层」，不是「让机器替你思考」。**
> 想不清楚哪一层最不常变的人，用它只会把项目搞得更难维护。
