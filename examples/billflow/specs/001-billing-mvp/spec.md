## 1. 背景与范围

订阅制产品的账单生成：给定一个订阅（起止日 + 月度费率）、一个账单周期、一张按生效日版本化的费率表，算出这一期该收多少钱，并逐日列出明细。

**为什么这个领域值得单独做一个案例**：金额计算里没有「大概对」。分摊少 1 分、跨费率变更时取整方向不一致，在生产环境就是账对不上，而且**对不上之后极难复现**。这类需求恰好是规格该发力、而 vibe coding 必然翻车的地方。

### 范围内

- 单个订阅在单个账单周期内的费用计算
- 按天分摊，含订阅只覆盖部分周期、周期内费率变更
- 费率表的生效日规则与冲突检测
- 逐日明细与可追溯信息

### 范围外（明确不做）

- 折扣、优惠券、税费、多币种换算（币种只做「一致性校验」，不做汇率）
- 支付、退款、发票开具、对账
- 订阅的创建/变更流程本身（本案例只接收已确定的订阅状态）
- 按使用量计费（usage-based）

## 2. 术语

| 术语 | 定义 |
|------|------|
| **账单周期（Billing Period）** | 一个**自然月**，半开区间 `[月首日, 次月首日)` |
| **计费范围（Covered Range）** | 账单周期与订阅有效期**按天求交**后的连续日期区间 |
| **费率版本（Rate Version）** | 一条「从某日（含）起月度费率为 M 分」的记录，带唯一标识 |
| **月度费率 M** | 该版本声明的整月费用，单位为**分**，正整数 |
| **应付总额（Amount Due）** | 本期应向用户收取的总额，单位为分 |
| **明细（Line Item）** | 某一天的金额，含日期、金额、适用的费率版本标识 |

## 3. 用户故事与验收标准

### US1 · 按天分摊

> **作为一个计费系统**，我要把月度费率按天精确分摊到用户实际使用的天数上，使账单金额经得起逐分核对。

| 编号 | 验收标准（EARS） |
|------|-----------------|
| 1.1 | THE SYSTEM SHALL 以**自然月**为账单周期，区间为 `[月首日, 次月首日)`，共 D 天（28–31 天） |
| 1.2 | WHEN 订阅有效期与账单周期存在交集 THE SYSTEM SHALL 得到计费范围 = 二者按日历天求交，记其天数为 N |
| 1.3 | WHEN N > 0 THE SYSTEM SHALL 按 `应付 = ⌊M × N / D⌋` 计算该段的应付总额（M 为该段适用的月度费率，单位分），使用**整数运算**，不得提前舍入、不得出现小数中间结果 |
| 1.4 | WHEN N > 0 THE SYSTEM SHALL 输出恰好 N 条明细，其金额满足：每日基数 = `⌊应付 / N⌋`，余数 R = 应付 − 每日基数 × N，且**从计费范围首日起按日顺序**为前 R 天各加 1 分 |
| 1.5 | THE SYSTEM SHALL 保证不变量 `Σ(明细金额) == 应付总额`，对任意 N ∈ [1, D] 与任意正整数 M 成立 |
| 1.6 | IF N = 0 THEN THE SYSTEM SHALL 输出零条明细、总额为 0 的空账单，且**不报错** |
| 1.7 | WHEN 账单周期内发生费率变更 THE SYSTEM SHALL 以费率版本的生效日为界，把计费范围切成若干连续段，对**每一段独立**应用 1.3、1.4，账单总额 = 各段应付之和，明细按日期升序拼接 |

### US2 · 费率生效规则

> **作为计费运营方**，我要能安全地发布新费率，且历史账单必须能被旧费率精确重算。

| 编号 | 验收标准（EARS） |
|------|-----------------|
| 2.1 | WHEN 判定某一天适用的费率版本 THE SYSTEM SHALL 取「生效日 ≤ 该日」的**最晚**一个版本；生效日**含当日** |
| 2.2 | IF 两条费率版本的生效日相同 THEN THE SYSTEM SHALL 拒绝加载费率表，并给出错误码 `RATE_OVERLAP` |
| 2.3 | IF 计费范围内的某一天早于最早的费率版本 THEN THE SYSTEM SHALL 报错 `RATE_MISSING`，**不得**回退到最近可用版本，也不得按 0 计费 |
| 2.4 | IF 任一费率版本的月度费率 ≤ 0 THEN THE SYSTEM SHALL 拒绝加载费率表，并给出错误码 `INVALID_RATE` |

### US3 · 金额与精度

> **作为一个要经审计的系统**，我要让每一分钱都可解释。

| 编号 | 验收标准（EARS） |
|------|-----------------|
| 3.1 | THE SYSTEM SHALL 以「分」为唯一金额单位，所有金额为整数；任何计算过程不得使用浮点数，也不得进行四舍五入以外的隐式取整（取整规则由 1.3、1.4 完全确定） |
| 3.2 | IF 两个金额的币种不同 THEN THE SYSTEM SHALL 拒绝相加并给出错误码 `CURRENCY_MISMATCH` |
| 3.3 | THE SYSTEM SHALL 保证账单总额 ≥ 0，且每条明细金额 ≥ 0 |

### US4 · 周期与边界

| 编号 | 验收标准（EARS） |
|------|-----------------|
| 4.1 | THE SYSTEM SHALL 把一切日期区间视为**半开区间** `[起始日, 结束日)`，结束日**不含**当日 |
| 4.2 | THE SYSTEM SHALL 按日历天计算天数，含闰年的 2 月 29 日；2 月按实际天数（28 或 29）参与 D |
| 4.3 | IF 账单周期的结束日不晚于起始日 THEN THE SYSTEM SHALL 报错 `INVALID_PERIOD` |
| 4.4 | IF 账单周期不是「月首到次月首」THE SYSTEM SHALL 报错 `INVALID_PERIOD`，不接受任意区间 |

### US5 · 可追溯

> **作为审计者**，我要能从账单反推出它用了哪一版费率、怎么算出来的。

| 编号 | 验收标准（EARS） |
|------|-----------------|
| 5.1 | THE SYSTEM SHALL 在每条明细上记录其适用的费率版本标识 |
| 5.2 | THE SYSTEM SHALL 在账单上记录：账单周期、应付总额、明细条数 |
| 5.3 | WHEN 输出账单 THE SYSTEM SHALL 按日期**升序**排列明细，且日期连续无重复 |

## 4. 计算示例（规格的"可执行性"检验）

**输入**：2026 年 2 月（D = 28），月度费率 M = 10000 分（￥100.00），订阅覆盖 2 月 1 日至 2 月 15 日（N = 14）。

- 应付 = `⌊10000 × 14 / 28⌋` = `⌊5000⌋` = **5000 分**
- 每日基数 = `⌊5000 / 14⌋` = 357，余数 R = 5000 − 357 × 14 = 2
- 明细：2/1 → 358、2/2 → 358、2/3 起至 2/14 → 各 357
- 校验：`358 + 358 + 12 × 357` = 716 + 4284 = **5000** ✅（1.5 不变量）

**再问一次：为什么不直接用 `10000 / 28 × 14`？**
因为 `10000 / 28 = 357.14…`，先除后乘会丢掉 0.14 × 14 ≈ 2 分。规格里的 1.3 明确要求**先乘后除**，这条差异在真实账务里就是每天几毛钱的长期偏差。

**跨费率变更的情形**（1.7）：3 月 D = 31，3 月 16 日起费率由 10000 变为 15000，订阅覆盖整月。

- 段 1：3/1–3/15，N₁ = 15，M₁ = 10000 → 应付 = `⌊10000 × 15 / 31⌋` = `⌊4838.7⌋` = **4838**
- 段 2：3/16–3/31，N₂ = 16，M₂ = 15000 → 应付 = `⌊15000 × 16 / 31⌋` = `⌊7741.9⌋` = **7741**
- 总额 = 4838 + 7741 = **12579 分**

注意：**不能**先用加权平均费率算一次（`(10000×15 + 15000×16) / 31` 再乘 N），那样会得到 12580 —— 与逐段取整差 1 分。1.7 的「逐段独立」就是为了消灭这个歧义。

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| 确定性 | 相同输入必须产生**逐字节相同**的账单输出（明细金额、顺序、可追溯字段全部确定） |
| 性能 | 单个账单周期的计算在 1000 天尺度内的输入上必须 < 50ms（分页/批量的规模上限不在本 MVP 内） |
| 依赖方向 | 领域计算不得依赖任何 I/O、序列化或持久化机制（见 `plan.md` 的模块边界） |
| 可追溯 | 每条明细可反查费率版本标识；费率表加载后不可变 |
