# 技术方案 · billflow 计费引擎（MVP）

**对应规格**：`specs/001-billing-mvp/spec.md`
**技术栈**：Java 17 · Maven 多模块 · JUnit 5 · ArchUnit · 自制注解处理器

> ⚠️ **本文件里的每一项技术决策都必须能追溯到规格的某一条。**
> 追溯不到的依赖 = 凭空出现的复杂度，应当在 review 时被删掉。

---

## 1. 架构：两个模块与它们的理由

```
billflow/
├── spec-guard/      编译期守卫：把规格编号变成编译器认识的符号
└── billing-app/     领域实现与测试（唯一的业务模块）
```

### 为什么是「两个模块」而不是一个

因为 `spec-guard` 必须在 `billing-app` **编译之前**就存在 —— 它是一个注解处理器，要参与 `billing-app` 的编译过程。这带来一个真实的多模块构建顺序问题，也是本案例的教学内容之一。

| 模块 | 职责 | 为什么单独成模块 |
|------|------|----------------|
| `spec-guard` | 提供 `@Ac` 注解 + 注解处理器，在**编译期**校验代码里引用的规格编号在 `spec.md` 中确实存在 | 它必须独立构建，否则注解处理器无法参与自身的编译（鸡生蛋问题） |
| `billing-app` | 领域模型、计费算法、测试 | 唯一的业务代码容器，边界清晰 |

## 2. 模块内分层与依赖方向

```
billing-app/
└── dev.billflow
    ├── domain/     金额、周期、费率表、分摊算法（纯计算，无 I/O）
    ├── app/        编排：把订阅 + 周期 + 费率表变成一张账单
    └── (测试)       domain / app 各自的测试 + 一个架构边界测试
```

**依赖方向是单向的**：`app → domain`，反向不允许。

| 约束 | 依据（规格条目） | 检查手段 |
|------|----------------|---------|
| `domain` 不得依赖任何 I/O、序列化、持久化机制 | 非功能需求「依赖方向」 | **ArchUnit 测试**（不是脚本） |
| `domain` 不得使用 `java.util.Date` / `Calendar` / `System.currentTimeMillis` | 4.1、4.2（半开区间与日历天计算必须显式） | **ArchUnit 测试** |
| `domain` 不得使用 `double` / `float` | 3.1（禁用浮点） | **ArchUnit 测试** |
| 每条验收标准的实现点必须标注规格编号 | 5.1、5.2（可追溯） | **注解处理器（编译期）** |

> 💡 注意最后三行的差别：前两行用**架构测试**表达，最后一行用**编译器**表达。这就是本案例与项目 B 的核心差别 —— 约束被前移到了构建期，而不是等测试跑起来才失败。

## 3. 关键决策与追溯

| # | 决策 | 服务的规格条目 | 代价 / 被否决的选项 |
|---|------|--------------|------------------|
| 1 | 金额用「整数分」，领域内不存在小数金额 | 3.1 | 代价：币种的最小单位不是全局常量（日元没有分 → 需按币种取小数位）。本 MVP 限定人民币语义，ADR-003 记录了这条取舍 |
| 2 | 取整一律「先乘后除」 | 1.3 | 被否决：先除后乘（丢分，见 spec §4 的示例） |
| 3 | 跨费率变更时**逐段独立取整**，不做加权平均 | 1.7 | 代价：与「按加权平均费率一次算」相差最多 (段数−1) 分。被否决：加权平均 —— 它看起来更"公平"，但使结果依赖于实现顺序，且无法从任何一个费率版本反推出该分钱归谁 |
| 4 | 余数分配方向固定为「从段首日按日顺序各加 1 分」 | 1.4 | 被否决：把余数全给最后一天（会让某天金额异常）、或平分到所有天（无法用整数表示）。固定方向是「账单可复现」的前提 |
| 5 | 半开区间 `[start, end)` 作为全项目的唯一日期约定 | 4.1 | 被否决：闭区间（每处都要 `+1`，是 off-by-one 的主要来源） |
| 6 | 费率表加载即校验（重叠 / 非正数），加载后不可变 | 2.2、2.4 | 代价：加载期报错而非使用期。收益：错误在**最早可能的时刻**暴露 |
| 7 | `RATE_MISSING` 不回退到最近版本 | 2.3 | 被否决：静默回退 —— 它会产出**看起来正常但错的**账单，是本领域最危险的失败模式 |
| 8 | 明细日期必须升序且连续 | 5.3 | 代价：跨段拼接时要保证顺序。收益：账单可以直接被人逐行核对 |

## 4. 为什么引入 ArchUnit（而不是继续用 grep 脚本）

课程前面的 `scripts/check-layer-boundary.sh` 是**自制的 grep 检查**，它在实际使用中误报过两轮（把注释里的模块名算成违规），最后修好的办法是「先过滤出真实的 import 行再匹配」。

ArchUnit 把这类检查交给一个成熟工具：它以**字节码**为输入，因此天然不受注释、字符串字面量、格式差异的影响。同一个约束的两种表达方式对比：

| | 自制 grep 脚本 | ArchUnit |
|---|---|---|
| 输入 | 源码文本 | 编译后的字节码 |
| 注释/字符串里的词 | **会误报**（已实测两轮） | 不受影响 |
| 跨语言/跨模块 | 每种语言写一份 | JVM 内统一 |
| 新增约束的成本 | 改正则（容易越改越松） | 加一行 `noClasses().that()...` |
| 失败信息 | 「文件:行号 + 匹配到的行」 | 「类 A 依赖了 类 B，违反规则 R」 |

**结论**：自制脚本适用于「没有对应工具」的场景；一旦生态里有成熟检查，自制脚本就变成了负债 —— 因为你需要维护它的误报，而误报会让团队关掉门禁（AP-18）。

## 5. 构建期守卫的设计（spec-guard）

### 它做什么

代码里这样标注实现点：

```java
@Ac({"1.3", "1.4"})
public List<LineItem> prorate(...) { ... }
```

编译时，注解处理器会：

1. 读取 `spec.md`（路径由编译参数 `-Aspec.file=...` 传入）
2. 提取其中**全部**验收标准编号（规格里的编号表格）
3. 若代码里出现了规格中不存在的编号 → **编译失败**，并列出规格里实际有哪些编号

### 为什么「未知编号」是 ERROR，而「未被引用的编号」只是 NOTE

这是本案例最值得记住的一条设计准则：

- **ERROR 必须满足「绝不可能是故意的」**。`@Ac("9.9")` 而规格里只有 1.1–5.3，这不是风格问题，是**规格与代码已经对不上**——没有一种合理解释。
- **NOTE 允许存在合理例外**。不是每条验收标准都对应产品代码：`4.3`（非法周期报错）可能只在参数校验里体现，`5.3`（升序）可能由数据结构的天然顺序保证。把这些也当错误，门禁就会频繁误报 → 被关掉。

> **门禁的价值建立在「红灯必有意义」之上。** 一条会误报的规则，最终会连真话一起失去。

## 6. 测试策略

| 层次 | 工具 | 覆盖目标 |
|------|------|---------|
| 领域单元测试 | JUnit 5 `@ParameterizedTest` | 分摊规则的边界：整月、单日、零交集、闰年 2 月、跨段取整 |
| 不变量测试 | JUnit 5 | `Σ明细 == 应付`（1.5）在参数矩阵上恒成立 |
| 架构测试 | ArchUnit | 依赖方向、禁用类型（`Date`/`double`） |
| 构建期校验 | 注解处理器 | 规格编号存在性 |
| 覆盖率门禁 | `scripts/check-spec-coverage.sh` | 21 条标准 ↔ 映射表逐条对应 |

**刻意不去做的**：不为 `domain` 里的 `record` 写 getter 测试、不为构造器写「能创建」测试。这类测试提供零信息量，却会拉低「测试套件里有多少条真的在守着规格」这个比值。

## 8. 验收

- `mvn verify` 全绿（含测试、架构检查、注解处理器）
- 元验证：注入一个规格里不存在的编号 → **编译失败**
- 元验证：让 `domain` 依赖一个被禁用的类型 → **架构测试失败**
- 覆盖率门禁：`bash scripts/check-spec-coverage.sh examples/billflow` 报「覆盖完整」
