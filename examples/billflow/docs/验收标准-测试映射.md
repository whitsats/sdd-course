# 验收标准 ↔ 测试映射 · billflow

**对应 feature**：`001-billing-mvp`
**规格**：[`specs/001-billing-mvp/spec.md`](../specs/001-billing-mvp/spec.md)（21 条验收标准）
**测试总数**：751（`mvn -B verify`，其中 712 条是不变量参数矩阵生成的用例）

> 本表由 `bash scripts/check-spec-coverage.sh examples/billflow` 机械校验：
> **规格条数必须等于本表行数**。少一行 = 有标准没人守 = 阻断合并。

---

## 本案例与前三个案例在"测试↔规格"上的差别

| | 前面的项目 | billflow |
|---|---|---|
| 映射靠什么强制 | shell 脚本比对条数（CI 里跑） | **编译器**：`@Ac` 引用不存在的编号 → **编译失败** |
| 架构约束靠什么 | 自制 grep 脚本（误报过两轮） | **ArchUnit**：字节码级检查，不受注释影响 |
| 不变量靠什么 | 测试断言 | **构造器强制**，不满足就根本无法创建对象 |
| 失败时机 | 测试阶段 | 编译期 / 构造期 / 测试期（三层，越早越好） |

## 未被映射到测试的架构规则

有一条约束来自**非功能需求**而不是编号条目，因此不在这张表里 —— 但它同样被机械强制：

| 规则 | 强制手段 | 元验证（故意违反后应当失败） |
|------|---------|--------------------------|
| `domain` 不得依赖 `app` 层 | `LayerBoundaryTest#domainMustNotDependOnAppLayer` | 在 domain 里 import app 包 |
| `domain` 不得触碰 I/O / 网络 / 持久化 / 序列化 | `LayerBoundaryTest#domainMustStayFreeOfInfrastructure` | 在 domain 里 `import java.sql.*` |
| `domain` 不得读时钟 | `LayerBoundaryTest#domainMustNotReadTheClock` | 调用 `LocalDate.now()` 或 `System.currentTimeMillis()` |
| 账单结果必须确定性可复现 | `BillingServiceTest#isDeterministic` + 上一条 | 同上 |

## 元验证记录（本表不是承诺，是实测）

| 试验 | 注入的违规 | 实际结果 |
|------|-----------|---------|
| A | `@Ac("9.9")`（规格里没有这个编号） | **编译失败**，错误定位到 `DateRange.java:[21,8]`，并列出规格实际范围 `1.1–1.7, 2.1–2.4, 3.1–3.3, 4.1–4.4, 5.1–5.3` |
| B | `Money` 里加 `static double toYuan(long)` | `LayerBoundaryTest#domainMustNotDeclareFloatingPoint` 失败：`Money#toYuan 返回 double` |
| C | `DateRange` 里加一个读时钟的方法 | 两条规则同时失败：`DateRange#hasStarted 调用了 java.time.LocalDate#now` 与 `java.lang.System#currentTimeMillis` |
| D | 从本表删掉一行 | `check-spec-coverage.sh` 报出「缺少测试映射的标准编号」并指出具体编号 |
| E | 用 `<proc>none</proc>` 关掉注解处理 | `mvn verify` **退出码 0、751 个测试全过**，但 `scripts/check-java-build.sh` 抓住「规格校验为零执行」并失败 |

> E 是五条里最重要的一条：它验证的不是「违反规则会不会被拦」，而是
> **「门禁到底有没有在跑」**。前四条证明红灯有意义，E 证明绿灯不是空的。

完整终端输出与复现命令见 [`notes/L13-构建期强制.md`](../notes/L13-构建期强制.md)。
