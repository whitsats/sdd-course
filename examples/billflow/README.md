# 项目 D · billflow —— 当约束被前移到构建期

> 订阅计费引擎（Java 17 · Maven 多模块 · JUnit 5 · ArchUnit · 自制注解处理器）
> **对应课程**：L13 · **等级**：Spec-Anchored 的**构建期强化版**

---

## 它补的是前面三个项目缺的那一级

三个现有案例的强制力上限都是「测试 + CI」，也就是**运行期红灯**。这个项目把同一件事推到了更前面：

| 约束想表达的意思 | 靠什么强制 | 违反时什么时候知道 |
|----------------|-----------|------------------|
| 代码引用的规格编号必须真实存在 | **注解处理器** | 编译期，连 class 都不生成 |
| 领域层不得依赖 I/O / 时钟 / 浮点 | **ArchUnit（字节码级）** | `mvn verify`，定位到具体方法 |
| Σ明细 == 账单总额 | **构造器强制** | 对象创建时，永远是"不可能存在"的状态 |
| 每条标准都有测试 | `check-spec-coverage.sh` | CI |

**四层里没有一层是靠"记得去做"实现的。** 这就是本案例唯一的主题。

## 从一个真实的钱的问题开始

按天分摊月度费率时，`M / D` 几乎总是不整除：100 元 / 31 天 = 322.580645… 分。
这逼出三个必须由**规格**回答、不能由实现者顺手决定的问题：

1. 中间结果用什么表示？
2. 什么时候取整？
3. 取整产生的余数归谁？

规格 `001-billing-mvp` 用 21 条验收标准回答了它们，其中三条最关键：

- **1.3 先乘后除**：`⌊M × N / D⌋`。写成 `M / D × N` 会在 28 天月、14 天覆盖时得到 4998 而不是 5000 —— 差 2 分，且用户无法解释。
- **1.4 余数从段首日按日顺序分配**：让账单逐日可核对、可复现。
- **1.7 跨费率变更逐段独立取整**：3 月 15/16 天两段分别取整得 **12579**；全程一次取整得 **12580**。差的这 1 分不是误差，是**归因能力** —— 逐段算时每分钱都能对应到一个费率版本。

这三个决策的取舍、被否决的方案、以及代价，全部写在 [`docs/adr/ADR-003-金额精度与取整.md`](docs/adr/ADR-003-金额精度与取整.md)。**先读 ADR，再读代码。**

## 怎么跑

```bash
cd examples/billflow

# 完整门禁：编译期规格校验 + 751 个测试（含架构检查）
MAVEN_OPTS="-Dfile.encoding=UTF-8" mvn -B verify

# 覆盖率门禁（在仓库根跑）
bash scripts/check-spec-coverage.sh examples/billflow
```

预期输出：

```
[INFO] 规格校验：spec.md 共 21 条验收标准，代码标注了 21 条
[INFO] Tests run: 751, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

> ⚠️ **必须在聚合根目录跑**（`examples/billflow`），不要进 `billing-app` 单独跑。
> 单独跑时编译器找不到 `spec-guard` 这个注解处理器，会**静默跳过**规格校验 ——
> 构建全绿，但什么规格检查都没做。这是本案例最值得警惕的失败模式。
>
> ⚠️ Windows 上 `MAVEN_OPTS="-Dfile.encoding=UTF-8"` 不是可选项，否则构建日志里的中文是乱码。

## 四条元验证（这才是本节的价值）

门禁必须**自证会红**。以下四条都实测过，原始输出在 `notes/L13-构建期强制.md`：

| # | 注入的违规 | 结果 |
|---|-----------|------|
| A | `@Ac("9.9")` —— 规格里没有这个编号 | **编译失败**，并列出规格实际的编号范围 `1.1–1.7, 2.1–2.4, …` |
| B | `Money` 里加一个返回 `double` 的方法 | 架构测试失败：`Money#toYuan 返回 double` |
| C | `DateRange` 里调用 `LocalDate.now()` 与 `System.currentTimeMillis()` | 两条规则同时失败，定位到方法 |
| D | 从映射表删掉一行 | 覆盖率门禁指出**缺的是 1.5** |

其中 C 还顺带说明了一件事：同一个意图「不得读时钟」需要**两条不同的规则**才能覆盖完整 ——
`System.currentTimeMillis()` 能被"类依赖"抓到，而 `LocalDate.now()` 不能（owner 是合法的领域类型）。
**约束的表达形式决定了它的覆盖范围。**

## 这个案例不适合什么

诚实记录边界，和项目 C 一样：

- **不是生产级服务**：没有 HTTP 接口、没有持久化、没有并发控制、没有多币种。
  它的目的是把「构建期强制」讲清楚，不是交付一个计费系统。
- **注解处理器有维护成本**：它参与每次编译，一旦出错会阻断所有人。所以它只做一件事
  （校验编号存在性），并且**读不到规格时宁可报错也不静默通过**。
- **ArchUnit 只能检查结构，不能检查语义**：它能保证 `domain` 不依赖时钟，但保证不了
  「分摊算法符合商业预期」—— 后者只能靠规格、测试和不变量。
