## 1. 正常构建

```bash
cd examples/billflow
MAVEN_OPTS="-Dfile.encoding=UTF-8" mvn -B verify
```

关键输出：

```
[INFO] 规格校验：spec.md 共 21 条验收标准，代码标注了 21 条
[INFO] Tests run: 751, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

那一行 `规格校验` **不是** Maven 插件的输出，而是我们自己写的注解处理器在编译期打印的。
它意味着：`billing-app` 的每一个 `@Ac` 编号都已经和 `spec.md` 对齐过了。

测试数 751 里，712 条来自一个不变量参数矩阵（4 种月天数 × 6 种月费率 × 每种情况下的所有覆盖天数）。

## 2. 元验证 A · 编号不存在 → **编译失败**

在 `DateRange` 上加一个规格里没有的编号：

```java
@Ac({"4.1", "4.3", "9.9"})
public record DateRange(LocalDate startInclusive, LocalDate endExclusive) {
```

```
[ERROR] COMPILATION ERROR :
[ERROR] /D:/Code/SDD/examples/billflow/billing-app/src/main/java/dev/billflow/domain/DateRange.java:[21,8] @Ac("9.9") 在规格里不存在。
      规格文件：D:\Code\SDD\examples\billflow\specs\001-billing-mvp\spec.md
      实际存在：1.1–1.7, 2.1–2.4, 3.1–3.3, 4.1–4.4, 5.1–5.3
      两种可能：① 规格改了但这里没跟着改；② 编号写错了。
      （这是编译期检查：不存在「下不为例」的例外，必须修正）
[INFO] BUILD FAILURE
```

**注意它失败了三次中的哪一次**：不是测试阶段，不是 CI 的最后一步，而是**连 class 文件都没生成**。
写错编号的人拿不到任何可运行的产物。

**也注意错误信息的内容**：它列出了规格里实际存在的编号范围。一条只说「编号不存在」的报错，
会让人去翻 spec.md 手动对照；列出范围之后，多数情况下一眼就能看出是笔误还是规格真改了。

## 3. 元验证 B/C · 架构规则 → **测试失败**

注入两处违规：`Money` 里加 `static double toYuan(long)`，`DateRange` 里加一个读时钟的方法。

```
[ERROR]   LayerBoundaryTest.domainMustNotDeclareFloatingPoint:163 金额计算不得使用浮点（ADR-003 决策 1）：
[ERROR]   LayerBoundaryTest.domainMustNotReadTheClock:133 domain 不得读时钟（相同输入必须产生逐字节相同的账单）：
[ERROR]   LayerBoundaryTest.domainMustNotUseLegacyTimeOrClock:100 domain 不得依赖时钟或旧时间类型（规格 4.1、4.2 要求日历天计算是显式且确定的）：
[ERROR] Tests run: 751, Failures: 3, Errors: 0, Skipped: 0
```

surefire 报告里的违规明细（这是架构检查相对于 grep 脚本的价值所在）：

```
domain 不得读时钟（相同输入必须产生逐字节相同的账单）：
DateRange#hasStarted 调用了 java.time.LocalDate#now
DateRange#hasStarted 调用了 java.lang.System#currentTimeMillis

domain 不得依赖时钟或旧时间类型（规格 4.1、4.2 要求日历天计算是显式且确定的）：
DateRange → java.lang.System

金额计算不得使用浮点（ADR-003 决策 1）：
Money#toYuan 返回 double
```

**事件精确到方法**，而不是「某一行匹配到了某个词」。这就是为什么本案例把架构检查
从自制 shell 脚本换成了 ArchUnit —— 课程前面的 `check-layer-boundary.sh` 因为
把注释里的模块名当成违规，误报过两轮。

### 一个必须单独说的细节

同一个意图「不得读时钟」，**需要两条不同的规则**才能覆盖完整：

| 违规写法 | 能被依赖规则抓到？ | 原因 |
|---------|-----------------|------|
| `System.currentTimeMillis()` | ✅ 抓到 | `java.lang.System` 是一个类依赖 |
| `LocalDate.now()` | ❌ 抓不到 | owner 是 `java.time.LocalDate` —— 一个**完全合法的领域类型** |

所以「不得读时钟」这条规则不能只用「依赖了哪些类」表达，必须按**方法调用**去查。
初版只写了依赖规则，`LocalDate.now()` 从旁边溜过去了 —— 这也是本节最实用的一条经验：

> **约束的表达形式决定了它的覆盖范围。说不清的规则，等于没有规则。**

## 4.5 元验证 E · 最危险的一种失败：构建全绿，但校验从未运行

前四条验证的都是「注入违规 → 门禁变红」。第五条要验证的东西不一样：
**门禁到底有没有在跑。**

在 `billing-app/pom.xml` 的编译器配置里加一行 `<proc>none</proc>`（关掉注解处理，
现实中完全可能有人为了构建提速而这么做）：

```bash
# 直接跑 Maven —— 注意结果
cd examples/billflow && MAVEN_OPTS="-Dfile.encoding=UTF-8" mvn -B -q verify
echo $?
# 0            ← 构建成功，751 个测试全过，一条警告都没有

# 但规格校验一次都没执行。
```

而 `scripts/check-java-build.sh` 会拦住它：

```
::error::注解处理器没有运行，本次构建的「规格校验」等于没做。
    构建退出码：0（可能仍是 0 —— 那正是危险之处）
    常见原因（两种，都是静默的）：
      ① 没有在聚合根 examples/billflow 上跑构建。
      ② 增量编译：本次一个字节码都没重新生成（日志里是 'Nothing to compile'）。
退出码 1
```

## 4.6 门禁自己踩的坑：**增量编译让处理器一次都没跑**

`check-java-build.sh` 的第一版写的是 `mvn -B verify`。第一次跑是**绿的**，
**第二次跑就红了** —— 而代码一行没改。

```
$ MAVEN_OPTS="-Dfile.encoding=UTF-8" mvn -B verify | grep -iE 'Nothing to compile|规格校验'
[INFO] Nothing to compile - all classes are up to date.     ×3
（没有「规格校验」那一行）

$ MAVEN_OPTS="-Dfile.encoding=UTF-8" mvn -B clean verify | grep -iE 'Recompiling|规格校验'
[INFO] Recompiling the module because of changed source code.
[INFO] 规格校验：spec.md 共 21 条验收标准，代码标注了 21 条
```

一个字节码都没重新生成，`javac` 自然没有加载注解处理器。
于是「处理器跑了没发现问题」与「处理器没跑」的差别，**取决于上一次构建有没有留下 `target/`** ——
一个与本门禁意图完全无关的状态。修法是 `clean verify`（已改）。

**教训比修法重要：**

> 一道门禁必须自己保证「被检查的东西有机会发生」。
> 如果它的结论取决于上一次构建留下的缓存，那它的绿灯和红灯都不代表任何东西。
>
> 同理，CI 上不要把 `target/` 缓存复用到这一步 —— 缓存让构建更快，
> 但在这一步它会静默改变被检查的内容。**这一步的结论比它的速度重要。**

### 一个值得记下的细节：**同一个红灯可能来自两个不同的原因**

这个门禁一共报过两种红：一种是「处理器被 `proc:none` 关掉」（真正的危险），
另一种是「增量编译导致处理器没跑」（环境状态）。**它的报错在两种情况下都必须正确** ——
而不是碰巧对。所以错误信息里现在会同时列出两种可能，并告诉读者去哪看日志证据
（`Recompiling` / `Compiling` 有没有出现）。

### 为什么要有这一条

因为它把本课程反复出现的那句话落到了实处：

> **门禁最危险的失效不是报错，而是沉默。**

一个会报错的门禁会被修；一个**沉默不查**的门禁会一直绿下去，而所有人都以为有保护。
同一个形态在本仓库已出现四次：

| 出现位置 | 沉默的方式 | 症状 |
|---------|-----------|------|
| `verify-generated.sh`（初版） | 先重新生成再 diff → 把手改覆盖掉 | 它**修好了问题却报告没事** |
| `check-rendering.sh`（初版） | awk 变量名撞上内建函数 `close`，报错被 `2>/dev/null` 吞掉 | 那段检查**从未运行过**，却每次都返回通过 |
| `mvn verify`（本案例） | 处理器不在 classpath / 被 `proc:none` 关掉 | 构建全绿、测试全过，**规格校验为零** |
| `mvn verify`（增量构建，见 4.6） | 一个字节码都没重新生成 | `Nothing to compile`，处理器**一次都没跑** |

四次的修法一致：**不要相信「没有输出就是没问题」，要主动断言那个「我确实做了」的证据。**
`check-java-build.sh` 断言的就是注解处理器打印的那行标记。

## 5. 这个项目验证了什么

| 断言 | 证据 |
|------|------|
| 规格编号可以成为编译器的符号 | 元验证 A：未知编号 → 编译失败 |
| 架构约束可以机械强制，且不受注释干扰 | 元验证 B/C：字节码级检查，违规定位到方法 |
| 不变量可以强制的比测试更强 | `Invoice` 构造器：Σ明细 ≠ 总额的对象**根本无法被创建** |
| 覆盖面取决于规则怎么写 | `LocalDate.now()` 漏过依赖规则，被调用规则抓住 |
| 门禁必须自证会红 | 元验证 A/B/C/D 全部实测（会红的那四条；E/F 验的是另两件事，见下两行） |
| 门禁还必须自证**真的运行了** | 元验证 E：`proc:none` 下 `mvn verify` 退出码 0，而 `check-java-build.sh` 抓住「校验为零执行」 |
| 门禁必须自己保证被检查的事情**有机会发生** | 增量编译下 `mvn verify` 是 `Nothing to compile`；门禁改用 `clean verify`（见 4.6） |

## 6. 代价（诚实记录）

- **构建时间**：本案例 `mvn verify` 约 6 秒（含 751 个测试与架构检查）。注解处理器带来的额外开销可以忽略。
- **多模块复杂度**：`spec-guard` 必须独立成模块（鸡生蛋问题），这带来一个真实约束 ——
  **必须在聚合根上跑构建**。单独进 `billing-app` 目录跑 `mvn verify` 时，编译器找不到处理器，
  会**静默跳过**注解处理：构建全绿，但一点规格校验都没做。
  这是本案例最值得警惕的失败模式，也是"门禁的失效往往不是报错，而是沉默"的又一个实例。
- **不支持多币种小数位**：见 ADR-003 决策 1 的取舍记录。
