# ADR-003 · 把「当前时刻」做成数据库里的一张表

**状态**：已采纳
**日期**：2026-09-23
**关联标准**：3.2、3.3、3.4、3.5

---

## 背景

规格 3.5 要求：**一切与时间有关的行为都必须从调用方提供的当前时刻推导，不得读取系统时钟。**
动机是确定性与可重放 —— 而这条要求在数据层的实现里立刻撞上一个具体问题：

> 触发器里怎么拿到「当前时刻」？

可选写法有三类：`CURRENT_TIMESTAMP` / `datetime('now')`（读系统时钟，违反 3.5）、
把时刻作为参数传进 SQL（触发器**接不到参数**）、或者让时刻**在库里有一个位置**。

第三类是唯一可行的 —— 因为**触发器的时间来源只能是数据库内部的状态**。

## 决策

建一张**单行表** `clock (id, now)`，作为全库唯一的时刻来源。

```sql
CREATE TABLE clock (
  id  INTEGER PRIMARY KEY CHECK (id = 1),   -- 只允许一行
  now INTEGER NOT NULL
) STRICT;
INSERT INTO clock (id, now) VALUES (1, 0);
```

触发器与查询一律写 `(SELECT now FROM clock)`。测试通过
`UPDATE clock SET now = ?` 推进时间。CLI 在每次命令开始时用系统时钟**写一次**这张表 ——
系统时钟只在**边界**出现一次，之后整条调用链都读这张表。

## 后果

**好的**：

- **测试可以钉住时间。** 过期边界（`expires_at = now`）是可精确命中的，不需要 `sleep`，
  也不需要放宽断言 —— 而放宽断言正是测试失去价值的方式。
- **同一条语句内只有一个时刻。** 若用 `datetime('now')`，一条扫描几千行的语句里，
  「现在」可能在执行过程中变化，于是一部分行按 T₁ 判断、另一部分按 T₂。
  这类 bug 极难复现。用 `(SELECT now FROM clock)` 则**一次读取、全语句一致**。
- **状态完全由输入决定** ⇒ 整库可重放。这是 4.1 的守恒断言能写成「对任意操作序列成立」的前提。

**坏的 / 代价**：

- **多了一处必须维护的状态。** 忘了推进它就等于时间静止。CLI 因此必须**无条件**
  在命令开始时写入 —— 这个「无条件」是有意为之：一个「只在需要时才推进」的实现，
  会让「测试忘了推进」和「时间恰好没变」无法区分。
- **时间成了全局单点。** 它相当于给整个数据库加了一把隐式的共享变量。
  在单库范围的引擎里可接受；**在分布式或多租户下不可接受**。
- **对系统时钟的依赖没有被消除，只是被推到了边界。** 说出来比藏起来好：
  生产环境的正确性最终仍取决于那一次写入是否可信（NTP、时钟回拨）。

## 被拒绝的替代方案

| 方案 | 为什么拒绝 |
|---|---|
| `CURRENT_TIMESTAMP` / `datetime('now')` | 直接违反 3.5；且无法在测试中制造过期场景，除非 `sleep` |
| 时刻作为绑定参数传进每条语句 | 触发器**无法接收参数**，而 2.1、2.2、4.3⑥ 都必须在触发器里判定 |
| 给每条 SQL 生成两个版本（生产版读时钟 / 测试版传参） | 两份实现意味着两套语义，测试就不再证明生产版正确 |
| 用 SQLite 的自定义函数注入 now | 依赖具体客户端 API，违反非功能需求里的「可移植」（必须能用通用命令行客户端检查） |

## 一条被这条决策顺带回答的边角问题

AC 3.2 要求可用量排除「已过期但未收割」的 `held`。这条规则**必须在查询和触发器里用同一个时刻**，
否则会出现这种交错：

```
触发器按 T₁ 判定「还没过期，占用有效」→ 允许预占
查询 按 T₂ 判定「已经过期，不占用」→ 报告可用量比实际情况小
```

**两者都没错，只是看的时间不同。** 时钟表把这种「两个人看表差了一毫秒」的偏差
从语义问题降级为零 —— 代价是必须承认时钟是一个共享状态。
