# ADR-004 · 数据层做不到的事（边界与代价）

**状态**：已采纳
**日期**：2026-09-23
**关联标准**：全部（这是一篇**反对无条件采纳 ADR-001** 的记录）

---

## 背景

ADR-001 的结论（存在绕过路径时，约束必须住在数据层）很容易被读成
「那就把一切都搬进 schema」。**这份 ADR 记录的是搬不过去的那部分。**

一份只知道「该搬什么」而不知道「什么搬不了」的方案，
在遇到第一条例外时就会变成一份被违反的方案 —— 而**被违反的方案比没有方案更糟**，
因为它让所有人以为有保护。

---

## 一、四类搬不过去的东西

### ① 需要「解释」的错误

规格 5.3 要求稳定错误码。schema 能给出的是：

```
CHECK constraint failed: qty > 0
```

它**不是** `INVALID_QTY`，也说不清「数量必须是正整数，你传了 0」。
`schema → 错误码` 的映射表（`src/errors.mjs`）只能做到「引擎报错了、照这个文本查表」这个粒度。

**精度上限被锁死在这里。** 而这不是可以靠「再努力一点」解决的 —— 引擎的报错文本里
没有足够的信息。想要更好的信息，就必须在**报错的位置**（应用层）做检查，
而那时你已经放弃了一部分保证。

### ② 需要跨表语义的规则

「一条预占的 SKU 必须属于同一个租户」—— 这需要读三张表。
触发器**可以**写，但会变成一段没人能验证的 SQL：它有多个分支、多个失败模式，
而它**自己**不受任何约束保护。

**判据：当触发器的可读性成本超过它带来的保证时，应该往回退**，
退到「应用层检查 + 一条能发现违规的巡检查询」。
巡检查询的价值在于：它把「有没有被绕过」变成一个**可以定期回答**的问题，
而不是一个只能相信的前提。

### ③ 与业务流程绑定的规则

「VIP 客户可以超卖 5%」「促销期间允许透支」—— 这类规则**随时间变化**，
而且**有例外**。它们属于策略（policy），不属于结构（structure）。
把策略写进 schema 的后果：每次调整都要一次迁移，而迁移可能**重建表**。

### ④ 需要人类判断的规则

「这条预占看起来像是测试数据，应该被拒绝」—— 无法表达，也不该表达。

## 二、演化的代价（一个必须量化的真实成本）

SQLite 的 `ALTER TABLE` 只支持很有限的操作：加列、改名、删列（3.35+）。
**修改一条 `CHECK`、给触发器换条件、改列类型 —— 一律要「建新表 → 搬数据 → 换名」。**

这意味着：**约束越深，规格演化的单位成本越高。**

| 规格改动 | 住在应用层 | 住在数据层 |
|---|---|---|
| 改一句判断 | 改一行代码，跑测试 | **一次迁移**：建新表 + 搬数据 + 换名 + 处理存量违规数据 |
| 加一条新约束 | 加一个 `if` | 一次迁移，而且要回答「存量数据违反新约束怎么办」 |
| 删除一条约束 | 删一个 `if` | 一次迁移（且**要重新声明一遍整个表**） |

因此本案例采用的判据是**加权的**，不是无条件的：

> **约束住在数据层，当且仅当「它要拦住的写入可能不经过应用」而「它本身足够稳定」。**
> 两个条件缺一不可。

对库存而言「不能为负」满足两个条件（几十年的供应链系统都同意这一条）。
对「VIP 可透支 5%」则不满足第二个 —— 它应该住在策略层。

## 三、被接受的替代方案：巡检查询

对搬不过去的那部分，不假装它被强制了，而是**把它变成可观测的**：

```sql
-- 巡检：任何一行都说明有人在约束之外写了数据
SELECT sku_id FROM sku
WHERE on_hand <> (SELECT COALESCE(SUM(qty),0) FROM receipt WHERE sku_id = sku.sku_id)
               - (SELECT COALESCE(SUM(qty),0) FROM reservation
                  WHERE sku_id = sku.sku_id AND state = 'committed');
```

**它与触发器的关键区别**：触发器让违规**不可能发生**；巡检让违规**可见**。
两者都需要，但适用的规则不同。

> 把「无法强制的规则」明确降级为「可观测的规则」，比把它伪装成强制的规则要诚实 ——
> 而这正是本项目在 5.4 上采取的态度：**它没有说「在手量一定正确」，它说了「在手量必须可被推导出来」，
> 后半句是可机械验证的。**

---

## 四、结论

数据层强制的边界，用一句话概括：

> **schema 能表达「什么状态是合法的」，但表达不了「为什么」和「什么情况下可以例外」。**

前一半正是本案例要放进去的（也正是「绕过应用的写入」需要的那一半），
后一半必须留在应用层。

**一个还没有答案的连带问题**（留给读者）：一旦约束分居两层，
「规格覆盖率」这个指标该怎么算？`check-spec-coverage.sh` 只检查「每条标准都有测试」，
它无法区分「这条标准被强制了」与「这条标准只是被测试了」。
本案例的映射表用「**保证者**」一列补上了这个区分 —— 这是个局部答案，不是通用答案。
