# ADR-001 · 把约束放进数据层的判据

**状态**：已采纳
**日期**：2026-09-23
**关联标准**：全部（这是「住哪一层」的总判据）

---

## 背景

规格里 24 条标准，如果全部用应用代码里的 `if` 实现，会得到一份必须在**每一个写入路径**上都正确
的代码。而在库存系统里，「每一个写入路径」这个前提不成立：手工补数据、迁移脚本、监控脚本、
另一个服务的直连、DBA 的一条 `UPDATE` —— 它们都不经过我们的代码。

## 决策

采用**单一判据**：

> 这条标准要拦住的写入，会经过我这段代码吗？
> **不会 → 它必须住在数据层。**

判据的含义不是「数据层更好」，而是**数据层是唯一还在场的位置**。
在这个意义上，把约束放进 schema 不是一种风格选择，而是**由「存在绕过路径」这个事实推出的结论**。

配套的三条落地规则：

1. **能用更简单的机制表达，就不要用更复杂的。** 阶梯顺序是
   `列类型/STRICT` → `CHECK` → `UNIQUE` → `FOREIGN KEY` → `TRIGGER`，
   理由是**失败信息的可定位性**：`CHECK` 的报错指向列（可直接对应规格编号），
   触发器的报错只指向触发器名。
2. **唯一性必须用 `UNIQUE`，不能用触发器里的「先 SELECT 再判断」。**
   后者是竞态：并发下两个请求可以同时通过 SELECT 检查、然后都 INSERT。
   唯一约束没有这个窗口。
3. **应用层的同类检查可以保留，但它的定位是「优化」，不是「保证」。**
   允许它给出更友好的提示，不允许它是唯一的检查。

## 后果

**好的**：

- 4.3 的六种非法状态**无法被写入**，与写入者是谁无关。测试可以完全不 import 应用代码来证明这一点。
- 4.1 的守恒等式变成**可查询的事实**（一条 `SELECT` 就能核对），而不是「相信代码是对的」。

**坏的 / 代价**：

- **代码不再是可读的规格。** 读 `migrations/001_init.sql` 需要 SQL 知识，而读一段
  `if (available < qty) throw ...` 谁都看得懂。这是真实的可维护性损失。
- **错误信息变差。** 引擎的错误是 `CHECK constraint failed: qty > 0`，不是
  「数量必须为正整数（AC 1.5）」。`src/errors.mjs` 的映射表就是在偿还这笔债 ——
  而它**只能**映射到「引擎有没有报错」这种粒度，精度上限由此被锁死。
- **规则演化变贵。** SQLite 的 `ALTER TABLE` 能力有限，改一条 `CHECK` 往往要**重建表并搬数据**。
  规格演化频繁的领域不适合这么做，见 ADR-004。

**一个必须写下来的连带决策**：本案例**不做 domain / store 分层**，与 `billflow` 相反。
分层的前提是「领域规则住在领域层」，而这里规则住在 schema 里。
硬造一个空的 `domain/` 目录会传递**错误的事实**——让读者以为规则在代码里。
目录结构本身就是文档，它不该说谎。

## 被拒绝的替代方案

| 方案 | 为什么拒绝 |
|---|---|
| 全部放应用层 | 拦不住绕过路径的写入，而绕过路径**存在**（这正是本案例的出发点） |
| 全部放数据层，应用层只做透传 | 做不到：4.4 的原子性必须由调用方开事务；2.1 的两步动作也需要一个事务边界 |
| 用 ORM 的校验钩子 | 钩子是**应用层**的机制，同样拦不住绕过路径 —— 但它读起来像数据层的保证，**这种错觉比没有更危险** |
| 加一个「写入服务」并要求所有人都走它 | 组织约束，不是技术约束。**能被绕过的约束不叫约束。** |
