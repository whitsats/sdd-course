# ADR-002 · 外键是唯一一种「schema 里有、但可能不生效」的约束

**状态**：已采纳（本案例最核心的一篇）
**日期**：2026-09-23
**关联标准**：1.6、4.3③、4.5

---

## 背景

规格 4.3③ 要求：引用不存在的 SKU 的写入必须被拒绝。
最自然的实现是 `FOREIGN KEY`。**实测结论：这不够。**

## 证据

同一个库文件 `probe.db`、同一个 schema、同一条语句：

```sql
INSERT INTO reservation (res_id, sku_id, qty, ...) VALUES ('r1', 'ghost', 1, ...);
```

`sku` 表里没有 `ghost`。三个客户端的结果：

| 客户端 | SQLite 版本 | `PRAGMA foreign_keys` | 结果 |
|---|---|---|---|
| Node `node:sqlite` | 3.50.4 | **1** | ✅ 拒绝：`FOREIGN KEY constraint failed` |
| Python `sqlite3` | 3.37.2 | **0** | ❌ **写入成功**，幽灵行留在库里 |
| `sqlite3` 命令行 | 3.44.4 | **0** | ❌ **写入成功** |

（完整复现脚本见 [`notes/L14-数据层强制.md`](../../notes/L14-数据层强制.md) 的 §3。）

## 根因

`PRAGMA foreign_keys` 是**连接级**设置，不是**库级**设置 —— 它**不随着 schema 一起持久化**。
谁建连接，谁就要负责把它打开；不开就是关的，而且**没有任何警告**。

三个客户端对「默认该不该开」做了不同的选择：

- **开**：认为「用户声明了 `REFERENCES`，就是想让它生效」。
- **关**：来自 SQLite 早期历史 —— 加这个特性时已有大量依赖「可以插幽灵行」的存量应用，
  所以为了**向后兼容**而默认关闭。Python 的 `sqlite3` 与命令行客户端保留了这个默认值。

**两个默认值都不是 bug。** 但它们意味着同一份 schema 的**实际强制力取决于客户端**。

## 决策

1. **仍然使用 `FOREIGN KEY`** —— 它是表达「1.6」的正确机制，不应该放弃。
2. **在建立连接的代码里显式开启，并立即断言**（对应规格 4.5）：

   ```js
   db.exec('PRAGMA foreign_keys = ON');
   const [{ foreign_keys: fk }] = db.prepare('PRAGMA foreign_keys').all();
   if (fk !== 1) throw new Error('引用完整性未启用：本次运行的所有外键约束都不会生效');
   ```

   注意顺序：**先设置，再读回来验证**。只写第一行是不够的 —— 见下面「为什么必须读回来」。

3. **把「哪些客户端默认关闭」写进本项目文档**，而不是指望每个人都记得。
   顺带记录 Node 侧的两个开关（实测）：构造器默认 `enableForeignKeyConstraints: true`；
   传 `false` 会让 `PRAGMA foreign_keys` 读回 `0`。也就是说**驱动的默认值也是可配置前提的一部分**。
4. **在 CI 里也检查一遍**（`scripts/check-sql-enforcement.sh`），因为这条规则的正确性
   依赖于**运行时**，而不是任何静态文本。

## 为什么必须读回来验证（而不是「写了 PRAGMA 就有把握」）

`PRAGMA foreign_keys` 还有一个不显眼的行为：**在事务内设置它会被静默忽略。**
实测（Node 24 / SQLite 3.50.4）：

```
① 默认值              = 1
② 显式关闭后           = 0
db.exec('BEGIN');
db.exec('PRAGMA foreign_keys = ON');     ← 不抛错
③ 事务内设 ON（读回）   = 0                ← 但没生效
COMMIT;
④ 提交后              = 0                ← 也没有「延迟生效」
db.exec('PRAGMA foreign_keys = ON');     ← 事务外设置
⑤ 非事务内设 ON（读回） = 1                ← 这才生效
   → 幽灵行被拒绝：FOREIGN KEY constraint failed
```

也就是说，**`PRAGMA foreign_keys = ON` 这一行本身就是一个「写了但没生效」的门禁** ——
与它要防的东西是**同一个形态**。

这条原则在整个课程里出现过四次（见 `notes/L14` 的 §5）：
`verify-generated.sh` 先重生再 diff、`check-rendering.sh` 的 awk 变量撞内建函数、
`mvn verify` 的 `proc:none`，以及这里的 PRAGMA。
四次都是**「代码在、但什么都没发生」**，四次都不能靠「读代码」发现，只能靠**读回来断言**。

## 后果

**好的**：

- 4.3③ 从「schema 里看起来有」变成「运行时确实有」。
- 这条 ADR 本身就是**一条可教的原则**：**声明性约束的可信度，取决于执行环境是否兑现了它的前提。**

**坏的 / 代价**：

- **强制力不再完全自包含。** schema 不再足以描述系统的真实保证 —— 还需要一份「连接建立规程」。
  这是一个真实的复利成本：每多一种客户端，就多一个需要验证的地方。
- 若某天有人绕过 `db.mjs` 直接用别的客户端连这个库（例如排障时用命令行），
  **他会看到一个没有外键约束的库**。这是无法通过技术手段消除的，只能通过文档与约定降低概率。

## 一个反直觉的推论

通常我们认为「约束越深越安全」。这里出现了反例：

> **约束放得越深，它的生效就越依赖「别人愿不愿意兑现前提」。**

应用层的 `if` 永不被绕过 —— 因为绕过它的人同时也绕过了这段代码。
数据层的约束反而引入了「schema 之外的前提」。

**这不推翻 ADR-001 的结论**（在存在绕过路径的前提下，数据层仍是唯一在场的位置），
但它给那个结论加了一个必须同时交付的配套件：**对前提本身的检查。**
