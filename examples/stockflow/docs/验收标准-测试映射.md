## 本表比前面四个案例多了一列，为什么

前面四张表回答的是「这条标准有测试吗」。本案例多一列 **保证者**，因为
「有测试」与「被强制」在本案里是**两个不同的问题**：

| | 有测试 | 被强制 |
|---|---|---|
| 含义 | 我们验证过它成立 | 它不可能不成立 |
| 反例 | 测试覆盖了「数量为 0 会被拒绝」，但有人用命令行直写 | 写不进去 |
| 本案例里 | 由 `node --test` 提供 | 由 schema 提供 |

`check-spec-coverage.sh` 只看前者的**条数**（它无法区分「被强制」与「只是被测试」）。
这一列是补上的定性说明 —— 它是一个**局部**答案，不是通用答案（见 `docs/adr/ADR-004` 结尾）。

**保证者一栏的取值**：
`STRICT` / `CHECK` / `UNIQUE` / `FK` / `TRIGGER` = schema 强制；
`事务` = 应用层用事务保证（唯一搬不过去的一类）；
`巡检` = 无法强制，只能观测。

## 元验证记录（本表不是承诺，是实测）

**全部为实际执行结果**，非预期值。复现命令见 [`notes/L14-数据层强制.md`](../notes/L14-数据层强制.md) §5。

| 试验 | 注入的违规 | 实际结果 |
|------|-----------|---------|
| A | 删掉 `trg_reservation_no_oversell` 整段触发器 | `check-sql-enforcement.sh` **4 项变红**：`超卖（AC 1.2）` 直接成功、过期后可用量算成 3、`③ 直写成功：超量预占`、巡检报出 `OVERSELL` |
| B | 删掉 `sku` 的 `CHECK (on_hand >= 0)` | **3 项变红**：`① 直写成功：在手量改负`、守恒被破坏、巡检报出 `delta = -1` |
| C1 | 在驱动层关掉外键（`enableForeignKeyConstraints: false`）并删掉显式 PRAGMA，**保留断言** | **连接时立刻抛错**：`引用完整性未启用（PRAGMA foreign_keys = 0）`，20 项几乎全红 —— 大声失败 |
| C2 | 在 C1 基础上**再把断言也删掉** | **静默降级**：`SKU 不存在（AC 1.6）` 期望 `UNKNOWN_SKU` 却「已预占」成功，`⑧-b` 也变红。**幽灵行经由应用写进了库** |
| D | 只删掉 `db.exec('PRAGMA foreign_keys = ON')`、保留断言（不碰驱动默认值） | **门禁依然全绿，20/20** —— 见下面的说明 |
| E | 从本表删掉一行 | `check-spec-coverage.sh` 报「缺少测试映射的标准编号」并指出具体编号 |

> **C1 与 C2 是本案例最有价值的一对**：同一个缺陷，有断言时是「连接就炸」，
> 没断言时是「安静地放行脏数据」。**断言的成本是一行代码，收益是把静默降级变成响声。**

> **D 是一个诚实但尴尬的发现，值得单独说。**
> `db.exec('PRAGMA foreign_keys = ON')` 那一行**在当前 Node 驱动上是冗余的** ——
> 驱动默认已经打开它，所以删掉它门禁不会红。
> 它的价值在于**未来的默认值变化**（或换驱动、换运行环境），而
> **门禁无法验证一个尚未发生的未来**。
> 这条记录下来的意义是：不要把「门禁没红」当成「这行代码没用」的证据 ——
> 它只说明**今天**它没有承担负荷。判据是「删掉它之后，什么情况下会出事」，
> 而不是「删掉它之后 CI 什么颜色」。
