## §1 一句话结论

> 前四个案例把约束往**早**推（测试 → CI → 生成 → 编译期）。
> 这个案例推到**最晚**：晚到应用程序已经不在了也拦得住。
>
> **代价是：强制力不再自包含。** 它取决于「谁来连接」。

## §2 约束阶梯：一条规格该住在哪一级

判据只有一条：

> **这条标准要拦住的写入，会经过我这段代码吗？** 不会 → 它必须住在数据层。

按「数据层能表达多复杂的条件」，从小到大排开，然后**优先用低的一级**：

| 级 | 载体 | 能表达 | 本案例承担 | 失败信息的定位精度 |
|---|---|---|---|---|
| ① | 列类型 + `NOT NULL` + `STRICT` | 「这一列必须是整数」 | 5.1 | 列 |
| ② | `CHECK` | **单行内**的取值 | 1.5、3.1、状态域 | 列 |
| ③ | `UNIQUE` / `PK` | 跨行**唯一性** | 1.4（幂等的载体） | 列 |
| ④ | `FOREIGN KEY` | 跨表**存在性** | 1.6 | 表 |
| ⑤ | `TRIGGER` | 跨行**聚合与派生** | 1.2、2.1、2.2、2.6、5.2、5.4 | **触发器名**（需要再翻译一次） |
| ⑥ | 事务（调用方） | 多个动作**同生共死** | 2.1 的另一半、4.4 | 应用 |

**为什么「优先用低的一级」是有理由的，而不是风格偏好**：`CHECK` 的报错是
`CHECK constraint failed: qty > 0` —— 它能直接对应到规格编号 1.5；
触发器的报错是 `INSUFFICIENT_STOCK` —— 它是**我们自己起的名字**，
读到它的人多了一步翻译。**可定位性是有成本的，能省就省。**

**③ 必须用 `UNIQUE` 而不能用「先 SELECT 再 INSERT」**：后者是竞态。
两个并发请求可以同时通过 SELECT 检查、然后都 INSERT。唯一约束没有这个窗口 ——
它由引擎原子保证。这是本案例里唯一一处**不是「更清晰」而是「根本做不到」**的选择。

**① 与 ② 的差别最容易被忽略，代价最大**：SQLite 默认**动态类型**，
一个声明为 `INTEGER` 的列会欣然接受 `'abc'`：

```
⑦ INSERT ... qty = 'abc' ...  → rejected: cannot store TEXT value in INTEGER column reservation.qty
```

没有 `STRICT` 的话，「数量是整数」这条标准其实**没有被任何东西保证**。

## §3 招牌演示：完全不加载一行 JavaScript

```bash
cp var/stockflow.db /tmp/bypass.db
sqlite3 /tmp/bypass.db "PRAGMA foreign_keys;"      # → 0
```

八条直写，**全部由引擎判定，没有任何应用代码参与**：

```
①  UPDATE sku SET on_hand = -1;                                    → rejected  CHECK constraint failed: on_hand >= 0
②  INSERT INTO reservation ... qty = 0 ...                         → rejected  CHECK constraint failed: qty > 0
③  INSERT INTO reservation ... sku_id = 'GHOST' ...                → ACCEPTED  ← 唯一漏掉的一条
④  INSERT INTO reservation ... qty = 999 ...                       → rejected  INSUFFICIENT_STOCK
⑤  UPDATE reservation SET state='held' WHERE res_id='R-DEMO';      → rejected  INVALID_STATE
⑥  UPDATE reservation SET qty=0 WHERE res_id='R-DEMO';             → rejected  IMMUTABLE_FIELD
⑦  INSERT INTO reservation ... qty = 'abc' ...                     → rejected  cannot store TEXT value in INTEGER column
⑧  INSERT INTO reservation ... expires_at < created_at ...         → rejected  CHECK constraint failed: expires_at > created_at

SELECT count(*) FROM reservation WHERE sku_id='GHOST';             → 1
```

**7 拦 1 漏。而漏掉的那一条，恰好是强制力挂在 `PRAGMA foreign_keys` 上的那一条。**

这不是运气不好，这是一个**结构性的结论**：`CHECK`、`STRICT`、`TRIGGER`、`UNIQUE`
都是 schema 的一部分，随库走；**只有 `FOREIGN KEY` 需要每一次连接兑现前提**。

### 为什么单看这一行「AC 4.3 有 6 个子项」是不够的

`4.3③`（引用不存在的 SKU）在规格里和 `4.3①`（负库存）长得一样 ——
都是「非法写入必须被拒绝」。但它们的**强制机制不同类**：
一个不需要前提，一个需要。规格没有区分它们，因为规格不该谈机制；
而**实现必须知道这个区别**，否则会写出「测试全绿、线上放行」的系统。

## §4 同一个库、同一条语句、三个客户端

```sql
INSERT INTO reservation (res_id, request_id, sku_id, qty, ...) VALUES ('r1','q1','GHOST',1,...);
```

| 客户端 | SQLite 版本 | `PRAGMA foreign_keys` | 结果 |
|---|---|---|---|
| Node `node:sqlite` | 3.50.4 | **1** | ✅ `FOREIGN KEY constraint failed` |
| Python `sqlite3` | 3.37.2 | **0** | ❌ **写入成功** |
| `sqlite3` 命令行 | 3.44.4 | **0** | ❌ **写入成功** |

**没有哪个默认值是 bug。** 这个 PRAGMA 默认关闭来自 SQLite 的早期历史 ——
加这个特性时已有大量依赖「可以插幽灵行」的存量应用，为了向后兼容才默认关闭。
Python 与命令行客户端保留了这个默认值；Node 选择了相反的一侧。

### 而且：那一行 PRAGMA 本身也可能「写了但没生效」

```
① 默认值              = 1
② 显式关闭后          = 0
db.exec('BEGIN');
db.exec('PRAGMA foreign_keys = ON');     ← 不抛错
③ 事务内设 ON（读回）  = 0                 ← 但没生效
COMMIT;
④ 提交后              = 0                 ← 也没有「延迟生效」
db.exec('PRAGMA foreign_keys = ON');     ← 事务外设置
⑤ 非事务内设 ON（读回）= 1                 ← 这才生效
   → 幽灵行被拒绝：FOREIGN KEY constraint failed
```

**「写了 PRAGMA 但没生效」与「schema 里写了 REFERENCES 但没生效」是同一个形态。**
所以 `src/db.mjs` 的做法是：**先设置，再读回来断言**（AC 4.5）。

### 附带的一个建设性发现

`journal_mode = WAL` 与 `foreign_keys` 都是 `PRAGMA`，但**前者随库文件持久化，后者随连接生灭**。
判断依据只能是查文档或实测一次 —— 靠直觉会猜错（我猜错了：我以为两个都随库）。

### C1 与 C2 是本案例最有价值的一对

同一个缺陷，**有没有那条断言**决定了它的形态：

| | 有断言 | 没断言 |
|---|---|---|
| 表现 | 连接时抛错 | 安静地放行脏数据 |
| 什么时候发现 | 立刻 | 不知道什么时候 |
| 成本 | 一行代码 | —— |

### 元 D 是一个诚实但尴尬的发现

`db.exec('PRAGMA foreign_keys = ON')` 那一行在当前 Node 驱动上是**冗余的** ——
驱动默认已开，所以删掉它门禁**不会红**。

它的价值在于**未来的默认值变化**（或换驱动、换运行环境），
而**门禁只能验证现在，无法验证一个尚未发生的未来**。

> 所以：**不要把「门禁没红」当成「这段代码没用」的证据。**
> 判据是「删掉它之后，什么情况下会出事」，而不是「删掉它之后 CI 什么颜色」。

## §5.5 门禁自己踩的坑（这一段比 §5 更有用）

写 `check-sql-enforcement.sh` 的过程中，这个门禁自己出了 **4 个问题**，
而且**全部是「静默不检查 / 报错报在错的地方」，没有一个误报**。
它们与它要防的东西是同一个形态，所以值得逐条记下来：

### ① 错误码检查读到空字符串

`run_cli` 的实现里有 `2>/dev/null`，而 CLI 的**稳定错误码是打到 stderr 的**（AC 5.3）。
于是「超卖 → INSUFFICIENT_STOCK」这类检查全部读到空：

```
✖ 超卖（AC 1.2） 期望 INSUFFICIENT_STOCK，实际：
```

修法：分成两个包装器 —— 取数值的丢掉 stderr，查错误的连 stderr 一起取。

### ② `$RID` 是空串 → 「什么都没发生」被当成「写入成功」

```bash
UPDATE reservation SET state='held' WHERE res_id='';   -- 匹配 0 行
```

不报错。而 `reject_case` 的判断是「没有输出 = 写入成功」，于是**假绿**：

```
✖ ④ 直写**成功**了：从终结态复活（AC 4.3⑤） —— 这条约束没有生效
```

实际情况是那条约束好好地在那儿，只是**没有任何行被碰过**。
修法有两处：用 `--res=` 固定标识（不让随机 id 造成这种歧义），
**并且**在直写之前先断言目标行存在且状态正确。

### ③ `set -o pipefail` 让「断言它失败」的检查永远失败

```bash
if cli reserve GHOST 1 | grep -q UNKNOWN_SKU; then ... fi
```

被检查的命令以 1 退出，`pipefail` 让**整条管道**返回 1 ——
于是 grep 找到了匹配也白搭，`if` 永远走 else：

```
✖ ⑧-b 同一写入经由应用**没有**被拒绝 —— 外键在我们的连接上也没生效
```

真相是它**被正确拒绝了**。这是本仓库里唯一一个**假红灯**，
而它比假绿灯更容易被忽略（人会去改代码，而不是去看门禁）。
修法：凡是「断言某命令失败」的地方，**先落变量再匹配**。

### ④ 元 C 第一次注错了

我一开始把「关掉外键」实现成「删掉那行 PRAGMA」，
结果门禁**全绿** —— 因为驱动默认是开的。于是我以为元验证失效了，
实际是我的注入没有关掉任何东西。**一次错误的元验证会让人误信门禁无效**，
这比不做元验证更危险：它会诱使你放宽门禁。

### 测试自己的两个坑

**⑤ 用一个没有真正违反约束的用例去测约束**

```js
// 旧值就是 'SKU-1'，于是 NEW <> OLD 为假，触发器**正确地**没有触发
for (const set of ['qty = 0', "sku_id = 'SKU-1'", ...]) { ... }
```

失败的是测试，不是代码。这类假失败会浪费一轮排查。

**⑥ `node:sqlite` 返回的行对象原型是 `null`**

`assert.deepStrictEqual` 会比较原型，于是两个字段完全相同的对象报「deepStrictEqual 失败」，
而打印出来的 actual 与 expected **一模一样**。看到这种报错先想原型。

## §6 规格还没说的地方（本次实现暴露出来的空白）

| 位置 | 空白 | 当前行为 | 风险 |
|---|---|---|---|
| AC 1.4 | 同一 `request_id` 配**不同参数**（不同 sku / 不同数量）时怎么办 | 照字面执行 1.4：返回首次结果，**忽略本次参数** | 调用方以为按新参数占用了，实际没有。这类错误在幂等接口上很常见且很难查 |
| 规格全文 | 「预占不存在」时返回什么 | `NOT_FOUND`（自定，规格未覆盖） | 与 `INVALID_STATE` 的边界靠调用方自己理解 |
| AC 4.1 | 入账这件事本身要不要留痕 | 已建 `receipt` 表（AC 5.4） | 规格 §6.1 已把它列为澄清项，本次按「要留痕」实现 |
| AC 2.6 | 已过期的 `held` 可否兑现 | **拒绝**（本次裁定，已写进规格） | 裁定理由见规格 §6.2 —— 双重计数 + 错误码质量 |

**其中 1.4 那条最值得回头补**：它是**幂等接口的经典歧义**，
而且本案例的实现选择（忽略本次参数）是**静默**的 —— 没有错误码，没有日志。

## §8 这一节留给读者的判断

数据层强制不是「更高级的做法」，它是一次**交换**：

| 换来的 | 付出的 |
|---|---|
| 绕过应用的写入也拦得住 | 强制力不再自包含：需要一份「连接建立规程」 |
| 不变量变成可查询的事实 | 代码不再可读地表达规格 |
| 测试可以不 import 应用代码 | 错误信息精度被引擎锁死 |
| 约束无法被绕过 | 每次规格演化 = 一次可能重建表的迁移 |

**判据（本案例采用的加权版本）**：

> 约束住在数据层，当且仅当 **「它要拦住的写入可能不经过应用」** 且 **「它本身足够稳定」**。
> 两个条件缺一不可。

「库存不能为负」两个都满足。「VIP 可透支 5%」不满足第二个 —— 它应该住在策略层。
搬不过去的那部分，不要假装它被强制了，**把它降级成一条能被定期执行的巡检查询**
（`queries/patrol.sql`），并在文档里说清楚它只是「可见」，不是「不可能」。

**把「无法强制的规则」明确降级为「可观测的规则」，比把它伪装成强制的规则要诚实。**
