# 功能规格 · stockflow 库存预占引擎（MVP）

**Feature**：`001-stockflow-mvp`
**等级**：Spec-Anchored 的**数据层强化版** —— 约束不只写在代码里，而是落在 schema 上
**状态**：待实现

> 📌 **本文件只描述「要什么」，不出现任何技术栈词汇。**
> 没有 SQLite、没有 Node、没有触发器。原因和 billflow 里一样，但在这里更关键：
> 一旦规格里出现「用触发器实现」，你就把**约束该放在哪一层**这个本该在 `plan.md` 里
> 权衡的决策，偷偷变成了需求的一部分。

## 1. 背景与范围

一个库存预占（reservation）引擎：客户下单时先**预占**库存，随后**兑现**（真出库）或**释放**。核心风险只有一个 —— **超卖**：卖出去的比库里有的多。

**为什么这个领域值得单独做一个案例**：前四个案例的约束都放在**代码路径上**（测试、CI、生成器、编译器），它们有一个共同的隐含前提 —— **所有的写入都会经过这段代码**。库存系统不满足这个前提：运维手工补数据、数据迁移脚本、监控系统、另一个服务的直连、DBA 的一条 `UPDATE`……每一个都是绕过应用的写入路径。

于是出现了这个案例要回答的问题：

> **一条规格，如果要拦住「不经过你的代码的写入」，它必须住在哪里？**

**答案是数据层** —— 不是因为它更好，而是因为它是**唯一**还在场的位置。本案例的一半价值在于这件事成立，另一半在于它的**代价和边界**（不是所有规格都能搬过去，而且搬过去之后强制力会变得依赖于客户端）。

### 范围内

- 库存单位（SKU）的在手量与可用量
- 预占 / 兑现 / 释放 / 过期收割四条状态流转
- 预占的幂等（同一请求重复提交）
- 并发预占下的不超卖保证
- 「绕过应用程序」的非法写入必须被拒绝
- 状态流转的可追溯留痕

### 范围外（明确不做）

- 多仓库、调拨、批次/序列号、保质期
- 采购入库、退货入库的完整流程（只提供设置在手量的入口）
- 价格、订单、支付、发货
- 分布式多节点的库存一致性（本案例是**单库**范围）
- 性能压测与容量规划（只验证正确性）

## 2. 术语

| 术语 | 定义 |
|------|------|
| **SKU** | 一个库存单位，拥有唯一标识与一个**在手量** |
| **在手量（on_hand）** | 物理上在库的数量，非负整数。**它是推导值，不是可直接修改的字段**（见 5.4） |
| **入账（Receipt）** | 一次库存增加的只增不改流水。在手量的**任何**增加都源于它 |
| **预占（Reservation）** | 一条「某 SKU 的 N 件已被占用、但尚未出库」的记录 |
| **可用量（available）** | `on_hand` 减去所有**生效中**预占的数量。可用量不落库，是**推导值** |
| **生效中的预占** | 状态为 `held` 且**未过期**（`expires_at > 当前时刻`） |
| **兑现（commit）** | 把预占转为已出库：在手量减少、预占终结 |
| **释放（release）** | 放弃预占：不改变在手量，预占终结 |
| **收割（reap）** | 把**已过期**的 `held` 批量终结为 `released` |
| **当前时刻（now）** | 一个**由调用方提供**的时刻，不是系统时钟。见 3.5 |
| **状态** | 每条预占恰处于 `held`、`committed`、`released` 三者之一 |
| **终结态** | `committed` 或 `released`。终结态不可再流转 |
| **请求标识（request_id）** | 调用方为一次业务操作生成的唯一标识，用于幂等 |

## 3. 用户故事与验收标准

### US1 · 预占

> **作为下单流程**，我要能占用库存并在之后确认或放弃，使「我看到的可卖数量」不会变成超卖。

| 编号 | 验收标准 |
|------|---------|
| 1.1 | WHEN 预占被接受 THE SYSTEM SHALL 创建恰好一条记录，其状态为 `held`，并记录 SKU 标识、数量、请求标识、创建时刻与过期时刻 |
| 1.2 | IF 预占后的可用量将小于 0 THEN THE SYSTEM SHALL 拒绝预占并返回 `INSUFFICIENT_STOCK` |
| 1.3 | IF 预占被拒绝 THEN THE SYSTEM SHALL 不留下任何痕迹：记录数、可用量、流转留痕三者在拒绝前后**完全相同** |
| 1.4 | WHEN 同一请求标识被重复提交 THE SYSTEM SHALL 返回**首次**的结果，且**不得**产生第二条记录、不得二次占用 |
| 1.5 | IF 数量不是正整数 THEN THE SYSTEM SHALL 拒绝并返回 `INVALID_QTY` |
| 1.6 | IF 目标 SKU 不存在 THEN THE SYSTEM SHALL 拒绝并返回 `UNKNOWN_SKU` |

### US2 · 兑现与释放

> **作为履约流程**，我要让「确认出库」和「取消占用」都不可逆、不可重复、且不破坏库存账。

| 编号 | 验收标准 |
|------|---------|
| 2.1 | WHEN 兑现一条 `held` 的预占 THE SYSTEM SHALL 同时完成两件事：该预占转为 `committed`，且对应 SKU 的在手量**减少该预占的数量**。两步必须同生共死 |
| 2.2 | IF 状态为 `held` 之外的状态被要求兑现或释放 THEN THE SYSTEM SHALL 拒绝并返回 `INVALID_STATE`；**终结态不得复活** |
| 2.3 | WHEN 一条已经是 `committed` 的预占被再次兑现 THE SYSTEM SHALL 判为幂等成功，且**不得**二次扣减在手量 |
| 2.4 | WHEN 释放一条 `held` 的预占 THE SYSTEM SHALL 使其不再计入可用量，且**不改变**在手量 |
| 2.5 | THE SYSTEM SHALL 保证不存在「已兑现却未扣减」或「未兑现却已扣减」的记录组合 |
| 2.6 | IF 一条 `held` 的预占**已过期**而被要求兑现 THEN THE SYSTEM SHALL 拒绝并返回 `EXPIRED`，**不得**扣减在手量（该分歧点在 §6.2 已裁定，裁定理由见 `plan.md` §3.2） |

### US3 · 过期

> **作为库存持有方**，我要让客户放弃的预占自动把库存还回来，而且这件事必须可复现、可重放。

| 编号 | 验收标准 |
|------|---------|
| 3.1 | IF 过期时刻不晚于创建时刻 THEN THE SYSTEM SHALL 拒绝创建并返回 `INVALID_EXPIRY` |
| 3.2 | THE SYSTEM SHALL 在计算可用量时**排除**已过期但尚未收割的 `held` 记录 |
| 3.3 | WHEN 收割在时刻 T 执行 THE SYSTEM SHALL 把所有满足 `expires_at ≤ T` 的 `held` 终结为 `released` |
| 3.4 | WHEN 收割被重复执行（或对同一批数据换一个更晚的 T 执行）THE SYSTEM SHALL 不产生任何额外的状态变更；收割是幂等的 |
| 3.5 | THE SYSTEM SHALL 从**调用方提供的当前时刻**推导一切与时间有关的行为（过期判定、收割范围、留痕时间戳），**不得**读取系统时钟，以保证同一组输入在任何时刻重放都得到相同结果 |

### US4 · 守恒、并发与绕过

> **作为系统的最终责任人**，我要在**任何**写入路径下都拿得到正确结果 —— 包括不经过这个应用的写入。

| 编号 | 验收标准 |
|------|---------|
| 4.1 | THE SYSTEM SHALL 在所有时刻满足**库存守恒**：`在手量 + Σ(已兑现数量) − Σ(已入账的入库量) == 0`，且该等式对任意操作序列成立 |
| 4.2 | WHEN N 个客户端并发对同一 SKU 预占时 THE SYSTEM SHALL 保证成功者数量之和不超过该 SKU 的初始在手量；**任何**并发交错都不得造成超卖 |
| 4.3 | IF **绕过应用程序**的写入试图造成下列任一非法状态 THEN THE SYSTEM SHALL 拒绝该写入：<br>① 负的在手量 ② 非正数量的预占 ③ 引用不存在的 SKU ④ 计次超量的预占 ⑤ 从终结态出发的状态流转 ⑥ 满足「生效中预占量 > 在手量」的写入 |
| 4.4 | IF 一个操作序列中途失败 THEN THE SYSTEM SHALL 保证其所有已生效的部分全部回滚，不留下部分状态 |
| 4.5 | THE SYSTEM SHALL 保证**每一个**建立到本库的连接都启用了引用完整性检查，并在**无法启用**时立刻失败，而不是静默降级 |

### US5 · 可追溯

> **作为排障的人**，我要能从数据本身还原「发生了什么」，而不是去猜应用日志。

| 编号 | 验收标准 |
|------|---------|
| 5.1 | THE SYSTEM SHALL 在每条预占上记录：SKU 标识、数量、状态、请求标识、创建时刻、过期时刻、终结时刻（若已终结） |
| 5.2 | WHEN 一条预占被创建或发生状态流转 THE SYSTEM SHALL 追加一条**只增不改**的留痕，记录来源状态、目标状态与发生时刻 |
| 5.3 | THE SYSTEM SHALL 以**稳定错误码**表达每一种拒绝原因（`INSUFFICIENT_STOCK`、`INVALID_QTY`、`UNKNOWN_SKU`、`INVALID_STATE`、`INVALID_EXPIRY`），调用方**不需要**解析错误文本即可分支处理 |
| 5.4 | THE SYSTEM SHALL 保证库存的**任何**增加都以一条只增不改的入账记录（含数量与时刻）表达，**不得**存在直接修改在手量的路径；在手量必须可完全由入账流水与已兑现预占推导出来 |

## 4. 规格的「可执行性」检验：三个必须能算清的例子

**例 1（边界）**：在手量 10，预占 10 条各 1 件 → 全部成功，可用量 0；再来 1 件 → `INSUFFICIENT_STOCK`。
注意 1.2 的措辞是「**预占后**的可用量将小于 0」，不是「预占量大于在手量」—— 差别在 4.2：
并发下若用后者判定，两条各占 6 件的请求会同时通过。

**例 2（过期与可用量的非对称）**：在手量 10，t=100 时预占 7 件、`expires_at=200`。
- t=150：可用量 = 10 − 7 = **3**
- t=250（**尚未收割**）：可用量 = 10 − 0 = **10**（3.2 排除已过期的 `held`）
- t=250 收割后：该条转为 `released`，可用量仍是 **10** —— **收割不改变可用量**，
  它改变的是**状态的可解释性**（库里不再有「一条永远 held 的记录」）。

这个非对称是刻意的：3.2 让「不收割」不会挡住生意，3.3 让「收割」可以被调度和审计。

**例 3（守恒的账）**：初始入账 10 件（一条入账流水），依次发生：预占 4 → 兑现 4 → 预占 3 → 释放 3。
- 在手量 = 10 − 4 = **6**
- Σ(已兑现) = 4
- 4.1 的等式：`6 + 4 − 10 = 0` ✅
- 被释放的 3 件**不出现在**这个等式里 —— 这正是 2.4（释放不改变在手量）在守恒账上的投影。

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| 确定性 | 给定相同的初始数据、相同的外部时刻序列、相同的操作序列，结果必须**逐字节可复现**（含留痕的时间戳与顺序） |
| 幂等 | 预占（1.4）、兑现（2.3）、收割（3.4）三者都必须幂等 |
| 依赖 | 不允许把「库存不能为负」这类规则**只**写在应用代码里；应用层的检查是**优化**，不是**保证** |
| 可移植 | schema 不得依赖任何单一客户端的私有扩展；能用通用命令行客户端直接检查 |
| 演化的代价 | 任何一次约束的增删都必须以**迁移**形式表达，且必须能说明它对**存量数据**的影响 |

## 6. 待澄清（Clarify 候选）

这些是**刻意留白**的部分，请在 `/speckit-clarify` 阶段决策，不要凭直觉实现：

1. 4.1 说的是「已入账的入库量」。入账这件事本身要不要留痕？如果只在 SKU 上存一个数字，
   那么「谁把 10 改成 12」就是不可追溯的 —— 这与 US5 的意图冲突。要不要加一张入账流水表？
2. ~~3.2 要求可用量排除已过期的 `held`。那么**兑现**一条已过期的 `held` 应该成功还是失败？~~
   **已裁定（记录如下，因为它示范了「澄清」该留下什么）**：选择**拒绝**，成为 AC 2.6。
   理由不是「哪个更好」，而是**一个具体的双重计数**：3.2 已把过期的 `held` 排除在可用量之外，
   于是同一批库存可以被一条**新**预占占用；若那条过期预占还能兑现，它就**被卖出两次**。
   另一个理由是错误码质量：允许兑现后，不一致会推迟到 `on_hand >= 0` 的 `CHECK` 才爆，
   调用方拿到的是 `CHECK constraint failed`，而不是可分支的 `EXPIRED`。
   （这条裁定的重要性不在于结论，而在于它**同时**给出了数据和可用性两个理由 —— 只给一个理由的裁定，
   在下一个相似场景里会被推翻。）
3. 1.4 的幂等键只有 `request_id`。它是全局唯一，还是「每个调用方唯一」？
   如果是后者，规格里少了一个 `caller_id` 维度 —— 这属于**会影响到 schema 的歧义**，越早定越好。
4. 4.5 说「无法启用引用完整性检查时立刻失败」。在连接池场景下，这条要求作用在**连接**上而不是**进程**上 ——
   规格要不要显式要求「池中每一条连接都被验证过」，还是接受「创建时验证一次」？
5. **5.4 让在手量成为推导值**，代价是每次读它都要做一次聚合，而**聚合无法被索引**
   （见 `docs/adr/ADR-004`）。要不要允许一个「缓存字段」？如果允许，它的不一致只能靠巡检发现，
   那要不要顺手给它写一条「必须能被流水验证」的标准？
