# 技术方案 · stockflow（MVP）

**对应 feature**：`001-stockflow-mvp`
**规格**：[`spec.md`](spec.md)（24 条验收标准）
**等级**：Spec-Anchored · **数据层强化**

> 本文件是**唯一**允许出现技术栈词汇的地方（另一处是 `docs/adr/`）。
> 规格回答「要什么」，这里回答「怎么落、落在哪一层、以及为什么落在那里」。

---

## 1. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | Node.js 24（ESM） | 仅作为**适配层**存在，代码量刻意压到最小 |
| 数据库 | SQLite（由 `node:sqlite` 内置提供，SQLite 3.50） | **零依赖**。这个案例的主角是 schema，任何需要下载的依赖都会转移注意力 |
| 测试 | `node --test`（内置） | 同上 |
| 迁移 | 手写 `.sql` 文件 + 一个 20 行的应用器 | 迁移本身要能被人工审阅；引入迁移框架会藏起最重要的那部分 |

**关于「零依赖」的取舍（写在前面，因为它会影响读者对案例的判断）**：
本案例**故意**不使用任何第三方库。这不是工程建议，而是教学取舍 ——
当库的数量为零时，「约束住在哪里」这个问题的答案只能是 schema 本身，
不存在「某某 ORM 帮我做了校验」这种模糊地带。

> ⚠️ `node:sqlite` 在当前 Node 版本会打印一行 `ExperimentalWarning`。
> 这是**有意的暴露**而非瑕疵：它提醒你「你正在依赖一个客户端的行为」——
> 而本案例的整个下半场（`docs/adr/` 的 ADR-002）都在讲这件事。

## 2. 约束落在哪一层：阶梯与判据

规格里 24 条标准，**不是每一条都住在同一层**。这是本案最需要讲清的一件事。

判据只有一条：

> **这条标准要拦住的写入，会经过我这段代码吗？**
> 不会 → 它必须住在数据层。会 → 可以住在代码里，但仍要问「住数据层是不是更便宜」。

按「数据层能表达多复杂的条件」，从小到大排成四级阶梯：

| 级 | 载体 | 能表达的条件 | 本案例里承担的标准 |
|---|---|---|---|
| ① | 列类型 + `NOT NULL` | 「这一列必须存在、必须是整数」 | 5.1 |
| ② | `CHECK` | **单行内**的取值约束 | 1.5、3.1、5.3、以及 `state` 的取值域 |
| ③ | `UNIQUE` / `PRIMARY KEY` | 跨行的**唯一性** | 1.4（幂等的载体） |
| ④ | `FOREIGN KEY` | 跨表的**存在性** | 1.6（SKU 必须存在） |
| ⑤ | `TRIGGER` | 跨行的**聚合与派生**（`CHECK` 里的子查询在 SQLite 被禁止） | 1.2、2.1、2.2、4.3 ⑥、5.2 |

**这五级不是"能用就行"，而是"能用但更该用哪一级"。** 判据是**可测试性**：

- 能用 ② 表达的，**不要**用 ⑤。`CHECK` 的失败信息定位到**列**，触发器的失败信息定位到**触发器名** ——
  前者能直接指向规格编号，后者需要人再翻译一次。
- 能用 ③ 表达的，**不要**用触发器里的「先 SELECT 再判断」。因为那是一次**竞态**：
  两个并发请求可以同时通过 SELECT 检查、然后都 INSERT。**唯一约束没有这个窗口，它由引擎原子保证。**
  1.4 的幂等因此**必须**是 ③，不能是应用层的「先查后插」。
- **① 和 ② 的区别最容易被忽略，代价也最大**：SQLite 默认是**动态类型**，
  一个声明为 `INTEGER` 的列**接受字符串 `'abc'`**。规格 5.1 要求数量是整数 ——
  这条标准的实现载体是 `STRICT` 表，而不是代码里的 `Number.isInteger()`。

### 阶梯之外：⑥ 事务

有两条标准**任何一级都表达不了**，因为它们不是「一个条件的真伪」，而是「多个动作的同生共死」：

- **2.1** 要求「状态转为 committed」与「在手量减少」同生共死 → 事务
- **4.4** 要求「中途失败则全部回滚」 → 事务

**这一条正好说明数据层不是万能的**：它保证的是**每一条语句**的合法性，
**不保证**一组语句的**原子性**。原子性必须由调用方用事务把它包起来 —— 应用层因此不可能被完全移除。
这是本案例最诚实的一句话：**数据层把「守住不变量」的责任接过去了，但没把「组织动作」的责任接过去。**

## 3. 数据库设计

### 3.1 表

```
sku                  库存单位
  sku_id       TEXT  PK
  on_hand      INTEGER NOT NULL CHECK (on_hand >= 0)

reservation          预占
  res_id       TEXT  PK
  request_id   TEXT  NOT NULL, UNIQUE          -- 1.4
  sku_id       TEXT  NOT NULL REFERENCES sku   -- 1.6
  qty          INTEGER NOT NULL CHECK (qty > 0) -- 1.5
  state        TEXT  NOT NULL CHECK (state IN ('held','committed','released'))
  created_at   INTEGER NOT NULL
  expires_at   INTEGER NOT NULL CHECK (expires_at > created_at)  -- 3.1
  settled_at   INTEGER                          -- 2.3：非 held 必须有，held 必须没有
  CHECK ((state = 'held') = (settled_at IS NULL))

reservation_event    只增不改的流转留痕               -- 5.2
  event_id     INTEGER PK AUTOINCREMENT         -- 保证顺序可复现
  res_id       TEXT  NOT NULL REFERENCES reservation
  from_state   TEXT  NULL                       -- NULL = 创建
  to_state     TEXT  NOT NULL
  at           INTEGER NOT NULL

clock                单行表：外部时刻                -- 3.5
  id           INTEGER PK CHECK (id = 1)
  now          INTEGER NOT NULL
```

**`clock` 表值得单独解释。** 3.5 要求「不得读取系统时钟」。把它做成一张表，
换来的是三件事：测试可以**把时间钉住**；触发器和查询可以用**同一个时刻**判断过期（否则同一条语句内
两次 `now` 可能落在过期边界的两侧）；整个数据库的状态**完全由输入决定**，因此可重放。

代价也很直白：这是**单一真相点的中心化**，任何写入都要先考虑时刻。对一个单库范围的引擎是可接受的，
对分布式系统则不然 —— 这条边界写进 ADR-004。

### 3.2 关键不变量 `available ≥ 0` 为什么不能是 `CHECK`

规格 1.2 的核心条件是一个**聚合**：

```
on_hand − Σ(生效中 held 的 qty) ≥ 0
```

`CHECK` 的表达式**不得包含子查询**（SQLite 如此，标准 SQL 亦如此）。
于是有两条出路，本案例**都留下**，并明确各自的位置：

| 出路 | 位置 | 性质 |
|---|---|---|
| **触发器** | ⑤ 级 | **保证** —— 无论谁写入都生效 |
| 应用层先读后写 | 代码 | **优化** —— 为了在常见路径上给出更友好的错误，不是为了保证 |

顺序不能倒过来。**如果应用层检查是唯一的检查，它就不是检查，是运气。**

## 4. 模块边界

刻意**不**做 domain / store 分层 —— 与 `billflow` 相反，这是有意的：

```
migrations/*.sql        ← 真正的实现（规格住在这里）
src/db.mjs              ← 连接 + 迁移 + PRAGMA 自检（见 §5）
src/store.mjs           ← 事务边界 + 参数绑定 + 错误码映射（薄）
src/errors.mjs          ← 稳定错误码（5.3）
src/cli.mjs             ← 人工演示入口
```

**为什么不分层**：分层的前提是「领域规则住在领域层」。本案例的规则住在 schema 里，
硬做一个空的 `domain/` 目录会传递一个错误的印象 —— 让读者以为规则在代码里。
**目录结构本身就是文档**，它不该说谎。

`src/store.mjs` 的自我约束（写进代码注释，由评审守住）：**不得包含任何业务条件判断**。
它只允许做三件事：开事务、绑参数、把引擎的错误码翻译成 5.3 的错误码。
一旦它出现 `if (available < qty)`，那条规则就**同时**住在两个地方了 —— 这是最坏的结果。

## 5. 强制力：谁在保证这一切

| 标准 | 保证者 | 可被绕过吗 |
|---|---|---|
| 1.4 幂等 | `UNIQUE (request_id)` | 不能（引擎原子保证） |
| 1.5、3.1、5.1 取值 | `CHECK` + `STRICT` | 不能 |
| 1.6 SKU 存在 | `FOREIGN KEY` | **取决于连接的 PRAGMA** ⚠️ |
| 1.2 不超卖 | 触发器 + 事务 | 不能（只要触发器在） |
| 2.1 兑现即出库 | 触发器 + 事务 | 不能 |
| 2.2 终结态不复活 | 触发器 | 不能 |
| 4.4 全或无 | 事务（调用方） | 不能 |

⚠️ 那一行的问号是本案例的核心发现，展开在 `docs/adr/ADR-002`：
**外键是唯一一种「schema 里有、但可能不生效」的约束**，因为 `PRAGMA foreign_keys`
是**每连接**的设置，而且**不同客户端的默认值不同**（实测：Node 默认开，Python 与命令行客户端默认关）。

因此 `src/db.mjs` 在建立连接后**必须断言**该 PRAGMA 已开启，否则立即抛错 —— 对应规格 4.5。
这条断言不是为了自己，而是为了让「运行时的实际强制力」与「schema 里看起来的强制力」一致。

## 6. 测试策略

| 层 | 手段 | 覆盖的标准 |
|---|---|---|
| 引擎能力 | **裸 SQL**，不 import `src/` | 4.3①②③④⑤⑥、5.1 |
| 行为 | `store.mjs` 的公开函数 | 1.1–1.6、2.1–2.5、3.1–3.4、5.2–5.3 |
| 时间 | 推进 `clock` 表，从不读系统时钟 | 3.2、3.3、3.4、3.5 |
| 并发 | `worker_threads` 起 N 个独立连接争抢 | 4.2 |
| 不变量 | 随机操作序列后校验守恒等式 | 4.1、4.4 |
| 连接 | 断言 PRAGMA | 4.5 |

**第一行是本案与前面四个案例最大的不同**：一组测试**故意不 import 应用代码**。
它们证明的不是「我们的代码很小心」，而是「**不经过我们的代码也拦得住**」。

一个只测应用层的测试套件，在「有别的写入路径」这个前提下，**提供的信心是假的**。
