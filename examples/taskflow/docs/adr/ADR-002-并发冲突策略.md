## 背景

spec 标准 3.5–3.6 要求：

> IF 请求携带的 `version` 与当前不一致 THEN 返回 **409**（`CONFLICT`），响应体含 `current` 对象。
> WHEN 500ms 内两个请求尝试将同一任务改为不同状态 AND 二者携带相同 `version`
> THEN 使**先到达者成功**，后到达者按 3.5 返回 409。

**这是本项目唯一涉及「正确性」而非「可用性」的需求。** 其他端点即使偶发异常也只是体验问题；
这个问题会导致**用户的输入静默消失**——而用户不会知道。

规模背景：5 人以内团队，任务的并发修改是**罕见事件**（同一天内同一任务被两人同时改的可能性很低）。

---

## 决策

任务表加 `version INTEGER NOT NULL DEFAULT 1`，写入时用条件更新：

```sql
UPDATE tasks
   SET status = $2,
       version = version + 1,
       updated_at = $3
 WHERE id = $1
   AND version = $4
RETURNING id, status, version, updated_at;
```

`task.repo.ts` 中的处理逻辑：

```typescript
export async function updateStatus(
  id: string, to: TaskStatus, expectedVersion: number, now: Date,
): Promise<UpdateResult> {
  const { rows } = await pool.query(SQL_UPDATE_STATUS, [
    id, to, now, expectedVersion,
  ]);

  if (rows.length === 1) {
    return { kind: 'ok', task: rows[0] };
  }

  // 影响 0 行：要么 version 不匹配（冲突），要么任务不存在（上层已预检）
  const current = await findById(id);
  if (!current) return { kind: 'not_found' };

  return { kind: 'conflict', current };   // → routes 层转成 409 + current
}
```

**关键点：`RETURNING` + 影响行数判定，是原子操作。** 不存在「先 SELECT 查 version，再 UPDATE」的竞态窗口。

---

## 代价

1. **客户端必须把 `version` 一路带回来。** 这意味着每个 PATCH 请求体多一个必填字段（标准 3.7 要求缺失时返回 `VERSION_REQUIRED`），且客户端在任何展示任务的地方都要保留 `version`。**这是真实的传播成本。**

2. **乐观锁在高冲突场景下会频繁失败并重试。** 如果将来出现「多人同时批量改状态」的用法，用户会频繁看到 409。当前场景冲突率极低，可接受。

3. **`version` 与 `updated_at` 是两个独立字段，语义不同。** `updated_at` 用于审计（标准 5.1），`version` 用于并发控制。二者在每次写入时都变，但**不能互相替代**（原因见下）。

4. **多一次数据库往返（冲突路径）。** 成功路径一次查询；冲突路径需要额外 `findById` 拿 `current`。冲突是罕见事件，这个额外开销可接受。

5. **DELETE 操作不参与版本控制。** 本次范围内没有任务删除端点，所以未处理。**如果将来加删除，需要重新评估**——删除与版本号的交互是一个独立问题（删除后重放一个旧的 PATCH 该怎么办）。

## 被否决的选项

### ① `updated_at` 时间戳比较 ⚠️ 最需要记下来的一条

```sql
-- 被否决的方案
UPDATE tasks SET ... WHERE id = $1 AND updated_at = $2
```

**支持理由**：不需要新增列；客户端本来就有 `updated_at`（因为它要展示"最后更新时间"）；看起来很省事。

**否决理由（两条，第二条是决定性的）**：

- 时间戳是**客户端从上次响应里带回来的**，中间要经过 JSON 序列化/反序列化。
  `TIMESTAMPTZ` 的微秒精度在不同运行时（JS `Date` 只有毫秒精度）往返时可能被截断，
  导致**明明没冲突却判定为冲突**。
- **决定性理由**：在毫秒精度下，同一毫秒内的两次写入会产生**相同的时间戳**，
  条件更新会**同时匹配**，于是两个请求都成功——**先到者胜的语义被破坏，冲突检测完全失效。**
  （这也是为什么标准 3.6 特意写了「500ms 内」这个测试场景——恰好是为了暴露这类方案的问题。）

> 📌 **这一条必须留在 ADR 里。** 因为「用 `updated_at` 做乐观锁」是三个月后最可能被重新提议的方案，
> 而它的失败原因**不是设计思路错，是精度不够**——不写下来就一定会被重新试一次。

### ② 悲观锁（`SELECT ... FOR UPDATE`）

**支持理由**：这是「处理并发写入」的教科书标准答案；语义直观；不需要客户端配合传版本号。

**否决理由**：

- **常态化成本换罕见事件。** 悲观锁要求每个 PATCH 都在事务里持有行锁，而本场景冲突是罕见事件。为 1% 的情况给 100% 的请求加锁成本，不划算。
- **死锁风险。** 一旦将来出现「一次请求修改多个任务」（如批量移动），加锁顺序不当就会死锁。
- **与 HTTP 语义冲突。** 事务在等待锁时会长时间持有数据库连接，Fastify 连接池会被打满，表现为「整个服务变慢」而不是「个别请求冲突」——**故障爆炸半径大得多**。

### ③ 后到者胜（last-write-wins，不加任何控制）

**否决理由**：**直接违反标准 3.6。** spec 明确要求先到者胜、后者收到 409。
更根本的是——它会让用户的输入**静默消失**，而用户完全不知道。这在协作工具里是不可接受的。

### ④ 递增的 `updated_at` + 版本号双字段冗余

**否决理由**：两个字段做同一件事会造成双真相源。我们明确区分语义：`version` 管并发控制，`updated_at` 管审计展示。

## 什么时候该推翻这个决策

| 触发条件（可观测） | 触发后该做什么 |
|------------------|--------------|
| **409 响应在真实流量中占比 > 5%** | 说明用户频繁碰到冲突。评估改为悲观锁，或引入自动重试 + 合并策略 |
| 新增**批量状态变更**端点 | 逐行乐观重试会变得很啰嗦。评估事务内批量 `UPDATE ... WHERE id = ANY(...) AND version = ?`，或改悲观锁 |
| 新增**任务删除**端点 | 必须重新评估：删除与 `version` 的交互（删除后重放旧 PATCH 该如何响应）未定义 |
| 出现**离线编辑**需求 | 乐观锁会变成冲突地狱（用户离线一天后同步）。需要 CRDT 或显式合并 UI，那是不同的架构 |
| 客户端反馈「不知道收到 409 后该做什么」 | 说明 `current` 字段不够用。评估增加 `changed_by` / `changed_at` 让 UI 能解释冲突 |

## 影响

- `migrations/001_init.sql`：`tasks.version` 列 + `CHECK (version >= 1)`
- `schemas/task.schema.ts`：`PatchTaskBody` 含必填 `version: z.number().int().nonnegative()`
- `repositories/task.repo.ts`：条件更新 + 影响行数判定（**禁止先查后改**）
- 契约测试：`tests/contract/task-concurrency.spec.ts`（标准 3.6 的并发用例）
- 审计：冲突被拒时仍记录，`result = 'conflict'`（标准 5.4）
- 前端契约文档：所有任务展示处必须保留并回传 `version`
