# feature 规格 · taskflow 任务标签

> **本文件是 L08 §4「多 feature 工作流」的参考产出。**
>
> 它的存在本身就是教学点：**这是第二个 feature，与 `001-taskflow-mvp` 完全隔离**——
> 独立的 spec / plan / tasks，但**复用同一份 `memory/constitution.md`**。
>
> 对照 `001` 的 spec 看两处：
> ① 它的非目标里有「任务标签（在 `002-task-tags` 中处理）」——**第一个 feature 主动把它排除了**
> ② 本文件没有再写一遍宪法里的约束（分层、错误码、测试要求）——**那些跨 feature 生效**

**Feature 分支**：`002-task-tags`
**状态**：已澄清，待规划
**依赖**：`001-taskflow-mvp`（本 feature 假设 001 已实现）

---

## 1. 概述

给任务增加标签能力，并支持按标签过滤任务列表。

**要解决的核心问题**：任务数量增长后，「哪些是紧急的」「哪些属于某个模块」这类横向信息无处安放。

**不解决**：标签的层级结构、标签的颜色/图标、跨项目的标签共享、标签重命名。

---

## 2. 语法约定

本节使用与 `001` 相同的 EARS 句式，编号**从 7 开始**（`001` 占用了 `1.x`–`6.x`），
避免两个 feature 的标准编号在映射表里冲突。

## 3. 用户故事与验收标准

### US7 · 给任务打标签

**作为**团队成员
**我想要**给任务打上标签
**以便**能从另一个维度组织任务

#### 验收标准

| # | 标准 |
|---|------|
| 7.1 | WHEN 项目成员执行 `POST /tasks/:id/tags` 且请求体含 `tag` THE system SHALL 为该任务添加标签，返回 **200**，响应含该任务当前的完整标签列表（按标签名升序）。 |
| 7.2 | IF 该任务已有 **5 个**标签 THEN THE system SHALL 拒绝并返回 **422**（`TAG_LIMIT_EXCEEDED`）。 |
| 7.3 | IF `tag` 为空、全空白、或长度不在 1–32 之间 THEN THE system SHALL 返回 **400**（`INVALID_TAG`）。 |
| 7.4 | IF `tag` 含除字母、数字、`-`、`_`、`/` 之外的字符 THEN THE system SHALL 返回 **400**（`INVALID_TAG`）。 |
| 7.5 | IF 同一项目内**已存在同名标签**且该任务尚未持有它 THEN THE system SHALL **复用**该标签（不新建），仍返回 200。 |
| 7.6 | IF 该任务**已持有**该标签 THEN THE system SHALL 返回 **200**（幂等，不产生重复），标签列表不变。 |
| 7.7 | IF 请求者不是任务所属项目的成员 THEN THE system SHALL 返回 **404**（`TASK_NOT_FOUND`），与 `001` 标准 3.9 一致。 |
| 7.8 | WHEN 标签被添加 THE system SHALL 记录审计条目，`action` 为 `task.tag_added`。 |

> **7.5 与 7.6 的区别值得注意**：
> 7.5 是「项目里已经有这个标签，但任务没打上」→ 复用；
> 7.6 是「任务已经打了这个标签」→ 幂等返回。
> **两者都返回 200，但语义不同**——不写清就会出现重复标签或多余的库写入。

### US8 · 按标签过滤任务列表

**作为**团队成员
**我想要**按标签筛选任务
**以便**聚焦在某一类工作上

#### 验收标准

| # | 标准 |
|---|------|
| 8.1 | WHEN `GET /projects/:id/tasks?tags=urgent` THE system SHALL 只返回持有 `urgent` 标签的任务。 |
| 8.2 | WHEN 查询串含多个标签（如 `?tags=urgent&tags=backend`）THE system SHALL 返回**同时持有全部这些标签**的任务（**「与」语义**，不是「或」）。 |
| 8.3 | IF 查询串中的标签在项目中不存在 THEN THE system SHALL 返回**空列表**（退出码 200），**不报错**。 |
| 8.4 | THE system SHALL 保证过滤后的结果**仍遵守 `001` 标准 2.6–2.9 的全部分页与排序规则**。 |

> **8.2 是 clarify 阶段问出来的。** 原始需求说「支持按标签过滤，多个标签之间为『与』语义」——
> 但「与」这个词在中文里既可能指 AND 也可能被读成「和/加」（即 OR 列表）。**必须写成英文关键词并举例。**

> **8.4 是一条跨 feature 引用。** 它说明 002 不能改变 001 已定的排序与分页行为——
> **这是两个 feature 之间的契约，必须显式写出，否则实现 002 时很容易顺手改掉 001 的排序。**

### US9 · 移除标签

| # | 标准 |
|---|------|
| 9.1 | WHEN 项目成员执行 `DELETE /tasks/:id/tags/:tag` THE system SHALL 移除该标签，返回 **200**。 |
| 9.2 | IF 任务未持有该标签 THEN THE system SHALL 返回 **200**（幂等）。 |
| 9.3 | IF 移除后该项目中**没有任何任务**持有该标签 THEN THE system SHALL **保留**该标签（不做自动清理）。 |

> **9.3 是一个刻意的选择。** 自动清理看起来更「干净」，但会导致：用户刚打完标签、又移除了一个任务，
> 标签却从项目里消失了——**而下次他打字时下拉列表里就没有这个标签了**。
> **代价是项目里会积累未使用的标签**，我们用 `GET /projects/:id/tags` 让用户自己管理。

## 4. 非目标（Out of Scope）

- 标签的层级结构（`a/b` 只是普通字符串）
- 标签的颜色、图标、排序权重
- 跨项目的标签共享
- 标签重命名（改名需删除后重建）
- 按标签的统计报表
- `POST/DELETE` 之外的标签管理端点（如批量替换）

---

## 5. 对 `001` 的影响（跨 feature 影响面）⭐

**这一节是本节最重要的部分。** 第二个 feature 最容易犯的错，是**无意中改掉了第一个 feature 已定的行为**。

| `001` 的既有约定 | 本 feature 会不会影响 | 处置 |
|----------------|-------------------|------|
| 端点数量「不超过 7 个」（`001` §8） | ⚠️ **会突破** | **显式声明**：`001` 的限制仅适用于该 feature 的范围。本 feature 新增 3 个端点（`POST` / `DELETE` tags、`GET` project tags） |
| 任务列表排序 `created_at DESC, id DESC`（标准 2.9） | ⚠️ 可能被顺手改掉 | 用标准 8.4 显式继承 |
| 分页默认 20 / 上限 100（标准 2.6–2.8） | ⚠️ 同上 | 用标准 8.4 显式继承 |
| `size > 100` 截断并返回 `effective_size`（标准 2.7） | ⚠️ 过滤后可能忘记带该字段 | 用标准 8.4 显式继承；映射表需加用例 |
| 非成员一律 404（标准 3.9 / 4.5） | ✅ 一致 | 标准 7.7 直接引用 |
| 审计五字段固定（标准 5.2） | ⚠️ 新动作需沿用同结构 | 标准 7.8 明确要求 |
| `tasks.version` 用于并发控制（ADR-002） | ⚠️ **打标签是否递增 `version`？** | **见下** |

### ⚠️ 一个必须在本 feature 里回答的问题

> **给任务打标签，算不算一次「任务修改」？要不要递增 `version`？**

两个选项的后果完全不同：

| 选项 | 后果 |
|------|------|
| **递增** `version` | 用户 A 在打标签时，用户 B 正在改状态 → B 会收到 409。**标签操作会干扰状态操作** |
| **不递增** | 标签与状态独立演进。**代价**：两个并发打标签可能互相覆盖（但标签是集合操作，覆盖的损失很小） |

**本 feature 的决定：不递增 `version`。**

理由与 ADR-002 的语义一致性有关——`version` 是**状态机层面的并发控制**，而标签**不属于状态机**。
把它纳入 `version` 的控制范围，会让「打标签」这个高频操作与「改状态」这个关键操作互相干扰，
**把罕见冲突放大成常见冲突**（对照 `ADR-002` 的「什么时候该推翻」：409 占比 > 5% 就该换方案）。

**这条决定必须写进 `003-...` 之前的某个 ADR，或在 `plan.md` 里显式记录。**
如果不写，实现者会随手选一个——**而选「递增」的那个人，会在两周后收到「打标签导致 409」的 bug 报告。**

## 6. 边界条件汇总

| 场景 | 期望行为 | 标准 |
|------|---------|------|
| 任务已有 5 个标签 | 422 `TAG_LIMIT_EXCEEDED` | 7.2 |
| 标签非法字符 | 400 `INVALID_TAG` | 7.4 |
| 项目内已有同名标签 | 复用，200 | 7.5 |
| 任务已持有该标签 | 幂等，200 | 7.6 |
| 非成员操作 | 404 `TASK_NOT_FOUND` | 7.7 |
| 过滤不存在的标签 | 200 + 空列表 | 8.3 |
| 多标签 | **「与」语义** | 8.2 |
| 过滤 + 分页 | 遵守 `001` 标准 2.6–2.9 | 8.4 |
| 移除不持有的标签 | 幂等，200 | 9.2 |
| 标签不再被使用 | **保留**，不自动清理 | 9.3 |
| 打标签 | **不递增 `task.version`** | 见 §5 |

## 7. 术语

| 术语 | 定义 |
|------|------|
| 标签（tag） | 任务上的一个横向分类标记。**非层级**，最多 5 个/任务 |
| 项目标签库 | 项目内所有出现过的标签集合；**不自动清理** |
| 「与」语义 | 多标签过滤时要求任务持有**全部**指定标签（AND，不是 OR） |
