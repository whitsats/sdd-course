# converge 不收敛案例 · 三层分流

> **本文件是 L09 §2 的完整参考产出。** 它记录了一次真实的「不收敛」及其误判→纠正过程。
> 核心结论：**反复重跑 implement 是最常见的误判。**

**时间**：2026-09-23
**feature**：`001-taskflow-mvp`

---

## 现象

`/speckit-converge` 连续三轮报告 gap，内容都在**任务列表的排序**上。

| 轮次 | converge 报告的 gap | 我的判定 | 我的动作 | 结果 |
|------|-------------------|---------|---------|------|
| 1 | 「任务列表排序规则与规格不一致」 | 实现没做 | 重跑 `/speckit-implement` | 仍然报 gap |
| 2 | 同上，措辞略变（「排序不稳定」） | 实现做错了 | 重跑 `/speckit-implement`，并手工改了 `task.repo.ts` 的 ORDER BY | 仍然报 gap |
| 3 | 同上 | ⚠️ **此处我停下来重新判断** | 回 spec 逐行核对 | **找到根因** |

---

## 误判过程

第 1 轮和第 2 轮我都判定为「第一层：实现没做」。理由是：spec 标准 2.9 里白纸黑字写着排序规则，而 converge 说代码与它不一致——**那当然是代码的问题**。

第 2 轮我甚至直接改了代码：

```diff
- ORDER BY t.created_at DESC
+ ORDER BY t.created_at DESC, t.id DESC
```

**改完 converge 还是报 gap。** 这才让我意识到：如果 spec 是清楚的，那么按 spec 改代码应该就能收敛。**两次都改不对，说明我对 spec 的理解有问题，而不是代码。**

---

## 正确判定：第二层（规格没说清）

回 `spec.md` 逐行核对后，发现问题在标准 2.9 的**措辞**：

```markdown
2.9 | THE system SHALL 按 `created_at` **降序**返回（新建的在前），WHEN 两个任务的
      `created_at` 完全相同 THE system SHALL 以 `id` 降序作为次级排序键。
```

**看起来很清楚。但 `id` 是什么？**

翻到 §7 术语表：

```markdown
| 任务（task） | 项目内的工作项。有状态、标题、创建者 |
```

**术语表里没有定义 `id` 的格式。**

而 plan §2 的 SQL 用的是：

```sql
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  ...
);
```

实现里用的是 **ULID**（`01JCFK...`，字典序 = 时间序）。但 spec 从未说明 `id` 是 ULID、自增整数、还是 UUID。

**关键差异**：

| `id` 格式 | `id DESC` 的实际含义 | 是否符合「次级排序保证稳定」 |
|-----------|-------------------|------------------------|
| ULID | 大致等于创建时间倒序 | ✅ 符合意图 |
| 自增整数 | 等于插入顺序倒序 | ✅ 符合意图 |
| **UUID v4** | **随机** | ❌ **完全不稳定** |

**所以标准 2.9 的验收条件实际上是歧义的**：它约束了排序**方向**，但没有约束 `id` 的**格式**——而格式决定了这个约束是否有意义。

converge 每轮都在报「排序不稳定」，正是因为这个歧义：它无法判定实现是「对的」还是「错的」，因为**规格本身没说清什么算对**。

---

## 修复：回 spec 补一个字面定义

在 spec §7 术语表补一条：

```markdown
| 任务标识（`id`） | 任务的唯一标识。**格式为 ULID**（26 字符 Crockford Base32），
  其字典序与创建时间顺序一致。这保证了标准 2.9 的次级排序键是稳定的。 |
```

同时在标准 2.9 后加一句说明：

```markdown
> **为什么 `id` 必须是 ULID（或任何字典序单调的格式）**：
> `id DESC` 只有在 `id` 的字典序与创建时间相关时才构成稳定的次级排序键。
> 若 `id` 是随机的（如 UUID v4），则 `created_at` 并列的两条任务在两次查询中
> 顺序可能不同，客户端翻页会漏数据或重复。**这是需要写进规格的约束，不是实现细节。**
```

**重跑 converge → clean。** 收敛。

---

## 教训（写在这里，不要只在脑子里）

### ① 「看起来能实现」不等于「规格说清了」

这是我最初误判的根本原因。标准 2.9 读起来**完全清楚**——它甚至写了 `id DESC`。但「清楚」是对**人**而言的：人会自动脑补「`id` 大概是有序的吧」。

**agent 不会脑补，它会问；而 converge 会报 gap。**

> agent 每次都能给你一个实现，**正是问题所在——因为它在替你补规格。**

### ② 三层分流的实用判据

| 判断问题 | 指向的层级 |
|---------|-----------|
| spec 里**白纸黑字**有这条，代码就是没有 | 第一层 → `implement` |
| 我**读了 spec 三遍**还是说不清「什么算做对了」 | 第二层 → `clarify` / `specify` |
| spec 清楚、代码也对，但 tasks 里没有对应的验收步骤 | 第三层 → `tasks` |

**第二个问题是关键判据。** 如果你读了三遍还说不出「什么算做对了」，那 gap 就**不在代码层**。

### ③ 一个操作性的止损规则

> **连续两轮 converge 报同一个 gap，就停止重跑 implement，改为回 spec 逐行核对。**

这条规则的价值在于：它把「无限循环」切断在一个有限次数上。**反复重跑 implement 是零信息量行为**——它不会让你更接近答案。

### ④ 这个案例的类型学意义

它属于「规格**看似完整、实则缺失一个关键约束**」，而不是「规格明显含糊」。

| 缺口类型 | 例子 | 发现难度 |
|---------|------|---------|
| 明显含糊 | 「要有权限控制」 | 低——clarify 直接会问 |
| **看似完整实则缺约束** | **「按 `id` 降序」但没定义 `id` 格式** | **高——这正是 converge 的价值** |
| 完全空白 | 需求里从没提并发 | 中——靠 checklist 的异常清单发现 |

**中间那一类是最危险的**，因为它在 spec review 时最容易通过。而 converge 恰好擅长抓它——这解释了为什么 converge 值得跑，即使 spec 看起来已经很清楚。
