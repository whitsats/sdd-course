**日期**：2026-09-23

## 第 ① 步 · 先改 `spec.md`

### 改动 1：§3 状态机追加 archived

```diff
    todo ──► doing ──► in_review ──► done ──► archived
                       ◄──────┘

+ **关于 `archived`**：由后台任务在任务进入 `done` 满 30 天后自动置入，
+ **不是用户操作**。
```

对应的合法流转表追加一行：

```diff
| done | *（除 archived） | ❌ | **`done` 之后不可回退** |
+ | done | archived | ✅ | **仅系统（后台任务）**可写入，用户请求不允许 |
| archived | * | ❌ | **终态** |
```

### 改动 2：新增验收标准 3.4 / 3.10 / 3.11

```markdown
| 3.4 | IF 目标任务当前状态为 `archived` THEN THE system SHALL 对任何状态修改返回 **422**（`TERMINAL_STATUS`）。 |
| 3.10 | WHEN 一个任务的 `done` 达成时间超过 30 天 THE system SHALL 将其状态置为 `archived`，且该操作不改变 `version`。 |
| 3.11 | IF 用户请求中的 `status` 为 `archived` THEN THE system SHALL 返回 **422**（`INVALID_TRANSITION`），**即使用户是 owner**。 |
```

**注意 3.10 的「不改变 `version`」** —— 这是追加规格时新引入的约束。理由：归档是系统维护动作，不是用户编辑；如果它递增 `version`，会让持有旧 `version` 的用户请求意外冲突，凭空制造 409。

> 📌 **这条约束在原始需求里根本不存在**，是写规格时才想清楚的。**这就是「先改规格」的价值：它逼你在动手前把语义想明白。**

### 改动 3：§6 边界条件汇总追加两行

```diff
| `archived` 后任何修改 | 422 `TERMINAL_STATUS` | 3.4 |
+ | 用户请求写入 archived | 422 `INVALID_TRANSITION` | 3.11 |
+ | done 满 30 天 | 系统置为 archived，`version` 不变 | 3.10 |
```

## 第 ④ 步 · 先让测试变红 ⭐ 关键步骤

**这是区分「真做」和「走过场」的地方。**

```typescript
// tests/contract/task-state.spec.ts 新增
describe('标准 3.10 · 系统归档（本次规格变更新增）', () => {
  it('done 满 30 天后被归档，且 version 不变', async () => {
    const task = await h.seedTask({ status: 'done', version: 4 });
    await h.ageTask(task.id, { days: 31 });          // 把 updated_at 改到 31 天前

    await h.runArchiveJob();

    const after = await h.getTask();
    expect(after.status).toBe('archived');
    expect(after.version).toBe(4);                   // ← 关键：version 不变
  });
});

describe('标准 3.11 · 用户不可写 archived', () => {
  it('owner 请求 status=archived → 422 INVALID_TRANSITION', async () => {
    await h.seedTask({ status: 'done', version: 4 });
    const res = await h.request('PATCH', `/tasks/${h.taskId}`, {
      as: 'owner', body: { status: 'archived', version: 4 },
    });
    expect(res.status).toBe(422);
    expect(res.body.code).toBe('INVALID_TRANSITION');
  });
});

describe('标准 3.4 · archived 是绝对终态', () => {
  it.each(['todo', 'doing', 'in_review', 'done'])('archived → %s 返回 422', async (to) => {
    await h.seedTask({ status: 'archived', version: 9 });
    const res = await h.request('PATCH', `/tasks/${h.taskId}`, {
      as: 'owner', body: { status: to, version: 9 },
    });
    expect(res.status).toBe(422);
    expect(res.body.code).toBe('TERMINAL_STATUS');
  });
});
```

**确认结果：7 条红。** 记录下这个时刻。

> **为什么必须先红？**
> 因为它证明这些测试**确实在检查你要改的行为**。
> 如果先写实现再补测试，测试可能因为写错断言、测错路径、被 mock 掉而「恰好」通过——
> 而你将永远不知道它其实什么都没检查。

**顺带一个发现**：标准 3.11 的测试**一开始就是绿的**。

这说明 `checkTransition('done','archived','user')` 的逻辑此前已经正确（在 state-machine.ts 里 `SYSTEM_ONLY_TARGETS` 已包含 `archived`）——**因为我在原始实现时就把「系统 vs 用户」的区分做进去了，虽然当时 spec 没要求。**

这是一个**好的信号**（说明领域层设计有余量），但也暴露了原 spec 的缺口：**当时没写 3.11，所以这条行为一直未被规格覆盖**。现在补上了。

### 与 vibe coding 的对比

**如果不用这套流程**，我会：

1. 直接改代码加 `archived`（不知道要改多少处）
2. 手动跑一下，看起来能用
3. 提交
4. 上线后发现：用户也能把任务改成 `archived`（因为没写 3.11 这条规格，自然不会想到要防）
5. 再上线后发现：后端归档任务递增了 `version`，导致用户在其他标签页的操作莫名 409
6. 这时才回去想「归档算不算一次编辑」

**第 4、5 两条都是规格级的缺口，而不是实现 bug。** 而它们只在写规格的过程中才会被想到——
因为写规格时的思考方式是「**什么算做对了**」，而不是「怎么让它跑起来」。

> **这套流程的成本是「多一点前置思考」，收益是「少两次线上事故」。**
> 这个账算得过来不算得过来，取决于你的系统对正确性的要求有多高。

## 附：本次变更暴露的流程问题

**问题**：第 ② 步 analyze 的报告里有两条是「缺口」而非「冲突」，其中「覆盖率将失败」这条其实 CI 就能抓到。

**结论**：analyze 与 CI 覆盖率检查**有重叠但不冗余**——

| | analyze | CI 覆盖率检查 |
|---|---------|-------------|
| 时机 | 动手前 | 提交时 |
| 范围 | spec ↔ plan ↔ tasks 三方交叉 | 只查 spec ↔ 映射表 |
| 能否发现「plan 的 SQL 缺 archived」 | ✅ | ❌ |

**两者都要保留。** analyze 的价值是**在动手前**把影响面摊开——这决定了你能否一次做对，而不是改七次才收敛。
