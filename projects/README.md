# 案例项目设计说明

三个项目不是三个玩具 demo，而是**同一件事的三个严谨度等级**。

你会亲手体验到那个核心问题：多花在规格上的成本，到底换回了什么？

---

## 总览

| | A. focuslog | B. taskflow | C. rulesmith |
|---|---|---|---|
| **一句话** | 开发者专注日志 CLI | 团队任务协作 API + 看板 | 报表规则引擎 |
| **等级** | Spec-First | **Spec-Anchored** ⭐ | Spec-as-Source |
| **课时** | L03–L05 | L06–L09 | L10 |
| **技术栈** | Python 3.10+ · Typer · uv · pytest | TypeScript · Fastify · zod · vitest · Postgres | TypeScript · Node · 代码生成器 |
| **规模** | 1 个 CLI，4 个命令 | 1 个 API，**7 个端点 / 2 个角色** | 1 个生成器 + 1 套 DSL |
| **核心教学点** | 最短因果链 | 强制力与漂移治理 | 生成与边界感 |

---

## 为什么这样选栈

你选择了「跟着案例走」，所以说明一下每个项目的选型理由——**这些理由本身也是 SDD 判断力的一部分**。

### 项目 A：Python（不是 TypeScript）

**理由：让因果链最短。**

`focuslog` 是纯本地逻辑：无网络、无 UI、无并发、无数据库。用 Python + Typer，一个命令的实现可能就 20 行。这样你能**清楚看到「一条 EARS 语句怎么变成一行代码」**——这是阶段二的唯一目的。

如果这里就上 TypeScript 全栈 + Docker，噪音会淹没信号。**规格教学的第一步是降低技术噪音，而不是展示你的技术栈。**

另外 Python 与 `specify-cli` 同生态，环境已经装好（uv 在手），零额外成本。

### 项目 B：TypeScript（不是继续用 Python）

**理由：让「强制力」有天然的载体。**

spec-anchored 需要把规格变成**可执行的约束**。TypeScript 提供了三层天然牙齿，每层都能精确对应到 SDD 的一个环节：

| 牙齿 | 技术 | 对应的规格环节 |
|------|------|--------------|
| 静态约束 | zod schema | 输入/输出契约、错误码表 |
| 契约测试 | vitest + OpenAPI | 每条验收标准 → 一个测试用例 |
| CI 门禁 | GitHub Actions | 漂移即红灯 |

换成 Python 也能做，但 TS 的类型系统让「规格即约束」这件事在**代码层面就可见**——你写错一个状态流转，编译器先骂你，不用等到跑测试。对教学来说这个反馈回路更紧。

### 项目 C：TypeScript + 代码生成器

**理由：让「规格即源」可验证。**

`rulesmith` 的核心不是生成出来的引擎，而是**生成器**。你改一处规格，全量再生成，然后用 CI 校验生成物可复现（重新生成 → diff 必须为空）。这在 Node 生态里工具链最顺。

## A. focuslog —— 开发者专注日志

**定位**：spec-first。规格是种子，无强制力。这是你第一次体验完整流水线。

### 功能边界（刻意保持小）

| 命令 | 行为 |
|------|------|
| `focuslog start --tag <标签>` | 开始一个专注会话 |
| `focuslog stop` | 结束当前会话并记录时长 |
| `focuslog report --week` | 输出本周 Markdown 报告 |
| `focuslog stats` | 输出各标签的时长统计 |

存储：用户家目录下一个 JSON 文件。**无数据库、无服务器、无第三方依赖。**

### 刻意埋进去的教学难点

这几个点不是随手加的，每一个都对应一类「正常路径 agent 会自己补、异常路径必须你给」的规格缺口：

1. **`start` 时已有活跃会话** → 是拒绝、还是自动结束前一个？→ 逼你写 `WHILE … SHALL …`
2. **过程中机器重启** → 活跃会话怎么办？→ 状态恢复的规格
3. **`report` 的周边界** → 周一还是周日开始？时区？跨月怎么办？→ 逼你消灭歧义
4. **一次会话的时长计算** → 跨天怎么算？算到哪一天？→ 边界条件的规格
5. **`report` 区间内无记录** → 报错还是空报告？退出码几？→ `IF … THEN … SHALL …`

### 阶段二验收

- [ ] 4 个命令全部可运行
- [ ] 每条 EARS 验收标准有对应的验证记录
- [ ] 你能指出这次实现里**哪一处曾偏离规格**、以及是怎么发现的

## B. taskflow —— 团队任务协作 API

**定位**：spec-anchored。**这是本课程真正的目标产物。**

### 功能边界（已刻意收紧）

> ⚠️ **端点从 12 个减到 7 个，角色从 3 个减到 2 个。**
> 原始设计是 12 端点 / 3 角色，审阅时砍掉了。理由：本项目的教学目标是**演示强制力**，不是建一个生产级协作平台。
> 端点越多、角色越细，噪音越大，而「漂移变红灯」这件事并不会更清楚。
> **技术规模冒充教学价值**，是本节最该避免的错误。

7 个端点，2 个角色（`owner` / `member`）：

| 端点 | 说明 |
|------|------|
| `POST /projects` | 建项目 |
| `GET /projects/:id` | 看项目 |
| `POST /projects/:id/tasks` | 建任务 |
| `GET /projects/:id/tasks` | 列任务（含分页） |
| `PATCH /tasks/:id` | 改状态（状态机 + 并发冲突） |
| `POST /tasks/:id/comments` | 发评论 |
| `GET /tasks/:id/comments` | 看评论 |

- 看板状态流转（`todo → doing → in_review → done`）
- 审计日志（字段固定，用于验证「改行为必须改规格」）

### 刻意设计的「漂移放大器」

这些是让规格漂移**变得可见**的设计，也是 L09 红蓝对抗的靶子：

| 设计 | 为什么这么设计 |
|------|--------------|
| **状态机只有 4 个状态，但流转有约束** | L08 会故意在 plan 里画 6 个状态，验证 `/speckit-analyze` 能否抓出矛盾 |
| **并发写入同一任务** | 强制你写 `IF <500ms 内并发> THEN …`，逼出幂等与冲突策略的规格 |
| **权限矩阵（2 角色 × 7 端点，14 格）** | 这是「契约测试只测 happy path」（AP-14）最容易翻车的地方。14 格已经足够暴露问题 |
| **审计日志字段固定** | 让「改行为必须改规格」有可检查的痕迹 |
| **分页上限 + P95 预算** | 逼你写带数字的非功能需求 |

### 阶段三验收（L09 达标条件）⭐

- [ ] `/speckit-converge` 报告 **Converged**
- [ ] 每条验收标准 ↔ 至少一个自动化测试，映射关系**显式记录**
- [ ] CI 门禁生效：**红蓝对抗中，刻意制造的漂移确实让它亮了红灯**
- [ ] 你能**量化说明**：相比项目 A，多花了多少成本、多拿回了什么

> 最后一条最重要。如果你说不清多花的成本换回了什么，说明你只是照着流程走了形式。

## C. rulesmith —— 规格即源的报表规则引擎

**定位**：spec-as-source 实验。**重点不是「好用」，而是找到它的边界。**

### 做什么

用一份规格声明报表规则 DSL（语法、语义、错误情形），然后**生成**：

1. DSL 解析器
2. 校验器（含错误码）
3. 规则用户文档

关键约束：**版本库里不存在手工编辑的生成产物。** 人改的只有 `spec.md`，然后全量再生成。

### 为什么这个领域适合 spec-as-source

规则 DSL 是**高度结构化、模式重复**的领域——这正是 spec-as-source 唯一站得住的适用条件。语法是有限的、错误情形可以穷举、产物形态固定。

### 判定验收

- [ ] CI 校验生成物可复现：重新生成后 `git diff` 为空
- [ ] 完成一次「只改 spec、全量再生成、行为变更生效」的完整演示
- [ ] **你写下了本项目不适合规格即源的部分，以及原因** ← 这才是本节的真价值

> 最后一条是刻意的。L10 的考核重点不是「你成功用了 spec-as-source」，而是「你有了边界感」。AP-20 就是这个边界感的缺失。

## 附加练习（非项目）

### L11 · 存量改造（brownfield）

挑一个**你自己手头的**存量小仓库（不要用这三个项目），按 Spec Kit 的存量项目指引接入，然后做逆向规格化：

从现有代码提炼 spec，产出两类偏差清单：

- **实现里有、规格没写**的 → 判断是「要补的规格」还是「该删的代码」
- **规格写了、实现没有**的 → 判断是 bug 还是过期的规格

**每一处都必须明确归类为「改代码」或「改规格」。** 不许留着「待定」。

这个练习最贴近你真实工作——你不会天天做新项目，但你会天天碰存量代码。

### L12 · 团队流程设计

设计一份 5 人团队的 SDD 落地方案，必须包含：

1. 第一周做什么
2. 第一个月看什么指标（漂移率？规格覆盖率？返工率？——并说明为什么选这几个）
3. **什么信号意味着该在这个项目上收手**（AP-25 的解法）

## 目录规划

三个项目会作为独立子目录落在 `projects/` 下，各自是独立的 Spec Kit 项目：

```
projects/
├── README.md            ← 本文件
├── focuslog/            项目 A（L03 创建）
│   ├── .specify/
│   ├── memory/          宪法
│   └── specs/001-.../   spec.md / plan.md / tasks.md
├── taskflow/            项目 B（L06 创建）
└── rulesmith/           项目 C（L10 创建）
```

> ⚠️ 每个项目用**独立的 `specify init`**，不要共用一个 `.specify/`。宪法、模板、集成配置都是按项目走的；混在一起会让「活跃 feature」的解析变得不可预测。
